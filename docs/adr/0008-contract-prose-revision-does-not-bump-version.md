# 契约散文修订不升版本号,版本号只锚定规则集取值

面向模型的契约(`docs/rules-vN/`)的**散文修订**——即补齐或改写机制描述、义务句、示例、对照表,而不动任何参数取值——**不升版本号**:文件名、`rulesets/vN.json`、冻结脚本 `meta.json` 的 `ruleset` 字段、以及 FR-10 AC2 的「版本号与 ruleset 一致、错配时 runner 拒跑」判据全部保持原样。版本号唯一锚定的对象是**规则集取值**,取值没变,版本就不变。判据与验收归 spec;散文与其规则机制的家归 gdd。

## Considered Options

- **散文修订也升版本(`v1` → `v1.1`,或干脆开 `v2` 契约目录)**:落选——版本号若同时锚「取值」与「文字」,它就不再是任何一件事的标识,只成了「改过」的记号。而 srs FR-10 AC2 的版本号是**有功能的**:它与 ruleset 错配时 runner 拒跑。让它跟着散文一起动,会带来两个坏结果:一是**同一套取值同时存在两个契约版本号**,任何一处要对齐都得先决定以哪个为准;二是「契约 v2」这个名字会被读成「规则变强了」,而实际上只是占领那一节从占位变成了正文。
- **给散文单开一个修订号(与规则集版本并列)**:落选——它需要第三个字段来表达「什么时候字变了」,而这套存档形状的十一字段是**一次定死**的(schema 的家 `packages/schema/src/archive-meta.ts` 头注:改字段要波及每一份已冻结的 `meta.json` 与每一份引用它的 `input.json`)。为一次「措辞改善」付这个代价不划算。
- **不升版本、靠别的机制保证「契约变了会被发现」(采纳)**:散文里那些**必须随取值一起变**的东西(数值表)本来就是 `rulesets/*.json` 的生成物,`check:drift` 盯着;散文里那些**由 gdd 拥有**的机制事实,gdd 改了就该由 review 发现「契约面没跟上」——这是文档对账的活,不是版本号的活。

## Consequences

- **规则集版本升级的触发条件因此是清楚的**:出现了新机制、新参数键、或任一现有键的取值变更——那时才开新的契约目录。**只改文字永远不升版**。
- **补齐占位节不算升版理由**。本仓库已经发生过一次:契约面 `rules.md` 的 §1 / §2 / §5 / §9 四节长期是 `TODO(→…)` 占位。面向模型的契约补齐那一格(R,`.scratch/contract-closure/spec.md`)只把其中 **§5 占领与 §9 确定性约束**补成正文——它们描述的是**早已生效**的规则(机制归 gdd,早已定稿并落进引擎),取值一个都没变,所以不升版。**§1(对局与时间)与 §2(tick 结算管线)同一格明文 out-of-scope、占位保留**:补它们要先给「谁来复述地图不变量」「七步管线对脚本作者意味着什么」派活,那是规则侧的另一张小图,不在这一格的重心。因此本 ADR 说的「补齐占位节」指的是 **§5 / §9 两节**,不是四节一起——不要把 §1 / §2 也算进这次已补的范围。
- **「契约与 ruleset 对不上」这类假设要改**:看到版本号相同的两份契约,读到的不代表文字相同。要判断内容一致,得比对散文本身或 gdd 的机制节——这也是为什么散文里凡是提到参数,一律只写键名 + 指针到生成出来的数值表(`rules-doc-prose` 门禁禁止在散文里写「参数键名 + 数字」的赋值形态):数值只有一份,文字只能指过去。
- **派生出一条归属纪律**:契约面**不新裁机制**。它把 gdd 已有的决策落成散文;遇到 gdd 还没裁的机制问题(例如脚本能不能读 `progress` 来推断「还差几 tick 易主」),交回 gdd 的开放项,不在契约面顺手定下来。散文升不升级是次要的,让一个未评审的机制决定经由散文沉淀下来才是贵的。
