# 脚本 API 的类型面归对局内核,注入面归沙箱执行器

脚本 API 的**类型声明面**(`packages/schema` 里那份 `.d.ts`,`tsconfig.scripts.json` 的 `types` 经它引入)由**对局内核**这一格回填并拥有;沙箱执行器只负责**照那份声明**把名字铺进 guest、捕获桥函数进闭包、删掉桥。形状已有的一句话「家定在真源包,内容由对局内核与沙箱执行器回填」据此拆开:类型面归 F,注入面归 G。

`packages/schema/src/script-surface.ts` 里那 22 行 `signature` **字符串**在本次回填中由类型面取代(生成或删除,不并列存在)。

## Considered Options

- **全归沙箱执行器**(类型面也归 G,runtime bundle 生成时一并产出 `.d.ts`):落选。类型面描述的是「脚本能读到什么状态字段」与「action 的签名与参数」,前者的源头是 F 的状态模型、后者的源头是 F 的 `intents` 的 `check()`/`run()` 对——G 只搬运名字,不定义任何一个。归 G 的话,G 写那份声明时手里只有注入面,类型要**倒推**自那份只含名字的数组,而 `adr/0004` 已裁「收脚本能在运行时当值用到的名字、**不收类型名**,因为类型名在类型面上」——名字表按定义给不出签名,倒推出来的声明必然与 F 的实现分叉。
- **拆开:查询函数与状态字段的类型归 F,action 签名归 G**:落选。它把一份**同一个模块的接口**劈成两半由两个格子拥有,而两半的变更频率完全一致(引擎加一个 action 或改一个快照字段时两边同时动)。劈开的成本是每次改动都要想起「另一半在谁那儿」,而收益为零——两边读的是同一份引擎代码。
- **类型面与符号表继续各自手写,加一条测试断言「文档里出现的每个名字都在符号表里」**:落选。那是 `adr/0004` 已经逐条驳过的形态(要解析 Markdown 抽标识符、比生成本身脆、只抓多出来的名字抓不到少写的)。本次的差别只是对象从「文档」换成「类型面」,而那三条反驳逐字成立。
- **让 `tsc` 承担 API 误用判定,不补类型面,让脚本的 API 调用全落在 `any` 上**:落选。那样白名单反转(编译器的「找不到这个名字」)会**放行**所有 API 名——`move` 拼错成 `moev` 编译通过、运行时才炸,而那条错误模型在五轮迭代预算里改得掉。hld §6.2「API 误用」那一行明写「放行的是编译器,静态校验器在这条上从不是裁判」,前提是裁判席上有东西。

## Consequences

- **`hld.md:632` 那一行「API 误用」的承载方第一次真的有人了**。此前 `tsconfig.scripts.json` 的 `types` 是空数组,那一行是空头承诺;本决定之后它由 F 兑现。
- **生成管线的编译步骤在 F 落地时解锁,不必等 G**。`tsconfig.scripts.json` 的类型面一落地,「编译通过 + 白名单反转 + API 签名」三件事同时成立,H 那一格可以起步。这把 H 与 F 的并行窗口从「等 F/G 两格」收窄成「等 F 一格」。
- **`docs/adr/0004` 留的那笔账在这里销掉**:它记着「`packages/schema` 里那张符号表的注释会说法错话,写着『刻意为空,回填触发条件是沙箱执行器产出注入面』,本决定之后必须改掉」。注释随本次回填一并改,`PENDING_SHAPES` 之外不留给下一格。
- **`check()` 必须能在 VM 内跑这条约束因此变成可编译的**:类型面既然由 F 出,F 就顺带保证「`check()` 的入参类型里没有写入口」——那条不是纪律而是类型形状(见 spec 的 Implementation Decisions)。若两者分属两格,这条约束没有承载者。
- **F 与 G 之间新增一条必须同步的边界**:类型面(形状、归 F)与注入面(名字铺放时机、桥函数删除时机,归 G)。两者同源于一份形状,但**只有一份形状**——G 落地时若发现某个名字在类型面里而在注入面铺不出来,那是 G 的缺陷,不是「类型面漏了」。
