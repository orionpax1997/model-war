# 传输失败不作为可恢复事件：三套预算、5xx 即时收口与受污染会话的报告分层

## 问题

agent 化把每模型的调用数从 ~15 抬到 30–60，传输失败的基数跟着抬。按 S4 档位算，429 的期望次数会从个位数涨到几十次量级——**这不是「遇到再说」的规模，是可以算出来的必然量级变化**。

而现有重试层（`packages/gen/src/retry.ts`）是**为 one-shot 写的**，它有三个在 agent 形态下会咬人的前提：

1. **一套预算装四类失败**。429、5xx、网络失败、空闲超时、`finishReason=length` 截断共享同一次重试预算（500 ms → 1 s → 2 s，共 3 枪，最坏总共等 3.5 s）。于是「一次 429」花掉了本该留给网络抖动的耐心，而 3.5 s 对速率限制来说又短得可笑。
2. **退避吃掉墙钟**。`sendMs` 的口径明写含退避等待（ADR-0035 曾把这条钉成「重试等待由步级 `sendMs` 覆盖」）。agent 形态下 `totalWallClockMs` 是唯一硬约束之二，于是**慢模型 + 被限流会双重受罚，用不完自己的步数预算**——而资源本该只被记录、不被门槛化。
3. **失败不可读**。`AttemptEvidence` 只有 `attempt / outcome / finishReason / stopDetails / usage`，**没有状态码**；`FailureClassification` 只有 `tsc / contract / transport / selection`（2026-11-19 起多一档 `budget`：会话预算耗尽——步数或墙钟用完；见 `packages/schema/src/failure-record.ts` 的 `FAILURE_CLASSIFICATIONS`）。于是 429、500、超时、连接重置在报告侧**加成一个数**，而重试成功时连诊断文本都被丢弃（`retry.ts` 的 `diagnostics` 是局部量，成功路径直接蒸发）。

还有一条前提必须先说清，因为整册的判断都建在它上面：**渠道不该限流，也不该配额耗尽**。这是本季的**假设**，不是观测——观测是反过来的（S4 有真 429；本册起草当天，一个子代理就被自家通道的配额上限打死）。所以本册要的不是「完美处理限流」，而是**在假设成立时几乎不付代价、在假设破裂时数据仍然可读**。

## Considered Options

- **把预算整体调大（更长的等待、更多枪）**（落选）：会让一次 `ECONNRESET` 陪着等几十秒，而它本来一枪就能过。参数是「一次设一个」，失败却是四类，调大等于把四类一起拖长。
- **任何传输错误立即失败**（落选）：一次连接抖动毁掉一个第 118 步的会话。连接抖动**没有**「这次数据不可信」的含义，它纯粹是运气；把它升级成整次失败，等于让运气决定榜。
- **把 429 标成 `retryable: false`**（落选）：`retryable` 的语义被钉死为「重发同一轮**可能成功**」，而 429 确实可能成功。改它等于让事实字段撒谎，也把「策略」混进「事实」——将来翻案要改传输层的真值判断而不是策略表。
- **让模型自己看见 429 并处理**（落选）：模型对渠道状态**无行动能力**——它看不到状态码、不能等、不能换通道。把不可行动的信息交给它，只会训练出 `sleep` 和重试循环，而 `sleep` 还会撞单步墙钟。
- **被限流的会话一律丢弃成绩**（落选）：一个跑满 30 分钟、产出真实候选的会话，因为中途等了几分钟就作废，是拿资源约束当判据。而「丢弃」这个动作一旦存在，就会被用来解释掉不好看的分数。
- **靠 `diagnostics` 文本 grep 分类**（落选）：已证明会假阳性——`archive/claude-opus-5-5/failed-2026-10-11…json` 里的「429」来自 `"prompt_tokens":54429`。
- **退避参数进 `harnessDigest`**（落选）：会得到一个荒谬结论——把 `maxRetries` 从 3 调到 5 就让所有模型的历史成绩不可比。退避参数是**测量条件的抗噪设置**，不是模型能感知的行为面。

## Consequences

### 三条界线：等一等有没有意义

| 失败                  | 语义                           | 处置                 |
| --------------------- | ------------------------------ | -------------------- |
| 429                   | 服务端还好，只是**现在不给你** | 重试，进自己的长预算 |
| 5xx                   | 服务端**自己坏了**             | **不重试**，立即收口 |
| 网络失败 / 空闲超时   | **无语义的抖动**               | 重试，短预算         |
| `finishReason=length` | 模型的输出形状，不是传输失败   | 重试一枪（ADR-0032） |
| 其余 4xx / 缺凭证     | 请求本身有问题                 | 不重试，立即收口     |

这条界线的用处不在分类本身，在**它是「等多久之后承认它不会好」的前提**。5xx 重发只是撞同一堵墙；429 等一等有可能过——但也可能永远不会过（配额耗尽型 429 与速率限制型 429 是**同一个状态码**），所以 429 的预算必须有一个「认输点」，不能只有「再等等」。

### 三套预算，互不侵占

参数是 gen 内部常量，真源是 `packages/gen/src/retry.ts` 的 `RETRY`，**不进 `rulesets/*.json`**（hld §2.2.6）：

| 预算   | 枪数 | 单次封顶 | 累计封顶 | 额外规则                           |
| ------ | ---- | -------- | -------- | ---------------------------------- |
| 429    | 5    | 60 s     | 300 s    | `Retry-After` 作下限，向上抖动 25% |
| 连接级 | 2    | 2 s      | —        | `1 s → 2 s`                        |
| 截断   | 1    | 2 s      | —        | 第二次仍截断即判传输失败           |

三条各自封顶的职责要写死，否则调参时会互相偷：**单次封顶**管「不服从 header 里离谱的值」，**枪数**管「撞几次算真不行」，**累计封顶 300 s**（= 会话总墙钟 1800 s 的 1/6）管「一次会话最多被限流偷走多久」。300 s 不是好数字，是**认输点**：超过这个量级，重跑一次会话已经比继续等便宜。

`Retry-After` 取 `max(指数退避, header)` 再封顶，**抖动只往上加**——不早了服务端要求的时间，却打散并发进程的重发相位（同一把 key 被多个进程共用时，无抖动的重发是教科书式的 thundering herd）。

### 失败必须可读

`AttemptEvidence` 加可选键 `failureKind: "rate-limited" | "server" | "network" | "timeout"`：

- **厂商无关**，读侧不解析文案、也不用对 502 和 503 分别写分支；
- **成功路径也写**——一次 429 被重试救回来时，那条尝试证据仍带 `failureKind`，否则「限流压力」在数据里根本不存在，而它恰恰主要由这种情况体现；
- **不含 `truncated`**：截断不是传输失败，`finishReason === "length"` 已经表达了它。给同一个事实两个家，会诱导读侧把「模型话太多」和「渠道坏了」混进同一个计数。

按 ADR-0031 的先例，可选键不升档案形状版本。

### 受污染是数据的分层，不是数据的注解

「这次会话撞过限流」与「这次会话成绩不可比」之间要有一条可执行的判据，而判据落在**报告侧**，不落在采集侧：

- 主排名只放干净会话；
- 撞过限流的会话**完整保留**（成绩、步数、被 429 挡了几次、等了多少秒），单列成另一张表；
- 「撞过」按阈值判（**累计退避 > 60 s** 或 **429 次数 ≥ 3**），阈值写在报告脚注里而不是藏进代码。

阈值化的理由：一次 500 ms 的抖动和一次被啃掉 5 分钟的重试放进同一张表，那张表就没有信息量。三档（干净/轻微/严重）被否掉，不是因为不该细，是因为**两条边界已经是猜，三条是猜两次**——等第一季数据回来再调，调的只是报告侧阈值，不动采集。

同一套口径覆盖 agent 的 `meta.termination ≠ "done"` 与 one-shot 的「失败档 + `candidates[]`」：前者落在**成功档**里、带着真实成绩，读者只会理解成「模型满意了就收工」，这是比失败档更危险的形状。**但 one-shot 侧今天读不到数据**——`readFailureRecords` 刻意跳过参赛模型（`reporter.ts` 的 `if (participatingSlugs.has(slug)) continue`，理由写在它的注释里：否则失败名单会与主排名自相矛盾）。本册不为封存的历史榜改那个口径，代价写在这里：**该列在 one-shot 档恒为 `null`，不是「没有不完整会话」**。

### 墙钟分两段记，但两段今天都不存在

`totalWallClockMs` 在代码里**不存在**（`grep maxSteps|stepWallClock|totalWallClock|deadline` 在 `packages/ apps/ scripts/` 零命中），它是 ADR-0029 与票 03/04 的设计值。所以本册只裁口径，不落码：

- deadline 按 `activeWallClockMs`（不含退避）判；
- 退避单独记 `backoffMs`，它自己受 300 s 累计封顶约束；
- `totalWallClockMs` 保留为真实墙钟（含退避），只作记录。

两段记之所以不会退化成「deadline 可被无限拉长」：**总退避预算是一个硬上限**，退避吃不满 30 min，它最多吃 5 min。

### 并发不由本册管

生成侧今天完全串行（`run.ts` 的 `for … await`，模型内轮次也串行），`season.yaml` 的 `concurrency` 只被对局调度器读。本册**不引入并行**，理由不是串行更好，是 429 已经证明在并发 1 下就会撞（S4 那 8 次全是串行撞的），而渠道的限流模型（速率桶？并发数？日配额？）我们**一条数据都没有**——没有数据时引入反馈控制，只会得到一个永远在抖的闸门。并行压缩整体生成时间的场景由外部按批跑，不在仓库里实现。

**单模型失败不中止同批**同样是本册的保证，不是现状的巧合：`run.ts` 的循环对每个模型 `try/catch`，失败计数 + 写失败档 + stderr 一行，然后**继续下一个**，全部跑完才以非零退出码收口。这条今天没有任何文档担保，本册把它钉住。

## 残余风险

1. **300 s 与 60 s 都是估值**，没有一个来自实测。它们的意义是「有上限」，不是「上限正确」。
2. **截断从三枪降到一枪改变了 one-shot 行为**。ADR-0032 裁的是 agent 形态「重试一次 → 格式反馈」，one-shot 没有格式反馈这条腿，第二次仍截断即判传输失败。chat 族的输出预算完全由服务端默认决定（已观测单轮 87,320 token），触发频率要等第一季数据。
3. **one-shot 档的「不完整会话」列恒为 `null`**。封存的历史榜因此无法用新口径复查，这是刻意的：改 `readFailureRecords` 会让失败名单与主排名自相矛盾。
4. **阈值 60 s / 3 次无数据**。它们定的只是「明显不是抖动」的量级。
5. **429 的双语义只能靠上限兜底**。速率限制型会等到时长，配额耗尽型会等到 300 s 才认输——后者是可接受的浪费，因为它是异常事件的浪费，不是常态成本。

## 重评条件

- **渠道真的开始限流，或 `Retry-After` 成为常态**：ADR-0028 的「`free` 席位重新裁决」条件同时触发，本册的「假设不会限流」前提作废，三套预算全部重裁。
- **`totalWallClockMs` 落地**：实现 deadline 的那一票必须按 `activeWallClockMs` 判，不得用含退避的墙钟；若它做不到，本册的墙钟口径要重新论证而不是被静默覆盖。
- **第一季数据显示「撞过限流」与会话时长强相关**（慢模型必然更长），而阈值化把慢模型整批推进污染表：那时要动的是阈值的形态（按比例而不是绝对值），不是把它去掉。
- **实测显示静默失败仍在发生**（`failureKind` 缺席的传输失败、或报告里 429 与 5xx 仍然不可区分）：说明采集侧的键没被所有路径填上，这是本册的体检指标。
- **档案形状版本在 A1 首档一次性升级**：本册的 `failureKind`、ADR-0035 的 `contextLength` 与终止原因字段（`termination` / `atStep`）必须同批带上。分批升级会让首批档案分成几代，而那一批正是所有后续比较的基线。
