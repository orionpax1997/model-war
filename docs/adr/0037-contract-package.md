# 契约包：一个目录、一个身份、一条生成链

`/contract` 挂进去的四条全部来自 `docs/rules-v2/`，所以「模型读到的契约」与「仓库里那份契约」是同一批字节。契约包作为**一个对象**成立：它由哪些字节组成、各条的真源在哪、以及它怎么被整体识别（身份是整棵树的哈希，不是版本号）。

## 问题

ADR-0030 把 `/contract` 钉成四条只读文件，但没说清其中两条的真源：目录说明从哪来，以及那份最小骨架怎么保证与 API 文档 §6 是同一份。ADR-0031 之后这件事更重一层——档案的 `prompts` 只存首条消息，而首条消息的全部内容就是目录说明，它决定档案能被复核到什么程度。

三处事实把这个缺口撑开了：

1. **契约目录不存在**。仓库里既没有 `contract/` 目录，也没有 `examples/minimal.ts`。唯一那份 21 行的目录说明是 `docs/rules-v2/README.md`，而它的读者是**人**：它讲「为什么不能删」、指向 ADR-0008 与 `rulesets/v2.json`，表格只列两份文档。「人读的仓库说明」与「模型读的目录说明」不是同一份。
2. **ADR-0030 的那句保证不成立**。它写「骨架由已有的编译测试保证与文档中的示例一致」——实测不成立：`api-example-compile.test.ts` 扫的是 api.md 全文、验的是每个可运行块零诊断，它压根不知道 `examples/minimal.ts` 存在。「能编译」是两份**各自**的性质，它证明不了两份相同。
3. **目录说明是契约里唯一没有门禁的散文面**。它不在 `GENERATED_ARTIFACTS` 里（不生成），也不在散文门禁的扫描面里。它自己那条「散文里不抄取值」的纪律，对它自己没有任何机制保证。

要裁的不是「README 放哪」这类实现细节，是**契约包的形状**：一个目录、四条、各自的真源、以及它的身份由什么承担。

## Considered Options

- **`/contract` 直接复用仓库根 `README.md`（落选）**：它的读者是人（安装、跑测试、贡献、仓库地图），3 KB 的体量答的不是「哪几个文件、各管什么」这个问题，而且随项目演进继续膨胀。塞给模型的不是契约，是贡献指南。
- **新增 `docs/contract/` 作 staging，组装产物入库（落选）**：`rules.md` 与 `api.md` 各多一份约 30 KB 的物理副本。「两份长期并存」要靠门禁盯一辈子，而它换来的只是「挂载目录看起来更整齐」。
- **运行期从宿主 checkout 多路 `ro-bind`（落选）**：零拷贝，但违反 ADR-0033 的「内容物是入库 rootfs、不从宿主借」；更要紧的是 `/contract` 在磁盘上从不作为目录存在，于是「模型当时读到的四条」没有任何一个可哈希的实体——而档案复核需要的正是那个实体。
- **`docs/rules-v2/` 就是挂载源（采纳）**：不新增目录、不新增 staging。`/contract/*` 与 `docs/rules-v2/*` 是同一批字节，新增的只有一份生成物（骨架）与一份改写的目录说明。代价是契约目录从「文档目录」变成「模型语料目录」——而 AGENTS.md 早就这么写它了：「模型唯一能读到的规则输入（相当于公开 API 文档）」。
- **骨架入库手写 + 逐字节 diff 测试（落选）**：测试把「两份要一致」焊进 CI，看似安全。它真实的代价是把 api.md 的排版（注释位置、换行）变成 `minimal.ts` 的格式约束——规则侧改一行注释，就得在那个 `.ts` 文件里对齐一次。
- **骨架只验编译（落选）**：即现状的等价物。两份之间零判据，而两者都会被模型读。

## Consequences

### 四条与各自的真源

| 挂载路径 | 源（同一批字节） | 真源 | 谁守 |
|---|---|---|---|
| `/contract/README.md` | `docs/rules-v2/README.md` | 手写（模型向） | `check:contract` + `check:prose` |
| `/contract/rules.md` | `docs/rules-v2/rules.md` | 表格区块：取值文件 + 键清单；散文：手写 | `check:drift` |
| `/contract/api.md` | `docs/rules-v2/api.md` | 表格区块：注入面符号表、后果行、取值；散文：手写 | `check:drift` |
| `/contract/examples/minimal.ts` | `docs/rules-v2/examples/minimal.ts` | `api.md` §6 的 `ts` 围栏块 | `pnpm run generate` + `check:contract` |

目录说明的读者从此是模型。人向的两条断言各有家，删掉开头的「它为什么不能删」不丢事实：「契约不可删」在 `AGENTS.md` 与根 `README.md`，「自包含：模型仅凭它们即可写出能过校验的脚本」在 hld §6.1；缺的只是那句**理由**（模型读不到代码 ⇒ 契约是投影而非第二套事实），它补进 hld §6.1。

### 骨架是抽出来的，不是另存的一份

`examples/minimal.ts` 由 API 文档 §6 那个 `ts` 围栏块**逐字节**抽出。真源唯一，所以一致性是构造性的：判据就是「产出的字节 == §6 那一块」，不需要一条「两份相同」的比对——那个比对只有在两份都存在时才成立，而那时真源已经有两个了。

因此这份文件**不带生成头注释**。别的整文件生成物都有「勿手改 / 真源在哪 / 为什么规则层读生成物」那三件套，这一件不能有：多一行注释就不再等于 §6，而模型 `cp` 走它时也会带上一段无用注释。补偿是三处：注册表里的登记（机器可读的真源声明）、目录说明里的那一条（模型读得到）、以及两道判据（漂移检查与 `check:contract`，后者在快门禁里）。

抽取的失败面按错误报，不折算成空产出：§6 里含顶层入口声明的块**一个都没有**（小节被移走、标题编号被改写）或**超过一个**（又贴了一段完整脚本），都非零退出并由人决定哪个才是骨架。抽错的那一份会被模型复制走。

「逐字节」也意味着 api.md §6 的排版约束扩展到了一块 `.ts` 正文：§6 那一块的缩进与换行同时是骨架的缩进与换行。这是选「抽」必付的账；替代方案就是两份。

### 契约包的身份是内容哈希，不是版本号

ADR-0008 让版本号只锚规则集取值、不锚文字，于是**同一个 `v2` 之下 `rules.md` 的字节是会变的**。所以「契约 v2」不足以定位「档案当时读的是哪份文本」——它连「当时是两条还是四条」都表达不了。

身份因此由**整棵挂载树的哈希**承担，口径写死为：

- 范围：挂载清单里的四条，按路径排序；
- 串接：逐条 `path` + `\0` + 该文件字节；
- 算法：`sha256`，小写十六进制；
- 落点：档案首条消息的末行，形状是 `contract: <版本号> tree=sha256:<hex>`。版本号前缀与哈希并列，是因为两者回答不同的问题：前者「哪一套取值」，后者「哪一份字节」。

为什么含目录说明与骨架：两者都改变模型行为——目录说明**就是**首条消息的全部内容，骨架是它复制的起点。把这两个的字节排除在指纹外，等于档案记不住「模型当时看到什么」，而这是 ADR-0031 之后唯一的复核依据。

为什么落首条消息而不新增档案字段：ADR-0008 已经把「改存档形状字段」的代价算过——十一字段一次定死，加一格波及每一份已冻结的 `meta.json` 与引用它的 `input.json`。而且首条消息是档案里唯一能让哈希与「模型当时看到的那段文本」待在同一处的地方。

**版本号不是契约包的标识，它仍是规则集取值的标识。** 这两件事各有一个承载者，所以形态变化（四条变五条、目录说明改写）既不升版，也不会丢身份。

### 可写面不写在目录说明里

「`/workspace` 是唯一可写面、交付物在那里」属于**这次会话**的任务与硬约束（ADR-0032 的 `system` / 首条 `user` 分界），不属于按版本冻结的契约目录。两处都写就是同一句话两个家，而漂移方向是固定的：前面那份能改、后面那份改不了。

判据落在 `check:contract`：目录说明里出现 `/workspace` 即红。另一条判据守相反的方向——目录说明点名的每个 `/contract/<path>` 必须在挂载清单里，清单里每一条也必须被目录说明点名（少写一条，模型就不知道它存在）。

### 拷贝发生在构建期，运行期零宿主依赖

`docs/rules-v2/` → 镜像里的 `/contract` 由 rootfs 组装期完成；运行期 `--ro-bind` 的是镜像里那份（ADR-0033）。所以更新链路是：**改规则 → `pnpm run generate` → 重新组装 rootfs**。ADR-0033 的「不从宿主借」因此读作「运行期不 bind 宿主」，不是「构建期不读仓库」。

这条链的前半（生成 + 漂移检查）今天就在；后半（rootfs 组装）尚未实现，ADR-0033 的残余风险已自认「谁来更新它、怎么验它，实现时才定」。本册不替它裁。

## 残余风险

1. **目录说明是手写的，而它是首条消息的全部内容。** 两条判据（`check:contract` 的覆盖率与可写面、`check:prose` 的禁抄取值）守的是形式，守不住「说得对不对」。后者只有 review——这是它作为「无生成物身份的手写契约面」必付的账。
2. **身份哈希没有消费者，直到 A1 落地。** 口径在本册写死，实现随 agent harness 一起落；在那之前「契约包身份」是一个已经裁定、但还没被写入任何档案的东西。
3. **骨架与 §6 逐字节相同，把 api.md 的排版变成了一份 `.ts` 的格式要求。** §6 那一块若被重新换行，骨架跟着变——这正确，但它让「改 §6 的排版」不再是纯文档编辑。
4. **`/contract` 的挂载点不带版本号，而源目录带。** 模型看不到 `rules-v2` 这个字符串，只能从首条消息里那行身份指纹与目录说明的标题知道自己是哪一版。这是有意的（挂载点稳定、版本住在路径里），但意味着「模型自报版本」这条路不存在。
5. **旧契约快照仍需保留，而保留理由没有 ADR。** `docs/rules-v1/` 的两份文档仍被 `check:drift` 托管，但「为什么留、给谁、留多久」只写在它自己的目录说明里。这与本册同源（档案要能被复核），已在 ADR-0031 的修订里收口。

## 重评条件

- **契约目录需要第五条文件**：四条这个数字由挂载清单承担，不由人记；加一条时要一起改的是清单、目录说明与身份哈希的范围。
- **rootfs 组装改为不拷契约、或改为运行期从宿主读**：上面「拷贝发生在构建期」与「身份是整棵树的哈希」两条的前提一起变。
- **需要「契约包形态变化」升版本号**：那要先推翻 ADR-0008——它的落选理由（同一套取值两个契约版本号）正是本册选内容哈希的原因。
- **实测显示模型照目录说明读的顺序不对**：要动的是目录说明的措辞与顺序，不是把它拆成多份或塞回首条消息之外的注入。
- **骨架的抽取目标从「§6 那一个块」变成多块**：例如骨架要拆成「文件级模板」与「函数级模板」两份，那时「恰好一个」的判据要重定，而不是放松成「取第一个」。
