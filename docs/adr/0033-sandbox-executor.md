# 生成期沙箱的执行器:bubblewrap,内容物以入库 rootfs 钉死

**约束**:生成期沙箱的执行器是 `bubblewrap`,每一步一个新进程树;内容物是一份入库、以字节钉死的 rootfs;执行器不可用即失败,不降级。

## 问题

此前的禁令都落在「内容物」上(不放引擎、不放试跑入口、无网络),没有一册回答**执行器是什么**,而它决定实现的第一行代码。三个问题捆在一起:谁提供隔离(PID / mount / 网络命名空间)、内容物从哪来(借宿主的还是自带)、以及「一步」在进程意义上是什么。

第一条已被排除:宿主进程 + 目录裁剪。`cmd &` 起的后台进程**活得过一步**,而步数、配额、观测、提交四件事全部建立在「一步 = harness 派生的一次 `bash -c`」上——后台进程白拿并行算力(步数上限与实际工作量脱钩)、让步与步之间的磁盘状态失去因果、并且能在 `evaluate` 之后继续持有写句柄,让「成绩取最后一次 `evaluate` 评的版本」失效。

另外两条事实决定候选集:仓库里 OS 级隔离零实现;`hld §2.2.11` 早已把「Docker(主路径)」列入明确不做——采纳容器化不是新增裁决,是推翻既有裁决。

> **修订(2026-11-20)**:本册原稿的「薄壳 + 一条只通向宿主的通道」已整条删除。协议换成原生工具调用之后,`check`/`probe`/`evaluate`/`finish` **不在沙箱里**:rootfs 的 `bin/` 只有静态 ELF,受限工具的家是请求体的 `tools` 声明,由宿主分派。执行器的职责因此更窄:**只负责「一步一个新进程树」**,不再为宿主服务提供任何传输。原文见 git 历史。

## 落选方案

- **宿主进程 + 目录裁剪**:没有 PID 命名空间,补法只剩「独立 mount namespace」(已经是容器)或 cgroup 清理(要 root 或可靠的委托,runner 上没有)。
- **Docker,每步一个容器**:隔离强度落在**威胁模型之外**(要防的是内核漏洞利用,而对手是一个在写 shell 命令的模型),代价(每步 200 ms–1 s、常驻 daemon)却落在预算之内。要区分两种形状:每步一次性的 `docker run`,与**持久会话**的 `docker exec`——后者正是重评条件点名的那种。
- **gVisor / Firecracker microVM**:同一错配再叠外部依赖——`/dev/kvm` 在托管 runner 上存在但未被文档化、官方声明不支持嵌套虚拟化,地基压在一项不承诺的能力上。
- **其余「非命名空间」路线(proot / nsjail / firejail / Landlock + seccomp / cgroup 兜底)**:每条只解掉半个问题——proot 是 ptrace 语义、**不是安全边界**;Landlock + seccomp 封得住文件系统与网络、封不住进程树;nsjail 要自编译,firejail 是 setuid + 有 CVE 史;cgroup 清理已被 PID 命名空间覆盖,且托管 runner 上不可靠。共同点是没有一条解掉「回收一棵不可信进程树」。
- **内容物从宿主借(白名单 + `ldd` 闭包)**:`bash`/coreutils/glibc 版本随机器漂移,后果直接打在等价基线上——同一模型换台机器成绩不同,先得排除 bash 版本。记版本加漂移门禁只是把不确定性**记下来**。
- **busybox-static 顶三个命令 + 宿主 `bash`**:只解掉三个 `.so`;换成 busybox 语义后 flag 差异会变成「模型失败原因不可归类」,最难修的一类噪声。

## 落了什么

### 隔离:每步一次 `bwrap`,不是「进一个沙箱」

根文件系统**从空开始**(`--tmpfs /`),宿主根目录一个 inode 都不出现;只 `--ro-bind` 入库 rootfs 与只读契约,`--bind` 进 `/workspace`;`--unshare-user/pid/ipc/uts/net/cgroup`、`--cap-drop ALL`、`--new-session`、`--die-with-parent`、`--clearenv`。

四条互不替代的性质:

1. **进程树回收靠内核语义,不靠 cgroup、不靠容器销毁**:命名空间的 init 退出时内核杀掉全部残留进程。所以 `cmd &` 只能在同一步内活着(`cmd & sleep 1; wait` 合法),步一结束即全灭。
2. **可见面是「从空根里长出白名单」,不是「把宿主的 `/bin` 裁掉」**:清单外的路径没有 inode 可指向,所以「绝对路径绕过 PATH 白名单」结构上不存在。
3. **无网络是结构性事实**:`--unshare-net` 连 loopback 都不给,所以也不存在「通道要走网络」这种设计冲动。
4. **两个生命周期分开**:沙箱实例 per-invocation(一步一次,没有可复用的旧实例),`/workspace` per-session(宿主持有、bind 进每一步)。「每步新实例」在 bwrap 下是定义使然而非不变量;只有容器方案里它才变成要付启动开销的决定。

单步启动在 10 ms 量级,**小到不值得为它改墙钟判据**;会话级 deadline 的起止点不在这册。

### 内容物:入库 rootfs,不从宿主借

十来 MB 的 rootfs 产物:静态 `bash` + 一组钉死的 coreutils + 只读契约。以字节为准,配「现算 == 入库」的漂移门禁(与 runtime bundle 同款)。**清单不在这册枚举**:家是 `packages/schema/src/sandbox-rootfs.ts` 与生成物 `PROVENANCE.md`——在 ADR 里抄一份只会过期。

实质是把「容器」唯一真实的优势搬了过来:**镜像的价值是「内容物可钉」,不是「隔离更强」**。钉住之后,等价基线不再依赖「两台机器的发行版恰好一样」,`ldd` 闭包门禁整条消失。

沙箱职责也随之缩小:`check`/`evaluate` 全在宿主侧,所以沙箱里**不需要** `node`、`tsc`、`node_modules`、`rulesets/`、测试框架,只要 `bash` 加那几个 coreutils——其中 `cp` 是首条消息写明的起手式(`cp /contract/examples/minimal.ts /workspace/script.ts`),缺它就是一次 `exit 127`。

### 资源上限:`ulimit`,并且承认它不完整

bubblewrap **没有**资源限制(没有 cgroup,也没有 rlimit 选项),而 **PID 命名空间只限制可见性、不限制数量**:fork bomb 照样吃得光宿主的 CPU 与内存。所以每步 shell 外面必须包一层 `ulimit`(进程数、地址空间、CPU 秒),由 `bash` 内置承担,零依赖。这是必须项,不是加固项。

边界要说清:rlimit 是**逐进程**额度,不是聚合额度,`N` 个子进程各有一份。所以它是把「一次炸穿」降级成「炸得慢一点」。彻底的办法是 cgroup v2 委托,它在托管 runner 上不可靠,所以不做,记进残余风险。

### 不可用就失败,不降级

启动时先自证:跑一条最小 `bwrap` 调用并断言成功,同时断言版本不低于下限。失败即 fail-closed,任务直接失败,**不回落**宿主进程。

理由:降级路径正是 `cmd &` 那条洞所在的路径,允许它存在会让威胁模型变成两套,逐条核对失去意义;而「标注降级」在实践中会退化成降级样本悄悄进了对比表。

报错必须写出已知成因(bwrap 从内核只拿到 `EPERM`,这是上游明说的限制,不是 bug):Ubuntu 24.04 的 `kernel.apparmor_restrict_unprivileged_userns` 一步 `sysctl` 可解;26.04 起 profile 默认加载,还要卸载它;在容器里跑要四个 override(seccomp、apparmor、systempaths、`SYS_ADMIN`)。**发行版收紧非特权用户命名空间是政策而非缺陷**,所以「每个大版本重验一次」是长期成本,不是一次性成本。

**CI 上必须让它真跑起来,不许 skip**:让环境变化失败在它自己那一行,而不是变成一串莫名失败或一整排静默跳过的用例。

### 调试面必须结构隔离

沙箱内没有 `ps`、`strace`,也没有「进容器看一眼」这回事。所以需要本地的诊断 profile(把宿主根 bind 进去),但它必须是**独立代码路径 + 只认显式环境变量**,结构上不可能在生产路径生效——否则「调试开关」就是自己留的洞。

## 残余风险

1. **逐进程 rlimit,不是聚合 cgroup**:fork bomb 能吃穿宿主;后果是可用性,不涉及读泄漏或逃逸。
2. **AppArmor 政策会一直变**:每个 Ubuntu 大版本都要重验 preflight,不是一次性适配。
3. **在容器里跑会缺能力,且 Linux-only**:四个 override,本册不提供兼容层;macOS / Windows 开发机跑不了这条路径,绕道容器又撞上这一条。
4. **不设 seccomp**:内核 bug 不在防线内——这是威胁模型划界,不是疏忽(对手是模型不是漏洞利用者)。
5. **rootfs 是新的入库件**:比代码产物更容易被「顺手升级一下」而无人察觉,所以它的更新路径必须显式。
6. **陌生环境 triage 成本是真实的**:bwrap 的报错只有 `EPERM` 一档信息量,preflight 的成因清单是唯一缓解。

## 重评条件

- **需要防内核漏洞的隔离**(对外公开发布 benchmark、或跑第三方交付的脚本):容器 / gVisor / microVM 重新上场,本册「威胁模型划界」这条理由失效。
- **目标环境里 bwrap 不可用且政策步骤解不掉**:退回每步一容器,但进程树回收与工作区生命周期要重测。
- **执行器引入持久会话,或工具调用不再由宿主分派**(执行器自带工具环、渠道代发调用):本册的隔离形状前提失效。
- **模型确实需要网络**(要装依赖才能跑 `check`):`--unshare-net` 要拆,信任方向要重新设计,不只是加一个开关。
- **要把 `check` 从宿主侧搬进沙箱**:rootfs 体积与漂移口径要重估,且与「宿主是唯一执行者」直接冲突。
