# 变异分数的历史住在入库基线里,不住在产物里

ADR-0026 把变异分数做成棘轮,并把「历史」判给了**入库基线**:「产物(`reports/mutation/`)可以过期,基线不能——不入库的棘轮不是棘轮」。这条 ADR 把那个判断往前推一步:**分片分数随时间怎么走**,是唯一一个「基线本身答不了」的问题。基线只记着「上一次是多少」,而棘轮要人做的判断恰恰是「这一片是在变好还是变坏」——只看到最后一个数,看不出它是慢慢爬上去的,还是被一次口径变更一次性抬上去的。这条 ADR 裁那个历史住哪。

## Considered Options

- **历史住在 CI 产物里(落选)**:夜间流水线已经上传整份 `reports/` 作为 artifact,但保留期只有 14 天,且流水线没有 `actions: read` 权限、也没有下载历史产物的步。于是「历史」在 CI 内根本不存在现成来源:要靠人工 `gh run download` 把散落的 artifact 拼起来。拼出来的东西还不在版本库里,谁也不会去查。落选理由不是「做不了」,是**做出来的历史没人会看**——与 ADR-0026 判 ADR-0010 的观测项落选是同一条理由。
- **历史住在单独的入库文件里(落选)**:例如 `stryker/baseline/history.jsonl`。落选理由是它会变成**第二个家**:同一件事(这一片的基线是多少)记在两个文件里,两者必然漂移——改了一个忘了另一个,没人会发现。而 ADR-0026 已经把「基线是历史的家」判定了,再造一个平行的历史文件等于把它推翻一半。
- **历史住在基线文件里(采纳)**:每个分片的基线 JSON 多一个 `history` 数组,按时间升序记每次抬升的数字。它与基线在同一个文件、同一次写入、同一个 diff 里,不可能漂移;它随仓库走,随代码评审被看见;它不依赖任何 CI 权限或保留期。

## Consequences

- **写口只有抬升命令**。`history` 由 `mutate:baseline`(`accept-baseline.ts`)在抬基线时追加,没有第二条路。这与 ADR-0026 的「抬升只能显式为之」是同一条纪律:能改判据的开关不能出现在判据自己的正常路径上。门禁自测守着它:抬基线的反例(写临时路径)断言历史被追加、且旧条目不动。
- **历史从下一次抬升开始积累**。在它之前立的基线文件没有 `history` 字段,趋势报告如实说「这个基线是在历史机制之前立的」,并在下一次抬升时把当前值补成第一条(`at` 记 `unknown`——旧基线建立的时间没有被记下来,不猜)。**不猜**是这条 ADR 的硬要求:历史里的每个数都要能追溯到一个真实时刻,补出来的时间戳会让「什么时候变坏的」这个问题失去答案。
- **趋势只做片内比较**。跨分片排名、汇总成总分,一律不做——理由与 ADR-0026 相同(分片的 mutate 范围与统计口径各不相同,跨包覆盖会被静默记成 Survived/NoCoverage)。趋势报告(`pnpm run observe:history`)逐片给序列与净变化,不给总分。
- **趋势报告是产物,历史数据是基线**。报告落 `reports/mutation/history.md`(不入库),数据在 `stryker/baseline/*.json`(入库)。两者分开:报告可以过期,历史不会。
- **趋势报告不改判据**。它只读基线、只写报告,不出现在任何流水线、默认链或常跑入口上。

## 重评条件

- **分片的 mutate 范围或统计口径发生结构性变更时**(例如换了 mutator、某片的排除项变了):历史序列在此处**不可比**,旧条目必须作废而不是继续接着画。此时的处理是清空该片的历史并在新口径下重新积累,而不是保留旧序列加一段说明——因为口径变更前后的分数不是同一个数。
- **分片被合并或拆分时**:历史随之拆分或废弃,不跨分片搬运。
- **出现能自动写回基线的机制时**(例如上游提供了可信的自动抬升):那时「显式为之」这条纪律本身要先被重评;本 ADR 的历史部分随之重写。
