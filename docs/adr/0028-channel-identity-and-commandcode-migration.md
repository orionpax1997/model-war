# 渠道身份进榜键：同一个 baseUrl 下档位决定能跑什么

## 问题

生成侧从 opencode go 迁到 commandcode。这次迁移暴露了一件在单渠道时代不需要回答的事：**「模型在哪个渠道上跑」本身是一个独立变量，而不是「模型」这个变量的附注。**

同一批 slug 在换渠道后行为就变了，实测有两处：`minimax-m3.1-flash` 在 opencode 上默认产出 17 个 reasoning token，在 commandcode 上探活是 0；`mimo-v2.6-flash` 在 opencode 上撞 ~305 s 硬切，在 commandcode 上 709 s 的调用完整返回了 87,320 token。这不是「模型变强了」，是渠道侧的行为不同。

更要紧的是：**`baseUrl` 相同不代表渠道相同**。commandcode 一个 `/provider/v1` 下面挂着三档订阅，同一 URL 决定的是「哪些 modelId 可用」与「配额窗口有多宽」。`gpt-6.1-sol`、`google/gemini-4-argon`、`claude-opus-5` 在某一档上是 403 `MODEL_NOT_IN_PLAN`，在更高档上就是 200。所以渠道身份是「渠道 + 档位」的合成，不是 URL。

第三件事：档案里已经有 102 份跨渠道的历史（69 成功 / 33 失败），它们全部产生于单渠道时代，没有渠道字段。

## Considered Options

- **从 `baseUrl` 推导渠道（落选）**：分不出档位。同一个 URL 在 GOAT 与 Provider+ 两档下可用模型集不同，推导出来的是「端点」而不是「渠道身分」。落选理由不是做不到，是推出来的东西答不了「这批数据能不能并列读」这个问题。
- **给历史档回填渠道标识（落选）**：历史档确实都来自 opencode，看起来回填是「补全信息」。但它们是**在字段还不存在的时候产生的**，回填等于替当时的记录者补写他没见过的一栏。这与本仓对 `attemptEvidence` 缺席的处理是同一条纪律：缺字段是配置代差，标注缺，不补值。
- **渠道标识作为榜键的第四维（采纳）**：榜键变成 `rulesetVersion + modelVersion + harnessVersion + channelId`，四键相同才允许并列读。历史档的 `channelId` 在类型上是可选的，装载期不因缺席拒跑。

## Consequences

- **`channelId` 新档必填、老档选填**。类型上可选不是「以后可能填」的缓兵之计，是**明确承认历史与新数据不同源**。
- **直接推论：跨渠道不并列读。** 把不同渠道的成绩放进同一张表，读者会把它当模型能力读，而实际读到的有一部分是渠道差异。这条纪律不需要靠读者自觉，榜键本身就不允许合并。
- **缓存开启按端点族分家，因为默认行为不同**。实测（commandcode provider v1）：`chat/completions` 族**零参数**就缓存，第二轮命中 98%；`messages` 族**默认完全关闭**，不发 `cache_control` 就永远是 0。所以策略是「跟随官方默认，只在默认缺位的地方补齐」——chat 族不加任何参数，messages 族显式打 `cache_control`。
- **`ttl: "1h"` 不需要 `anthropic-beta` 头**。这是实测推翻的一个猜测：`{type:"ephemeral", ttl:"1h"}` 直接被接受并返回 `cache_creation.ephemeral_1h_input_tokens`。选 1h 而非默认 5min 的理由是轮次节奏——单轮生成的耗时中位数在数百秒量级，5min 断点在下一轮之前就失效。
- **~305 s 不是本渠道的属性**。它是 opencode 侧的特产，commandcode 侧没有这个闸门。这条写在这里是因为它曾被当成「某个模型结构性不可用」的证据，那个结论随渠道迁移一起失效了。
- **免费档在 20 次突发下未触发限流**。`thinkingmachines/inkling-2-small:free` 与 `stealth/glyph-cluster:free` 各连发 20 次最小请求，全部 200，无 429、无 `Retry-After`。这是**当前观测，不是保证**——免费档的额度策略随时可变，所以它不是一条可以长期依赖的事实，只是「现在不必为它预留退避预算」。
- **网关会往请求里塞前缀**。极短 prompt 的 `prompt_tokens` 回显约 130–150，实际内容只有十几 token。真实可用上下文比标称略小，量级上是千分之几，对当前最紧的那条（标称 256k）无实质影响；但按标称做预算时要知道这不是精确值。
- **`gpt-6-luna` 两个端点族都通**，`/chat/completions` 与 `/responses` 各自 200 且形状正确。所以不需要为它增加第四族路由。顺带观测到 `/responses` 族默认带 `prompt_cache_retention: "24h"` 与 `reasoning.effort: "medium"`，这属于该族的默认值，不等于我们需要跟随。

## 重评条件

- **再换渠道，或档位变更**：榜键的第四维取值随之变，跨该点的数据不并列。若某次迁移后大量模型在两个方向上表现一致，「渠道是否值得单独成维」这个判断本身要重估。
- **免费档出现限流**：一旦观测到 429 或 `Retry-After`，S5 名册里带 `:free` 的席位要重新裁决——不是因为限流本身，而是因为它在分步形态下会被放大两个数量级。
- **上游对某族加了新的硬闸门**（超时、并发、单次最大输出）：这类闸门只在渠道侧存在，正是本 ADR 要隔离的变量；出现了就补进本条，而不是修改模型的评价。
- **`/responses` 族成为某模型的唯一入口**：那时需要裁决「换人」还是「加一族」，那是 harness 侧的改动，不动本 ADR 的渠道身份判断。
