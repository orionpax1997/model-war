# 规则文档的表格由真源包生成,而它的真源时点在规则落库那一格

`docs/rules-vN/` 两份文档的**表格部分**(API 表、常量表、`ERR_*` 表、数值表)改由真源包与 `rulesets/vN.json` 生成,散文段(机制、语义、示例)仍手写;为此给生成物加一种**区块形态**——真源产出 `{ marker, content }`,漂移检查按 marker 把工作树文件里对应的区块抽出来逐字节比,区块外的散文不比。配套的一条时点决定:**沙箱注入 API 符号表由规则落库这一格回填**,不再等沙箱执行器——终稿 API 面是那一格的交付物,等一个下游格子来定上游的名字,同源就只剩一句人话。

## Considered Options

- **符号表继续留空、回填仍归沙箱执行器,规则文档全手写**:落选。那样「终稿 API 面与静态校验器、沙箱注入面同源」这句话没有任何机器支撑,只剩三处人工同步;而 API 文档是**直接进 prompt** 的东西,名字错一个就是模型写错代码,且错得静默。交接时写一句「G 回填时逐个核对」不构成防线。
- **整篇生成(散文也由真源产出)**:落选。语义段与机制段天生是散文,把它们搬进生产函数会让一份 Markdown 的正文分裂在真源包与生成器之间,改一句话要跨两个文件,而这类改动频率远高于改一个码名。
- **拆出第三份全生成的文件**(表格单独成文,两份散文文档指向它):落选。它要改 hld §6.1 明写的「两份文档」契约;更麻烦的是规则文档里有些内容本来就不是表(设计时间轴的四个边界、C1~C7 的验收口径),拆出去会得到一份两边都不像的文件。
- **不生成,加一条测试断言「文档里出现的每个名字都在符号表里」**:落选。它要解析 Markdown 抽标识符,比生成本身脆;而且只能抓「多出来的名字」,抓不到「少写了一个错误码的触发条件」——而错误码正是最容易漂的一类。
- **符号表拆成两张**(契约面归规则落库、注入面归沙箱执行器):落选。v0 两张表必然逐字相同,而两张相同的表会凭空造出一个「它们什么时候会分叉」的问题。真要分叉的那天,升级条款另有位置。
- **脚本 tsconfig 也做成真源包的生成物**:落选。那份配置的身份是 tsc 的输入,没有任何仓库代码 import 它;做成生成物等于给一份静态配置白付一次漂移检查,以及「改了真源先跑一遍生成器」的往返。它落在根配置堆场。

## Consequences

- **「生成物」这个概念多了一种形态**,漂移检查要多一段判定分支(按 marker 抽区块比对)。回报是规则文档不必在「全生成」与「全手写」之间二选一,而这两者对散文占七成篇幅的文档都不成立。
- **`packages/schema` 里那张符号表的注释会说错话**:它写着「刻意为空,回填触发条件是沙箱执行器产出注入面」。本决定之后,「刻意为空」这段历史陈述必须改掉,否则后来者会按注释把它当成待办而跳过。
- **规则落库这一格多带一件东西**:脚本 tsconfig 的取值与依据(它归这一格定,归生成管线实现)。这不是新职责,是「编译器的名字解析承担白名单反转」那条已裁决定的直接后果——承载它的配置形状与契约面同源,而它是下游的实现。
- **收录判据必须写死在注释里,而不是留给消费者各自理解**。本决定采纳的那一句是「收脚本能在运行时当值用到的名字」:函数、helper、错误码字符串收;类型名不收(它们在类型面上,与「API 误用」那条判据同一张脸);数值不收(归规则集文件那条生成链)。判据缺失时的失败模式是两侧各自往表里塞东西,而两张只会越塞越不像的表比一张判据分明的表糟得多。
- **错误码必须全定或全删**。草案里只有错误资源不足那一码在来源文档被点名过,其余是按界检查职能反推的候选;半截的码表比没有码表更坏,因为模型会当真。
