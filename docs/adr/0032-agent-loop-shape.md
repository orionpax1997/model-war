# agent loop 的形状：接缝、历史组成、动作边界与每步预算

## 问题

前三册把世界搭好了：ADR-0029 定 harness 是谁（bash-only、单会话、宿主侧配额、两种 deadline），ADR-0030 定模型能碰到什么（三档工具、无提交动作、观测外置），ADR-0031 定这次会话留下什么记录（过程记录、候选序、形状版本）。**没有一册回答「loop 怎么跑」**，而实现第一天就要回答五个问题。

接缝在哪：现有生成侧是一条 `for (round)` 外循环，阶段由「已入档的有效候选数」隐式推进（`stage = OPTIMIZATION_STAGES[candidates.length]`）。agent 形态要把这条循环整个换掉，而不是把它包起来。

历史里存什么：分步形态每步都发完整对话，所以「对话」不是一份 prompt，而是一份只增不减的记录。它由哪些部分组成、哪部分是模型写的、哪部分是 harness 写的，决定了模型能不能信任自己的记忆。

动作怎么解析：只暴露 bash 意味着没有 tool-calling 接口，所以「一次输出算几个动作」这条协议要由我们发明，并且它会直接变成「模型怎么表示这一步做完了」。

每步能看多少字节：线性历史每步重发，某一步的输出会被后续每一步重复付费。上限放在哪一层、由谁截断，决定模型的世界与磁盘上的一致性能不能成立。

推理怎么带：本季名册跨四个端点族（名册是本机 `models.yaml`，不入库、随赛季变，本条不枚举席位），其中 `claude-haiku-5-5` 的 thinking 需要签名回传，`glyph-cluster` 的推理是加密不透明块（`{type:"reasoning.encrypted", data:"gwst1.…", format:"stealth-v1"}`）。ADR-0030 已把「某席位推理是加密块」列为重评条件，在这里结账。

## Considered Options

- **保留外循环、把 agent loop 包在里面（落选）**：它同时保住「阶段」与「`maxSteps=1` 退化路径」两条已被裁决删掉的路径，后者没有消费者，只有维护成本（ADR-0031）。
- **每条 bash 命令算一步（落选）**：直接违反已定口径。一步 = 一次模型调用，模型一次输出跑三条命令就成三步，deadline 的语义随之漂移。
- **抽第一个动作块执行、多余块忽略（落选）**：不浪费步，但会造出最难诊断的失败模式——模型写了三条，只跑了第一条，其余静默消失，然后它基于「三条都跑了」继续推理。宁可浪费一步，也不要在错误的世界观上继续。
- **静态解析动作块、按白名单放行命令（落选）**：它会把 bash 退化成命令列表执行器。而写文件的方式本身是重定向（`cat > … <<'EOF'`），支持重定向就必须支持管道才不荒谬，然后就是重写一个 shell。更要紧的是它证明不了「没有任何旁路」——循环、子 shell、`eval` 都能绕过静态解析。
- **结构化 `write-file` 动作（落选）**：等于把 tool-calling 偷回一小块，并且立刻引出「能不能写别的路径」「能不能 append」一串新问题；它唯一的收益（省掉 heredoc 的 token）已被「`/contract/examples/minimal.ts` 可 `cp`」覆盖。
- **reasoning 一律丢弃 / 一律尽力回传（落选）**：前者让 messages 族丢掉签名（可能 400，或让多轮退化），后者让 chat 族带上它不认识的字段（同样可能 400）。
- **每步一个合计上限，三个键共享（落选）**：会造出「stderr 短，stdout 就被允许更长」的相互挤占，模型无法预测自己的预算。
- **截断 assistant 自己的输出、只落全文（落选）**：同一件事在「模型看到的」与「落盘的」里成了两个字节串，ADR-0031 那条「模型看到的字节 = 落盘的字节」当场作废；而省下来的上下文是假的——那段字节上一轮已经是响应 token，已经在上下文里付过费了。
- **历史裁剪（丢掉旧步）（落选）**：违反线性历史这条铁律，并让「协议轮数 = 过程记录条数」失去意义。
- **把窗口上限做成静态约束（落选）**：按最坏情况（步数 × 上限）给所有席位削足，对窗口充裕的席位是白砍。

## Consequences

### 接缝是替换，不是包裹

那条外循环整个换掉：它原有的四项产出（阶段推进、反馈轮数、跨阶段复用、网格计划与陪练身份）全部是一次性形态的产物，留着它们等于每加一个字段、每加一条断言都要维护两遍。

**终止原因与落档判据正交。** 终止原因只决定循环怎么停，落档只看「有没有候选」。模型叫 `done`、步数上限耗尽、总墙钟耗尽、上下文守卫触发，四种都立即停；动作解析失败不停，写一条非零退出码的过程记录条目让模型自己看到并重试，连续三次才停；传输重试耗尽立即停，且那次调用不进过程记录、不进协议轮数（ADR-0031）。停下之后有候选就是成功档，成绩取最后一次 `evaluate` 评的那个版本；一个候选都没有就是失败档（ADR-0030）。

把墙钟耗尽判成失败是不行的：那等于拿资源约束当成绩判据，与「资源不平权、只记录」直接冲突，而且会让一个已经产出成绩的会话被超时判死。反过来，这条正交性也让失败档的含义单一化——**失败 = 一个候选都没有**，不是「没跑完」。

零步会话因此是这条规则的自然端点：一次模型调用都没成功（传输重试耗尽在第一次），过程记录为空、起始 prompt 为空、协议轮数为零、无优化段，落成失败档（ADR-0031）。

`done` 与 `evaluate` 一样计入过程记录，并且**照常占 `maxSteps` 的额度**。不占是更漂亮的规则，但它是「所有调用都算一步，除了这个」这条例外的又一个实例，而 ADR-0030 已经用同一个理由否掉过 `check` 的例外。

### 历史只由模型写的东西和工具吐的东西组成

历史是 `system` + 首条 `user` + 每步一对（`assistant` 原文、`user` 观测）。

**assistant 那一条是模型当时的原始文本，一个字节都不改写。** 不改的理由是「不代言模型」：一旦 harness 把它的输出规范化成「解析后的动作」，模型看到的自己与它实际写的就不是一回事，而它下一轮是照着自己写的原文推理的；一旦 harness 在解析失败时把 assistant 消息改写成「你上一步的动作无法解析」，那是在篡改历史，模型会以为自己没写过那句话。解析失败不是历史问题，是**工具结果问题**：另起一条观测消息说明抽不到动作、退出码非零。

**观测消息的角色是 `user`，不是 `tool`。** 不走 tool-calling 就没有 `tool_use_id` / `tool_call_id` 可配对，用 `tool` 角色在 messages 族会被要求配对、在 chat 族会被要求带 id，等于把 tool-calling 的接口悄悄引进来。

**格式协议住在 `system`，任务与目录住在首条 `user`。** 「每一步恰好一个 `bash` 代码块、只有它是动作、违反的后果」是不变的协议，属于 harness 身份的一部分；契约目录、任务说明与三条硬约束属于这一次会话。这个分界同时与「system 是 messages 族的缓存断点」对得上。

**三条硬约束的清单就在这里定死**，不再只活在票里（ADR-0030 只提了这个词）。它全部落在首条 `user` 侧，判据是「**换一次会话它会不会变**」：写哪、看多少、几步，每次都不同。

1. **可写面与交付物**：`/workspace` 是唯一可写面，`/contract` 只读；交付物是 `/workspace` 里那份单文件脚本，成绩取最后一次 `evaluate` 时它的内容（ADR-0030）。
2. **单步观测上限**：每一步回给模型的观测有个上限，超出的部分它看不到——处方是定向读，不是重跑一遍换个输出。
3. **步数预算**：会话有步数上限，用完即止。收工命令 `finish` 不是免费出口（上文已裁它占额度）。

**收工语义归 `system`，不在上面三条里。** 它是动作语法的一部分：`finish` 是一条命令，会话在这一步结束之后停下。把它放进首条 `user` 会让它变成「这次的约定」，而纠正消息要与 `system` 里那份协议呼应（见下文「一次输出恰好一个动作块」）——两处规定会打架。上面那条「换一次会话会不会变」的判据在这里给出的答案是「不变」，所以它归协议。

> 本节以上是初版措辞；`done` → `finish` 的改名与其理由见文末「修订（2026-11-19）：`done` 从文本哨兵改成命令」一节。

三个数的取值不在本节复述：它们在本册「每步上限」一节与残余风险里各露一次，且全部进 `harnessDigest`。

模型原文**落盘**：过程记录条目带一个可选的原文键，与发回去的字节同源。ADR-0031 原本写的是「不含模型原始文本的存储义务」，这条现在收窄——不是反悔，是它当初的理由（「那是 loop 侧的语义，另行裁决」）在这里被裁了：模型当时看到什么，在读侧只有原文能复原，而这是唯一一次付得起的机会。代价是 ADR-0029 里「既有档案不含模型原始输出」那句话的适用范围要从「全部档案」改成「既有 one-shot 档案」，且它挂在重评条件上，现在可以结账了。

### 一次输出恰好一个动作块

动作块是「```bash」围起来的代码块，整块交给一次 `bash -c`。块内可以有多行命令，按一块计——这既是「一步 = 一次模型调用」的直接推论，也保住了 mini 铁律里真正重要的那半条：每步一个独立无状态子进程。

**解析是严格的：恰好一个块。** 零个（模型只说了话）、多个（模型想一次跑几件事）、块标记不是 `bash`（模型在解释里贴了别的代码），三种都不执行任何命令，只回一条与 `system` 里那份协议呼应的纠正消息。放宽到「抽第一个」省一步，代价是模型以为自己跑完了全部——那笔账不划算，因为它换来的是后续每一步都在错误前提上推理。

用 `bash` 标记而不是照 mini 的私有串（`mswea_bash_command`）：私有串的价值只是把动作块与思考里的普通代码块区分开，`bash` 标记同样做得到（模型贴的 TypeScript 片段是 ` ```ts `），而私有串要求模型记住一串没有语义的字符；在多个不同家族的模型上，这条指令的服从率是未知数，`bash` 是训练分布里的东西。

**收工是块里的一条命令（`finish`），不是文本哨兵。** 整块原样交给一次 `bash -c`；模型在块里调用 `finish`（rootfs 里那条薄壳），薄壳经通道报给宿主，宿主据此在本步**结束之后**停下。所以 `finish` 之后写的行**仍会执行**。这一条替代了本册初版写的「块级 `done` 哨兵」（切掉后半段、之后的行不执行）：那个设计的判据是「整行去空白后等于 `done`」，而 `for … do … done` 的收尾正是独占一行的 `done`——两块内存真会话先后因此报废（`archive/minimax-m3.1-flash/2026-11-18T08-48-17-718Z` 第 19 步、`archive/hy4-flash/failed-2026-11-19T01-39-45-389Z` 第 3 步），`bash -c` 拿到半截块报语法错误、终止判定已生效、会话零候选。理由与改名见文末修订段。

**响应被输出上限截断时，重试一次，仍截断就转格式反馈。** 现有传输层对 `finishReason === "length"` 的处理是丢弃半截响应、退避重发同一轮、四次耗尽判传输失败。那套逻辑的前提是 one-shot 无法自我修正；agent 形态下模型能改——所以第二次仍截断时，回一条「你的响应被输出上限截断，请更简洁并只给一个动作」，而不是继续退避。否则一个可自我修正的截断会被升级成整次失败，正好违反上面那条落档正交性。

### 受限工具不是二进制，是宿主侧的服务

ADR-0029 的配额强制依赖「harness 是唯一执行者」：执行前解析命令、命中受限工具就查内存计数器、超限返回伪造 stderr 而不执行。而「整块交给 `bash -c`」意味着任意 shell 语法都能到达那些命令，静态解析必然漏。

所以 `check`、`evaluate`、`finish` 在沙箱里是**薄壳**：它们不是真实现，而是通过一条只通向宿主的通道请求执行，配额与计时在宿主侧的服务里查，超限就把伪造的 stderr 还给调用方、命令不执行。模型无论用循环、管道还是子 shell 调用，都只能打到薄壳；宿主始终是唯一真执行者，这条前提由结构性位置保住，而不是靠解析器的覆盖度。

代价是沙箱镜像要多带几个薄壳并配一条通道。执行器选型（用哪个隔离技术）不在这里裁，但**分派形状**在这里定死：任何关于「模型能不能绕过配额」的重测，都要从这条形状出发。

### 每步的字节由三条键级上限管，截断在生成侧

| 键 | 上限 | 保留 | 理由 |
|---|---|---|---|
| `stdout` | 16 KiB | 头 30% / 尾 70% | 诊断尾部常有汇总 |
| `stderr` | 4 KiB | 头 70% / 尾 30% | 类型检查的第一条错误在全量诊断的开头 |
| `raw`（模型原文） | **不截断**（仅 64 KiB 病态保护） | — | 上一轮已是响应 token，回传不增加新信息成本 |

截断发生在生成侧：模型看到的字节就是落盘的字节（ADR-0031）。三条键级上限而不是一个合计上限，是因为合计会造出键间的相互挤占。

超限时给的不是一行标记，而是一段带**可执行建议**的告警：输出过长，改用 `head` / `tail` / `sed -n` 定向读，或用 `grep` 收窄模式，或把输出重定向到文件再搜，并给出被省略的字节数。这段文本是唯一能教会模型「怎么在 16 KiB 上限下工作」的地方；只告诉它「你被截了」而不告诉它下一步做什么，等于白截。

`raw` 不截断是本 ADR 对 ADR-0031 唯一一处收紧的反向：截它的收益本来就是假的（那段字节已经付过费），代价是模型下一轮看到「自己刚写的代码被砍断」，进而重写或误判。写策略文件走 heredoc，原文动辄数 KB，这个错误发生的概率不低。

**上下文守卫。** 每步调用前用上一轮响应的用量读数（精确值，不是估算）判断「再发一次会不会越过窗口的 80%」，会就越过即停。它是一个**新的终止原因**，不是新的落档判据（正交性见上）。它存在的理由只是逻辑兜底：一旦某个席位持续整读大文件，请求会撞到端点 400，而那本可以在本地判掉。

### reasoning 按端点族分家，通道是不透明的

三个族三份策略，实现为模型客户端的一个**能力声明**而不是调用点上的条件分支：messages 族是「签名回传」（thinking 块连签名原样送回，缺签名则送回时不带它并记一条标记），chat 族是「不回传」（推理内容丢弃），responses 族是「加密回传」（加密条目原样送回）。

`glyph-cluster` 的加密块按加密回传处理，而不是丢弃：这类块的设计意图就是「给你一段只有服务端能解的令牌，你负责原样带回来」，丢掉等于主动放弃跨步连续性，而它是 chat 族里唯一有东西可回传的形态。

传输这些块的是 `ModelResponse` / `ChatMessage` 上的一个**不透明字段**：由该族的客户端生产，历史原样带回，序列化只在对应端点族的请求体构造里发生。签名与加密块对 loop、档案、报告都是无意义的字节，它们的语义只能有一个解释者。

它**不落档案**：加密块进档案既涨体积又没有读侧用途，读侧回放不需要推理连续性。

### 候选与步号是单向引用

候选条目记自己的步号，过程记录不记「我产出了第几个候选」。逆推靠动作类型（`evaluate`）在过程记录里的出现序。

单向的理由是「一个事实一个家」：候选序里的下标恒等于 `evaluate` 的出现序，把它的镜像再写进过程记录，就是两条会不一致的判据。步号从 1 起，与既有「`observed-<runId>-round-<步号>`」命名族一致，快照文件名与档案内步号不必差一。

报告侧的那条链因此只有一个方向：生成日志行（按轮号）→ 过程记录步（按步号）→ 候选条目（按步号）。

> **修订（2026-11-19）：第一句与那条「一个事实一个家」的理由仍成立，中间那句「逆推靠动作类型」作废。** 读侧不再由动作类型逆推候选序：`action === "evaluate"` 过滤出来的序会把「`check` + `evaluate` 写进同一块、动作记成 `bash`」那次提交静默丢掉（真档：`archive/gpt-6-luna/2026-11-19T01-33-42-820Z` 第 22 步，档案里 2 个候选、报告只列 1 条）。现在读侧直接读 `optimization.candidates`（候选的家），动作标签降级为注（「这一步除了提交还跑了什么」）。
>
> 这**不违反**「一个事实一个家」：候选描述符是候选的家，动作标签是人读的注解；旧写法让动作标签代管「有几个候选」这个事实，那才是第二个家。生成侧一行没动——候选记自己的步号，过程记录不记候选下标，单向引用仍是那条链。实现与接线见票 03 与 `packages/runner/src/archive-report.ts`。

### 与 mini 的两处有意分歧

抄 mini 的三条铁律不等于逐字抄它的实现。两处不同，都是主动选择：

1. **`stdout` 与 `stderr` 分开存**。mini 把两者合并成一路（`stderr=subprocess.STDOUT`）。分开的好处是 `stderr` 能用与 `stdout` 相反的保留策略——类型检查的第一条错误在开头，而列表类输出的价值常在中段之后。
2. **收工是一条真命令**。mini 检测输出的首行是不是提交哨兵，整块照跑。我们让收工走与 `check` / `evaluate` 同一条通道——但它是一条**能被 bash 解析到的命令**（`finish`），不是输出里的一个形状。

其余与 mini 一致：整块一次 `shell` 执行、观测用 `user` 角色、超长输出给带建议的告警、格式错误不执行任何命令。

### 身份清单收什么

每步上限的三个数、截断保留比例、上下文守卫、抽取规则、收工命令的语义，以及**「被拒的动作格式」清单**（`actionSyntax.rejects`，含 XML 工具调用那一档），全部进 `harnessDigest`。判据是一条：档案形状版本管「读侧能不能解析这个文件」，身份清单管「模型当时处在什么世界里」。上限从 16 KiB 改成 32 KiB 时档案结构完全一样、读侧照读，但模型的世界变了——那是换 harness，不是换档案版本。

副作用是好的：调上限即断代，与「步数上限实测后回填即断代」是同一条纪律，不需要再单独记一笔。

## 残余风险

1. **`opaque` 回传零实测**。它是否被端点接受、多轮是否真的不退化，目前没有证据。实现前必须跑一次一次性探针（三族各三步，只判「有没有 400」「echo 是否被接受」），结论进本 ADR 的表；若被拒，`glyph-cluster` 的落表改成不回传，该席位的去留重新评估（ADR-0030 的重评条件）。
2. **`raw` 不截断把「节省」从单步挪到了整体历史**。模型每步都写大段 heredoc 时，历史会快涨（每步 10 KB、六十步约 200k token）。守卫是唯一兜底，而它在 1M 窗口下不会触发。
3. **严格「恰好一个块」加 `bash` 标记的服从率未实测**。多家族的名册里可能有一两个反复违规，代价是浪费步数。补救方向是调步数上限（ADR-0030 已定这条方向），不是放松判据——放松就回到「模型以为它跑完了全部」。
4. **chat 族的输出预算完全由服务端默认决定**。已观测到单轮输出 87,320 token 的席位；`length` 的处理链（重试一次 → 格式反馈）在真实分布下会触发多频繁，要等第一季数据。
5. **每步上限与步数上限都还是估值**。16 KiB / 4 KiB / 120 步都按「够用」估，没有一个来自实测。

## 重评条件

- **出现一步多调用的动作形态**（一次模型输出触发多条 harness 调用，或 harness 替模型补发调用）：ADR-0031 那条「轮号等于步号」的左连接要重定，本 ADR 的动作边界与计数口径随之作废。
- **探针证明加密块回传被拒或被端点忽略**：reasoning 的按族表要改一格，且「跨族复用 echo 会静默 400」这条要靠测试钉住的约束要重新论证。
- **S5 出现窗口小于 1M 的常驻席位**（现在的 256K 席位只是临时测试用）：守卫从兜底升级成主约束，那时「上限 × 步数」必须重新分配，`raw` 不截断也要重估。
- **第一季实测显示读契约的步数远超预期**：要动的是步数上限与 `stdout` 上限，不是把契约正文塞回首条消息——后者等于取消分步形态。
- **沙箱执行器引入持久会话或模型可触达的控制面**：薄壳—宿主通道这条分派形状的前提失效（ADR-0029 同一条重评条件）。
- **`CONTEXT.md` 里 one-shot 时代的词汇在分步形态下失去所指**：本 ADR 与它同批收口，词汇的处置不在本 ADR 内。

## 指针

传输失败的处置已在 [ADR-0036](./0036-transport-failure-not-recoverable.md) 收口：本册「传输重试耗尽立即停」不变，但重试预算拆成 429 / 连接级 / 截断三套，5xx 改为不重试；截断「第二个仍截断就转格式反馈」这条仍是 loop 侧的活，one-shot 退化为判传输失败。

## 修订（2026-11-19）：`done` 从文本哨兵改成命令

初版把收工写成「块级 `done` 哨兵」：一块内遇到独占一行的 `done` 就把后半段切掉、结束会话。这次改动把它整个换掉，三件事按顺序记在这里。

### ① 文本哨兵作废：判据与 bash 的循环收尾撞车

判据是「整行 `trim()` 后等于 `done`」，而 `for f in …; do … done` / `while …; do … done` 的收尾**正是**独占一行的 `done`。两块内存真会话先后撞上它：

- `archive/minimax-m3.1-flash/2026-11-18T08-48-17-718Z` 第 19 步（`for f in /workspace/.observations/*.md; do … done`）——切成半截后 `bash -c` 报 `syntax error: unexpected end of file from 'for' command`，退出码 2；
- `archive/hy4-flash/failed-2026-11-19T01-39-45-389Z` 第 3 步——同一形状；因为终止判定已生效，整次会话**零候选**。

所以「切掉后半段」的收益（少执行几行）不再是可接受的代价：它买的是一个更弱的保证，而付出的是整场会话。整块从此原样交给一次 `bash -c`。

### ② 改成真命令之后发现：`done` 是 bash 保留字，工具必须改名 `finish`

原计划是「`done` 本来就是 rootfs 里那条薄壳，删掉文本切分即可」。这条前提不成立：`done` 是 bash 的**保留字**，裸写一行 `done` 是**语法错误**——

```
$ bash -c 'echo before; done; echo after'
before
bash: -c: 行 2: 未预期的记号 "done" 附近有语法错误
$ echo $?
2
```

整块根本不会被执行到，薄壳一次都不会被调到，收工请求永远发不出来。而「整块只有一行 `done`」恰恰是模型最常用的收工写法（`archive/gpt-6-luna/2026-11-19T01-33-42-820Z` 第 24 步）。删掉文本切分之后，那种写法会从「干净收工」变成「这一步退出码 2、会话不收工，一路跑到步数上限」——比改动前更差。

于是收工工具改名 **`finish`**：rootfs 里 `bin/finish` 与 `bin/check` / `bin/evaluate` 是同一份 `shim.sh` 字节（工具名取自 `$0`），`TOOL_NAMES` 与 `SANDBOX_ROOTFS_SHIMS` 一起改。`bash -c 'evaluate; finish; echo after'` 能被正常解析并执行到薄壳。

**档案形状不跟着改名。** `action.kind: "done"` 与 `termination: "done"` 是 v3 档案形状里的常量，语义是「这一步以收工工具结束」，与那条命令叫什么名字无关；改它等于升 `archiveSchemaVersion`，而本批明确不升。因此出现一处**有意的不一致**：模型看得见的命令叫 `finish`，档案里的枚举仍叫 `done`——旧档照旧可读，读侧一个字都不用改。身份清单把这条不一致记在 `finish` 那一格（键名随真源叫 `finish`）。

### ③ 行为放宽：`finish` 之后的行会执行

整块由 bash 解析，所以 `finish` 之后写的行**仍会执行**，会话只是在这一步结束之后停下。这是从「少执行」变成「会执行」，不是收紧：写进 `prompts/agent-system.md` 与 `prompts/agent.md` 两处契约，并由 `packages/gen/src/agent/host/finish.test.ts` 正面断言（用副作用文件证明之后的行真的跑了）。`harnessManifest().finish.stopsRemainingCommands` 因此是 `false`——清单的描述必须与实现同义。

### 被否的中间路：切之前先跑 `bash -n`

考虑过「对前缀跑 `bash -n`，语法完整才切、不完整就整块跑」：它两头都能保住（循环不被切断，`done` 之后的行也不执行）。落选的理由是**规则对模型变成条件式**——模型无法预知自己这次写的 `done` 算不算哨兵，它要在每次收工时赌一把 `bash -n` 的结论。协议的可预测性比「少执行几行」值钱：一条能被解释、能被写进契约、能被测试钉死的规则，胜过一条在多数情况下更好但在少数情况下沉默变脸的规则。

### 这批一并改的两件

- **纠正消息带逐字正例与逐字反例**：零块 / 两块 / 非 `bash` 标记 / XML 工具调用（`<tool_call><function=bash>`）四种，各自点名**被拒的那一处**，本次踩到的那种带 `◀`。
- **`actionSyntax.rejects` 收录这四种**，XML 那一档是新增。**默认不接受 XML 工具调用**：接受它等于给协议开第二套语法，而「恰好一个块、整块交给一次 shell」是本册的身份项。若逐字反例之后某席位服从率仍为 0，结论是「该席位与 bash-only 协议不适配」，写进名册，不放宽协议。

**这一版的实测结论（2026-11-19，`archive/hy4-flash/failed-2026-11-19T05-42-42-929Z`）**：`hy4-flash` 三回合都发 `<tool_calls:<id>><tool_call:<id>bash>…</attribute>`，逐字正例与「被拒的是 `<function=bash>` 这一处」的纠正消息没能让它改形状（第 2/3 步它自己在文本里说「我明白了，要写一个 bash 围栏块」，随后照旧发 XML）。按上面那条裁决：**这是该席位与 bash-only 协议不适配，不是协议要放宽**。同一版契约下 `gpt-6-luna`（`archive/gpt-6-luna/2026-11-19T05-32-34-331Z`，17 步、3 个候选、以 `finish` 收工）与 `minimax-m3.1-flash`（`archive/minimax-m3.1-flash/2026-11-19T06-04-46-434Z`，32 步、2 个候选、以 `finish` 收工）都正常走完。

这批改动动三处身份（收工语义、被拒格式、`visibleBinaries` 的上一票改动），对外只断代一次 `harnessDigest`。

## 修订（2026-11-20）：协议从文本围栏块换成原生 tool calling

初版把动作写成「一轮一个 `bash` 围栏代码块」，并把「结构化动作」明确列进落选。这一版把协议整个换掉：请求里带 `tools`，响应里读 `tool_calls`，**一步恰好一次调用**。下面五件按顺序记。

初版正文与上一节修订（`done` → `finish`）**一个字都没有改**——ADR 的价值在「当初为什么这么想」。本节只说清哪几条已经作废，以及为什么。

### ① 初版那条前提从来没有被验证过，而它是错的

问题节那句「只暴露 bash 意味着没有 tool-calling 接口，所以『一次输出算几个动作』这条协议要由我们发明」，「一次输出恰好一个动作块」整节都建立在它上面。

它的错法不是「模型不服从」，而是**我们从没发过 `tools` 字段**：改动之前全仓 `grep` 的结果是 0 处 `tools` / `tool_choice` / `functions`，请求体只有 `model` + `messages` + `params`，解析只读 `choices[0].message.content`。而这批渠道（commandcode，`chat-completions` 族）上的模型，训练分布里熟的是**原生工具调用**——渠道的 chat template 会把工具调用渲染成文本塞进 `content`：

```
<tool_calls:6124c78e><tool_call:6124c78e>bash
<命令原文>
```

那个 `6124c78e` 是**模板里的固定字面量**（三场、11 步、46 次出现全是同一个 id；真实工具调用 id 每次都不同）。于是模型在复述「它见过的工具调用形状」，我们的解析器在找围栏块，两边错开。

2026-11-19 拿真实首条消息（`prompts/agent-system.md` + `prompts/agent.md` 的渲染结果，与真会话逐字相同）打同一端点，唯一变量是请求里有没有 `tools`：

| 席位 | 不给 `tools` | 给 `tools` |
|---|---|---|
| `tencent/hy4-flash` | XML 6/6 次 | **tool_calls 6/6**，0 XML |
| `xiaomi/mimo-v2.6-flash` | XML 3/5，围栏块 1 | **tool_calls 3/4** |
| `stealth/glyph-cluster:free` | `finish=length`，content 空 | **tool_calls 1/1** |
| `minimax/m3.1-flash` | 围栏块 ✓ | tool_calls ✓ |
| `thinkingmachines/inkling-2-small:free` | **content 空**（`finishReason: tool_calls`） | 免费档已下线 |

`hy4` 那 6/6 是在同一份 message 上重复六次得到的，无一次退化成 XML。同一批模型、同一渠道、同一份提示词，唯一变量是请求里有没有 `tools`——所以「这个席位与 bash-only 协议不适配」那条上一节裁决的适用范围要收窄：**当时不适配的是我们没发的那个字段**。

`inkling-2-small` 那一场是最干净的证据：`steps[i].raw == ""`（0 字节）、`generationLog[0].finishReason == "tool_calls"`、`completion_tokens 55`。**它不是没说话，是它说的话全在 `tool_calls` 字段里，而我们只读 `content`。** 这同时是 ADR-0031「模型看到的字节 = 落盘的字节」的一次结构性违背——那一册的修订段接住了它（`steps[i].toolCall.argumentsJson` 逐字落档）。

### ② 「结构化动作等于把 tool-calling 偷回来」这条落选理由失效了

初版落选「结构化 `write-file` 动作」，理由是「等于把 tool-calling 偷回一小块」。这条推理成立的前提是**协议由我们发明**：既然不承认工具调用这层接口，任何结构化动作都是在一个自造协议里偷偷开第二套语法。

那个前提已经不存在。现在的形状是：**协议由渠道提供，我们只做声明**——`tools` 是一等发送参数，动作就是模型发起的调用，判据变成「恰好一次、名字在声明里、`arguments` 是合法 JSON」。这不是把 tool-calling 偷回来，这是承认它本来就在那儿。

顺带一并失效的还有两条：

- **「围栏块用 `bash` 标记而不是 mini 的私有串」**那整段（初版「一次输出恰好一个动作块」末段）——没有围栏了，标记服从率也不再是一个问题。
- 上一节修订里「**默认不接受 XML 工具调用**，接受它等于给协议开第二套语法」——方向反了：XML 工具调用是同一份 `tool_calls` 被 chat template 渲染出来的样子，接受它才是接受渠道给的事实，而我们的自造文本形状才是第二套语法。那一条裁决随本修订作废。

### ③ 观测的角色从 `user` 改成 `tool`，初版那条理由作废

初版写「观测消息的角色是 `user`，不是 `tool`」，理由是「不走 tool-calling 就没有 `tool_use_id` / `tool_call_id` 可配对，用 `tool` 角色在 messages 族会被要求配对、在 chat 族会被要求带 id」。

理由的前提同样没了：现在**有** id 可配对。而 `user` 在这个形状下反而是错的——工具调用那一轮 assistant 的 `content` 是空串（它没说话，只调了一次工具），后面跟一条 `user` 会让模型读到「它什么都没说，然后我自己说了一段」，历史读起来像自言自语。`tool` + `tool_call_id` 配对是渠道唯一认的配对方式（不配对与缺 `id` 分别会静默读错与 400）。

配对的 id 由我们**确定性派生**（`call-<步号>`），不用渠道给的那串每次不同的字节：id 的唯一用途是让 assistant 与 `tool` 消息在自己的历史里配对，两处都由我们写，于是重跑一次历史的字节仍然相等。真请求已验证自己编的 id 被渠道接受。

`renderObservation` 仍是观测文本的唯一渲染处，只是信封从 `{role:"user", content}` 换成 `{role:"tool", toolCallId, content}`。

### ④ 删了什么，留了什么

**删掉的**（都是为「自造文本协议」付的账）：

- 围栏块与它的正则/切块/白名单（`action.ts` 的正则与 `fencedBlocks` 整段）；
- **fd 3 薄壳通道**：`shim/shim.sh` 145 行、`sandbox/execute.ts` 的 `wireChannel`、`tool-channel.ts` 的请求/响应序列化与七条转义、rootfs 里三个薄壳副本与 `SANDBOX_ROOTFS_SHIMS`；
- 清单里的 `actionSyntax.fenceTag` / `actionSyntax.rejectExitCode` / `finish.stopsRemainingCommands` / `services.channelFd` / `services.args.exitCode`——**清单的作用是「模型当时面对的世界」，留一格旧协议就是清单在说谎**；
- 上一节修订的「`finish` 之后写的行仍会执行」那条行为放宽：一次调用就是一个动作，没有「之后的行」这个位置。

**留下来的铁律**（换协议不动它们）：

- **一步一次 `bash -c`**：整串命令交给一个独立无状态子进程，多行 / `&&` / `for … do … done` / heredoc 都按 shell 的规则走。这是「步 = 一次模型调用」在进程侧的落点，也是进程树回收（ADR-0033）成立的前提。
- **超长输出带可执行建议**：截断仍发生在生成侧，告警仍给 `head -c` / `tail -c` / `sed -n` / `grep -n` / 重定向这些方向。那是唯一能教会模型「怎么在 16 KiB 上限下工作」的地方。
- 严格解析那一半也不动：零次 / 多次 / 名字不认识 / 参数坏了，一律不执行、计一步、回带逐字正反例的纠正消息。换的只是「被拒的是哪一处」的措辞（从「不是 `bash` 标记」变成「不在声明的五个里」「`arguments` 坏了」）。

### ⑤ 新的残余风险

1. **三族工具形状不同，而 `messages` 族零证据。** 它的声明是 `name` / `description` / `input_schema`，结果是 `tool_result` 块，与 chat 族不是一份翻译。2026-11-20 主线程真请求探针的读数（`claude-haiku-5-5`，`/messages`）：

   ```
   without tools → HTTP 403 {"type":"error","error":{"type":"permission_error",
                   "message":"The provider refused this request. The refused request wasn't charged."}}
   with tools    → HTTP 403 同上
   ```

   **不带 `tools` 也 403**：该席位在本账号档位下整体被渠道拒。所以「声明形状会不会 400」「`tool_result` 能否配对」**零证据**。按 fail-closed，这一族**不声明** `tools`，用它的席位在会话起跑前拒跑并点名——不是「没试过」，是「试了，席位被拒，所以没有证据，不写未验证的翻译」。`responses` / `generate-content` 两族同一条规矩（本季名册不用）。
2. **`arguments` 是模型写的 JSON 字符串，可以被写坏。** 归 `malformed-arguments` 拒绝档：不执行任何工具、计一步、回纠正消息。解析放在动作层而不是传输层，是因为它是一条模型能自我修正的格式失败——放进传输层就变成了端点错误。
3. **并行调用被拒，但渠道可能自己并行。** 判据在动作层（一次以上一律拒绝），而请求体里**不发** `parallel_tool_calls: false`（那是 OpenAI 专有键，别的渠道收到不认识的键可能直接 400）。于是存在一个渠道侧的可能：它一次给我们多条 `tool_calls`——那正好落进 `multiple-tool-calls` 的拒绝档，代价是浪费一步，不是静默执行一条。
4. **`raw` 在工具调用轮次里常态为空，逐字字节搬到了 `toolCall.argumentsJson`。** 初版「`raw` 不截断」（残余风险 2）那条的关切没有消失，只是换了字段：真正的正文在 `argumentsJson` 里，而它同样不截断、原样落档。读侧必须知道「两个字段各管一件事」，否则会从 `raw == ""` 误判成「模型什么都没说」——`inkling` 那场就是这个误判的真实样本。
