## 1. 范围

v0 交付五个工件:`engine`(确定性对局引擎 + 沙箱)、`runner`(赛季调度 + 排名)、`gen`(脚本生成管线)、`docs/rules-vN`(给模型看的规则文档)、首轮赛季报告。不含 Web UI、视频生产、练习赛(见 §5、§6)。赛季赛制与积分规则待定(§6);v0 首轮按 gdd §8.2 名次积分制执行。

## 2. 功能需求

### FR-1 对局引擎:领土争夺 RTS 模拟

引擎以 tick 为唯一时间单位,无头运行,模拟**四方(1v1v1v1)**脚本控制的单位在网格地图上争夺领土,规则集为最小闭环(占领 → 采集 → 生产)。

- AC1:引擎可在无任何网络/模型 API 的环境下完整跑完一场对局并给出结果。
- AC2:对局四方初始条件严格对等:地图四重旋转对称、四方初始单位与资源配置相同(可用对局配置断言验证)。
- AC3:规则集的设计基准已定稿于 [gdd.md](./gdd.md)(含 ⚙ 可调参数标记),最终面向模型的版本落入 `docs/rules-vN`。

### FR-2 确定性与回放

同一种子 + 同一对脚本,任何时间、任何次数的重放与重新执行,对局结果**逐 tick 完全一致**。

- AC1:同配置重跑同一场对局 10 次,每 tick 的完整状态 hash 全部一致。
- AC2:回放产物(JSONL 状态流)记录每 tick 足以复现观演的状态;直接读取 JSONL 回放的结果与重新执行脚本的结果一致。
- AC3:引擎状态演化不使用浮点运算(以 lint 或代码审查条款固化)。

### FR-3 脚本接口(action 接口 + 只读 state)

- 脚本通过**明确的 action 接口**下发指令;通过**只读快照**读取局面。
- state 不暴露引擎内部结构与可变引用:快照不可变,脚本无法通过任何途径改写引擎状态。
- 脚本拥有跨 tick 记忆能力(模块级状态在常驻 VM 生命周期内保留,见 hld §5)。

- AC1:脚本读取到的每个 state 对象均为冻结/复制副本,修改它不影响后续引擎状态(以专门测试脚本验证)。
- AC2:action 接口在规则文档(`docs/rules-vN`)中有完整签名与语义说明,无需阅读引擎源码即可正确调用。
- AC3:接口面(可用 action 与可读 state 字段)有运行时校验,越权调用(访问未暴露字段、调用未定义 action)被拒绝并按校验规则处理。

### FR-4 沙箱与计算预算

参赛脚本为不受信任代码,在隔离环境运行,带资源上限,防死循环与内存爆炸。

- AC1:沙箱内脚本无网络、无文件系统、无宿主进程访问能力。
- AC2:存在超时与内存上限机制;超限行为(跳过/判负的细则)见 §5 设计待定指针,预算形态与细则见 hld.md §5.3,但必须保证:同一种子+脚本重复执行时,预算机制的裁决结果一致(受 FR-2 约束)。
- AC3:一方脚本的崩溃/异常不会中断对方脚本与引擎运行。

### FR-5 脚本生成管线(纯静态校验协议)

`gen` 离线运行,不与引擎耦合:输入规则文档与模型配置,输出冻结的参赛脚本 + 模型名。

- 协议:规则文档 + API 文档 → 模型生成 TS 脚本 → 静态校验(编译 + API 误用检查)→ 失败则将**校验错误**回喂模型 → 迭代,至多 5 轮 → 通过则冻结。
- v0 **不提供任何对战反馈**:无练习赛、无战绩回喂。

- AC1:管线全程只回喂静态校验错误,代码中不存在将对局结果传回生成环节的路径(以架构审查条款固化)。
- AC2:5 轮迭代后仍未通过校验的模型,产出"校验失败"记录并进入报告的失败名单,不占用对局名额。
- AC3:接入新模型只需增加一份配置(模型名、API 端点、凭证引用),不改代码。

### FR-6 可追溯性存档

每个冻结脚本强制存档元数据,缺档结果不得进入正式报告。

- AC1:每个冻结脚本连同元数据落盘:模型名、模型版本/快照标识、生成日期、协议迭代轮数、完整 prompt、生成日志。
- AC2:runner 拒绝运行无元数据的脚本(报错退出,而非跳过)。
- AC3:给定正式报告中的任意一场对局,可以从存档还原:四方脚本、元数据、种子、地图。

### FR-7 赛季调度 runner

- AC1:支持赛季调度:N 个参赛脚本按 **4 人组合**对战 × M 张地图 × K 个种子,场次的选取对全体参赛者一致(无人可选种子/地图)。
- AC2:对局可并发执行,单场对局互不干扰;某场对局崩溃不影响其余场次,并在报告中记录。
- AC3:一场对局的输入被完整物化(脚本存档引用 + 地图 + 种子),报告中的每场胜负都可凭该输入复算。

### FR-8 排名与报告输出

- AC1:以**名次积分制**为主排名(每场按最终名次 3/2/1/0 记分,超时按领土分定名次,同分并列);胜率矩阵与 Elo 作为可选副产品输出。
- AC2:同时产出 Markdown 报告(人类可读,可直接用作自媒体素材)与 JSON 原始数据(每场对局的输入引用与结果,机器可复算排名)。
- AC3:报告中标注规则文档版本(`ruleset vN`);规则版本不同的结果不出现在同一份排名中。

### FR-9 CLI 回放查看器

- AC1:提供终端 ASCII 回放查看器:读取 JSONL 回放,逐 tick 渲染网格局面,支持单步/暂停。
- AC2:查看器只读 JSONL,不依赖引擎运行时;查看器仅依赖带版本的 JSONL schema,且 schema 保证向前兼容(跨版本以 schema 版本号为准)。
- 定位:调试工具,用于 v0 设计阶段人工验证规则质量;非 UI 产品需求,不承诺观战体验。

### FR-10 规则文档(`docs/rules-vN`)

写给模型的完整契约,模型可读性是硬性验收项。

- AC1:自包含:仅凭该文档(含 API 签名)即可写出可过校验的脚本——以"人类不读引擎源码、只读文档写出基准脚本"作为验证方式。
- AC2:带版本号;版本号与引擎行为一致(文档版本与引擎版本错配时 runner 拒跑)。
- AC3:包含确定性约束的显式说明(哪些行为被禁止/裁决一致),使模型可据此规避不确定行为。

## 3. 非功能需求

### NFR-1 确定性(最高优先级)

FR-2 是系统第一约束:任何导致重放不一致的实现选择自动否决,无需另行讨论。

- AC:CI 中存在"重放一致性"测试:抽正式对局样本,重新执行并与 JSONL 比对,每 tick 状态 hash 一致。

### NFR-2 可信性

排名的每个数字可被第三方复算:原始数据 + 脚本存档 + 种子即全部输入。

- AC:由 JSON 原始数据独立重算的胜率矩阵与报告一致。

### NFR-3 性能

- AC:给定赛季配置(参赛模型数 N、地图数 M、种子数 K,总场次 = C(4,N)×M×K),整轮在一台普通开发机、无人工干预下跑完,且单场平均耗时 ≤ X ⚙(X 用 ≥2 个人类基准脚本标定,见 §4-2)。若不满足,先查沙箱开销,再考虑并发度,不得牺牲 NFR-1。算例:N=5/M=3/K=5 → 75 场。

### NFR-4 可维护性

- AC1:规则数值与引擎逻辑分离:改数值不改代码(规则以数据文件/配置表达)。
- AC2:`engine`/`runner`/`gen` 三个包之间只通过文件(JSONL、脚本存档、配置)交换,不共享运行时进程——`gen` 永远不在对局进程内。

## 4. 验收口径(v0 整体)

v0 完成当且仅当:

1. FR-1 ~ FR-10 的全部 AC 通过;
2. 存在至少 2 个人类手写基准脚本,能完成对局并体现不同策略(用于验证规则集有区分度,对应 FSR 风险 R2);
3. 完成一轮含 ≥4 个真实模型(四方对局下限)的首轮赛季,产出正式报告(含失败名单);
4. 设计待定项全部定稿:gdd §11(规则清单)与 hld §12.2(工程清单)清零,规则部分落入 `docs/rules-vN`(指针见 §5)。
