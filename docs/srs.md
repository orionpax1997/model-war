## 1. 范围

### 1.1 v0 交付物

`engine`(确定性对局引擎 + 沙箱)、`runner`(赛季调度 + 排名与报告)、`gen`(脚本生成管线)、`docs/rules-vN`(面向模型的规则与 API 文档)、CLI 回放查看器。

### 1.2 不在 v0 范围

Web UI 与观战渲染、视频内容生产管线、开放式练习赛与持续策略优化(显式启用的固定事实优化协议归 FR-5)、模型自动接入平台化(接新模型 = 改配置重跑)、战争迷雾与多资源种类等复杂规则、跨赛季规则版本演化策略(v0 只做版本隔离:不同 ruleset 版本的结果不入同一排名,FR-8 AC3)。

### 1.3 交付时点

- **v0**:上列五个工件 + 一轮真实模型赛季报告。
- **v0.5**:Web 渲染器(规则侧要求:回放自 v0 第一天起按可渲染设计,见 gdd《娱乐产出设计》)。

## 2. 功能需求

### FR-1 对局引擎:领土争夺 RTS 模拟

引擎以 tick 为唯一时间单位,无头运行,模拟**四方(1v1v1v1)**脚本控制的单位在网格地图上争夺领土(占领 → 采集 → 生产)。

- AC1:引擎可在无任何网络/模型 API 的环境下完整跑完一个对局并给出结果。
- AC2:四方初始条件严格对等:地图四重旋转对称、四方初始单位与资源配置相同,并以对局配置断言验证。
- AC3:规则机制以 gdd 为设计基准,面向模型的版本落入 `docs/rules-vN`;引擎不硬编码规则数值(取值真源为 `rulesets/*.json`)。

### FR-2 确定性与回放

同一种子 + 同一组四份脚本,任何时间、任何次数的重放与重新执行,对局结果**逐 tick 完全一致**。

- AC1:同配置重跑同一个对局 10 次,每 tick 的完整状态 hash 全部一致。
- AC2:回放产物(JSONL 状态流)记录每 tick 足以复现观演的状态;读取 JSONL 得到的结果与重新执行脚本得到的结果一致。
- AC3:引擎状态演化不使用浮点运算(以 lint 或代码审查条款固化)。

### FR-3 脚本接口(action 接口 + 只读 state)

- 脚本通过**明确的 action 接口**下发指令;通过**只读快照**读取局面。
- state 不暴露引擎内部结构与可变引用:快照不可变,脚本无法通过任何途径改写引擎状态。
- 脚本拥有跨 tick 记忆能力(模块级状态在 VM 生命周期内保留)。

- AC1:脚本读取到的每个 state 对象均为只读封存/复制副本,修改它不影响后续引擎状态(以专门测试脚本验证)。
- AC2:action 接口与可读 state 字段在 `docs/rules-vN` 中有完整签名与语义说明,无需阅读引擎源码即可正确调用。
- AC3:接口面有运行时校验,越权调用(未暴露字段、未定义 action、宿主桥函数)被拒绝并按 hld《沙箱》的异常裁决处理。

### FR-4 沙箱与计算预算

参赛脚本为不受信任代码,在隔离环境运行,带资源上限,防死循环与内存爆炸。

- AC1:沙箱内脚本无网络、无文件系统、无宿主进程访问能力。
- AC2:存在控制流事件、API 调用、内存、时间四类上限;预算形态与判罚细则见 hld《计算预算》,且必须保证:同一输入重复执行时,预算裁决结果一致(受 FR-2 约束)。
- AC3:一方脚本的崩溃/异常不中断其他方脚本与引擎运行。

### FR-5 脚本生成管线

`gen` 离线运行,通过文件与试跑子进程解耦:输入规则文档与模型配置,输出冻结脚本 + 模型名。

- 默认协议:规则文档 + API 文档 → 模型生成 TS 脚本 → 编译、静态校验与冻结期试跑 → 校验或候选预算失败时回喂诊断 → 迭代至配置的轮数上限 → 通过则冻结脚本。具体控制流见 hld §6.2。
- 默认不回喂胜负、排名或策略表现。规范生成的配置政策与 CLI 启动方式见 hld §2.2.6/§9。显式 `--score-source-feedback` 启用固定事实优化协议:所有模型统一获得两次行动事实与终局事实回喂,形成初次、第一次优化、第二次优化三个有效候选;正式参赛验收仍须通过原校验与候选预算检查。机会分配决定见 [ADR-0017](./adr/0017-uniform-two-fact-feedback.md),终局事实反馈决定见 [ADR-0019](./adr/0019-terminal-match-facts-feedback.md),工程循环见 hld §6.2。

- AC1:默认回喂仅含编译、静态校验和候选预算诊断;不回喂正式赛季结果,不引入 gen 对引擎或赛季调度器的运行时依赖。
- AC2:默认流程的配置轮数上限或事实优化当前阶段的统一响应上限耗尽后仍未通过校验的模型,产出“校验失败”记录,披露实际失败阶段与已有候选并进入报告失败名单,不占用对局名额。
- AC3:接入新模型只需增加一份配置(模型名、API 端点、凭证引用),不改代码。
- AC4:启用事实优化时,前两个有效候选各获得一份自身真实优化试跑事实反馈,每份包含该候选固定三场对局的行动事实及终局事实;第三个有效候选完成最后试跑并保存终局事实后,未启用选拔时定版,不触发第三次反馈或第四个有效阶段。不因 `noScoreSource`、非零行动或其他表现提前结束、增加或减少优化轮,选拔仅在三个阶段全部完成后按预定独立条件进行,不影响优化机会。编译、静态或候选预算失败的响应不计有效候选。
- AC5:初次生成与两个优化阶段各自采用相同的独立响应上限,每阶段一次生成与至多四次诊断修复;逐模型配置不改变开启事实优化后的额度,阶段内的诊断修复不占用两次事实优化机会;传输重试及作废对局重跑不冒充有效优化。后续阶段修复耗尽时,不得将已有候选冒充完成两轮优化的最终候选。
- AC6:两次事实反馈对所有模型采用统一、确定、可审计的格式,同时陈述前一有效候选的行动尝试、公开即时错误、独立结算效果与覆盖范围,以及固定三场对局的真实终局计分依据和四方结果。终局计分依据包括四方各自的控制基地数、控制资源点数、存活单位总造价与领土分;四方结果明确座位及身份,包括领土分、名次、名次积分、存活状态、淘汰时间和结束原因。不回喂独立选拔或正式评测结果、因果结论或策略建议;缺失不补零,不完整行动计数不发送,基础设施错误不转为策略反馈。事实边界见 gdd §3.3,数据采集与投影见 hld §7.4。
- AC7:未启用开关时,原生成、诊断修复、定版及历史观测读取行为保持兼容;不会额外产生事实优化调用。
- AC8:规范配置对整个既有名册统一表达推理意图、输出计量口径和官方/渠道支持状态,不施加额外采样偏置;未知支持与输出上限如实披露,不隐式探测、换模型或换渠道,结构/映射冲突在请求前拒绝。重试与诊断修复不扩大模型预算;HTTP 接受、服务端模型名与推理统计不证明后端身份或参数实际执行。
- AC9:显式启用有效候选选拔要求同时启用事实优化,请求前检查开关关系;只在本轮规定阶段全部完成后选拔,不回喂选拔分数、不追加模型改写。只有完整选拔才可发布胜者;异常或缺失终局不按部分证据选胜者,生成失败且不发布冻结脚本。计分/决胜约束见 gdd §3.3,执行计划与预算见 hld §6.3。

### FR-6 可追溯性存档

每个冻结脚本强制存档元数据,缺档结果不得进入正式报告。

- AC1:每个冻结脚本连同元数据落盘:模型名、模型版本/快照标识、生成日期、协议迭代轮数、完整 prompt、生成日志、编译器版本、产物 hash。
- AC2:runner 拒绝运行无元数据的脚本(报错退出,而非跳过)。
- AC3:给定正式报告中的任意一个对局,可以从存档还原:四方脚本、元数据、种子、地图。
- AC4:启用事实优化时,初次、中间及最终候选的实际编译产物和对应观测独立保存并可校验归属,不得覆盖、互换或混加;各阶段使用固定优化地图、对手与座位,保存每场真实终局事实。正常游戏超时、提前获胜、合法淘汰与并列均按真实终局保留,不确定墙钟超时、执行故障或缺失终局不得伪造完整结果或零分。候选保持真实阶段身份;未启用选拔时最后有效阶段对应冻结脚本,启用选拔时仅选拔胜者的原始源码与编译字节定版入场。历史存档不迁移或追填 hash,缺少终局事实的旧观测继续可读并标为未知。

### FR-7 赛季调度 runner

- AC1:支持赛季调度:N 个参赛脚本按 **4 人组合**对战 × M 张地图 × K 个种子,对局选取对全体参赛者一致(无人可选种子/地图),座位分配规则对全体参赛者一致。
- AC2:对局可并发执行,对局之间互不干扰;一个**对局进程**崩溃不影响其余对局,并在报告中记录(脚本自身异常是判罚而非崩溃,见 gdd《异常与出局》)。
- AC3:一个对局的输入被完整物化(脚本存档引用 + 地图 + 种子 + ruleset 版本),报告中每场胜负都可凭该输入复算。
- AC4:正式评测采用对全体参赛者统一的种子选择与座位分配规则,实际评测种子集合与参赛归档记录的优化试跑及选拔种子集合均不相交;用户配置产生交集时明确拒绝,不得静默换种子或按模型单独挑种子。比较须覆盖引擎归一化别名并在任何输入物化、续跑或对局进程启动前拒绝整季;旧档没有选拔记录时不推测其参与过选拔。执行条件见 hld §6.2/§6.3/§8.1。

### FR-8 排名与报告输出

- AC1:以**名次积分制**为主排名(每场按最终名次记分,超时按领土分定名次,同分并列);Elo 作为可选副产品输出。
- AC2:同时产出 Markdown 报告(人类可读,可直接用作自媒体素材)与 JSON 原始数据(每场对局的输入引用与结果,机器可复算排名)。
- AC3:报告标注规则版本(`ruleset vN`);规则版本不同的结果不出现在同一份排名中。
- AC4:产出校验失败名单。
- AC5:生成归档报告分别标识初次候选、各次优化候选、最后有效阶段及实际冻结脚本,逐候选披露观测、实际保存的终局计分依据与四方结果及缺失范围;未保存的历史终局事实标为未知而非零分。优化未完成时披露已有候选与失败阶段,不得标记优化完成或合并读数。初次候选表现与优化后表现分开报告,优化试跑和选拔数据不并入正式赛季排名。
- AC6:生成归档报告提供参数意图、能力/停止证据、收敛与尝试用量覆盖、有效阶段与不同脚本数、完整选拔分母/胜者身份/理由/复用及模型与本地执行预算;缺统计不记零、重叠用量不充当账单。所有公开摘要出口不得泄漏凭据、原 prompt/响应、provider 错误体、坏日志原行或失败诊断原文;历史失败与显式指定本轮失败分开统计,未指定本轮时不推断。

### FR-9 CLI 回放查看器

- AC1:提供终端 ASCII 回放查看器:读取 JSONL 回放,逐 tick 渲染网格局面,支持单步/暂停。
- AC2:查看器只读 JSONL,不依赖引擎运行时;只依赖带 `schemaVersion` 的回放 schema,跨版本兼容性以 `schemaVersion` 为准。
- 定位:调试工具,用于 v0 设计阶段人工验证规则质量;不承诺观战体验。

### FR-10 规则文档(`docs/rules-vN`)

写给模型的完整契约,模型可读性是硬性验收项。

- AC1:自包含:仅凭该文档(含 API 签名与数值表)即可写出可过校验的脚本——以"模型仅凭文档生成可过校验脚本"作为验证方式(盲写:输入只有文档,不读引擎源码;静态校验错误可回喂,≤5 轮)。**缺口已消解(2026-10-07)**:终稿契约在 `docs/rules-v1/rules.md` §5〈占领〉落库后重跑盲写,三舱 0 轮契约静态校验通过 3/3,无一舱再猜机制(「站上去驱动 / 站相邻静默」都按契约写出);上一轮「三舱各自猜出互斥占领机制」的读数作为**已消解缺口的实证**记在 `.scratch/contract-closure/verdict-2026-10-07.md`(§3)与 `.scratch/rules-landing/blind/verdict-2026-10-04.md`(§4/§7.1)。归属、裁决与读数归 gdd(§3.2 与《规则侧记录》#14),本条不复制。
- AC2:带版本号;版本号与 ruleset 一致(错配时 runner 拒跑)。
- AC3:包含确定性约束的显式说明(哪些行为被禁止/裁决一致),使模型可据此规避不确定行为。

## 3. 非功能需求

### NFR-1 确定性(最高优先级)

FR-2 是系统第一约束:任何导致重放不一致的实现选择自动否决,无需另行讨论。

- AC:CI 中存在"重放一致性"测试:抽正式对局样本,重新执行并与 JSONL 比对,每 tick 状态 hash 一致。

### NFR-2 可信性

排名的每个数字可被第三方复算:原始数据 + 脚本存档 + 种子即全部输入。

- AC1:由 JSON 原始数据独立重算的名次积分与报告一致。
- AC2:启用事实优化的生成记录可独立核对两次行动事实与终局事实回喂、各阶段诊断修复、实际生成调用及候选身份;每场终局计分依据、四方结果与名次积分可对照真实终局、当局 ruleset 与既有并列均分规则核验,不从累计交付、易主次数或最后行动采样推断终局。报告能审计优化试跑、选拔与正式评测的种子集合隔离,复算选拔身份和成绩,不把优化试跑或选拔读数作为正式成绩。

### NFR-3 性能

- AC:给定赛季配置(参赛模型数 N、地图数 M、种子数 K,总对局数 = C(4,N)×M×K),整轮在一台普通开发机、无人工干预下跑完,且每个对局的平均墙钟耗时 ≤ **5500ms**(X 由 ≥2 个模型基准脚本标定,见 §4 第 2 条;余量口径与取值规则见 hld §10.1,单局墙钟分布读数与本次采样见 `.scratch/release-gates/readings.md`,K 节点的基准读数在 `.scratch/budget-calibration/readings.md`)。若不满足,先查沙箱开销,再考虑并发度,不得牺牲 NFR-1。算例:N=5/M=3/K=5 → 75 个对局。

### NFR-4 可维护性

- AC1:规则数值与引擎逻辑分离:改数值不改代码(规则以数据文件表达)。
- AC2:`engine`/`runner`/`gen` 之间只通过文件(JSONL、脚本存档、配置)交换,不共享运行时进程——`gen` 永远不在对局进程内。

## 4. 验收口径(v0 整体)

v0 完成当且仅当:

1. FR-1 ~ FR-10 的全部 AC 通过;
2. 存在至少 2 个模型生成的基准脚本,能完成对局并体现不同策略(验证规则集有区分度,对应 fsr R2);
3. 完成一轮含 ≥4 个真实模型的首轮赛季,产出正式报告(含失败名单);
4. gdd《开放项》与 hld《开放项》清零,规则部分落入 `docs/rules-vN`。**对账(2026-10,L 收口)**:工程侧 hld 可执行项已清零——#6(快照拷贝粒度)与 #7(回放体积与存储/IO)随 L 收口关闭,剩余 #3(座位轮换实效)已随 B 收口关闭(2026-10-09,verdict 红档:基准 H 异质 12 局最大 seat 胜率落差 58.3% >15%,判据文本回流 hld §12 #3,触发条件交回 gdd §3.3、规则侧动作另立);规则侧 gdd 仍有 #11(参赛脚本是否受整数闭包约束)与 #15(能否用 `progress` 反推占领进度)两条未裁,二者已列入 L spec 的 Out of Scope、留待后续规则侧节点,**如实登记不假装清零**。规则数值已落 `rulesets/v1.json`,面向模型的正文落 `docs/rules-v1/`。
