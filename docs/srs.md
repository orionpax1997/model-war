# SRS:model-war v0 软件需求规格

| 项 | 值 |
|---|---|
| 版本 | v2.3 |
| 状态 | 已确认 |
| 上游文档 | [fsr.md](./fsr.md)(定位与风险)、[gdd.md](./gdd.md)(规则)、[hld.md](./hld.md)(设计) |
| 本文件拥有 | 范围与交付时点、FR/NFR 需求与验收条款、v0 验收口径 |

只覆盖 **v0**。需求编号(FR/NFR)供 spec 与 issue 引用;每条需求附**可检查的验收条款**,验收不通过即需求未完成。

## 1. 范围

### 1.1 v0 交付物

`engine`(确定性对局引擎 + 沙箱)、`runner`(赛季调度 + 排名与报告)、`gen`(脚本生成管线)、`docs/rules-vN`(面向模型的规则与 API 文档)、CLI 回放查看器。

### 1.2 不在 v0 范围

Web UI 与观战渲染、视频内容生产管线、练习赛(含任何把对局反馈回喂模型的协议)、模型自动接入平台化(接新模型 = 改配置重跑)、战争迷雾与多资源种类等复杂规则、跨赛季规则版本演化策略(v0 只做版本隔离:不同 ruleset 版本的结果不入同一排名,FR-8 AC3)。

### 1.3 交付时点

- **v0**:上列五个工件 + 一轮真实模型赛季报告。
- **v0.5**:Web 渲染器(规则侧要求:回放自 v0 第一天起按可渲染设计,见 gdd《娱乐产出设计》)。

## 2. 功能需求

### FR-1 对局引擎:领土争夺 RTS 模拟

引擎以 tick 为唯一时间单位,无头运行,模拟**四方(1v1v1v1)**脚本控制的单位在网格地图上争夺领土(占领 → 采集 → 生产)。

- AC1:引擎可在无任何网络/模型 API 的环境下完整跑完一个对局并给出结果。
- AC2:四方初始条件严格对等:地图四重旋转对称、四方初始单位与资源配置相同,并以对局配置断言验证。
- AC3:规则机制以 gdd 为设计基准,面向模型的版本落入 `docs/rules-vN`;引擎不硬编码规则数值(取值真源为 `rulesets/*.json`)。

### FR-2 确定性与回放

同一种子 + 同一组四份脚本,任何时间、任何次数的重放与重新执行,对局结果**逐 tick 完全一致**。

- AC1:同配置重跑同一个对局 10 次,每 tick 的完整状态 hash 全部一致。
- AC2:回放产物(JSONL 状态流)记录每 tick 足以复现观演的状态;读取 JSONL 得到的结果与重新执行脚本得到的结果一致。
- AC3:引擎状态演化不使用浮点运算(以 lint 或代码审查条款固化)。

### FR-3 脚本接口(action 接口 + 只读 state)

- 脚本通过**明确的 action 接口**下发指令;通过**只读快照**读取局面。
- state 不暴露引擎内部结构与可变引用:快照不可变,脚本无法通过任何途径改写引擎状态。
- 脚本拥有跨 tick 记忆能力(模块级状态在 VM 生命周期内保留)。

- AC1:脚本读取到的每个 state 对象均为只读封存/复制副本,修改它不影响后续引擎状态(以专门测试脚本验证)。
- AC2:action 接口与可读 state 字段在 `docs/rules-vN` 中有完整签名与语义说明,无需阅读引擎源码即可正确调用。
- AC3:接口面有运行时校验,越权调用(未暴露字段、未定义 action、宿主桥函数)被拒绝并按 hld《沙箱》的异常裁决处理。

### FR-4 沙箱与计算预算

参赛脚本为不受信任代码,在隔离环境运行,带资源上限,防死循环与内存爆炸。

- AC1:沙箱内脚本无网络、无文件系统、无宿主进程访问能力。
- AC2:存在指令、API 调用、内存、时间四类上限;预算形态与判罚细则见 hld《计算预算》,且必须保证:同一输入重复执行时,预算裁决结果一致(受 FR-2 约束)。
- AC3:一方脚本的崩溃/异常不中断其他方脚本与引擎运行。

### FR-5 脚本生成管线(纯静态校验协议)

`gen` 离线运行,不与引擎耦合:输入规则文档与模型配置,输出冻结脚本 + 模型名。

- 协议:规则文档 + API 文档 → 模型生成 TS 脚本 → 静态校验(编译 + API 误用检查)→ 失败则仅将**校验错误**回喂模型 → 迭代,轮数上限为 gen 配置项(默认 5)→ 通过则冻结脚本。
- v0 **不提供任何对战反馈**:无练习赛、无战绩回喂。

- AC1:管线全程只回喂静态校验错误,代码中不存在将对局结果传回生成环节的路径(以架构审查条款固化)。
- AC2:5 轮后仍未通过校验的模型,产出"校验失败"记录并进入报告失败名单,不占用对局名额。
- AC3:接入新模型只需增加一份配置(模型名、API 端点、凭证引用),不改代码。

### FR-6 可追溯性存档

每个冻结脚本强制存档元数据,缺档结果不得进入正式报告。

- AC1:每个冻结脚本连同元数据落盘:模型名、模型版本/快照标识、生成日期、协议迭代轮数、完整 prompt、生成日志、编译器版本、产物 hash。
- AC2:runner 拒绝运行无元数据的脚本(报错退出,而非跳过)。
- AC3:给定正式报告中的任意一个对局,可以从存档还原:四方脚本、元数据、种子、地图。

### FR-7 赛季调度 runner

- AC1:支持赛季调度:N 个参赛脚本按 **4 人组合**对战 × M 张地图 × K 个种子,对局选取对全体参赛者一致(无人可选种子/地图),座位分配规则对全体参赛者一致。
- AC2:对局可并发执行,对局之间互不干扰;一个**对局进程**崩溃不影响其余对局,并在报告中记录(脚本自身异常是判罚而非崩溃,见 gdd《异常与出局》)。
- AC3:一个对局的输入被完整物化(脚本存档引用 + 地图 + 种子 + ruleset 版本),报告中每场胜负都可凭该输入复算。

### FR-8 排名与报告输出

- AC1:以**名次积分制**为主排名(每场按最终名次记分,超时按领土分定名次,同分并列);Elo 作为可选副产品输出。
- AC2:同时产出 Markdown 报告(人类可读,可直接用作自媒体素材)与 JSON 原始数据(每场对局的输入引用与结果,机器可复算排名)。
- AC3:报告标注规则版本(`ruleset vN`);规则版本不同的结果不出现在同一份排名中。
- AC4:产出校验失败名单。

### FR-9 CLI 回放查看器

- AC1:提供终端 ASCII 回放查看器:读取 JSONL 回放,逐 tick 渲染网格局面,支持单步/暂停。
- AC2:查看器只读 JSONL,不依赖引擎运行时;只依赖带 `schemaVersion` 的回放 schema,跨版本兼容性以 `schemaVersion` 为准。
- 定位:调试工具,用于 v0 设计阶段人工验证规则质量;不承诺观战体验。

### FR-10 规则文档(`docs/rules-vN`)

写给模型的完整契约,模型可读性是硬性验收项。

- AC1:自包含:仅凭该文档(含 API 签名与数值表)即可写出可过校验的脚本——以"模型仅凭文档生成可过校验脚本"作为验证方式(盲写:输入只有文档,不读引擎源码;静态校验错误可回喂,≤5 轮)。**已知缺口**:终稿盲写三舱在「占领」一处各自猜出互斥机制,说明该节尚未落库;归属、裁决与读数归 gdd(§3.2 与《规则侧记录》#14),本条不复制。
- AC2:带版本号;版本号与 ruleset 一致(错配时 runner 拒跑)。
- AC3:包含确定性约束的显式说明(哪些行为被禁止/裁决一致),使模型可据此规避不确定行为。

## 3. 非功能需求

### NFR-1 确定性(最高优先级)

FR-2 是系统第一约束:任何导致重放不一致的实现选择自动否决,无需另行讨论。

- AC:CI 中存在"重放一致性"测试:抽正式对局样本,重新执行并与 JSONL 比对,每 tick 状态 hash 一致。

### NFR-2 可信性

排名的每个数字可被第三方复算:原始数据 + 脚本存档 + 种子即全部输入。

- AC:由 JSON 原始数据独立重算的名次积分与报告一致。

### NFR-3 性能

- AC:给定赛季配置(参赛模型数 N、地图数 M、种子数 K,总对局数 = C(4,N)×M×K),整轮在一台普通开发机、无人工干预下跑完,且每个对局的平均墙钟耗时 ≤ X(X 用 ≥2 个模型基准脚本标定,见 §4 第 2 条)。若不满足,先查沙箱开销,再考虑并发度,不得牺牲 NFR-1。算例:N=5/M=3/K=5 → 75 个对局。

### NFR-4 可维护性

- AC1:规则数值与引擎逻辑分离:改数值不改代码(规则以数据文件表达)。
- AC2:`engine`/`runner`/`gen` 之间只通过文件(JSONL、脚本存档、配置)交换,不共享运行时进程——`gen` 永远不在对局进程内。

## 4. 验收口径(v0 整体)

v0 完成当且仅当:

1. FR-1 ~ FR-10 的全部 AC 通过;
2. 存在至少 2 个模型生成的基准脚本,能完成对局并体现不同策略(验证规则集有区分度,对应 fsr R2);
3. 完成一轮含 ≥4 个真实模型的首轮赛季,产出正式报告(含失败名单);
4. gdd《开放项》与 hld《开放项》清零,规则部分落入 `docs/rules-vN`。
