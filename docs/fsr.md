## 1. 项目定位

**model-war 是一个私有、防污染的 LLM 对战项目,娱乐优先、兼作 benchmark**:各参赛大模型在赛前一次性编写 TypeScript 策略脚本;随后脚本在确定性引擎中自动进行 **1v1v1v1 四方领土争夺 RTS** 混战,人类仅观战。

**首要定位是娱乐内容生产**:多方混战、偷点、翻盘构成的对局是主产品;模型排名是副产品。

它同时测两种能力:

1. **读文档写代码**:模型能否根据规则文档 + API 文档,一次写出能通过校验、可运行的策略代码;
2. **策略质量**:写出的策略在对弈中是否真的会赢。

内容生产是首要定位,但内容管线本身(视频生产自动化)仍非 v0 范围;v0 只保证回放数据"可渲染、可叙事"(见 [gdd.md](./gdd.md) §8.3)。

**核心差异化**:规则文档私有、带版本、可演化。题目本身不公开冻结,厂商无法对固定题目做专项训练;新模型发布后重跑一轮 benchmark 即可得到横向对比,这正是本项目对自媒体场景的价值。

## 2. 需求范围

### 2.1 v0 范围(In Scope)

| 模块 | 内容 |
|---|---|
| 确定性引擎 | tick 驱动的领土争夺 RTS 模拟,全整数运算,同输入必同输出 |
| 回放 | 对局输出 JSONL 状态流;回放 = 种子 + 四方脚本(确定性重放) |
| 沙箱 | 运行不受信任的参赛脚本,带指令/时间预算,超限判负 |
| 脚本生成管线(离线) | 读规则文档 → 调模型 API 生成 TS 脚本 → 编译/校验 → 报错回喂迭代 ≤5 轮 → 冻结。**引擎不接模型**,只消费"脚本 + 模型名" |
| 对战 runner | CLI,赛季调度(每场 4 份脚本混战)× ≥3 地图 × ≥5 种子,输出名次积分排名(v0 首轮;赛制与积分规则待定,见 srs §6) |

### 2.2 v0 明确不做(Out of Scope)

- 任何 Web UI / 可视化观战界面(远期规划为 web 渲染,但 v0 只要 tick + 回放)
- 战争迷雾、多资源种类等复杂规则(留给 v1)
- 对战结果反馈给模型做策略迭代(协议只允许基于编译/校验错误的修复)
- 视频内容生产管线
- 模型自动接入/平台化(接新模型 = 改配置文件重跑)

### 2.3 关键设计决策(已定)

| 决策 | 结论 | 理由 |
|---|---|---|
| 脚本语言 | TypeScript 子集 | 模型熟练度高;与引擎技术栈同构;沙箱与生态现成 |
| 引擎技术栈 | TS 单仓,无头引擎 + CLI | 与 web 远期规划同构;回放即重放,零额外存储 |
| 确定性手段 | 全整数运算,禁浮点 | 跨机器可复现是赛季结果可信的前提 |
| 赛季协议 | 单脚本冻结,仅允许编译/校验错误驱动的迭代(≤5 轮) | 纯一次性生成会被偶发语法错误污染;自由迭代会退化成工程循环赛,测不准"一次写出好策略" |
| 评估方式 | 多地图多种子循环赛 | 单场方差大,结论发到公共平台会被质疑 |
| 玩家角色 | 模型即玩家,人类仅观战 | 定位即 benchmark,无人类游玩需求 |

## 3. 竞品与先例分析

### 3.1 直接先例:LLM Skirmish

[llmskirmish.com](https://llmskirmish.com) 与本项目几乎同构:LLM 在 Docker 隔离环境中写 JS 代码,基于 Screeps 衍生 API 打 1v1 RTS 循环赛,每个模型提交脚本、两两对战、按胜率排名。

它验证了本路线的**核心可行性**:前沿模型确实能为陌生 RTS API 写出可运行、有分化胜率的策略代码。其公开数据显示各模型间胜率差异显著,说明该题目有区分度——这正是 benchmark 的价值。

与 model-war 的关键差异:

| 维度 | LLM Skirmish | model-war |
|---|---|---|
| 测什么 | 上下文内学习(5 轮比赛间可看战绩改脚本) | 一次写出好策略(只给编译错误反馈) |
| 题目公开性 | 公开网站,规则可被抓取训练 | 规则私有、版本化演化,防专项训练 |
| 交付形态 | 网站 + 排名 | v0 为 CLI + JSONL 回放,内容二次加工友好 |

### 3.2 经典编程对战游戏(设计经验来源)

| 项目 | 对本项目的启示 |
|---|---|
| Halite(Two Sigma → Kaggle) | 规则文档仅 1~2 页、上手快是成功关键;Halite 4 强制 Python 导致头部选手流失——**语言选择影响公平性** |
| Battlecode(MIT,25 年) | 计算预算要公平(bytecode 计数可复现但极难用);比赛节奏与反馈速度决定选手体验 |
| Screeps | "写代码打 RTS"范式的鼻祖,JS 生态验证充分;LLM Skirmish 即基于其衍生 API |
| Lux AI Challenge | 多语言支持(含 TS)+ Kaggle 托管的现代实现,规则复杂度居中,可作规则设计参照 |

### 3.3 LLM 实时决策类 benchmark(反例参照)

SC2Arena、TextStarCraft II、LLM-PySC2 等让 LLM 在对局中逐帧决策。它们共同暴露的问题——延迟(秒级/步)、token 成本随对局数线性膨胀、决策不稳定——**恰好是 model-war 架构完全规避的**:AI 只在赛前出现一次,对局阶段是纯确定性代码执行。

### 3.4 结论

无直接冲突的竞品:LLM Skirmish 证明了路线可行但不做防污染、不测"一次性写出好策略";经典编程对战游戏提供规则设计经验但不面向 LLM。model-war 的定位(私有防污染 + 单脚本冻结协议)有真实空缺。

## 4. 技术方案与可行性

### 4.1 架构

```
[脚本生成管线(离线,可人工触发)]          [引擎与对战(在线赛季运行时)]
  规则文档(vN) + API 文档                  runner CLI
      ↓                                      ↓
  模型 API(各厂商) ──脚本+模型名──→  沙箱(TS 子集,预算限制)×4
      ↑                                      ↓
  编译/校验错误回喂(≤5 轮)            确定性引擎(整数 tick)
                                           ↓
                                    JSONL 回放 + 排名(名次积分制,见 srs FR-8)
```

### 4.2 逐项可行性评估

| 项 | 评估 | 依据 |
|---|---|---|
| LLM 能写出可运行策略代码 | ✅ 高 | LLM Skirmish 已验证;TS/JS 是模型高熟练度语言 |
| 策略质量有区分度 | ✅ 高 | 先例显示模型间胜率差异显著,是 benchmark 价值所在,而非风险 |
| TS 沙箱运行不受信任代码 | ✅ 高 | quickjs-wasi 隔离执行 + 指令/API 双计数预算(见 hld §5);脚本无网络/IO 权限,威胁模型简单(参赛者只有 LLM,无恶意人类) |
| 确定性引擎 | ✅ 高 | 全整数运算 + 固定迭代顺序;TS 单线程模型天然利于此 |
| 回放 | ✅ 高 | 确定性引擎下,种子 + 四份脚本即可完整重放,无需存储帧数据 |
| 评估统计可信 | ✅ 中高 | 多地图多种子循环赛在工程上简单;地图池的**策略多样性**需要设计验证(见风险 R3) |
| 防污染 | ⚠️ 中 | 见风险 R1,无法根除,只能持续抬高专项训练成本 |

### 4.3 开放项(v0 设计阶段需定,本次 FSR 有意不下结论)

1. **具体规则集**:地图形状、单位种类与数值、经济/产能模型、胜负条件、tick 频率与对局时长。
2. **脚本 API 面**:暴露给模型的感知与操作接口(视野读取、移动/攻击指令、跨 tick 记忆机制)。
3. **指令预算的具体形态**:按 tick 计时、按操作计数,还是混合;超限的判罚(跳过本 tick vs 判负)。
4. **规则文档的版本演化策略**:何时换版本、旧排名如何与新版对齐。

## 5. 成本可行性

- **API 成本**:仅脚本生成阶段消耗 token。按每模型 ~5 轮迭代 × 规则+API 文档约 10k~30k token 上下文估算,单模型单轮生成成本约 ¥1~10;整轮成本 = N × 单模型成本(N 为赛季参赛模型数,属赛季配置)。
- **算力成本**:对局为本地确定性模拟,无 AI 调用。场次 = C(4,N)×M×K(N = 参赛模型数、M = 地图数、K = 种子数,均为赛季配置);算例 N=5/M=3/K=5 → 75 场,在普通开发机上分钟级~小时级完成。
- **结论**:成本不构成任何约束。新模型发布后"随时重跑"在成本上完全可行。

## 6. 时间可行性(v0 里程碑,按业余时间估算)

| 里程碑 | 内容 | 估算 |
|---|---|---|
| M1 规则 v1 | 最小规则集 + 脚本 API 定稿(§4.3 开放项 1、2),人类手写 2 个基准脚本验证规则闭环 | 1 周 |
| M2 引擎 | 确定性引擎 + tick 循环 + JSONL 输出 + 沙箱与预算 | 1~2 周 |
| M3 生成管线 | 规则文档 → 模型 API → 校验迭代 → 冻结脚本 | 1 周 |
| M4 runner | 赛季调度 + 排名输出;用 ≥4 个真实模型(四方对局下限)完成首轮赛季(赛制与积分规则待定,见 srs.md §6) | 1 周 |
| 合计 | | **3~6 周** |

关键依赖:无外部依赖,全部自研;最大不确定项是 M1 的规则设计迭代(规则不好玩/无区分度需要返工)。

## 7. 风险清单

| # | 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|---|
| R1 | **防污染失效**:排名要可信需公开协议,公开即可能被训练 | 中 | 高(定位受损) | 规则文档版本化演化,每赛季更换/微调规则;核心价值在"新模型发布后第一时间横向对比",时间差内被污染的收益本就有限 |
| R2 | **规则无区分度**:规则太简单则最优策略平凡(如无脑爆兵必胜),排名退化为编程功底排名 | 中 | 高 | M1 用人类基准脚本做策略多样性测试;参考 Halite 的"短规则、深博弈"设计;先例显示 RTS 领土争夺具备足够策略空间 |
| R3 | **地图池偏差**:少量地图可能被特定策略(如出生点 rush)主导 | 中 | 中 | ≥3 张风格迥异的地图 + ≥5 种子;出生点对称/距离约束 |
| R4 | **模型脚本整体质量低**:弱模型全灭、对局单调 | 低 | 中 | LLM Skirmish 已证明强模型可写出高胜率策略;若整体偏低,可放宽协议(增加迭代轮数)作为版本调整 |
| R5 | **沙箱逃逸/资源滥用**:LLM 生成的死循环、内存爆炸 | 低 | 中 | quickjs-wasi 隔离 + 中断/内存上限 + 超限判负(见 hld §5);无人类恶意参赛者,威胁模型简单 |
| R6 | **确定性破损**(意外引入浮点/非确定迭代) | 低 | 高(赛季结果失去可信度) | 引擎层 lint 禁浮点;CI 中对每场对局做"重放一致性"断言 |

## 8. 结论

**可行,建议启动 v0。**

- 技术路线已被最近似先例(LLM Skirmish)验证,且本项目架构(赛前写码、赛中无 AI)规避了 LLM 游戏 benchmark 的全部运行时风险;
- 成本可忽略,时间 3~6 周业余时间可交付;
- 真正的项目风险不在工程,而在**规则设计**(R2)与**防污染机制**(R1),二者分别由 M1 里程碑和规则版本化策略承接;
- 下一步:进入 v0 规则设计,解决 §4.3 的四个开放项(建议以 `.scratch/v0-rules/spec.md` 起题,见 `docs/agents/issue-tracker.md`)。
