# FSR:model-war 可行性分析报告

| 项 | 值 |
|---|---|
| 版本 | v2.0 |
| 状态 | 已评审通过:可行,建议启动 v0 |
| 本文件拥有 | 定位与目标、竞品与先例分析、可行性结论、成本与时间估算、项目级风险 |
| 本文件不写 | 需求条目(→ srs)、规则机制与数值(→ gdd / `rulesets/*.json`)、工程方案(→ hld) |

## 1. 定位

**model-war 是一个私有、防污染的 LLM 对战项目,娱乐优先、兼作 benchmark**:各参赛大模型在赛前一次性编写 TypeScript 策略脚本;随后脚本在确定性引擎中自动进行 **1v1v1v1 四方领土争夺 RTS** 混战,人类仅观战。

**首要产出是好看的对局**:多方混战、偷点、翻盘构成的对局就是主产品;模型排名是副产品。

它同时测两种能力:

1. **读文档写代码** —— 模型能否根据规则文档 + API 文档一次性写出能通过校验、可运行的策略;
2. **策略质量** —— 写出的策略在对弈中是否真的会赢。

**核心差异化**:规则文档私有、带版本、可演化。题目本身不公开冻结,厂商无法对固定题目做专项训练;新模型发布后重跑一轮即可得到横向对比,这是本项目对自媒体场景的价值。

## 2. 竞品与先例

### 2.1 直接先例:LLM Skirmish

[llmskirmish.com](https://llmskirmish.com) 与本项目几乎同构:LLM 在 Docker 隔离环境中写 JS 代码,基于 Screeps 衍生 API 打 1v1 RTS 循环赛。它验证了本路线的**核心可行性**:前沿模型确实能为陌生 RTS API 写出可运行、有分化胜率的策略代码,各模型间胜率差异显著——这正是 benchmark 的价值。

关键差异:

| 维度 | LLM Skirmish | model-war |
|---|---|---|
| 测什么 | 上下文内学习(5 轮比赛间可看战绩改脚本) | 一次写出好策略(只给编译错误反馈) |
| 题目公开性 | 公开网站,规则可被抓取训练 | 规则私有、版本化演化,防专项训练 |
| 交付形态 | 网站 + 排名 | v0 为 CLI + JSONL 回放,内容二次加工友好 |

### 2.2 经典编程对战游戏(设计经验来源)

| 项目 | 启示 |
|---|---|
| Halite(Two Sigma → Kaggle) | 规则文档 1~2 页、上手快是成功关键;Halite 4 强制 Python 导致头部选手流失——语言选择影响公平性 |
| Battlecode(MIT,25 年) | 计算预算要公平(bytecode 计数可复现但极难用);反馈速度决定选手体验 |
| Screeps | "写代码打 RTS"范式的鼻祖,JS 生态验证充分;LLM Skirmish 即基于其衍生 API |
| Lux AI Challenge | 多语言(含 TS)+ 托管式现代实现,规则复杂度居中,可作规则设计参照 |

### 2.3 LLM 实时决策类 benchmark(反例)

SC2Arena、TextStarCraft II、LLM-PySC2 等让 LLM 在对局中逐帧决策,共同暴露延迟(秒级/步)、token 成本随对局数线性膨胀、决策不稳定——**恰好是 model-war 架构完全规避的**:AI 只在赛前出现一次,对局阶段是纯确定性代码执行。

### 2.4 结论

无直接冲突的竞品:LLM Skirmish 证明路线可行但不做防污染、不测"一次性写出好策略";经典编程对战游戏提供规则设计经验但不面向 LLM。本项目的定位(私有防污染 + 单脚本冻结协议)有真实空缺。

## 3. 可行性

| 项 | 评估 | 依据 |
|---|---|---|
| LLM 能写出可运行策略代码 | ✅ 高 | LLM Skirmish 已验证;TS/JS 是模型高熟练度语言 |
| 策略质量有区分度 | ✅ 高 | 先例显示模型间胜率差异显著,是 benchmark 价值所在,而非风险 |
| TS 沙箱运行不受信任代码 | ✅ 高 | 沙箱选型与预算机制见 hld《沙箱》;脚本无网络/IO,威胁模型简单(参赛者只有 LLM) |
| 确定性引擎 | ✅ 高 | 全整数运算 + 显式结算顺序;TS 单线程模型天然有利(手段见 hld《确定性保障》) |
| 回放 | ✅ 高 | 确定性引擎下,种子 + 四份脚本即可完整重放,回放数据只服务于"可观看" |
| 评估统计可信 | ✅ 中高 | 多地图多种子循环赛工程上简单;地图池的策略多样性需要设计验证(风险 R3) |
| 防污染 | ⚠️ 中 | 见风险 R1,无法根除,只能持续抬高专项训练成本 |

## 4. 成本与时间

### 4.1 成本

- **API 成本**:仅脚本生成阶段消耗 token。按每模型 ~5 轮迭代 × 规则+API 文档约 10k~30k token 估算,单模型整轮生成成本约 ¥5~50(量级估算,随模型定价波动)。
- **算力成本**:对局为本地确定性模拟,无 AI 调用;场次公式与算例见 srs FR-7 / NFR-3。结论:**成本不构成任何约束**,"新模型发布后随时重跑"完全可行。

### 4.2 时间(里程碑,按业余时间估算)

| 里程碑 | 内容 | 估算 |
|---|---|---|
| M1 规则 v1 | 最小规则集 + 脚本 API 定稿,人类手写 ≥2 个基准脚本验证规则闭环与区分度 | 1 周 |
| M2 引擎 | 确定性引擎 + tick 循环 + JSONL 输出 + 沙箱与预算 | 1~2 周 |
| M3 生成管线 | 规则文档 → 模型 API → 校验迭代 → 冻结存档 | 1 周 |
| M4 runner | 赛季调度 + 排名与报告;用 ≥4 个真实模型完成首轮赛季 | 1 周 |
| 合计 | | **3~6 周** |

- 关键依赖:无外部依赖,全部自研;**最大不确定项是 M1 的规则设计迭代**(规则不好玩 / 无区分度需要返工)。
- 估算边界:以上只覆盖四个里程碑的主干。hld 中已定稿的工程面(沙箱集成实测、schema 真源与生成物 CI、工具链选型)不计入该估算,可能推翻合计值。

## 5. 项目风险

工程风险(沙箱逃逸、确定性破损等)由 hld 的设计手段承接,不在此重复;本表只列会让**项目定位失败**的风险。

| # | 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|---|
| R1 | **防污染失效**:规则一旦离开私有仓库即可能被训练。注意泄漏路径不止"公开网站"——**生成管线本身就要把规则文档全文送进各厂商 API**,厂商是否用 API 流量训练无法验证 | 中 | 高(定位受损) | 规则文档版本化演化,每赛季更换/微调;核心价值在"新模型发布后第一时间横向对比",时间差内被污染的收益有限。接受为残余风险 |
| R2 | **规则无区分度**:规则太简单则最优策略平凡(如无脑爆兵必胜),排名退化为编程功底排名 | 中 | 高 | M1 用人类基准脚本做策略多样性测试,以 gdd《设计约束》中的不等式为验收命题;参考 Halite 的"短规则、深博弈" |
| R3 | **地图池偏差**:少量地图可能被特定策略(如出生点 rush)主导 | 中 | 中 | ≥3 张风格迥异的地图 + ≥5 种子(K 的边际价值见 gdd《开放项》);出生点对称/距离约束;由 map-lint 与基准脚本对局验证 |
| R4 | **模型脚本整体质量低**:弱模型全灭、对局单调 | 低 | 中 | LLM Skirmish 已证明强模型可写出高胜率策略;若整体偏低,可放宽协议——静态校验的迭代轮数是 gen 配置项(默认 5,见 srs FR-5),按版本调大即可,不必改代码 |

## 6. 结论

**可行,建议启动 v0。**

- 技术路线已被最近似先例验证,且本项目架构(赛前写码、赛中无 AI)规避了 LLM 游戏 benchmark 的全部运行时风险;
- 成本可忽略;真正的项目风险不在工程,而在**规则设计**(R2)与**防污染机制**(R1),分别由 M1 里程碑和规则版本化策略承接;
- 下一步:进入 v0 规则设计,解决 gdd《开放项》,以 `.scratch/v0-rules/spec.md` 起题(见 `docs/agents/issue-tracker.md`)。
