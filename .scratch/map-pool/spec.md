# 地图池与种子变体定案

Status: ready-for-agent

## Problem Statement

gdd §8 的 #2 与 #6 是两条仍然开着的规则侧开放项,而它们的产物**在磁盘上一个字都没有**:`maps/` 只有一个 `.gitkeep`。四件事同时为真:

1. **地图池不存在,对局引擎无从装载初始条件**。hld §7.2 已把地图 JSON 的七字段形状定稿,`packages/schema` 也已交付对应的类型与 JSON Schema,但没有任何一张地图。因此 FR-1 的「四方初始条件严格对等」目前只能靠桩模拟器夹具地图口头担保,真引擎落地时第一条就断。
2. **`variantSlots` 是一个刻意写松的过渡形状,回填的触发条件已经成熟**。真源包里 `MapVariantSlot` 取 `JsonValue`,JSON Schema 侧是一个不带任何约束的 `items: {}`,两处的 description 都写着「待 A 节点回填」,并且明写回填时要一次改三处(TS 类型、schema 的 description、map-lint 的四重对称断言)。C 节点立下的「家已定、字段未交付」纪律,这是第二笔账到期。
3. **地图校验器 `map-lint` 只有名字**。hld 在四处提到它(§9 的子命令表、§11 追溯矩阵、§7.2 的强制校验清单、§3.x 的包职责),并把 FR-1 AC2 的满足挂在它身上,但没有实现、没有包归属、没有任何一条断言落地。
4. **规则标定环的 1336 场证据全部跑在无墙的夹具上,而真地图必须有墙**。桩的地形是全平原,gdd §4 却写「机动价值靠地图形状与速度差体现,不靠地形税」。墙一加,农民的行走距离变长、采集吞吐下降,**枯竭被推后而不是提前**——而 gdd #8 记录 #8 的两条等效命题(拉满经济 tick 400–600 枯竭 / 典型经济消耗不超过总储量 1/4)正是在无墙夹具上验过的。加墙后这两条命题从未被验证过。

这四件事互相咬合:地图要画就得先定点位,点位一动 `resourcePerSite=200` 的标定依据(全图 16 点 = 3200)就失效,而重标定要重跑 1336 场并作废 gdd §8 的两条记录。**这个耦合必须在本 feature 里一次性解掉,而不是拖到引擎需要地图时才发现。**

## Solution

解掉点位与墙的耦合,并把三张地图连同校验器一次落库:

- **点位布局锁死,三张地图共用一套**:4 个主基地 + 8 个中立基地 + 16 个资源点 = 28 个点位,坐标沿用标定环的 `center-fortress` 夹具(它在 size=64 下已实测枯竭中位 479,落在 400–600 内)。**风格差异 100% 由 terrain 的墙承载**,地图池在「开局布局」这个维度上零多样性。
- **`size` 取 64**,池内三张图一致(map-lint 断言)。
- **三张风格地图**按 gdd §4 的三种风格落地:开阔对攻图 / 廊道分割图 / 中心要塞图,四重旋转对称。
- **`variantSlots` 定稿为「静态候选轨道清单」**,元素是一条完整四重轨道的 4 个坐标对。种子只决定从候选里选哪些填,地图 JSON 是纯静态数据。
- **`map-lint` 落地**,承担 hld 点名的那几条断言,外加三条本 feature 新增的:「最近一圈资源点」的归属判定、三图墙体的两两 Jaccard 上限（已校准为 0.15）、以及「矿路不许被墙拉过 10 格」这条经济红线。
- **用带墙的真地图重跑那两条等效命题**,并裁决 gdd #6:变体是纯装饰、不参与策略决策,因此 K 取 4。

## User Stories

1. As a **对局内核实现者**, I want 地图池里有三张可直接装载的地图, so that 我不用在引擎落地时临时编一张夹具图来跑通流程。
2. As a **对局内核实现者**, I want 三张地图的点位布局相同, so that 我能假定「全图 28 个点位」并把它写进胜利判定与领土分的推导,而不是对每张图各写一遍。
3. As a **对局内核实现者**, I want 变体槽位是静态数据而不是运行时产物, so that 一张地图 JSON 加上一个种子就能完整重放出地形,不需要再跑一遍生成器。
4. As a **对局内核实现者**, I want 一个变体槽位就是一条完整的四重旋转轨道, so that 我按种子填墙时不必在引擎里重新实现旋转——把四个坐标填进去,对称性自动成立。
5. As a **地图作者**, I want 我改墙的时候 map-lint 立刻告诉我破坏了四重对称, so that 我不必等到对局跑起来才发现地图是斜的。
6. As a **地图作者**, I want 我把一个资源点放得离两家一样近时 map-lint 报错, so that 「家附近最近一圈」不会在我没意识到的时候变得有歧义。
7. As a **地图作者**, I want 我画完三张图后能立刻知道它们是不是真的「风格各异」, so that 我不会交出三张只是墙的密度不同的图。
8. As a **维护者**, I want 真源包里的 `MapVariantSlot` 不再是 `JsonValue`, so that 「形状由真源包拥有」这条纪律在地图这一侧也兑现,而不是留一个谁都能往里塞任何东西的口子。
9. As a **维护者**, I want 校验规则是纯函数、断言对象是地图数据, so that 我能对它写属性测试,而不用先造一个文件系统。
10. As a **维护者**, I want 规则标定环那两条等效命题在带墙的真地图上复验过, so that gdd #8 那条记录不是关于一个已丢弃实现的观察。
11. As a **赛季调度实现者**, I want 知道 K 该取多少而不是「≥5」, so that 我不用在写枚举逻辑时猜一个数。
12. As a **审查者**, I want 地图与校验的实现与 hld §7.2 写的「七字段全部必填」一致, so that 架构审查不会被一条需要改字段契约的承载条款带偏。
13. As a **审查者**, I want 风格判据落在实际地形上而不是一张自报的标签, so that 一张标着「开阔」但布满墙的图会被挡住。
14. As a **基准脚本作者**, I want 我的脚本在任何一张地图上都能跑, so that 换地图不等于换脚本。

## Implementation Decisions

### 边界:这是交付节点,不是迷雾节点

本 feature **走完整交付流程并落库**,不出「只给决策、交给下游实现」的东西。三个理由:

1. gdd #8 的两条等效命题**必须在带墙的真地图上实跑**才成立,这不是纸面判断,是必须拿数据说话的验证。跑完的那一刻坐标与墙已经定稿,再交出去就是把已跑通的证据与已定稿的设计分居两处。
2. `maps/` 是继 `rulesets/` 之后第三个只有 `.gitkeep` 的落库目录。规则标定环已经为「两张 wayfinder map 都没出落库」付过一次账。
3. `variantSlots` 的三处回填(TS 类型 + JSON Schema + map-lint 断言)是**跨会话最容易丢的机械活**:它要求三处同时改,少一处不会报错,只会在下一次 schema 变更时以漂移的形式冒出来。

代价是本 feature 的边界比原定的 wayfinder 节点宽,节点性质从迷雾层移到交付层,v0 里程碑 DAG 的节点表与波次表要相应改。

### 点位布局:三图锁死,风格全交给墙

**三张地图共用一套点位,坐标沿用夹具的 `center-fortress` 变体在 size=64 下的展开结果**:

| 类别 | 数量 | 说明 |
|---|---|---|
| 主基地 | 4 | 每方恰好 1 个,四象限对称,开局归属各家 |
| 中立基地 | 4(中路)+ 4(边路) | 成组四重对称 |
| 资源点 | 4 条轨道 × 4 格 = 16 | 内圈高危(4)+ 次内圈(4)+ 更内圈(4)+ 中路(4) |

gdd §7 参数清单里「点位数量不变量」这一行的含义列写的是「每方主基地数;其余点位的数量与对称性由地图声明、map-lint 断言」——也就是说**数量不变量的家是地图数据 + 校验器,不是规则集**。三图共用布局不违反任何一处:它只是让「地图声明的那个数」在三张图上恰好相同。

**为什么不随风格变点位**:改资源点数量会让 `resourcePerSite=200` 的标定依据失效(它是按「全图 16 点 = 3200」定的),而采集吞吐只与农数、农到矿的距离有关、与矿的数量无关——所以改 N 会平移枯竭时点,gdd #8 的命题①直接失守,要救必须重标定并重跑 1336 场,作废 gdd §8 的两条记录。中立基地数虽然不吃 `resourcePerSite`,但它改「全部点位归属单一玩家」的达成难度,等于改领土分的总分结构,同样会动 gdd #9 的终局形态结论。

**这条选择的代价要说清楚**:中心那 2×2 的中立基地块读起来像「要塞」语义,而它会同时出现在「开阔对攻图」上。这是本 feature 已知的一处语义张力,缓解手段是**让墙真正区分三图**——开阔图的墙少而分散、廊道图的墙成条、要塞图的墙在中心成环。点位相同、墙不同,风格判据也只判墙。原型阶段要专门看一眼开阔图上那个中心基地块读起来违不违和,如果违和严重,再回头讨论「要不要给开阔图换一套点位」(那会触发上面那条重标定的账)。

### 网格尺寸:64

map-lint 断言地图池内 `size` 一致,所以这一个数锁死三张图。选 64 的理由是 gdd §2 的时间轴:首触须落在 tick 40–160 的设计窗口内,`size=40` 的理论首触约 30 tick 达不到,`size=64` 约 45–70 tick 落在窗口内。

**原型阶段已复核,结论是「墙不是首触的杠杆」**:三张真图的首触估算为 34–37 tick(估算口径 = 全平原实测基线 34 + 该对玩家的绕路格数 ÷ 2,首触判据是「两军 Chebyshev ≤ 2」,两家对进各走一半)。最差的廊道图只把首触推到 37,离 160 上界差两个数量级,原因是绕路成本落在**路径**上而首触判据吃的是**接近度**。

**但复核顺带暴露了一条继承来的账,与墙无关**:标定环在无墙夹具上实测的首触中位就是 **34**,而 gdd §2 的第一段窗口是 `0 ~ 1/15`(tick 0–40)。34 落在段内,标定环自己的验收也判它合格(±20% 验收带 `[0,48]`,436 场里 420 场落在带内)——**它不是勉强过关,而是合规**。真正值得记的是:34 比 `1/15 = 40` 这个设计锚点早 6 tick,属于「开局节奏略早于设计预期」,与 `size` 选型无关。因此本 feature 不改 `size`,但要把这条基线偏差与「带墙后复核首触」一起交给 F,否则 F 复核出来的数会被误读成「墙把首触推了」。

### terrain:墙是三图唯一的差异来源

三张地图的 `terrain` 各自手写,标点 `.` = 平原、`#` = 墙,行数与行长都等于 `size`。墙的设计目标是**风格可辨**而不是随机密度差异:

- **开阔对攻图**:墙少、分散、不成线(象限里 12 撮散墙,2–4 格小块与三格 L),另加 2 撮站在矿→中心对角线上的小墙。首次接触容易,正面推进是主流打法。原型终稿 132 格 / 3.2%。
- **廊道分割图**:两层同心方环把战场切成「外缘带 / 中间带 / 中心盒」三条同心带。外环盒开口 3 格、内环盒开口 5 格,均偏心排布(风车式),所以绕路最贵但中路推进仍可通行。原型终稿 200 格 / 4.9%。
- **中心要塞图**:中心紧环盒(4 个 2 格宽正门)+ 四角 L 碉堡线 + 每家角落两小撮幕墙。中立基地的价值因此被地形放大——中心基地到次内圈矿的路径从 7 拉到 11。原型终稿 72 格 / 1.8%。

**三张图的中心都不放墙**(开阔图尤其),这是原型阶段的实际观感结论:开阔图的 2×2 中心中立基地块读作「地图正中的争夺目标」而不是「主堡」,因为要塞语义完全由墙给出。

**四重旋转对称是构造保证**:墙形只在左上象限书写,展开器补 4 次旋转。从 terrain 纯文本独立读回复核,三张图 64 行、对称性违例 0 格。这也是「墙必须满足四重旋转对称」(hld §7.2 对 map-lint 的硬要求,gdd §3.3 公平性的前提)在数据上的兑现方式。

**墙的经济后果必须在交付前验掉**:加墙拉长农民的行走距离,采集吞吐下降,枯竭时点**推后**。这与直觉相反(「墙多 = 更难 = 更耗资源」是错的),而标定环的 1336 场是在全平原夹具上跑的。验收口径见下节。

### variantSlots:静态候选轨道清单,元素是 4 个坐标对

**`variantSlots` 是地图 JSON 的静态字段,内容是候选轨道清单;种子只决定从候选里选中哪些填上墙。** 这与桩的实现不同:桩把候选代表元硬编码在地图构造逻辑里,输出的 `variantSlots` 只记录「本次种子实际填了哪些」——那是运行时产物。本 feature 把它翻过来:候选进地图 JSON,种子进对局输入,两者合成地形。这样「地图 + 种子 → 地形」是一个纯函数,`input.json` 里的 `mapHash` 与 `seed` 就足以复算(hld §7.3 已经这么写了)。

**元素形状是一条完整四重轨道的 4 个坐标对**,即 `[[x,y],[x,y],[x,y],[x,y]]`,而不是一个代表元坐标,也不是带语义字段的对象。理由是把四重对称这条不变量**从运行时断言挪进类型层**:类型写成 4 元组之后,map-lint 的对称断言从「旋转之后整张图自洽」退化成「长度是不是 4、这 4 个是不是某个点的轨道」,而后者在类型层面就几乎已经保证了。选代表元 + 引擎旋转展开会把旋转塞回引擎,多一层间接,且 map-lint 仍要重算轨道才能判——选带语义字段的对象则给了一个现在没有语义可填的框架。

**槽位不得与点位或其八邻域重叠**,这是桩已经确立的卫生规则:墙格压住点位或压住起始单位会改变点位可达性与初始条件的对称性,而那属于对局条件的改动,不属于「装饰性微扰」。原型阶段在 size=64 下逐格体检过:8 个代表元各展开成 4 格共 **32 格候选**,过滤后**一格不掉**——8 条整条干净、0 条半脏、0 条全脏,即这套点位布局下不存在「半条轨道」,静态候选清单占全图 **0.781%**。map-lint 把这条断言落成机器检查。

> **一处必须记下的读法纠正**:先前引用的「过滤后剩 20 格 / 0.488%」是误读,那 20 格是 `buildMap(seed=1)` 在某个种子上**实际填上**的 5 条轨道——种子相关的运行时产物,正是本 feature 要杀的那个东西。候选清单是静态的 32 格,与种子无关。混淆这两者会让人以为「候选清单的大小随种子变」,而那会直接推翻「地图 + 种子 → 地形是纯函数」这条。

**填充率沿用桩的 50%**,判定在引擎侧(随对局内核落地),不在本 feature。stub 重跑时用同一套机制以保持可比。

### 风格判据:比地形,不自报标签

**map-lint 断言三张地图的墙体集合两两 Jaccard 相似度低于阈值(0.15),不引入 `style` 字段。** 判据是 `|A∩B| / |A∪B|`,A、B 是两张图的墙格集合。

三条理由:

1. **判实际地形而不是声明**。加一个自报的 `style` 枚举字段,判据就退化成「三张图标了三种不同的值」——一张标着 `open` 但布满墙的图照样通过。gdd §4 的要求是「风格各异」,而「各异」是一个关于地形的事实,不是一个标签。
2. **不动七字段契约**。hld §7.2 写的是「七字段全部必填,并且禁止额外属性」,schema 侧关着 `additionalProperties: false`。加字段要改 hld 的字段表,而 hld 是数据格式的家——为一个判据去扩契约不划算。
3. **Jaccard 顺带挡住一个真实风险**:三张图地形如果高度相似,「地图池偏差」(fsr R3)与「座位轮换实效」(hld #3)的归因都会变得困难——分不清是座位偏置还是地图偏置在起作用。

**阈值已由原型阶段校准:0.2 → 0.15。** 实测三图两两 Jaccard 为 0.0000 / 0.0200 / 0.0247,而 0.2 这条线**落在真图与「结构相关」之间那道缝的外侧**——原型用一组负对照探针量出了缝的边界:

| 探针 | Jaccard | 0.2 判据 | 0.15 判据 |
|---|---|---|---|
| 三张真图两两 | 0.0000 / 0.0200 / 0.0247 | 过 | 过 |
| 同风格只加密度(开阔 116 → 212 格) | 0.509 | 挡住 | 挡住 |
| **只把外环挪 1 格**(内环逐格不动) | **0.195** | **放过 ✗** | 挡住 ✓ |
| 只把外环挪 2 / 3 / 4 / 6 / 8 格 | 0.200 / 0.205 / 0.211 / 0.222 / 0.308 | 挡住 | 挡住 |
| 只剩内环(外环整个没了) | 0.320 | 挡住 | 挡住 |
| 廊道图再加第三层环 | 0.510 | 挡住 | 挡住 |

那条被 0.2 放过的探针正是**最像真实手误的情况**:作者复制一张图微调几格后交付,两张图共享一整圈环带,人眼会说「不一样」。0.15 对真图留 6 倍余量(0.0247),同时把最小的结构共享探针(0.195)仍挡在门外。**不放宽**——放宽没有证据支持,只会让这条断言在第一次压力下退化成摆设。

### 「最近一圈资源点」的判定:Chebyshev,并列判失败

handoff §1 把这条定为规则不变量(**不是** ruleset 键),由 map-lint 对地图 JSON 断言:每方开局恰好拥有家附近最近的一圈资源点,数量为 4 的倍数,其余资源点中立、须先占领 `captureTicks` 才有开采权。

**判据用 Chebyshev 理论距离,不按绕墙的实际路径距离(BFS)。** 三条理由:

1. **度量自洽**。gdd §4 已经把 Chebyshev 定为移动度量(八向移动,对角与直行等价),「最近」用同一个度量才是同一件事的同一把尺。
2. **避免把点位不变量耦合到地形设计上**。若用 BFS 路径距离,改一堵墙就可能改掉某家的开局矿归属——于是地图迭代变成排雷:每加一堵墙都要重验四条归属。理论距离下,点位与墙是两个正交的设计维度,各自可独立调整。
3. **并列要判失败,而不是 tie-break**。若两组资源轨道到某家的距离相等,「最近一圈」不唯一,任何自动选择都会把一个设计歧义悄悄定死。并列时报错,把「你的图有歧义」变成一条明确的 lint 消息,是这张图唯一有用的行为。

断言写成:对该方主基地计算全部资源点的 Chebyshev 距离,取 `d_min`;该方开局归属的资源点集合必须**恰好**等于距离等于 `d_min` 的那组点,且那组点构成一条完整的四重轨道。这套布局在 size=64 下实测四家的 `d_min` 均为 6、次近均为 9,无并列,判定成立。

`initialOwner` 用 `null` 表中立(真源包的形状已经这么定),不引入桩里的 `-1`。

### 变体裁决与 K:纯装饰,K=4

**gdd #6 裁决：地图变体是纯装饰性微扰，不参与策略决策。** 依据是量级而不是印象：变体填充率 50%，静态候选清单实测 8 条轨道 / 32 格 = 全图的 **0.781%**，且**一格都不压点位及其八邻域**；1336 场里没有任何一条记录提到变体对结果有影响；gdd §4.1 已经写明变体「不增加风格多样性,也不改变点位数量」。原型阶段对候选轨道逐格体检过：8 条整条干净、0 条半脏、0 条全脏，即这套布局下不存在「半条轨道」。

**因此 K 取 4。** 推导链是:变体纯装饰 → 多种子不产生新信息 → K 唯一的实际作用变成 hld §8.1 的座位均摊(`M × K ≡ 0 (mod 4)`,M=3 故 K 需为 4 的倍数)→ 最小值是 4。这推翻了 fsr R3 记的「≥5 种子」,但推翻它的理由变了:R3 的 ≥5 是为了压地图池偏差的方差,而方差现在由 M=3 承担。

**不改 fsr。** 按文档分工,fsr 是风险与估算的家,而这是 gdd #6 裁决的回流——落点是 gdd §8 #6 那条记录里带一句指针,把 K 的取值与它的推导链一起写进去。

一个附带好处:K=4 时一个四元组合跨 3 图 × 4 种子 = 12 场,五个组合共 60 场,比 K=5 的 75 场更省,而「座位轮换实效」那张图要的恰恰是这个均摊样本。

## Testing Decisions

### 什么算好测试

只断言**外部可观察行为**。本 feature 的外部行为只有两件:一张地图(或一个地图池)被 map-lint 接受或被带定位信息的诊断拒绝;桩在一组地图上跑出可复算的统计数字。凡是能靠改内部结构而失效的断言都是坏断言。

### 缝(三条,按高到低)

1. **纯规则的「地图数据 → 违规」**。这是主缝,沿用 `packages/tools` 已落地的纯规则形状(一段输入 → 一组带定位的违规),不碰文件系统。每条断言带正例与反例。
   - 四重旋转对称:一张破坏 terrain 对称的图必被拒;一张破坏 sites 对称的图必被拒。两张独立的反例,因为它们走不同代码路径。
   - 点位不在墙上、不重叠、不越界:各一条反例。
   - 池内 `size` 一致:一张异尺寸的图必被拒。
   - 最近一圈归属:正例(本 feature 的三张图)、反例(把某家的最近矿判给别家)、**并列反例**(构造一组等距资源轨道,必须报错而不是挑一个)。
   - 变体槽位轨道合法性:长度不足 4 的槽位、非轨道的 4 个坐标、与点位重叠的槽位,各一条反例。
   - Jaccard：三图互异必过（真图实测 0.0000 / 0.0200 / 0.0247）。**负对照用例**：一张图只把外环挪 1 格（实测 0.195）必须被 0.15 挡住。这条是本判据存在的理由，没有它就会有人把阈值调回 0.2。
   - 矿路红线：矿路 `d ≥ 11` 的图必被拒（顶破 600），`d = 10` 必过（599，窗口内）。
   - **同源断言**:改真源包里的 `MapVariantSlot` 类型与 schema,map-lint 的判据随之改变。它证明的是「map-lint 从真源包读形状、自己不存第二份」。
2. **schema 与类型对齐**。沿用 C 节点已落的纪律:同一组 fixture 既过 TypeScript 类型又过 ajv,加上那条「schema 的必填键集合等于类型的键联合」的类型级断言。变体槽位的过渡形状退役后,这条断言要覆盖收紧后的类型。
3. **桩的复跑结论**。不作为回归测试,而是 implement 期间的验收证据。

### 明确不测

- **地形画得好不好不落仓库测试**。「三张图风格够不够迥异」是人的判断,由原型阶段的实际观感承担;机器能判的是 Jaccard 上限,不是审美。
- **墙的数值参数(密度、开口宽度)不进 schema**。它们是地图数据的一部分,不是需要 schema 约束的东西;schema 只管形状与跨字段自洽。
- **变体填充后引擎侧的对称性**。本 feature 的 map-lint 只判**候选清单**的轨道合法性;「按种子填完之后整张地形仍然对称」是对局内核那一侧的事,由内核的断言承担。桩在生成地形时已经保证这一点(整条轨道填或不填),实现阶段沿用同一机制。
- **CLI 子命令的进程级行为**。map-lint 是 hld §9 已登记的六个子命令之一,它是纯函数之上的一层薄壳,沿用 D3 立下的「目录薄壳不单独测」先例。

### 验收集:带墙真地图上的两条等效命题

gdd §8 记录 #8 给的两条命题必须在**带墙的三张真地图**上复验,不许沿用无墙夹具的数字:

- **命题①**:全图储量须使拉满经济剖面(每家 6–8 专职农)在 tick 400–600 枯竭。
- **命题②**:典型经济(4 份基准脚本实测吞吐,整局约 440)消耗不超过总储量的 1/4。

**验收口径：三张图各自跑桩，①的枯竭中位都要落进 400–600。** 这是本 feature 最贵的一条验收，理由是它把地图设计与规则数值绑在了一起：墙太厚 → 农走不动 → 吞吐降 → 枯竭推后 → 命题①失败 → 要返工改图。约束是**上界**（墙不能厚到把枯竭推出 600）；下界（不早于 400）由经济剖面本身保证，墙只往上推。

**原型阶段已把这条红线的边界量出来了**：采集往返 = `2d + 20`（`d` = 矿路，即家到最近自家矿的格数），按线性放大——`d=6` → 479、`d=7` → 509、`d=8` → 539、`d=9` → 569、`d=10` → 599、**`d=11` → 629 顶破 600**。三张真图的矿路都是 `d=6`，红线是「家门到自家矿那一小片不许被墙拉过 10 格」。**这是画墙的硬规则而非风格偏好**，它要落成 map-lint 的一条断言（或至少是票的验收条款），否则日后改墙的人看不到它。

返工风险可控:标定环已经给了无墙基线(`center-fortress@64` 枯竭中位 479、`open-four@64` 550),三张图第一版跑出来就知道偏差方向与量级。迭代到满足口径为止,不设轮次上限——设轮次上限等于允许交出一张明知不合口径的地图。

这四条基准脚本**不进仓库测试**(沿用 D 节点的「一次性证据不是回归基线」纪律),但它们是本 feature 必须用的那四份。

## Out of Scope

- **对局内核侧的变体填充实现**(种子 → 确定性填充候选轨道)。本 feature 定稿候选清单的形状与断言,填充归 F。
- **`variantSlots` 的填充率标定**。沿用桩的 50%,它随对局内核落地。
- **开局资源点的「占领 10 tick 才有开采权」的实现**。`captureTicks` 的取值归规则集,判定归对局内核;本 feature 只判地图 JSON 的归属声明是否符合规则。
- **四份基准脚本落进 `benchmarks/`**。归 E 的落库;本 feature 用它们做 implement 期间的验收。
- **终稿契约下的复跑**。本 feature 用标定环留下的脚本与桩。终稿契约在 E 落地,届时这两条命题要在终稿脚本上再验一次(见 Further Notes 的交办)。
- **地图进引擎后的寻路性能**。归 L 的性能节点。
- **地图池扩容到 3 张以上**。gdd §4 的下限是 3,本 feature 交付 3 张;扩容时 Jaccard 断言自动覆盖新图。
- **`style` 字段**。已裁决不引入(见 Further Notes 的张力)。

**残留的三条,全部要带进实现期**:

1. **中心基地块的违和有一条非机器守卫**。中心 2×2 位于切比雪夫 5.5 的对称「内堡」位,开阔图的空旷反而把它衬成一个对称焦点。这在当前墙形下读起来是对的,但**若日后有人给开阔图中心加环,违和会立刻回来**——map-lint 判不出来(它不判审美),这条只能由人守住。
