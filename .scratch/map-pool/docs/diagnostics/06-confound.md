## 0. 一句话结论

**分类：(b) 试点设置的混淆因素主导，不是 (a) 地图设计的真问题。**

试点测到的「交付量掉了 77%」几乎全部发生在**扩张阶段**（占点 → 拿到第 2 个矿），
而不是发生在**采集阶段**（自家矿往返）。在采集阶段，几何被完全控住（四张图「家↔自家矿」
的网格最短路都是 6），四张图的采集速率逐场一致（120 tick 采出 804 / 757 / 800 / 800）。
把墙从因果链里拿掉，交付量就回来了。

但**不是零地图成分**：真图上确实存在能把「无墙感知贪心寻路」困死的墙构型（本文件给了逐格证据）。
只不过那是对**探针**的发现，不是对**规则+地图**的发现——因为票面自己定的返工触发条件
（「矿路被墙拉过 `d = 10`」）**没有被触发**：家↔自家矿 BFS = 6，三张图全都是。

**因此票面「命题①不过就返工改图」的前置条件尚不成立，本轮不应动图。**

## 2. 混淆因素逐条（按贡献排序）

### F1（主因）探针的 `stepToward` 是**无墙感知的贪心**，在真图上会进局部极小

`.scratch/rules-calibration/sim/probes/farmer.js:86` 起：

```js
// 贪心一步：先走"对角→横→纵"里第一个可走的；都不行就退到"使目标 Chebyshev 距离下降最多"的邻格
```

下降判据是 **Chebyshev 距离**，跟墙无关。探针从不调用 `findPath`/`moveTo`
（`runtime.mjs:225-226` 提供了 `findPath`/`moveTo`，`pilot-matches.json` 里 `pathCalls=0`）。

**证据 A —— 卡死普查**（t=200，对每个 worker 按探针自己的规则算出它此刻的目标，
再看它 8 邻格里有没有「使 Chebyshev 下降」的合法着地格）：

```
=== fixture @t200 ===          WEDGE=0   (24 个 worker)
=== open-clash @t200 ===       WEDGE=2
=== corridor-split @t200 ===   WEDGE=12   ← 12 个扩张农，全部卡死
=== fortress-core @t200 ===    WEDGE=6
```

corridor-split 的 12 条原文（每方 3 扩张农，共 12 个，**一个不剩全卡死**）：

```
WEDGE p0#40@41,22 → 扩张目标 resource#17@44,19(cheb 3)｜空邻格: 41,23(cheb 3→4) 40,23(cheb 3→4)
WEDGE p0#44@37,22 → 扩张目标 resource#25@37,18(cheb 4)｜空邻格: 38,22(4→4) 36,22(4→4) 37,23(4→5) …
WEDGE p1#41@37,12 → 扩张目标 base#10@37,37(cheb 25)｜空邻格: 36,12(25→25) 37,11(25→26) 38,11(25→26) 36,11(25→26)
WEDGE p1#45@38,12 → 扩张目标 base#10@37,37(cheb 25)｜空邻格: 38,11(25→26) 39,11(25→26) 37,11(25→26)
…
```

注意 `p0#40@41,22` 距目标只有 **3 格**，8 邻格全部被墙或单位占住，一个能下降的都没有。
`p1#41@37,12` 距目标 25 格，空邻格的 Chebyshev 要么不变要么变大。

**证据 B —— 卡住的墙长什么样**（corridor-split，x∈[32,46]，y∈[8,30]，`#`=墙）：

```
   234567890123456
13 ###############      ← y=13 整行墙，x=32..46
…
21 ###########....      ← x=42 竖墙
22 ..........#....
23 ..........#....
24 ..........#....
```

`p1#41@37,12` 就在 y=13 那行墙的正下方。要到南边的 `base#10@37,37`，
必须先向西走到 x≤31 或向东走到 x≥47 才能下到 y=13 以下——这两条路都让 Chebyshev **先变大**，
贪心一步永远不会选它。于是这个单位从 tick ~90 起就再也没动过。

**证据 C —— 逐 tick 位移计数**（instrumented 重跑，`/tmp/diag5.mjs`）：
corridor-split 上 24 个 worker 的「连续未移动 tick 数」从 t≈100 起单调增长到 t=600 的 500+，
例如 `p0#40@41,22 s=53`(t=100) → `s=553`(t=600)；位置逐帧不变。

对照：夹具上也有 stuck 计数很高（`s=521`）的单位，但那些是**已经站到认领点位上、
按 `farmer.js:189` `if (u.x === t.x && u.y === t.y) continue;` 合法待命**的扩张农——
它们的据点数确实涨到了 28/28。**「stuck 计数」本身不是判据，「stuck 且据点数不涨」才是。**

### F2（次因）真图 `site.id` 是 0-based，探针的分车道公式是按 1-based 调的

`.scratch/rules-calibration/sim/probes/farmer.js:125`：

```js
if ((s.id - 1) % 4 === seat) myClaims.push(s);   // 认领：id mod 4 = 自座位
```

- 夹具：`map.mjs:113` `const nextId = (() => { let n = 1; return () => n++; })();` → id = **1..28**
- 三张真图：`maps/*.json` 的 `sites[].id` = **0..27**（如 `maps/corridor-split.json`：4 个家主基地 id 0–3，
  中立基地 4–11，自家矿 12–15，中立矿 16–27）
- 适配层原样透传：`harness.mjs:593` `id: s.id`

于是真图上每一方拿到的车道相对夹具**整体转了一格（90°）**。实测车道（seed 11）：

```
夹具   seat0 家@10,10 → r#17@19,19(d=9)  b#9@26,26(d=16) r#25@18,26(d=16) b#5@29,6(d=19) r#21@30,16(d=20)
真图   seat0 家@10,10 → b#9@37,26(d=27) r#25@37,18(d=27) r#17@44,19(d=34) r#21@47,30(d=37) b#5@57,29(d=47)
```

夹具里 seat0 第一个抢的是**家门口 9 格的中立矿**；真图里那个 `19,19` 的矿被分给了 **seat3**
（seat3 家在 `10,53`，过去要 34 格），seat0 的最近认领点变成 27 格外的一家中立基地。

**受控实验**（只在内存里把真图的 `site.id` 整体 +1，其余一字不动，`/tmp/diag4.mjs`、`/tmp/diag8.mjs`）：

| 图 | 原样 del | id+1 del |
|---|---:|---:|
| open-clash | 1760 | **2980** |

**这说明 open-clash 那 1760 里，绝大部分是编号相位带来的，不是墙带来的。**

顺带一个数字，说明 F2 的伤害不止是「慢」：open-clash 上 p0 的三个己方矿在
`37,18 / 44,19 / 47,30`，距家 `10,10` 的 Chebyshev 是 **27 / 34 / 37**（夹具 p0 的对应值是 6 / 9 / 16 / 20）。
往返一趟 54–74 tick，600 tick 只够跑个位数来回——这就是 p2/p3 只交付 180 的直接原因。

### F3（口径缺陷，影响命题①的成立与否）探针的资源自记是坏的，经济剖面**根本没拉满**

`farmer.js:170`：

```js
if (getRange(u.x, u.y, b.x, b.y) <= 1) { if (transfer(u.id)) pendingDeliver.push(u.id); }
```

但 `runtime.mjs` 的 `transfer()` 成功时 **`return undefined`**（不是 `true`）。
于是 `pendingDeliver` 永远是空的，`myRes` 永远不增。

instrumented 读数（fixture，seat 0）：

```
t=50   workers=6  myRes=0  pending=0  引擎真实资源 res=60
t=300  workers=6  myRes=0  pending=0  引擎真实资源 res=480
```

探针手里有 480，它以为有 0。所以：

- **所有 32 场试点，每家终局恰好 6 农，`workerPeak=6`，`farmer6` 与 `farmer8` 逐字段完全相同**
  （`del`、`harv`、`remainPct`、`t50`、`t100`、据点数全部逐字一致）。
- 命题①要求「每家 **6–8** 专职农」，**8 农这一档从来没有被跑到过**。
- 标定环那个 479 基线用的是同一份探针，所以 P0/P1 的**相互**比较仍然自洽；
  但两边都不是「拉满经济剖面」——**没有一边能对地图质量做出经济响应**。

（顺带：把 `transfer` 判定改成 `=== undefined` 也不够——`pendingDeliver` 的清账条件
`farmer.js:141` `if (w && w.owner === seat && w.type === 'worker') stillPending.push(...)`
等的是「单位消失」，而交付后单位不会消失，于是 `pendingDeliver` 变成只增不减的泄漏
（实测 t=60/120/199 → 3/9/15），`myRes` 依然恒为 0，worker 依然停在 6。这条要修的是记账模型，不是返回值。）

### E6 `farmer` 会去抢中立矿吗？——**不会**

`farmer.js:122` `myMines` 只收 `s.owner === seat` 的矿；`farmer.js:176` 注释明写
「自家矿枯竭 → 待采（不越权采中立矿）」。所以中立矿必须先被扩张农站上去占下来才可采。
**「抢矿」这一步完全依赖扩张农能走到点位——也就是 F1/F2 作用的那一步。**

### E7 `reachableCells` 够用吗？——不够，但这不是本轮的真因

`assertConnectivity`（`map.mjs:253`）只从 `0,0` 做一次 BFS，证明「所有点位可达」。
它**不**证明「家↔自家矿的最短路没变长」。E3 用逐对 BFS 补上了这个洞，结论是没变长（=6）。
**建议把「家↔自家矿 BFS ≤ d」加进 map-lint 的池级断言**，这是本诊断的可复用产出（见 §5）。

### E8 四颗种子带来了什么？——什么都没带来

`pilot-tables.md` 每格的括号 min–max 全为同一个数；三张真图 4 个种子的
`deliveredMean` / `remainingEndPct` / `ticks.p50` 逐字相同。种子维度在这批试点里不携带信息
（与票面 K=4「多种子不产生新信息、只做座位均摊」的论证方向一致，但这里的机制是
「卡死模式对变体填充率不敏感」，值得记一笔）。

## 5. 结论与下一步

### 分类

**(b) 试点设置的混淆因素主导。** 具体是三条互相独立的混淆：

| 编号 | 混淆 | 性质 | 单独贡献（可量化） |

| F4 | 起始单位偏移差 1 格 | 口径分歧，可忽略 | — |

**(a) 地图设计的真问题：目前证据不支持。** 按票面自己写的判据，
三张图的家↔自家矿 BFS 都是 6（触发线是 >10），采集阶段速率与夹具一致（≤6% 差）。
**本轮不应返工改图。**

但记录一条**尚未定性的地图侧观察**（不是结论）：
真图上确实存在能把「无墙感知贪心」困死的构型（corridor-split 的 `y=13` 整行墙 +
`x=42` 竖墙）。票 07 的模型盲写脚本同样从未在带墙地图上验过，它们的移动实现是未知的。
**「真图对盲写脚本是否可玩」是一个独立的、尚未测过的问题**，不属于票 06 的命题①。

### 下一步建议（按顺序）

**第一步：修试点，不动图。** 三处，都在 `.scratch/rules-calibration/sim/probes/farmer.js`：

1. **F3（必须先修，否则重跑没意义）**：重做资源记账。最省事的做法是不要自记，
   改成每 tick 从快照读自己的资源（探针本来就 `getObjectsByType('unit', {owner: seat})`，
   确认快照里有没有资源字段；没有就退一步：交付成功当 tick `pendingDeliver.push`，
   **下一 tick 无条件 `myRes += CARRY_LIMIT` 并清空队列**，不要等「单位消失」）。
   修完的验收判据：`WORKER_TARGET=8` 时 `workerPeak` 能到 8，且 `farmer6` 与 `farmer8`
   的 `delivered` **必须不相同**（现在逐字相同，是 bug 的指纹）。
2. **F1**：`stepToward` 的下降判据从 Chebyshev 换成墙感知距离场，
   **并且保留原版的拥堵兜底**（首步格被占时退到「次优的下降邻格」而不是放弃移动）——
   我第一版就是漏了兜底才把夹具臂打崩的。验收判据：夹具臂 `delivered` 相对 3080 的漂移 ≤ 5%。
3. **F2**：统一 `site.id` 基数。两条路选一条，别混：
   - (a) 把 `maps/*.json` 的 `site.id` 改成 1-based（**要改地图文件，但改的是编号不是几何**，
     需要同步跑 `modelwar map-lint`）；或
   - (b) 把 `farmer.js:125` 的车道公式改成不依赖编号基数（例如按「到本方家的方位角」分道）。
   推荐 (b)：车道本质是「各家沿自己的方向扩张」，用几何定义比用编号定义更贴近意图，
   也不让地图 JSON 承担一个与几何无关的约定。

**第二步：补 map-lint 的两条断言**（本诊断的可复用产出，E7）：

- **矿路判据从 Chebyshev 理论距离改成网格最短路**：断言 `BFS(家, 自家矿) ≤ 10`
  （票面触发线）。现在 `map-lint` 用 Chebyshev，三张图都能过，但换成 BFS 之后**也都能过**
  （实测 6）——这条断言现在加进去是零成本的，将来改图时会真的咬人。
- **新增「无墙感知可达性」不是 map-lint 的判据**（地图不该为探针的笨让路），
  但可以加一条**报告项**：对每个点位，统计它周围 8 邻格中被墙挡掉的「向家方向」格子数，
  用来在评审时看见「这块墙会不会卡住直线行进的单位」。

**第三步：重跑试点，判据不变。** 修完 F1/F2/F3 后重跑 `pilot.mjs`，
**先看夹具臂**：如果夹具臂的 `采空(p100)` 还落在 479±5%、`delivered` 落在 3080±5%，
说明改动受控，再读三张真图的数字。**如果夹具臂自己漂了，先修探针，别碰图。**

**第四步：口径统一。** F4（起始单位偏移）顺手统一掉——要么把真图 JSON 的 offset 改成
夹具缩放后的 `(2,0)/(0,1)`，要么把 `map.mjs` 的 `START_UNITS` 偏移改成缩放前就声明 (1,0)/(0,1)。
前者更简单，但同样要跑 `map-lint`。
