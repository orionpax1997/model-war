## 1. 把命题判据化（消耗到底是什么）

命题原句只说「消耗」，本仓有两个能读成「消耗」的量，两个都报、都判：

| 量 | 定义（本仓字段） | 语义 |
|---|---|---|
| **消耗**（判定用） | `depletion.total − depletion.remainingEnd` | 全图储量被采走、离开资源点的量 |
| 交付 | `Σ players[].delivered` | 送到自家基地的量（标定环 `tables.md` §6.2 叫「全场交付合计」） |
| 采获 | `Σ players[].harvests` | 只用作「消耗没凭空蒸发」的自洽校验 |

- 选**消耗**做判据：命题说的是「消耗**总储量**」，分母是 `depletion.total`（`tables.md` §6.1 那句
  「结束时全图剩余储量均值 78.2%（即平均只消耗了 21.8%」）就是这个量。
- 交付 ≤ 消耗，差额是造兵花掉的 + 在途携带的。两个口径的读数都进表，结论不依赖选哪个。
- 自洽校验：**全部 64 场 `消耗 ≡ 采获`**（`prop2-summary.json` 的
  `batch.consumedEqualsHarvestedEveryMatch = true`），所以「消耗」这个读数没有丢资源。

总量口径：三张真图 `sites[].kind === 'resource'` 各 16 个，`resourcePerSite = 200`
→ **total = 3200**，`prop2-summary.json` 每行 `depletion.total = 3200` 与之一致。
**1/4 配额 = 800。**

## 4. 判定

**命题② 过**（中位口径与最坏场口径都过）。

一句话理由：4 份基准脚本在带墙真图上的整局消耗中位 332–384、占总储量 10.4%–12%，
连同无墙夹具对照一起，64 场里最坏的单场也只有 460（14.4%），离 1/4 配额 800 还有 1.74 倍余量；
墙把典型经济的消耗占比**没有推高也没有推低到量级变化**（三张真图 332–384 vs 夹具 350.5，同一档）。

判读补充：这条命题在 gdd 里的用途是「地图可改资源点数量 N，但须使 ② 同时成立」。
本批三张图 N 都是 16，实测留出的余量很大，所以**它对这三张图不构成约束**——
这不是「图好」，是「当前 N 与配额的关系离触发线很远」。见 §5.1。

## 5. 口径问题（收口时需要主线程裁决的几条）

### 5.1 「整局 ≈440」在仓库里查不到直接记录，且它继承的是 `resourcePerSite=125` 口径

`grep -rn "440" .scratch/rules-calibration/ docs/` 在标定环记录里**零个命中是「整局消耗 440」**
（命中的全是 sha256 前缀 `067d844…`、`farmer2` 的 1440、以及首触验收带 `[0,48]` 的 440/488）；
这个数只出现在 `docs/gdd.md` §8 #8 与 `handoff.md:71`。能复现出 440 的唯一口径是：

```
sim/data/tables.md:308  「结束时全图剩余储量均值：78.2%（即平均只消耗了 21.8%）」
→ 那批是 resourcePerSite=125，total = 16×125 = 2000
→ 2000 × 21.8% = 436 ≈ 440
```

所以 **「≈440」和「1/4」是同一个 125 口径的产物**（当时的配额是 2000/4 = **500**，
436/500 = 87%，只剩 13% 余量）。票 09 把 `resourcePerSite` 改成 200 之后（gdd §8 #7），
总量变成 3200、配额变成 800，而典型经济的**绝对吞吐没跟着翻倍**——所以今天这条命题的余量
从 13% 变成 1.74 倍。**这条命题的松紧度是被 `resourcePerSite` 那一刀改掉的，不是被地图改掉的。**

另有一处更细的分歧：那 21.8% 是 `tables.md` §6.1 的**全矩阵**（125 口径 1168 场）平均值，
不是「4 份基准脚本」的口径。我用同一套 M1 口径（`a/b/c/d` 镜像混战、4 座位 × `SEEDS_PROBE`）
在 `resourcePerSite=125` 下跑夹具臂做溯源对照（一次性脚本，未入库）：

| 口径 | total | 消耗 min/中位/均值/max | 占 total |
|---|---:|---|---:|
| M1（4 份基准脚本）@125 | 2000 | 242 / 285 / 281.3 / 332 | **14.1%** |
| M1（4 份基准脚本）@200 | 3200 | 242 / 350.5 / 350.8 / 460 | **11.0%** |

即 **M1 口径下没有 440**（281）。所以 gdd §8 #8 ② 那句括号里的「≈440」与其修饰语
「4 份基准脚本实测吞吐」对不上：440 是全矩阵口径的数，修饰语写的是 M1 口径。
**主线程收口时需要决定 ② 括号里那个数按哪个口径写**——本票实测 M1 口径下是 **351（11.0%）**，
若沿用全矩阵口径，200 口径下的对应数是 `data-rerun-200/tables.md` §6.1 的
「19.9% × 3200 = 637」，那个更贴 1/4（79.7% 配额），**也仍然过**。两种口径同向、同结论。

### 5.2 种子维度对这条命题零信息 → 每臂有效样本只有 4

补充扫把种子从 4 颗扩到 8 颗，**每一格 min/中位/max 逐字不变**。逐场拆开看，原因很干净：

```
P0/fixture        s11=[242,341,460,360]  s23=s37=s41=s59=s71=s83=s97 完全相同
P1/open-clash     s11=[367,340,381,447]  s23=…=s97 完全相同
P1/corridor-split s11=[263,362,406,406]  s23=…=s97 完全相同
P1/fortress-core  s11=[259,412,322,342]  s23=…=s97 完全相同
```

机制（不是「变体填充不敏感」这么简单）：`grep -n "seed" sim/engine.mjs` → **零命中**，
引擎没有任何随机源；4 份基准脚本里 `Math.random` 只出现在「不使用它」的注释里。
所以一颗种子只经 `buildMap`/`mapFromJson` 的**变体填充**进对局。而变体填充**确实随种子变**
（实测 8 颗种子填了 2–6 条轨道：open-clash 墙 140/156/148/148/148/144/144/152 格），
**却一次都没改掉任何一个消耗值**——装饰性微扰对这 4 份脚本的采集路径无影响。

**结论：本批的有效独立样本是「每臂 4 个座位轮转」= 全批 16 个不同对局，64/128 是它的复制。**
引用时必须写「4 座位轮转 × 4 种子（种子维度零方差）」，不能写「128 场独立样本」。
这与 `06-confound.md` E8 的观察同向，但那里没有给出机制。

### 5.3 消耗 ≠ 交付，差着造兵开销；两个口径都过

`P0/fixture` 中位：消耗 350.5 / 交付 280；`P1/open-clash` 中位：消耗 374 / 交付 300。
差额是「采到了但花在造兵上 + 在途携带」。命题的字面是「消耗总储量」，所以判定用消耗；
但**如果收口时想改成用交付**，结论不变（最坏交付 420 = 13.1%）。两种口径都留在
`prop2-summary.json` 的 `consumed` / `delivered` 两栏里，不做取舍。

### 5.4 判定不是被「提前结束」撑起来的（反向检查）

按结局分组看消耗：

| 结局 | 场 | tick 范围 | 消耗 min–max | 占 total |
|---|---:|---|---:|---|
| `timeout`（跑满 600） | 12 | 600 | 242–263 | 7.6%–8.2% |
| `victory` / `shortcut`（提前收） | 52 | 220–427 | 322–460 | 10.1%–14.4% |

**跑满 600 tick 的场反而消耗最低**（爆兵脚本互殴要么早早分出胜负、要么打成僵局没人采集）。
也就是说「最坏场 460」来自**提前结束**的对局，而提前结束在本指标上是**抬高**消耗的方向，
所以这条判定没有被截断撑起来——真要按最保守读法（只看跑满 600 的 12 场），消耗是 242–263（8.2%），更安全。

### 5.5 本票不能替 ② 回答的：N 的敏感性

命题②在 gdd 里的设计意图是「地图可改 N 但须同时成立」。本批三张图 N 都等于 16，
消耗 332–384 对配额 800 留了 1.74 倍余量，**这条命题目前对 N 几乎没有约束力**
（典型吞吐由 4 份脚本的采集能力封顶，不由地图资源点数封顶）。
要真验 N 的敏感性需要改 `maps/*.json` 的资源点数，**本票明确不许改地图，未做**。
是否需要另开一张票去扫 N，交给主线程判断。
