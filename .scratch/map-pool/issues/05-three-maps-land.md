## Answer

落库的是两张新文件：`maps/corridor-split.json`（廊道分割图）与 `maps/fortress-core.json`（中心要塞图）。`maps/open-clash.json` 一个字节都没动。

### 抄，不是画

`terrain` 直接从原型产物 `terrain-*.txt` 剥掉 3 行注释头取那 64 行；`sites` / `spawnUnits` / `variantSlots` 三图共用，所以**不是从 open-clash.json 手抄的坐标，而是程序读出那个对象再序列化**——脚本先拿同一条生成路径重建 `open-clash.json` 并与磁盘上的文件**逐字节比对一致**，才写出另两张。这条自检是必要的：坐标手抄错一位，对称性断言未必会红（sites 的对称判据只判「旋转伙伴存在」，坐标整体平移一格仍然自洽），而那正是标定环 1336 场证据的地基。

### 本分支真实验证过的（数字都是从落库后的 JSON 现量的）

| 判据 | open-clash | corridor-split | fortress-core |
|---|---|---|---|
| 墙格 / 密度 | 132 / 3.2% | 200 / 4.9% | 72 / 1.8% |
| 四重旋转违例（terrain / sites） | 0 / 0 | 0 / 0 | 0 / 0 |
| 可达格（八向 BFS，墙不可通行） | 3964 | 3896 | 4024 |
| 非墙格总数 `4096 − 墙` | 3964 | 3896 | 4024 |
| `variantSlots` 8 条 / 32 格 | 非轨道 0、压点位八邻域 0、压初始落点 0、与墙重叠 0（三图同） | | |
| 点位压墙 / 点位重叠 | 0 / 0 | 0 / 0 | 0 / 0 |

**连通性怎么量的**：以 4 个主基地各自为起点做**八向 BFS 泛洪**（八向是因为 gdd §4 已把 Chebyshev 定为移动度量；墙格不可通行），看 28 个点位格与 8 个初始单位落点（家 + offset）是否落在可达集里。三图的可达格数恰好等于各自的非墙格总数，即**每一张图都是单一连通分量**——不只是「点位可达」，是所有非墙格全部归到同一个连通块，这比票面要求的「点位与起始位连通」更强。原型报的 3964 / 3896 / 4024 三个数在这三张 JSON 上原样复现。

**矿路**：四家 `d_min` 全部 6，归属集合恰好等于最近一圈那一组、第二 9、第三 16，**无并列**。另量了一条票面没要求的：家到自家矿的**包围盒内 0 格墙**，且八向 BFS 的实际路径长度也是 6（等于 Chebyshev 理论距离）——即「家门到自家矿那一小片留空」在三图上都成立，红线余量 4 格（`d=11` 顶破 600）。

**单图校验器**：`modelwar map-lint maps/<name>.json` 三张各退出 0（票 03 落的那版）。为确认这个 0 不是空过，做了一条负对照：往 corridor 的 `(0,0)` 塞一格墙，校验器报 2 处 `terrain` 对称违例并退出 1。

**风格结构也复核了一遍**（不是靠数密度，是看连通分量）：廊道图 8 个分量 = 外环 4 段各 34 格 + 内环 4 段各 16 格，外环开口在 `x=17..19`、内环开口在 `x=25..29`，四边开口位置互为旋转 → 风车式。要塞图 16 个分量 = 4×7 格的四角 L 碉堡 + 4×5 格的中心紧环盒（盒上 4 个 2 格宽正门在 `x=31..32` 一带）+ 8×3 格的角落幕墙，合计 72。三图正中 `x,y ∈ 30..33` 的核心 4×4 无墙。

### 未验的，以及为什么

**「池级校验全绿」这条我没有勾，也无法勾。** 池级判据是票 04 的活，本分支上 `map-lint` 的入口只吃单个文件、没有池级断言，两票在任务图上串行、并行改 `apps/cli/src/map-lint/` 会冲突，所以我一个字没动那个目录。为了对自己的数据负责，我按票 04 判据在 `/tmp` 下写了一次性脚本自己算了一遍（不入库）：

- 池内 `size` 一致：64 / 64 / 64 ✓；地图数 3（规则下限 3）✓
- 最近一圈归属：四家 `d_min` = 6，无并列，归属集合恰为最近一圈 ✓
- 矿路红线：四家 `d` = 6 ≤ 10 ✓
- 两两 Jaccard：`open↔corridor` = 8/324 = **0.0247**、`open↔fortress` = 4/200 = **0.0200**、`corridor↔fortress` = 0/272 = **0.0000**，全部 ≤ 0.15 ✓

**这三个 Jaccard 与原型阶段报的值逐位相同**，且离阈值有 6 倍余量。票 04 合并后主线程真跑一遍池级校验器时，这三个数可以直接对。

**发现但没动的问题**：

1. `open-clash` 的「撮数」与票面描述有出入。票面写「象限里 12 撮散墙 + 2 撮站在矿→中心对角线上的小墙」= 14 撮/象限；实测按 8-连通是 **12 撮/象限**（其中确实有 2 撮站在矿→中心连线上：`(22,22)(23,23)` 与 `(30,24)(30,25)`，另 10 撮是散墙），按 4-连通是 13 撮/象限（有两撮是对角相邻被算开）。墙格数 132 / 3.2% 与票面完全一致，所以这是**描述层面的计数出入，不是数据缺陷**，且属票 02 的判断范围，我没改它的文件。
2. 「三张图的中心都不放墙」这条有个读法要留给后来人：地图正中的 4×4 核三图都空，但要塞图的紧环盒**内部**（`x,y ∈ 26..37` 那圈）在四个内侧角落各有一撮 3+1 的小 L 墙（合计 20 格，即那 4 个 2 格宽正门的门垛）。若把「中心」读成「2×2 中心中立基地的包围盒」，要塞图那条不成立；读成「地图正中的争夺目标格」则三图都成立——我按后者勾的。这条恰好落在原型残留项里说的「非机器守卫」那一类：日后有人给要塞图中心再加墙，map-lint 不会拦。
3. `maps/` 目录下的池级入口现在仍然是「一条命令一张图」：三张图要跑三次。票 04 落地后才是 `modelwar map-lint maps/` 一次跑完。
