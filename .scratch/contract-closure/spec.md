# 面向模型的契约补齐与 M1 基准复验

Status: ready-for-agent

图上的节点 R(`docs/diagrams/v0-milestone-dag.md` §4)。工作单元 = 一个 `.scratch/<feature>/`,走 `grill-with-docs`(已完成)→ `to-spec`(本文件)→ `to-tickets` → `implement`。

## Problem Statement

`docs/rules-v1/rules.md` 有四节还是 `TODO(→ 机制契约:…)` 占位:§1 初始条件与地图点位不变量、§2 tick 结算管线、**§5 占领**、§9 确定性约束。四处不是同一种欠账,但其中一处是全局卡点:

1. **FR-10 AC1 自包含不成立,且 srs 自己承认**。`docs/srs.md:106` 的 AC1 写着「已知缺口:终稿盲写三舱在『占领』一处各自猜出互斥机制,说明该节尚未落库」。机制归 `docs/gdd.md:73-88`(§3.2)是齐的,缺的是把它变成**脚本作者可据以写码的散文**。于是有一件自相矛盾的事同时成立:契约自称两份合起来是一份自包含契约(`rules.md:3`),而模型读完仍不知道占领要站在哪里。
2. **三份基准脚本全部写在 §5 落库之前,因此全部不能当基准**。`benchmarks/README.md:63-67` 的口径是「换契约版本时,基准脚本一律重跑,不保留」——本轮契约换版本了。`benchmarks/cell-c-claim-no-harvest/script.ts:81-82` 的注释是自白:「站点格本身多半不可站立(采集规则要求站在相邻格),所以占领靠相邻」。`cell-b` 犯同一个错(`script.ts:118-123`),`cell-a` 的「站上去」分支在真规则下会被走到但被判读标为死代码。`selfproof` 报告里三舱的 `captures` 读数(0 / 0 / 23)跑的是**标定环的桩**,不是真引擎,不能当终局。
3. **§9 是 FR-10 AC3 的字面载体,而它也是空的**。AC3 要求「包含确定性约束的显式说明(哪些行为被禁止/裁决一致),使模型可据此规避不确定行为」。契约里与裁决相关的散文散在 §3.1 / §8,没有任何一处把「哪些行为被裁决成一致结果」集中成可查的清单。
4. **「≤5 轮回喂」至今是纸面机制**。两轮实跑(`.scratch/rules-calibration/` 与 `.scratch/rules-landing/`)全部 0 轮回喂,`.scratch/rules-landing/blind/verdict-2026-10-04.md` §7.3 明写「这条机制至今没被走过一次」。而**回喂会把一个猜错机制的脚本救回来**这件事从未被测量过——它正是判断「缺口在契约还是在模型能力」的关键量。
5. **四笔连带对账会因占位被删而分叉**:① `docs/srs.md:106` 的缺口句 ② `docs/gdd.md:241` 记录 #14 的整条口径 ③ `packages/engine/src/processor/capture.ts:14-21` 那段**逐字复述了占位原文**的引擎注释 ④ `pnpm run check:selfproof` 跑的是桩。①②③ 必须同批改;④ 是身份问题,不是过期问题。

## Solution

补两节契约,重跑一轮盲写,用**真引擎上的读数**给出「缺口已消解」的证据,并把 M1 关掉。

1. **`rules.md` §5 占领落库**。按 gdd §3.2 的机制写,加三样机制本身不含、但模型实际猜错的东西:占领没有动作函数(只能 `moveTo` 到点位格)、站错了地方**不产生任何错误码**(唯一的自证办法是读 `site.progressOwner` / `site.progress`)、以及一段与 §3.1 同体例的示例。
2. **`rules.md` §9 确定性约束落库**。「禁止 / 保证」两栏对照表,只收**引擎裁决行为**一条线;`api.md` 已经写全的语法与可见面禁令一律指针过去。
3. **重跑三舱盲写**。策略沿用 A 爆兵压制 / B 扩张运营 / C 占点不采集,分别由三个不同模型写;产物替换 `benchmarks/` 三份。
4. **真引擎复验**:10 个对局(每舱 1v1v1v1 × 三张图各一个 = 9,加一场四座混编 A/B/C/A = 1),走 `modelwar match` 与 `modelwar verify`。
5. **四笔对账**同批改;新增一条 gdd 开放项交回规则侧;ADR 一条 + 词汇表一条。

做完之后 M1 的两条验收(M1 = 规则 v1:最小规则集 + 脚本 API 定稿,模型生成 ≥2 个基准脚本验证规则闭环与区分度)有证据可查,`srs.md:106` 那句「已知缺口」可以划掉。

## User Stories

1. 作为参赛模型,我想要在契约里读到占领的完整进度机(触发位置、累积、转轨、易主清零、不衰减),这样我不必靠猜。
2. 作为参赛模型,我想要知道占领**没有动作函数**、只能靠 `moveTo` 把单位送到点位格触发,这样我不会去找一个不存在的 `capture()`。
3. 作为参赛模型,我想要知道站错位置(占相邻格)**不会报任何错误码**,并且知道唯一的自证办法是读 `progressOwner` / `progress`,这样我不会把「没报错」读成「成功了」。
4. 作为参赛模型,我想要一份「禁止 / 保证」对照表,告诉我哪些写法会被裁决成一致结果,这样我据此规避不确定行为(FR-10 AC3)。
5. 作为维护者,我想要契约里不出现同一批禁令的两种措辞,这样规则侧的 §9 与 API 侧的 §1.2/§1.3 不会各说一套。
6. 作为验收者,我想看到**三个不同模型**在终稿契约下盲写出的脚本 0 轮通过静态校验,这样「契约自包含」这句话有外部证据,而不是自证。
7. 作为验收者,我想看到这些脚本在**真引擎**上真的产生了占领(`captures > 0`)且零异常轨,这样「规则闭环」不是在一个桩上成立。
8. 作为验收者,我想看到三舱在同一局里读出**不同的策略**,这样「区分度」有判据,而不是「三份脚本跑完了」。
9. 作为验收者,我想知道每一份基准脚本是**几轮回喂**换来的,这样「0 轮通过率」这个主指标不被回喂掩盖。
10. 作为后来者,我想要 `srs.md:106`、`gdd.md:241` 与 `capture.ts` 的注释都不再逐字复述一个已经不存在的占位,这样我不会同时读到两套说法。
11. 作为规则侧,我想要拿到「`progress` 能不能被读来算还差几 tick」这个开放问题被记进 gdd,这样 R 不会顺手替规则侧裁掉一个未评审的机制问题。

## Implementation Decisions

### 1. 范围:补 §5 + §9,§1 / §2 判 out-of-scope

- §5 是 M1 的唯一真卡点(§4.1 / §4.3 两节把它的结论当指针引)。
- §9 是 AC3 的字面载体,且它的内容「逐条对上本文件各节已写下的事实」——**不需要任何新决策**,成本最低而直接买下一条 AC。
- §1 / §2 的占位理由自己写着「各有家」「未派活」。补它们要先给「谁来复述地图不变量」「七步管线对脚本作者意味着什么」派活,那是规则侧的小图。塞进 R 会让这一格的重心从「占领 + 盲写证据」漂走。
- **动作**:§1 / §2 的占位**保留**,但占位理由改写成「R 已裁定 out-of-scope」+ 指针,保住 `rules.md:5` 那条头部约定(占位里必须写「归哪一批 / 为什么还没写」,现在多出第三件事:**谁裁的、裁在哪**)。

### 2. 证据形态:重跑新舱替换三份,旧三份的失败结论升级为消解证据

- `benchmarks/README.md:63-67` 的口径是「一律重跑,不保留」;旧三份的历史由 git 承担。
- **旧三份不作为「可用的旧基准」留在 `benchmarks/`**——c 舱在真规则下 `captures` 恒 0,留着会让 srs §4 第 2 条的「不同策略」判据踩空。
- 但它们是 srs AC1 那句「已知缺口」的**实证**:`verdict-2026-10-04.md` 里「三舱各猜出互斥占领机制」要作为**已消解缺口 + 消解证据**被写进 srs,而不是随文件删除沉掉。

### 3. 盲写口径:0 轮通过率是主指标,回喂轮次进附记

- srs AC1 的「静态校验错误可回喂,≤5 轮」是**允许**不是强制,0 轮不违规。
- 主指标 = 0 轮通过舱数 / 总舱数,它是 M1 真正在买的东西;回喂轮次另记一栏。
- 这样做顺带把「≤5 轮」从纸面机制变成被走过的机制,并测出「回喂能不能把猜错机制的脚本救回来」——这是判断缺口在契约还是在模型能力的关键数据。

### 4. 舱与模型:三策略 × 三模型,退路只降一轴

- 三舱沿用 A / B / C 策略(与旧轮逐策略可比),分别由 `deepseek/deepseek-v4.1-flash`(终稿两舱的唯一成功先例)、`MiniMaxAI/MiniMax-M3`(唯一写出完整经济链条的那份)、第三模型各写一份。
- **一次同时买下** M1 的「≥2 模型」与 srs §4 第 2 条的「不同策略」;两轴交叉(某舱同时换了策略和模型)比同策略换模型更能暴露「是契约写得不够,还是模型能力不够」。
- 第三模型首选 `claude-sonnet-5`,它是端点分家(`/messages`,见 `.modelwar-providers.md` 的端点归属)最干净的对照组。
- **已知阻塞与退路**:`/messages` 与另两个模型完全不同 API 形态,舱内 pi provider 侧**当前没配 Claude**。按 J 的口径这件事归 `wizard`,不在 R 里手搓。**顺序上先跑三舱、后配 provider**——三舱是硬要求,端点配置不是。若 `/messages` 那条路不通,该舱降级为 deepseek:只降一轴不降验收(M1 要的是「≥2 模型 + 不同策略」)。

### 5. 场次矩阵:10 个对局,两种形态都要

`match` 的输入是四座存档的数组且**下标即座位**,所以一个对局必须凑齐四份脚本。两种形态各自买下不同的东西:

- **每舱 1v1v1v1 × 三张图各一个对局 = 9 个**:每份脚本单独行为,策略自己会跑成什么样是可读数。
- **一场四座混编(A / B / C / A)= 1 个**:唯一能同时读出「策略差异」与「同场互相干扰」的形态。

### 6. 判据:captures > 0 且零异常轨(硬门禁);区分度走定性三元组

- **闭环硬门禁**:三个舱的每一个对局都 `captures > 0`(占领真的发生)且**零异常轨触发**。
- **区分度**:混编对局里三舱的读数三元组 `(单位类型构成, captures > 0, 经济死亡)` **两两不同**。
- **不定数值阈值**:三个量都是粗粒度分类,在 10 个对局的样本上硬编一条可被偶然跨过的线,会让判据形同虚设。
- 读数来源是 `modelwar match` 产的 `replay.jsonl`(meta 行 + 每 tick stateHash + 末行结果)与 `observations.jsonl`。
- **不读**资源数与击杀数:前者会被时长与终局条件污染,后者在「互不接触」策略下恒 0。

### 7. §5 写什么:三层 + 一段示例

- **机制**:gdd §3.2 的全部要点——点位为单格、同一时刻最多一个驱动者;**单位站在点位格上**即驱动;累积到 `captureTicks` 后所有权易主且**进度清零**;全兵种一致(农民不加速);驱动者与属主同阵营 → 进度保留不动;驱动者换人 → 若 `progressOwner` 不是新驱动者则**从 1 重新起算(无侵蚀)**,否则 `progress + 1`;无人站立 → 保留不动、**不衰减**;自家单位站自家点位格是合法堵点;占领**不耗资源**(故经济死亡 ≠ 出局)。
- **同格多单位时的驱动者判定**:**这一条 gdd §3.2 没写,引擎已裁**——`packages/engine/src/processor/capture.ts:41-56` 的开局退化情形按数值 id 最小的单位为驱动者。契约必须写它,否则脚本读到的 `progressOwner` 与自己的预期可能对不上。本 spec 采「**复述引擎已有行为**」的落法,不新裁机制;若评审认为它该回 gdd 补一条,归属可在 `to-tickets` 时改,写回 `rules.md` 的文字不变。
- **义务句**:占领没有动作函数,只能 `moveTo` 到点位格坐标触发;目标格本轮被占则该次意图失败(受 §3 的单格裁决约束)。
- **静默失败警告**:站相邻格**不累积、也不衰减、不产生任何错误码**——`api.md` 的错误码表里没有任何一个是占领专用码。唯一的自证办法是读 `site.progressOwner` 与 `site.progress`,确认驱动方是自己。
- **示例**:一段 3×3 坐标系的示例(与 §3.1 同体例),把「站上去才算、站旁边不算」演一遍。
- **不写**:`progress` 清零时被清成 `-1` 的内部表示(它把「无轨道」与「有轨道但进度 0」分开,`capture.ts:59-70`,对脚本没有可操作差异)。

### 8. `progress` 的决策用法:R 不裁,交回 gdd

「脚本能不能读 `progress` 算『还差几 tick 易主、该不该继续站』」是**规则侧空白**:gdd §3.2 没裁,引擎也没特殊暴露(`api.md:127` 那栏注释只说读得到)。

- R 的性质是「让已有决策落到契约面」,不是「替规则侧开新决策」。开一个新能力要在 gdd 留痕、走机制评审。
- **动作**:`docs/gdd.md` §8 新增一条开放项记录这条问题;`rules.md` §5 只描述读得到,不建议用法。

### 9. §9 的分家线:只收引擎裁决行为

`api.md` §1.2 / §1.3 已经把禁令写全了(禁模块语法、禁 `Date` / `Math.random` / `performance`、禁 `typeof`、禁缓存跨 tick 的对象引用与查询结果)。§9 若再抄一遍就是**一个事实两个家**。

- **分家线**:**关于运行时可见面的禁令归 `api.md`,关于引擎裁决结果的禁止与保证归 `rules.md` §9**。§9 里凡是 `api.md` 已有的,一律写成指针。
- AC3 的原话是「使模型可据此**规避**不确定行为」——可规避的是**裁决结果**(「我这样写会不会导致不确定」),而不是「这个函数能不能调」。
- **形态**:**禁止 / 保证两栏对照表**,每条带 § 指针。这是查询结构(读者拿着的是「我这类写法会不会不确定」);按节序罗列是作者的核对工序,不是读者的事。
- **措辞约束**:`packages/tools/src/rules-doc-prose.ts` 的门禁禁止散文中出现「参数键名 + 数字」的赋值形态。§9 里凡是提到参数,**只写键名 + 指针到 §10 数值表**(`captureTicks: 10` 会红,`captureTicks: 10 个 tick` 放行)。

### 10. 版本号不升(ADR 0008)

契约散文修订**不动任何取值**,因此不升版本号:文件名 `rules-v1/`、`rulesets/v1.json`、meta 里的 `ruleset` 字段与 AC2 的「版本号与 ruleset 一致」判据全部不变。详见 `docs/adr/0008`。

### 11. 四笔连带对账的归属

| 笔 | 落点 | 理由 |
|---|---|---|
| ① `docs/srs.md:106` AC1 缺口句 | **R**:改成已消解 + 指向本轮证据 | 占位删掉后原话即分叉 |
| ② `docs/gdd.md:241` 记录 #14 | **R**:口径改为「以 §3.2 为准」的现状描述 | 同上 |
| ③ `packages/engine/src/processor/capture.ts:14-21` 注释 | **R**:改成不指占位 | 留着占位原文等于对着实现讲「这里还没写」 |
| ④ `pnpm run check:selfproof` 的桩口径 | **不动** | 它的使命是**契约自证**(等效命题复验),桩口径是它身份的一部分;把它改成真引擎会改变这道门禁的判据基准,那是 L 的账。R 只在报告里写明「selfproof 的 `captures` 是桩口径,终局读数取 `match` 的真引擎读数」,**两个数字不共用** |

### 12. 不新增 captures 机器门禁

- L 那一格的交付物里已经明写着「**基准门禁(双脚本对打)**」——常驻读数门禁天然是 L 的家,R 新开一条会与它重复。
- 成本也不成立:CI 无凭证、无沙箱产物依赖,10 个真沙箱对局进 `check` 链会把门禁从秒级拖到分钟级。
- R 要的是**一次性的证据**,判据成立与否写在报告里,由这一格的收口负责。

## Testing Decisions

本节点的主判据是一次性的证据而非单元测试;但它碰到的每一道既有门禁都必须保持绿,且**新基准脚本要成为受门禁管的入库产物**:

1. **既有门禁不回归**(逐条跑 `pnpm run check:quick` 与默认 `test`)
   - `check:rules-prose`(或同族散文门禁):§5 / §9 落库后散文里不许出现「参数键名 + 数字」赋值形态(§9 尤其危险,它要提到 `captureTicks`)。
   - `check:drift`:§10 数值表是生成物,本轮**不动 `rulesets/v1.json`**,表内容应当逐字不变;若漂移,说明有人手改了生成区块。
   - `check:selfproof`:桩口径不动,门禁必须仍绿(它验的是等效命题,不是真引擎行为)。
   - `check:bench`:新三份 `script.js` 必须入库且与「现编译 == 入库」逐字节一致。
2. **每份新基准脚本的准入**(静态校验器)
   - `node packages/tools/src/validate/run-validate-script.ts <script.js> --max-bytes <N> --phase freeze`,退出码 0。
   - `--max-bytes` **不给默认值,必须现算**:`rulesets/v1.json` 的 `scriptSizeLimit` 目前是 `0`(未定值),口径按上一轮自证门禁取三份入库产物的最大值。
   - 回喂过的舱要单独跑一次 `--phase freeze` 并把回喂轮次记进报告。
3. **真沙箱复验**(每份脚本)
   - `modelwar match <input.json> --root .` 退出码 0;产物 `replay.jsonl` 与 `observations.jsonl` 与 `input.json` 同目录。
   - `modelwar verify <replay.jsonl> --root .` 退出码 0(逐 tick `stateHash` 比对 + meta 五栏一致)。
   - `meta.json` 的 `sandboxRuntimeHash` 必须等于本仓真值,否则装载期即拒跑退 1;`archive/` 与 `runs/` 目前都是空的,三件套与 `input.json` 由本轮现造。
4. **判据脚本**(一次性,不是门禁)
   - 读 `replay.jsonl` 与 `observations.jsonl` 算:每座位的 `captures` 次数、异常轨触发次数、单位类型构成、经济死亡与否;混编对局再算三元组两两不同。
