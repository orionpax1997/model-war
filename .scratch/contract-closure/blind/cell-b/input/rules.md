## 3. 移动与碰撞

- **一轮移动结算只以该轮开始时的占位为准**:单位离开本轮所在格,不使该格对后来者可进入;
  同一格至多一个单位成功进入。
- **同格竞争**:多方目标格相同 → 算出每个竞争者的**轮转优先值** `(tick + playerIndex) mod 4`,
  按这个值排序,**值大者胜**;落败者原地不动,不尝试次优目标格。四个玩家的轮转优先值互不相同,
  所以这一层不会有平手。`tick` 是正在结算的这一 tick,`playerIndex` 是你的座位号(取值见
  [`api.md`](./api.md) 的 `getMyIndex()`)。
- **交换与穿行**(A 要去 B 所在格、B 同时要去 A 所在格)与**链式移动**(A 要去 B 所在格、B 同时要去
  C 所在格):按本轮开始时的占位,B 格本轮被占,故 A 失败;B 能否进入 C 格只看 C 那一格自己的竞争,
  与 A 无关。二者互不牵连,没有链式裁决,也没有环形追逐。
- **己方单位之间同样按这套裁决**:没有友军穿越,自己人也会互相挡路。
- **`moveTo`**:引擎每 tick 沿寻路结果走一步,等价于本 tick 的 `move`,参与同一套裁决。路径不跨
  tick 缓存,每 tick 重算。
- **骑兵的二次移动**:重复整轮结算一次——第一轮结算后的占位就是第二轮的基准,两轮里的 `tick` 值
  相同(轮转优先不因多走一步而重排)。

### 3.1 先后手:轮转不是「永远后手」

- 轮转优先的算法只有一条:同格竞争时算 `(tick + playerIndex) mod 4`,**值大者先动**。`tick` 逐 tick
  加一,`playerIndex` 固定,所以你的优先值每四 tick 绕满一圈。
- 由此可得偏置的形状:座位号相差 d 的两方中,**座位号大的那一方**在 `(4−d)/4` 的 tick 里先动,
  **座位号小的那一方**在 `d/4` 的 tick 里先动。两个数都大于零——座位相邻时是三比一,座位相对时
  是一比一。
- 因此**没有任何一方是永远后手**:轮转说的是优先权逐 tick 换人,不是「你的座位固定吃亏」。真正
  存在的只是**比例**上的偏置,而它由座位在赛季内轮换摊平,不由你在脚本里补偿。
- 结论:**先手随 tick 轮转,不要赌先手**。不要写只有某个座位才成立的分支,也不要按「我先手 /
  我后手」分两套策略。

示例(3×3 坐标系,无地图假设;`(tick+index) mod 4` 值大者胜):

- 同格竞争:A(0,0)→(1,1)、B(2,2)→(1,1),(1,1) 空 → 轮转优先值大的一方进入,另一方原地。
- 交换穿行:A(0,0)→(1,0)、B(1,0)→(0,0) → 两者都失败(目标格本轮被占),均原地。
- 链式移动:A(0,0)→(1,0)、B(1,0)→(2,0),(2,0) 空 → A 失败((1,0) 本轮被占),B 能否进入 (2,0)
  只看 (2,0) 自己的竞争,与 A 无关。

## 4. 经济与生产

四方对局里没有被动收入:资源只从**采集**来,一切扩张都要先有资源。

### 4.1 采集与交付

```
采集: 农民站在己方资源点的相邻格上即开采,每个 tick 得 harvestRate 资源(射程见 §10 的 worker.range)
携带: 携带量上限 carryLimit;满载一次需要 ⌈carryLimit ÷ harvestRate⌉ 个有效采集 tick,满即停
交付: 走到己方控制基地的相邻格,调 transfer(射程见 §10 的 worker.range),一次交出全部携带量
      同时相邻多个己方基地时,交付给数值 id 最小的那个
归属: 资源进玩家全局共享池,无上限,不按基地分池
```

- **一个「有效采集 tick」= 满足全部三条的那个 tick**:农民**站在己方控制的资源点的相邻格**上、
  **携带量还没满**、该 tick 的结算确实结算到了它。站在中立资源点旁边不采集;站在己方基地旁边不
  采集;携带满了之后原地不动也不再计数。所以「一次满载」的时间是把往返的路程算进去之后的时间,
  不是满载所需 tick 数本身——地图上家与矿的距离直接决定你的经济节奏。
- **资源点**:开局时**你已经拥有家附近最近的一圈资源点**(数量为 4 的倍数、四方四重对称;具体
  布局与数量由地图数据声明,见 §1),可以直接开采。其余资源点**中立,必须先完成占领才有开采权**
  ——占领进度机的规则见 §5,占领一个点位所需的累积 tick 见 §10 数值表的 `captureTicks`。
  「先占矿才能采」只对中立资源点成立,不是开局条件。
- 每个资源点有**有限储量**(`resourcePerSite`,见 §10 数值表):采空之后**点位不会被移除**,它仍然
  计入胜利条件,只是再也产不出资源。矿采完不能续,所以开局占下多少矿是这局经济上限的一部分。

### 4.2 为什么采集与产能的取值是这样定的

单基地满产的烧钱率(§10 派生量表里的 `FULL_PRODUCTION_COST_RATE`)与**单农收入**
(§10 数值表的 `harvestRate` ÷ `carryLimit`,即一个农民跑一趟的净产出)之间必须留出一个明确的
倍数关系:**满产消耗要显著高于单农收入**。这个比值就是这两个数为什么定在这里的理由——比值太小,
「只开矿不扩产」与「只扩产不开矿」两条路都能赢,经济不再是决策;比值太大,产能完全压过采集,
采矿与护矿就退化成走过场。两个取值都在 §10 的表里,这里只留这条关系与它的指针(设计意图与
清零过程见 gdd §5《经济与生产》与 gdd §8 开放项 #5)。

### 4.3 经济死亡

- **无被动收入是刻意取舍**(不做死锁保护)。**经济死亡**:你没有任何农民单位,且 `resources`
  不足以再造一个农民(农民造价见 §10 数值表的 `worker.cost`)。这个状态**不可逆但不是出局**——
  占领资源点不会给你农民,没有被动收入,所以经济回不来。
- 但你**仍可用残兵抢点、阻断、拿下胜利**:占领不需要资源(见 §5),所以经济死亡之后
  对局照常继续。「翻盘」指整局仍可翻盘,不指经济可以复活。

### 4.4 生产

- 任何己方控制的基地都是**一条独立产线**(每基地一条队列,一次一个订单);多基地 = 并行产能。
  基地**不可摧毁、无攻击能力、无维修**;基地格可通行,且单格单单位。
- **下单即扣款**;资金不足时下单无效(`ERR_NOT_ENOUGH_RESOURCES`,错误码见
  [`api.md`](./api.md)),不占队列也不扣款。**同一条产线上已有订单时重复下单被静默丢弃**:
  不扣款、不计异常、队列不变——所以你可以每 tick 无脑重发生产请求,不必自己记队列。
- **出兵格就是基地格本身**。它被**任意单位占据(含你自己的单位)**时,该队列**挂起等待**;
  格子一空就**自动续出**,订单不会丢。所以**自家单位堵自家基地会阻塞自己的产线**——这是堵点
  战术的自限成本,不是 bug。
- **基地易主**时,该基地队列取消并**全额退款给原主**;原主已淘汰(基地回归中立)时**不退款**。

## 5. 占领

每个可占领点位(基地、资源点)有**属主**(可为中立)和一条**占领轨道**;轨道上记着**进度属主**与**累积进度**。
占领是**位置触发**的被动结算,不是一个动作。

- **点位是单格,同一时刻至多一个驱动者**。驱动者 = **站在点位格上**的那个单位所属的方,占领进度只由它推进。
- **站上去才驱动**:单位**站在点位格上**即开始推进;累积到 `captureTicks`(见 §10 数值表)后**所有权易主,
  进度清零**。
- **全兵种一致**:占领速度与兵种无关,农民不加速——农民的价值只在经济与堵点(见 §6.1)。
- **驱动者与属主同阵营**:进度**保留不动**(不清、不增)。自家单位站在自家点位上因此不推进任何东西,
  只是一个合法占位——这正是**堵点战术**:敌方要踩点,必须先消灭这个单位(单位可被攻击,基地不可)。
- **驱动者与属主不同**:新驱动者与轨道上的**进度属主不是同一个方**时,进度**从 1 重新起算**(转轨重计,
  **无侵蚀**——旧进度不折算、不保留);进度属主就是新驱动者时,进度**加一**。
- **无人站立**:进度**保留不动,不衰减**。占领不是「离开就清零」,跑开再回来接着算。
- **占领不耗资源**:踩点、堵点都不花钱,所以**经济死亡不等于出局**(见 §4.3)。

**标错位置的代价是静默的**。占领**没有动作函数**——`api.md` 的动作表里只有 `move` / `moveTo` /
`attack` / `harvest` / `transfer` / `spawnUnit`,没有任何一个是「占领」。占领只能靠 `moveTo` 把单位
**送到点位格坐标**上被动触发;把单位送到**相邻格**上什么都不会发生:**不累积、也不衰减、不产生任何
错误码**(`api.md` 的错误码表里没有任何一个是占领专用码,所以「没报错」不等于「占上了」)。唯一的
自证办法是读快照里的点位字段 `site.progressOwner` 与 `site.progress`,确认**驱动方是自己**。目标格本轮被
别人占着时,那次 `moveTo` 意图失败(单格裁决,见 §3),单位原地——它同样不会报错。

**一个点位格上同时有两个驱动者时怎么判**:正常路径下不会有这种情况——同一 tick 两个单位抢一格,由 §3 的
单格裁决判掉一个,**单格单单位**。唯一的例外是**开局**:地图数据若声明了两个落在同一格的初始单位,
那次摆放绕过了移动裁决;此时引擎按**单位数值 id 升序取第一个**(即数值 id 最小者所属的方)作驱动者。
这一条是**复述引擎已有行为**(`packages/engine/src/processor/capture.ts` 的 `captureDriverAt`),不是本节
新立的机制。

示例(3×3 坐标系,无地图假设;中立点位落在中心格,`captureTicks` 见 §10 数值表):

- 站上去才算:A 的单位 `moveTo` 到点位中心格 (1,1) 并停在那里 → 进度逐 tick 累积,达 `captureTicks` 后
  该点位易主给 A、进度清零。
- 站旁边不算:A 的单位 `moveTo` 到点位的相邻格 (0,1) 就停手 → 进度**始终为 0**、没有驱动方,
  不报错、不累积,也不衰减。
- 换驱动者:A 的单位累积到 3 后离开 (1,1),B 的单位踩上 (1,1) → 进度**从 1 重新起算**(进度属主换成 B,
  无侵蚀);B 站够 `captureTicks` 就易主给 B。
- 人走进度在:A 的单位累积到 3 后离开 (1,1) → 进度**停在 3**,不衰减;A 回来就接着从 3 往上算。

## 6. 战斗

### 6.1 兵种定位与设计约束

四种固定兵种,不可拼装。本节只说**每个兵种为什么长这样**;造价、生命、伤害、射程、速度、生产耗时
这六个取值一律见 §10 数值表的兵种属性表,本节一个字也不复述。下面的「约束」是**取值必须同时
满足的关系**,是给调参者的判据,不是脚本运行时要遵守或要检验的东西——脚本只管按 §10 的取值
写就行。

- **农民**(`worker`):经济与堵点。采集、携带、交付,**无攻击能力**。它是全图最脆弱也最高价值的
  目标,所以护矿是常态、敌方切农是最廉价的打击。它不加速任何机制,它的价值只在经济与堵点。
- **近战**(`melee`):正面战力与抗线的**性价比标杆**,射程只有相邻一格。要求:等成本的站桩对拼
  里它打得过远程与骑兵,且它的「每造价生命」与「每造价伤害」都是全兵种最高——使「数量 × 抗线」
  成为正面主策略,把战术差异让给机动与射程。
- **远程**(`ranged`):**阵地输出**,射程超出相邻一格且不随距离衰减,靠纵深与保护发挥。要求:
  近战贴脸后很快就能把它打死(它的生存期短到不足以当通用兵种),输出必须靠保护与纵深换来。
- **骑兵**(`cavalry`):**高机动**——袭扰、抢点、切农、直插后方。射程只有相邻一格,速度是其余
  兵种的两倍,造价不低于近战的两倍。要求:等成本的站桩对拼里它打不过近战与远程——**它的价值
  全部来自速度,不值在正面**,必须贵到不能当主力。

### 6.2 战斗结算

- **同 tick 的全部攻击同时结算**(批处理,没有先手秒杀):先一次性算出本 tick 的全部伤害,再统一
  扣血。**攻击者本 tick 死亡不影响它的攻击生效**。
- 伤害进**单一血池**扣减,归零即死;无护甲、无技能、无冷却。是否命中没有任何随机成分(对局内
  没有随机源,见 §9)。
- **目标不可为基地**(基地不可摧毁)。`attack` 的目标必须是敌方单位,**任意兵种都可被攻击,
  含农民**。**无攻击能力单位**(农民)的 `attack` 无效:丢弃,不扣资源、不计异常。
- 伤害、射程、速度的取值见 §10 数值表的兵种属性表。

## 7. 胜利、淘汰与超时名次(判定顺序即规范)

对局不会一路打满上限:先说终局大致长什么样(它决定你该在哪一段做取舍),再给规范性的判定顺序与名次。

### 7.1 终局形态:它是条件,不是日程

- **决战是收束,不是预定时刻**:它出现在领先格局定型之后,典型落在整局的三分之二前后,强弱悬殊时更早。
  没有任何一个 tick 是"到点必开决战"的闸门——时间是条件,不是目标。
- **终局压力来自淘汰与领土分结算**:谁被先清出局、下架时手上还剩多少点位与单位,构成最后一轮的压力来源。
  **资源枯竭不是典型终局的必经阶段**:它只在把经济拉到极端剖面时才出现。每个资源点储量有限(见 §4.1),
  把储量采空是一道可能碰到的天花板,不是节奏的一部分——别把"拖到矿采光"当作一条取胜路线去设计。
- 下面两条是**读法,不是策略指令**(证据是标定跑的实测方向,不带数字;数字与口径留在规则侧记录里):

  - **近战最强,不等于只爆近战**。近战是等成本对拼里的性价比标杆,这是它的设计定位(§6.1),不是"唯一解"的
    判据。实测方向上:四份盲写脚本里有两份收敛到爆兵压制;唯一会造骑兵的那份成绩更差,但那处差距与模型档位、
    严谨度完全混淆,归因不成立;机制层的受控对照显示,在"守点 + 抢中立点"这种打法下造骑兵是劣势——它把兵力
    送去切农、放弃了守点。所以能得出的只有一句:**骑兵的价值全部来自速度,会玩速度才造它**。这**不**等于
    "近战爆兵已被证实是全场景唯一解",那条仍是未闭合的缺口。
  - **超时名次不要照着反推策略**。名次由领土分算,并不因为你在最后阶段囤兵而变便宜。实测方向上:临近终局时
    各方的单位数没有出现净增长,也没有出现一次性丢掉大批单位的情况——**"屯兵 / 卖兵等超时"这个动机实际
    并不存在**。别为了名次去囤兵或弃兵。

  这两条的证据与口径见 gdd §8 的规则侧记录(记录 #7 资源枯竭的定位、#9 终局形态的已知边界、#10 骑兵)。那批数字出自
  标定环的一次标定跑批,是**证据不是契约**;本节写下来的是它的方向,不替它背书任何具体数值。
  **口径**:那些数字出自草案契约下盲写的四份脚本,与终稿契约下重跑的三舱
  (`.scratch/rules-landing/blind/verdict-2026-10-04.md`)**不可互比**——契约形态、移动层与错误处理三层都变了。

### 7.2 胜利与淘汰(判定顺序即规范)

- **主胜利条件**:单一玩家控制地图上全部点位(含敌方主基地)的**瞬间**获胜,无需持续任何时长。
- **捷径条款**:其余三方全部被淘汰时,仅剩的玩家立即获胜(避免清场阶段的空转)。
- **淘汰条件**:玩家**同时**没有任何单位且没有任何基地。部队尚存就仍有翻盘可能——被夺家之后靠残兵反夺基地是
  刻意保留的空间,所以被抢光矿不等于出局(经济死亡的边界见 §4.3)。
- 被淘汰玩家名下残余的点位**全部回归中立**。
- **每 tick 的判定顺序(判定即规范)**:先判淘汰 → 被淘汰者点位回归中立 → 再判全点位归属 → 最后判捷径条款
  (兜底)。回归中立可能破坏"全点位"条件时,由捷径条款接住。

### 7.3 超时与名次

- **超时不判负**:tick 达到 `tickLimit`(见 §10 数值表)时走名次结算,不由超时本身判负。

```
1) 获胜者(胜利或捷径条款)为第 1 名
2) 其余参赛者按存活状态分层:存活者排在已淘汰者之前
3) 层内:存活者按领土分降序;已淘汰者按淘汰时间倒序(后出局者名次更前)
4) 仍完全相同 → 并列同名次
```

```
领土分 = baseScore × 控制基地数 + resourceScore × 控制资源点数
       + ⌊Σ存活单位造价 ÷ unitCostDivisor⌋
```

- 三项权重(`baseScore`、`resourceScore`、`unitCostDivisor`)的取值见 §10 数值表,本节不复述。
- 最后一项计入你**所有**存活单位的造价总和,下称「存活单位总造价分」——不分兵种,农民也在内。
- 并列名次怎么进赛季记分是引擎之外的事(见 hld《排名》),本契约只保证名次由上面这个分层算出。

## 8. 异常与出局(披露分级)

这一节按三层写:**必知**的是会改变你脚本行为的机制事实;**建议知**的是不必依赖、但知道更稳的机制事实;
**不披露**的是引擎如何计量预算的实现细节——那一层只留一条结论。分层的意义是:必知层你可以按它写脚本,
建议知层你可以按它做假设,不披露层**不是**给你用的边界。

### 8.1 必知:两句,后果明确

1. **某一 tick 里你的脚本抛异常(包括调用了契约里不存在的 API),或超出本 tick 的计算预算** → 该 tick 你在
   `loop()` 里提交的全部意图**全部丢弃**(你的单位原地待命),并给该方**记一次异常**。这件事只影响你一方,
   不影响其他三方与引擎。累计异常数跨 tick 累加,快照里能读到当前值。与之相对,**意图被判无效而丢弃的**
   (重复下单、无效攻击,见 §4.4 与 §6.2)**不计异常**——被丢弃和被计异常是两件事。
2. **累计异常达到 `exceptionTickLimit`(见 §10 数值表)** → 该方**判负出局**:按 §7.2 的淘汰规则处理,名下点位
   全部回归中立,判定顺序照 §7.2 那一串走。

### 8.2 建议知:失控不等于清零

- **异常与超预算都不清你的模块级记忆,也不重建脚本环境**:模块级变量保留,下一个 tick 你从原处继续写。
  一次手滑(比如除零、访问了不存在的东西)不会把你整局的长期规划抹掉。
- **只有引擎级故障会重建脚本环境**,而它是极罕见、脚本不可触发的;真发生时模块级记忆清零——那一刻起你就是一个
  刚被载入的新脚本。
- **异常计数随对局状态持久化,重建或中断后继续累计,不清零**。否则"反复失控"就能绕开淘汰这条线。
- **耗时本身不参与判罚**:墙钟只作观测,不因为你写得慢而判你负。真的把整场卡死时,那一作会作废该场、按重跑 /
  剔除处理,不算你输——所以别把"跑不完"当成一种战术。

### 8.3 不披露:预算怎么计量,只留一条结论

- **每 tick 有计算预算上限,超限视同异常**(后果与 §8.1 第一条同轨)。上限的取值见 §10 数值表。
- 引擎**如何计量**这份预算——计数的粒度、内存读数的口径——**不在本契约披露**。这一层的存在只有一个用处:
  提醒你别把任何实现细节当成可依赖的边界来设计脚本。按 §10 给出的上限留足余量,然后把精力放在规则本身上。

## 9. 确定性约束(禁止 / 保证对照)

这一节只回答一个问题:**「我这样写,引擎会裁成什么?」**。它答的是**引擎裁决结果**,不答「这个函数
能不能调」——后者是运行时可见面的事,家在 [`api.md`](./api.md)。两栏按问题的类型切:

| 禁令类别 | 家 | 判据 |
| --- | --- | --- |
| 运行时**可见面**:某个名字能不能出现在脚本里、某个函数能不能调、值能不能跨 tick 存 | [`api.md`](./api.md) §1、§2.3 | 问的是**语法 / 可见面 / 接口** |
| 引擎**裁决结果**:同一格谁先动、离开的点位进度算不算、异常丢多少意图 | **本节** | 问的是**引擎怎么裁、结果一不一致** |

`api.md` 已经写全的可见面禁令,本节**一条不抄**,只留指针:脚本形态(模块语法 / 动态求值 / 裸脚本)、
非确定源与宿主桥、座位自认、每单位每 tick 一条意图、跨 tick 只存数值(不缓存对象引用与查询结果)在
[`api.md`](./api.md) §1,错误判别不许用 `typeof` / 真值去猜在 [`api.md`](./api.md) §2.3。

AC3 说的「可据此规避不确定行为」指的就是下面这一类:你规避的不是一个不可用的函数,而是一个**没有裁决
保证的依赖**——写法本身能跑,但引擎按另一套规则裁它,或结果取决于你控制不了的东西。下表把这类依赖
逐条拆成两栏:**禁止** = 这样依赖会踩到不受保证的行为;**保证** = 引擎的裁决规则固定、逐 tick 可复算,
可以照它设计。每行带 § 指针。

| 你可能会依赖的东西 | 禁止(不受保证,别这么写) | 保证(裁决固定,可照它设计) | 见 |
| --- | --- | --- | --- |
| 同一格两个单位谁进得去 | 假定「先提交的先动」「后来的顶掉先来的」「友军之间可以穿行」 | 一轮只按轮次起点的占位裁决:同格竞争算轮转优先值 `(tick + playerIndex) mod 4`,值大者胜、落败者原地不动也不试次优目标;交换与链式各自独立,没有链式让路,也没有环形追逐 | §3 |
| 谁先手 | 赌某个座位永远先手;按「我先手 / 我后手」写两套分支;按座位号补偿 | 优先权随 tick 轮转,座位间只有**比例**偏置、没有永远后手;同一份写法在任何座位都按同一条规则裁 | §3.1 |
| 占领进度会不会动 | 假定「离开点位进度就清零 / 衰减」;假定「自家单位站自家点位会推进或清空进度」 | 驱动者与属主同阵营 → 进度保留不动;无人站立 → 保留不动、不衰减;换驱动者才从 1 重算 | §5 |
| 同 tick 的攻击顺序 | 假定「先出手的先生效」「同 tick 有先手秒杀」「命中带随机」 | 同 tick 全部攻击**同时结算**(先算总伤害再统一扣血),攻击者本 tick 死亡不影响它的攻击生效;对局内**无随机源**,结果只由状态与 tick 决定 | §6.2 |
| 胜负判定链与名次 | 假定「淘汰」与「全点位归属」可以换序;照名次反推策略;假定超时本身判负 | 每 tick 判定顺序固定:淘汰 → 回归中立 → 全点位归属 → 捷径条款(兜底);超时不判负,名次按固定分层式算(`tickLimit` 见 §10 数值表) | §7.2 §7.3 |
| 失控一次丢多少 | 假定「抛一次异常只丢那一条意图」;假定「`try/catch` 吞掉就零痕迹」;假定「一次失控会清掉跨 tick 记忆」 | 抛异常或超预算 → 本 tick 该方**全部**意图丢弃 + 记一次异常(只影响本方);被丢弃 ≠ 被计异常;跨 tick 记忆保留;累计达 `exceptionTickLimit`(见 §10 数值表)判负出局、点位回归中立 | §8.1 §8.2 |
| 写得慢会不会被判负 | 假定「耗时参与胜负裁决」「把整场卡死算你输」 | 墙钟**只观测**、不判罚;硬超时只作废该场(按重跑 / 剔除处理),不算你输——别把「跑不完」当战术 | §8.2 |
| 回放里能读到什么 | 依赖只进观测、不进回放的读数(例如单 tick 耗时) | 回放收的是对局状态与事件;只观测的读数(墙钟软限)写进观测、不进回放 | §8.2 §10 数值表 |
