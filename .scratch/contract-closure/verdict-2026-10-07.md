## 2. 逐舱判读(只读三份源码)

三份入场产物 = `benchmarks/` 的 `script.ts`(源码)与 `script.js`(编译产物),由本轮三舱产出经票 04 替换。

- **cell-a —— 读出来是「留 2 个农民的近战全场扑敌」**。生产先读 `producing`,空才下单:农民下限
  `desiredWorkers = 2`,其余全投 `melee`。农民满载(`carrying >= 20`)时在相邻己方基地 `transfer`,
  否则去最近**己方**资源点,相邻(`getRange <= 1`)就 `harvest`,再远就 `moveTo`。战斗单位取**全场最近的
  敌方单位**,射程内 `attack`、射程外 `moveTo` 追;全场无敌人时压向最近**非己方点位**并 `moveTo` 到点位格
  坐标(站上去驱动占领)。每单位每 tick 一条单位级意图。
- **cell-b —— 读出来是「5 农 + 近战的扩张运营,占点靠站上点位格」**。生产目标 `workerCap = 5`(tick<250)
  或 3,之后转 `melee`;先读 `producing`。农民满载交付 → 有己方资源点就采 → **没有可采的己方矿就把一个
  工人标为 capturer 去最近的中立资源点**,`moveTo` 到**点位格坐标**,已在点位格上就本 tick 不发意图
  (让进度推进)。战斗单位射程内 `attack`,否则追最近敌方单位。
- **cell-c —— 读出来是「零农民纯近战占点」**。只造 `melee`,每个空产线一单,余额 < 8 停手;**全程不造
  农民、不调 `harvest`、不调 `transfer`**。单位射程内有敌人就 `attack`,否则用 `claimed[]` 认领一个
  未占点位(自家被驱动回防 > 中立 > 敌方),`moveTo` 到**点位格坐标**,已在点位格上就原地驻守
  (`if (u.x === tgtX[pick] && u.y === tgtY[pick]) continue;`)。市场数据确认它开局 16 资源出 2 个近战后归零,
  按 rules §4.3 经济死亡且不可逆,靠占点与残兵继续——**这是契约 §4.3 写明的合法打法**。

**区分度(定性)**:三份确实是三种打法(留经济底线的近战扑杀 / 有链条的扩张运营 / 零经济的纯占点),
不是同一份脚本换个名字。A 与 C 的内核仍有重合(都只造近战、都把战斗单位往点位方向赶),真正的分野
在「留不留农民」;这与旧四舱那轮「两份收敛到爆兵压制」的现象同向。

## 3. 上一轮缺口的消解(实证引用)

**上一轮(`.scratch/rules-landing/blind/verdict-2026-10-04.md`)三舱各自猜出互斥占领机制,是本轮
「缺口已消解」的实证来源。** 该判读 §4 记着:三舱全部撞上 `rules.md` §5 的占位原文,然后各自猜——
a 舱 `moveTo` 到**点位格坐标**上(假设能站上去),b / c 两舱走到**相邻格**后停手(假设站相邻即累积);
c 舱整份「占点不采集」策略建立在这个猜测上。该判读 §7.1 明写「三舱全部撞上、全部自造机制、且造出
两种互斥的版本……这不是措辞问题,是缺一节机制」;§7.3 明写「本轮没有触发任何一轮校验回喂……『≤5 轮回喂』
这条机制本轮根本没被走到过一次」。

**本轮消解**:§5 落库后,三舱**没有任何一舱再猜机制**。三份入场产物都按契约写「站上去驱动」:
A 与 C 的源码里有 `moveTo(...site.x, site.y)` + 「已在点位格上就原地」分支,B 的 capturer 注释
「已在 site 上时不发任何意图,让 capture 进度推进」。结论:**缺的是契约已补,不是模型读错**——
上一轮那两种互斥猜法里正确的是「站上去」,本轮三舱不必猜即可读到。

## 4. 三舱暴露出的契约歧义清单

逐条收 `/tmp/model-war-notes/contract-closure/ambiguities.md`(A 舱 7 条 + B/C 无新增 + 一条工具面发现)。

### A 舱(`commandcode/deepseek/deepseek-v4.1-flash`,爆兵压制)暴露的 7 条

1. **`getObjectsByType("player")` 的数组次序没被契约钉死**。`api.md` §2.2 说「每行按 `index` 编号;
   你自己的那一行是 `index === getMyIndex()`」,但示例与模型都写 `players[me]`(按下标取),契约没有
   一句保证返回数组按 `index` 升序。模型思考里明确纠结过,最终照示例用了 `players[me]`。
2. **采集是「被动」还是「意图」没裁定**。`rules.md` §4.1 写「农民站在己方资源点的相邻格上**即开采**」
   (像自动),而 `api.md` 动作表又列了 `harvest()`。模型直接问「why harvest action … maybe redundant?」,
   最终每 tick 显式调 `harvest`。契约没说必须显式提交。
3. **「相邻格」是否含「站在点位上(距离 0)」没写**。模型两处都写 `getRange(...) <= 1`(含 0),
   `moveTo` 直接指向资源点/基地精确坐标。若「相邻」严格等于 Chebyshev 距离 1,站点位格上再
   `harvest`/`transfer` 是否有效没有契约依据。
4. **类型名算不算「可见面」没写**。PROMPT 说「只调 `api.md` 第 3 节 API 表里那些名字」,而
   `Unit`/`Site`/`Player`/`UnitType` 只在快照形状与类型面(`d.ts`)、不在 API 表。模型不确定引用它们会
   不会被判违规,自造 `type UnitView`/`SiteView` 绕开。契约没说类型标注里的名字不受白名单约束。
5. **§1 是 TODO,而正文有指针指进 §1**。`rules.md` §4.1 资源点布局写「具体布局与数量由地图数据声明,
   **见 §1**」,可 §1 明确 out-of-scope。模型读不到开局单位构成/地图尺寸/初始资源点数量,只能「assume
   至少一个农民」。这是契约里唯一一处「指针指向一个明确不写的节」。
6. **`spawnUnit` 下单扣款在本 tick 内是否立即可见没写**。模型思考:「ambiguous whether resources
   deduction is immediately visible. To be safe, track budget locally」,自己维护本地预算账。§4.4 只说
   「下单即扣款」,没说同 tick 内后续读 `players[].resources` / 再下单能否看到扣减。
7. **预算取值仍「未定」**:`scriptSizeLimit` / `apiCallTickLimit` / `eventTickLimit` /
   `memoryTickCeiling` / `exceptionTickLimit`,模型据此主动收敛 API 调用(与旧轮同现象)。

### B / C 舱(票 04)补充

- **B / C 两舱未新增契约歧义**:§5 落库后都正确读出「站上去才驱动 / 站相邻静默无效果 / 无占领动作
  函数」,`getRange` 是 Chebyshev、「相邻 = 距离 1」、`Player.index` / `progressOwner = -1` 都被契约写清。
- **一条工具面(非契约)发现**:盲写 prompt 只说「静态校验错误会回喂」,没告诉作者编译面的严格档位
  (`strict` + `noUncheckedIndexedAccess`)。C 初版过了契约静态校验器,却撞在严格 `tsc` 的 `TS2345` 上,
  而 `check:bench` 把 `TS2345` 归入 `unexpected`(另两类 `implicit-any` / `possibly-undefined` 才放行)。
  写得越精确类型化的脚本反而越容易踩。建议:要么让盲写 prompt 明示编译档位,要么把 `TS2345` 归入
  `possibly-undefined` 同档(二者同根:`noUncheckedIndexedAccess`)。
- **C 舱编译面回喂 1 轮**(非契约静态校验回喂):初版契约静态校验 0 轮通过,但严格 tsc 报 3 处 `TS2345`,
  同一会话 `pi --continue` 续写把下标取值加非空断言 `!`(纯类型层,行为零改动),终稿编译干净。

  占位措辞(已在票 01/02 完成)。
