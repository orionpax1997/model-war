throwaway 原型,不进 packages/;结论只回答"哪个形态进 v0",bundle 打包方式细节留给实现期。

结论与建议

建议:保留 hld §4.5 的 runtime bundle 设计,不回退逐函数注入。(§2.2.2 的回退路径照旧留档,本原型不要求删除。)

  • 交叉点 ≈24–210 次调用/tick(随快照粒度 2KB→64KB 上移),而中局脚本遍历对象/逐单位调度的现实密度是数百次/tick——bundle 省 1.25–6 倍;病态负载(寻路轰炸)下省 45–230 倍。
  • 注入形态的成本随玩家野心线性无界:实测 1 万次调用 = 10.7ms/tick(单方!),对 NFR-3 是结构性风险;bundle 形态边界成本固定、只由快照粒度决定,性能面与 §5.3 的 API 计数判罚面解耦。
  • 优劣不对称:输的小、赢的大。注入只在交叉点以下的稀疏区更省,那里差额是几 µs~几十 µs/tick(四方合计 ≲0.25ms),对 NFR-3 无感;而稠密区/滥用区注入的劣势上不封顶(单方每 tick 毫秒级)。不值得为小赢换形态、把大输请进门。
  • 实测单价是"数字返回"的最便宜注入调用(0.85µs/次);真实查询返回对象/数组更贵,注入形态的实际曲线只会更差。

盲区(不在本对比口径,标定 NFR-3 时须补):

  • host 侧快照序列化/深拷贝:bundle 形态每 tick 每方要做一次(回放路径本来也序列化状态,粗判不翻转结论,但单场墙钟预算里是真实成本)。
  • VM 内执行成本差:bundle 形态的查询与 findPath(A*)在 VM 内用 QuickJS 解释执行,比宿主 V8 慢——寻路轰炸下成本从"边界"转移到"VM 计算",由指令计数 + API 计数裁决(hld §4.7/§5.3 的既定设计),不属于形态对比。
  • 模型是 9+2 个 µs 级实测点的线性外推,噪声 ±3–4%(1KB 档实测点本身离散 11.1–24.7µs)。
