# 05: 错误码全定与 API / 常量表区块

**What to build:** 终稿 API 面里最容易漂的那一类被钉死：**每个错误码都有名字和一句触发条件**，并且错误码集合与「丢弃 vs 异常」对照表逐条对齐。

草案里只有「资源不足」那一码在来源文档被点名过，其余是按界检查职能反推的候选码。终稿要么全定、要么全删——**半截的码表比没有码表更坏**，因为模型会当真。所以本票的产物是：一张完整的码表 + 与它逐条对齐的对照表 + 出成区块的 API 表与常量表。

同时把草案常量表标题下的三种东西拆开：**类型名**（归类型面，不进这张生成表）、**错误码字符串**（进）、**数值**（归规则集文件那条链，不进）。

**Blocked by:** 02（符号表判据与回填）、03（区块形态）

**Status:** ready-for-agent

- [ ] 错误码**全定**：每个码有名字 + 一句触发条件；码的集合与符号表里那一份**由同一次书写产生**，不是两处对齐
- [ ] 每个错误码**标明它落在「丢弃」还是「异常」**——这两类的后果不同（一个丢单条、一个丢整 tick 且计一次），模型据此决定要不要兜
- [ ] 「丢弃 vs 异常」对照表**重写一遍**：它原本按旧的错误返回形态写，现在错误码形态变了，表不动就是错的
- [ ] **「资金不足无效」与「`loop()` 抛异常」两行必须能在表里被区分**，这是那轮措辞裁决明确点名要保住的一组对照
- [ ] API 表与常量表出成区块：API 表一栏签名、一栏一句语义；常量表分**类型名**（不进生成表）与**错误码**（进）
- [ ] 收进生成表的每个 API 名字都在符号表里——落成机器断言（文档多写一个名字即红）。这是「同源」的可执行证据
- [ ] 符号表里有、文档里没有的名字也要报——它是「文档漏披露了一个符号」，模型会当它不存在
