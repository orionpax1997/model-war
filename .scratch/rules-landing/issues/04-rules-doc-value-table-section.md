# 04: 规则文档的数值表区块

**What to build:** 规则文档里那张数值表第一次**由规则集文件生成**。规则侧定案的 21 个键、以及派生出来的兵种表，在这里对模型呈现成一张可读的表；而 8 个预算类键**渲染成「未定」而不是 0**。

这一票是「取值真源只有一个家」这句话的兑现点：文档里的数字不再是人抄的，改真源即改文档，不改真源而改文档会被漂移检查判红。

**Blocked by:** 01（规则集取值落库）、03（区块形态）

**Status:** resolved

- [x] 数值表成成区块挂进规则文档；**同一份内容生成两次**（规则文档里的数值表与 API 文档里的数值常量表引同一处真源），不是两处各自维护
- [x] 13 个定稿键渲染成**数字**；8 个预算键渲染成「未定」
- [x] 「未定」的判据是键身上的**状态标记**，不是「值是不是 0」——`0` 在别的键上完全可能是真取值，判据写成 `value === 0` 就会把两者混成一件
- [x] 兵种表（造价 / 生命 / 伤害 / 射程 / 速度 / 生产耗时）由四兵种键生成，**生产耗时那一列是按公式算的**，不是抄进去的第二份
- [x] 内存软阈**出现在文档的表里**（它是推导展示项，模型该看到它），但**不出现在规则集文件里**——两者的分工在文档上一句话说清
- [x] 漂移检查覆盖这个区块：改规则集文件里的值而不重跑生成器 → 判红；手改区块正文 → 判红
- [x] 文档里凡是引用某个键的地方，改键名即改文档——**不留下手抄的第二份**
## Answer

**一个生产函数、两件生成物**：`packages/tools/src/generate/rules-value-table.ts` 只产出一段字节，
`rulesValueTable`（落 `docs/rules-v1/rules.md`）与 `apiValueTable`（落 `docs/rules-v1/api.md`）
交付它的同一份内容，差别只在落点与两行定界标记。两份文档逐字节相同——两处手抄的后果是模型照着
一张过期的表设计脚本，而分叉只是时间问题。

**真源是两份，合起来才够渲染一张表**：取值在 `rulesets/v1.json`，键序 / 量纲 / 标定状态 / 一句说明
在 `packages/schema/src/ruleset-keys.ts`。键清单给不了值，取值文件给不了「这个键是什么、是不是未定」。

**生产函数读盘，这是票面那个问题的答案**：漂移检查与生成器共用同一个生产函数，所以检查读到的就是
真源的现状——改了取值不重跑生成器，检查当场读到新值、文档里是旧值，判红。不读盘的话①判定只剩
「文档被手改」那一半，而「改真源即改文档」就没有机器保证。既有两件的真源是 `.ts`，走
`@model-war/schema` 的编译产物；本件的真源是数据文件，直接读。分界线是**真源是代码还是数据**。
为此 `artifact.ts` 里「生产函数纯函数，不碰文件系统」那句改了口径（改成「不看时钟、不写文件」，
并加了「读真源不在禁止之列」那段头注）——不改就是让契约文件与实现各说一套。

**「未定」只由 `calibration.state` 决定**。表里 17 行整数值键：9 个定稿键渲染成数字、8 个预算键渲染成
「未定」；`worker.damage` 那一格的 `0` 是真取值，与「未定」在同一次渲染里并存——判据写成
`value === 0` 就会把这两件事混成一件。内存软阈跟着它依赖的 `memoryTickCeiling` 走：那个键还是未定值，
软阈也渲染成「未定」，而不是把系数乘占位算出一个看着像真的 `0`。

**生产耗时一列现算**：`⌈cost × SPAWN_TICKS_COEFFICIENT⌉`，系数取自真源包，不抄取值文件里双存的第二份；
两者不等时生成器非零退出并说清是哪一条键（表里渲染的是式子算出来的那个，所以这一列与式子永不脱钩）。
兵种表六列的字段名在本文件里只有一个家（`UNIT_STAT_COLUMNS`），表头、取值与形状校验三处都从它推。

### 逐条对着验收条款

| 条款 | 落点 | 怎么验的 |
|---|---|---|
| 数值表成区块、同一份内容生成两次 | `rules-value-table.ts` 的 `sectionOf` + `registry.ts` 加的两行；两份文档里各一段 `generated:*-value-table` 标记 | 门禁自测：改取值不重跑 → 判红，且报告**同时**点名两份文档（少一份就是有一份挂的不是这份真源） |
| 13 个定稿键渲染成数字、8 个预算键渲染成「未定」 | `parameterTable` 的 `calibration.state` 分支 | 表内实拍：9 行数字 + 8 行「未定」；`worker.damage` 的 `0` 与「未定」同表并存 |
| 「未定」判据是状态标记不是值是不是 0 | 同上分支条件（`entry.calibration.state === "undetermined"`） | 真源包里 `worker.damage = 0` 渲染成 `0`，正是「写成 `value === 0` 就会混掉」那条的反例 |
| 兵种表由四兵种键生成、生产耗时按公式算 | `unitTable` + `spawnTicksOf`（`Math.ceil(cost × SPAWN_TICKS_COEFFICIENT)`） | 表内实拍 4×6 格，生产耗时 2/4/6/8；`spawnTicksOf` 与文件里的双存不等时生成器非零退出 |
| 内存软阈进表不进键清单，文档上一句话说清 | `derivedTable` 的一行 + `rules.md` §10 表后说明第二条 | `rulesets/v1.json` 里没有这一格（键清单 21 个键不含它），表里有它；说明那句话在文档里 |
| 漂移检查覆盖这个区块（两条红） | `check:drift` 的①判定对区块形态（票 03 的机械） | 门禁自测两条：改 `rulesets/v1.json` 不重跑 → 红；手改表里一格 → 红；两条都「红 → 还原 → 绿」 |
| 不留下手抄的第二份 | 散文只写键名与机制，数字全在表里；两份文档的表出自同一函数 | `rules.md` §9 之前所有 `TODO(→…)` 骨架行里没有一个数字；表后说明里的「8 个预算键」也改成「表里取值渲染成「未定」的键」 |

### 票面之外的几条判断

1. **`docs/rules-v1/rules.md` 只立骨架，不搬草案散文**。十节标题照草案的编号与标题，正文是
   `TODO(→ 机制契约)` / `TODO(→ 异常披露与终局措辞)`。理由有二：票 09/10 要改的是这些散文，
   提前搬一版等于让它们再改一遍；而 `resourcePerSite` 那类取值在草案里是旧的（125），搬进来就是
   手抄的第二份，正是本票要消灭的东西。
2. **`api.md` 只放一个数值区块 + 一张「尚未落定的章节」表**，不写 API 表、常量表与错误码表——
   那是票 05/07/08 的活。表里点明「三处分工写在 `rules.md` §10 的表后说明里」，所以同一件事
   在两份文档里各有一句指路的话，而内容只有一个家。
3. **取值文件读进来的形状由生产函数自己收**：缺键、兵种键写成整数、六字段少一个，都在生成时非零退出
   并点名是哪个键，不渲染一张缺格的表（缺格比没有表更坏）。`JSON.parse` 的 `any` 在边界上**只断言一次**
   （到真源包自己的 `Ruleset` 类型，不是手抄的结构），之后全走取值口。
4. **散文手改会让 `check:drift` 变红，但红的原因是「未提交」不是「散文漂移」**——票 03 的第 5 条
   已经点过这个边界。门禁自测里专门把这一形态钉住：手改散文时内容判定必须沉默（报告不含
   「区块与真源不一致」），而退出码仍是 1。写这条是因为它是「同一份文件里的两种所有权」最容易
   被后来者误读成「整份锁死」的地方。
5. **`repoRoot` 没有抽公共模块**：新文件用 `resolve(import.meta.dirname, "../../../..")` 直接算出
   取值文件路径。抽它要改生成器入口与漂移门禁两个骨架文件，而「新增生成物只加一行、不动骨架」
   正是注册表那条纪律的证据；为一行路径去动骨架不划算。
6. **`docs/hld.md` §2.2.5 的「文档生成」那一行补齐**（票 06 的先例）：原文只说数值表在 `rules.md`，
   而实际是两份文档各挂一份同一个生产函数的产物。不补的话后来者可能把 `api.md` 那份当重复而删掉——
   那正是「同一份内容生成两次」最典型的腐化方式。
7. **`rulesets/.gitkeep` 与 `docs/rules-v1/.gitkeep` 都没删**：票 01 落了 `rulesets/v1.json` 之后
   那个 `.gitkeep` 也还在，本票沿用同一处置（清理是票 15 的事）。
