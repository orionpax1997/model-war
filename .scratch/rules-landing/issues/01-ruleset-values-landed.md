# 01: 规则集取值落库

**What to build:** `rulesets/v1.json` 第一次有了内容——21 个键，13 个定稿键取标定环的终值，8 个预算键取未定值占位。它必须能被真源包现有的 ajv 校验通路收下，版本断言与派生量断言全过，于是「规则集有取值」这件事第一次变成机器可读的事实，而不是散落在一张一次性 markdown 表里的抄本。

这一步做完之后，标定环那张交接单里「取值真源是 `rulesets/v1.json`」这句话才第一次指向一个真实存在的文件。

**Blocked by:** None (can start immediately)

**Status:** resolved

- [x] 21 个键一个不少，键名与真源包的键清单逐字一致；键数不对时**校验器拒收**而不是接受一份缺键的规则集
- [x] 13 个定稿键取交接单 §1 的终值；派生规则（生产耗时 = 造价 × 0.5 上取整、满产烧钱率）**不作为独立键出现**，它们是公式
- [x] 8 个预算键取未定值占位，且**「未定」由键自己身上的状态标记**，不由「值是不是 0」推断
- [x] 内存软阈（硬判罚线的 0.8 倍）**不出现在文件里**，它是由另一个键推导出来的展示项
- [x] 开局资源点归属**不作为键**——它是地图侧的不变量，由地图声明与地图校验器断言
- [x] 读入端校验这条通路能跑通并给出带定位的诊断：**刻意不接进任何子命令的装载路径**（那个调用点随对局执行器落地），也不新增子命令
- [x] 用一条可执行的断言证明「这份文件里的键集 == 真源包的键清单」，两个方向都查（缺键、多键）
- [x] 记录事实并收口：`FR-10 AC2` 的「错配拒跑」与「读入端强制校验」**仍按尚未兑现记**，机制已定死、差的是接线，不是设计

## Answer

`rulesets/v1.json` 落库：21 个键，13 个定稿键逐字取标定环交接单 §1（`resourcePerSite` 是票 09 改值后的 **200**，不是草案里的 125），8 个预算键各取**该键自己标定的占位值**。不写版本字段——版本仍由文件名 / 目录名 / `RULESET_VERSION` 三处名字承担。

**新文件只有一个测试**：`apps/cli/src/ruleset-file.test.ts`（unit project，11 条）。它与 `apps/cli/src/validator.test.ts` 分开是因为断言对象不同：那边断纯函数「一段 JSON 值 → 接受/带诊断拒绝」，这边断**仓库里那一份文件**（读真文件，不重抄）。

- **键集两个方向都查**：键集断言比的是「文件里的键 vs 键清单」（不是两个常量互比——后者在文件落库前恒真）；缺键与多键各取四个名字现做现验，断言诊断的 **JSON 指针**指向那个键。
- **派生量与推导项**：改一个 `spawnTicks` 即在装载期被拒（`derived-spawn-ticks` @ `/worker/spawnTicks`）；满产烧钱率、内存软阈、派生系数、开局资源点归属各自断言**不是键**。
- **「未定」由标定状态判别**这条的反例就在文件内部：`worker.damage` 是一个**真的 0**，而它所在的键标着 `final`——判据若写成「值是 0 就渲染未定」，农民会被误标。
- **13 个定稿键另有一份交接单 §1 的抄本**（测试里的 `FINAL_VALUES`）。它存在的唯一理由是把「文件里的数 = 交接单的数」变成机器可判的；取值真源仍是 JSON 文件。做过 mutation check：把 `resourcePerSite` 写回 125、删掉 `carryLimit`、把 `worker.spawnTicks` 改成 3 —— 7 条用例当场红，还原后全绿。
- **不接进任何子命令、不新增子命令**，因此也**不进 `gates` project**：`gates` 断的是命令/门禁的退出码与报告文本，而这条通路刻意没有命令可断；断纯函数判决的用例属 `unit`，混进 `check` 的全量门禁才对。
- **FR-10 AC2 的兑现状态记在 `docs/hld.md` §2.2.5 那段**（它本来就是这个状态的家）：补一句「取值文件已落库并被单元用例读真文件校验过，但被校验过 ≠ 被装载时校验过，仍按尚未兑现记」。DAG 的基线表与「M1 交付物仍缺四件」那行留给 15 号票对账。
