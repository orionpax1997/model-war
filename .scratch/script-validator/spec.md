# 参赛脚本静态校验器

Status: ready-for-agent

## Problem Statement

M1 的真源已经落库,但**从「一份模型写好的 TS 文件」到「一份可以进沙箱执行的 JS 文件」这条路一步都还没走**。hld §6.2 列了六类静态校验规则,没有一条有实现;`packages/tools` 里唯一的静态校验是禁浮点门禁,而它跑在**仓库自身的引擎源码**上,不跑在参赛脚本上。于是这四件事同时为真:

1. **脚本能不能编译、能不能被载入,无人判定**。hld §2.2.2 已把入口契约定稿(单文件 script-mode TS、顶层 `function loop(): void`、不写 `export`/`import`),并有实测证明带 `export` 的产物在载入期直接取 `SyntaxError`——但没有任何东西在编译期就报出来。模型可以交一份根本载不进去的脚本,然后在生成管线的五轮迭代里反复改不对。
2. **「参赛脚本能用什么」这个问题只有一个不成文的答案**。C 刚把四张名单类数据的家搬进真源包(内置全局白名单、宿主桥前缀、禁列全局名、沙箱注入符号表),并明写「静态校验器一个名字都不许自己存」。但**没有消费者**,所以那句承诺现在只是一句注释。
3. **「校验器放行但运行时报未定义」在结构上还可能发生**。沙箱的隔离靠「不给」而非「拿掉」,引用一个不存在的名字在运行时只是普通 `ReferenceError`,而脚本可以 `try/catch` 吞掉它,宿主零痕迹。hld §5.2 的越权那一行明写「吞掉时 host 无感知,防线是静态禁令」——那条防线现在不存在。
4. **脚本体积上限没有判据**。hld §6.2 说它的作用是封「直线代码不计量、大循环体放大每格工作量」的控制流计数盲区,而它的取值在规则集文件里,**那个文件还不存在**(归 E)。

有一件事在动手前必须先知道:**`oxc-parser` 0.152 不暴露任何作用域信息**。`ParseResult` 只有 `program` / `module` / `comments` / `errors` 四个 getter,没有符号表、没有引用解析、没有「这个 identifier 是自由变量还是局部声明」的任何 API;更硬的一条是,`IdentifierReference` 与 `BindingIdentifier` 在反序列化后是**结构完全相同的对象**。而「全局白名单」这条规则的本质就是自由变量判定。**这直接推翻了 hld §2.2.3 与 §6.2 关于「这条规则由 tools 在 oxc-parser 上自建承担」的承载条款**,本 feature 的第一件事就是把它改掉。

## Solution

把 hld §6.2 的六类规则**重新分配给三个执行者**,让每条规则落在能做它的那一层上:

- **`tsc` 承担两条**:编译通过,以及**全局白名单反转**。后者的判据就是 tsc 的「找不到这个名字」诊断——脚本在一个不含 DOM、不含任何 `@types`、只额外引入脚本 API 类型声明的环境里编译,任何不在声明集合里的名字都会报错。那是**精确的**自由变量判定,零自建分析、零维护。
- **本 feature 承担四条**:模块系统(禁 `export` / `import` / 动态 `import()` / `require` / 动态 `eval`)、宿主桥前缀、禁列全局名、脚本体积上限。它们**全都不需要作用域信息**。
- **入口签名**由编译配置的类型声明保证,不在静态规则里单列。

本 feature 交付:一个跑在**编译产物**上的纯规则校验器、一个供生成管线以子进程调用的入口(退出码 + 面向模型的文本),以及 D 节点对四张名单的**唯一消费方式**。

## User Stories

1. As a **参赛模型作者**, I want 我的脚本若用了 `export` 或 `import` 就在编译期被拒, so that 我不必等到沙箱载入失败才发现整份脚本报废。
2. As a **参赛模型作者**, I want 我的脚本若引用了宿主能力(`console` / `process` / `fetch` / `setTimeout` …)在编译期被拒, so that 我知道那个东西在沙箱里不存在,而不是运行时拿到一个可以被我 `try/catch` 吞掉的 `ReferenceError`。
3. As a **参赛模型作者**, I want 我拿到的校验反馈是一句能照着改的话而不是一串内部记号, so that 五轮迭代预算花在改代码上而不是猜编译器在说什么。
4. As a **参赛模型作者**, I want 同一类错误被合并成一行, so that 五个同类错误不占掉五轮里的两轮。
5. As a **参赛模型作者**, I want 体积超限时被告知「改算法,不要拆直线代码」, so that 我不会用拆循环的方式去压体积——那恰好是这条规则要封的盲区的另一面。
6. As a **参赛模型作者**, I want 我在早期轮次收到体积提示但不被拦下, so that 我不会为了压体积把可读的循环改成直线代码。
7. As a **生成管线维护者**, I want 校验器以子进程调用、只依赖退出码与标准输出, so that 我不必把一个以源码形态执行的包拉进我的构建树。
8. As a **生成管线维护者**, I want 同一份源码在两次校验里得到**顺序完全相同**的违规序列, so that 我能 diff 两轮的结果、看出模型改了哪里。
9. As a **生成管线维护者**, I want 解析失败的源码只报「解析失败」而不报任何规则违规, so that 一棵残缺的语法树不会产出不可复现的结论。
10. As a **生成管线维护者**, I want 校验器一个名字都不自己存, so that 「参赛脚本能用什么」在名单、规则文档与沙箱注入面三处永远同源。
11. As a **维护者**, I want 改真源包里的名单,静态校验器的行为随之改变, so that 「同源」这句话有可执行的证据而不是注释。
12. As a **维护者**, I want 四份合规脚本不被任何规则误伤, so that 校验器不会在生成管线里反复拒掉本来能跑的脚本。
13. As a **维护者**, I want 每条规则都有一个能被弄红的反例, so that 我知道它不是摆设。
14. As a **维护者**, I want 体积上限作为参数传入而不是写死, so that 预算终值标定那一张图定下取值时不必改校验器。
15. As a **维护者**, I want 内置全局白名单有一条可判的收录判据, so that 往表里加一个名字时我知道自己在加什么。
16. As a **审查者**, I want hld 关于「这条规则由谁承担」的表述与实现一致, so that 架构审查不被一条已经失效的承载条款带偏。

## Implementation Decisions

### 承载的重新划分:这是本 feature 最重要的一条

hld §6.2 与 §2.2.3 都把**全局白名单**写成「由 `packages/tools` 的静态校验器在 `oxc-parser` 上的自建检查承担」。实测推翻了这个前提,原因是具体的而非风格性的:

- `oxc-parser` 不暴露作用域信息,而白名单规则的本质就是自由变量判定;
- `IdentifierReference` 与 `BindingIdentifier` 在反序列化后结构完全相同,判定只能靠**父节点字段位置**自维护作用域栈;
- 那条栈必须正确处理提升(函数声明的作用域是整个函数而非声明处)、解构、`catch` 参数、`for-of` 绑定、类型标注里的名字算引用还是类型、暂时性死区、闭包;
- **漏任何一处声明位置 = 误报一份合规脚本**。而误报在五轮迭代预算里是**不对称地致命的**:模型收到一条它改不掉的违规,五轮耗尽,这一轮生成作废;而漏报的代价只是回到现状。

所以:**全局白名单反转由 `tsc` 执行**。脚本在一个 `lib` 只含现代 ECMAScript、不含 DOM、不含任何 `@types`、只额外引入脚本 API 类型声明的环境里编译,「找不到这个名字」就是精确的白名单反转。理由有三条:它已经在流水线上(编译是 gen 的前置步骤),本 feature 要自建的是一个**严格更差**的版本;hld §2.2.3 已经为「不建在 oxlint 的 alpha 插件通道上」付过一次谨慎,同样的谨慎应该延伸到「不建在一个不提供作用域的解析器上」;它是**唯一**一个对误报/漏报不对称性零成本的选项。

**连带后果,三条都要写进文档**:

1. 参赛脚本的**编译配置**归 E(生成管线的编译步骤)。没有它,白名单反转无从执行。
2. 「脚本 API 的类型声明」**家定在真源包、内容由对局内核与沙箱执行器回填**。C 交付的是一张**符号表(名字数组)**,不是类型面——**符号表 ≠ 类型面**,C 没覆盖这一层,而 hld §6.2 早已预告它存在(「API 误用 | 类型层面由 `schema` 包的公开 `.d.ts` 约束」)。这正是 C 立下的「家已定、字段未交付」纪律的第三次应用。
3. 禁 `__*` 与禁列**仍然是本 feature 的**,因为它们不需要作用域:判据是「标识符链等于某个禁用链」,出现在任何位置都违规,查都不用查它是不是全局的。

### 规则清单与判定链

四条规则,每条一个纯函数,形状沿用已落地的禁浮点规则(「一段源码 → 一组带行列的违规」,不碰文件系统):

| 规则 | 判据 | 备注 |
|---|---|---|
| 模块系统 | 出现任一模块语法(静态 `export` / `import`、动态 `import()`、`require`、动态 `eval`)即违规 | hld §2.2.2 已实测:这四种在沙箱载入期取 `SyntaxError`,是编译期即可判定的事实 |
| 宿主桥前缀 | 任何标识符链的根以桥前缀开头即违规 | 桥函数在初始化后即被删除(实测结论 #5),静态拒掉是纵深防御的最后一层 |
| 禁列全局名 | 标识符链命中禁列表即违规 | 禁列表是**标识符链**而非裸全局名(成员路径也在内),这是 C 交付的接口形状 |
| 脚本体积 | 字节数超过传入上限即违规 | 不是 AST 规则,见下 |

**判定链的顺序是固定的,不是实现细节**:语法失败 → 禁列 → 桥前缀 → 模块系统 → 体积。禁列必须先判,否则会出现一个具体漏洞——禁列表里有 `Math.random`,而 `Math` 在内置白名单里;按白名单先判就会把 `Math.random` 放行。违规输出带规则类别,便于归并与 diff。

**没有第四条之外的白名单规则**:全局名级白名单之外的一切由 `tsc` 管(上一节),而 `Math` 的成员级禁令**不加**。理由见下面的「一处已知缺口」。

### 规则跑在编译产物上

四条规则**统一跑在编译后的产物上**,不在原始 TS 上跑。理由是三条语法层事实擦不掉:模块语法、桥前缀、禁列在编译后全都仍可判定;而在原始 TS 上跑会漏掉 TS 特有形态的类型断言与类型标注,等于为它们再写一套判据。这条同时消掉了「模块源码 / 脚本源码」两种源形态带来的分支——**本 feature 只有一个源形态**。

hld §6.2 规则表首行「编译 | `tsc` 编译通过」应读作「**校验流水线里必须有这一步**」而不是「静态校验器内部跑这一步」:编译责任归生成管线(hld §7.4 已如此规定,且引擎不引入 tsc),编译诊断由它直接透传给模型。

### 脚本体积上限

- **量编译后产物的字节数**,不量原始源码。理由是这条规则的**意图**:它要封的是运行时体量,而 3000 行类型注解可能编译后只剩几百字节;量原始源码会把「写了很多类型」误判成风险。
- **上限作为参数传入,校验器不给默认值。** 取值在规则集文件里,那是 E 的交付物、现在不存在;写一个默认值就是给一个未定值编答案。单元测试传显式值。「上限从规则集文件读」是交给 E 的一条。
- **检查时机:每轮迭代都查,但早期只提示不拦,冻结前才拦。** 理由是一个具体的失效模式:体积超标往往要到后几轮功能写完才成为决定性因素,而每轮都拦会在早期把模型逼向「压体积」——最自然的压法是**把循环拆成直线代码**,而那恰好是这条规则要封的盲区的另一面(直线代码不计数、但每格工作量放大)。所以**「体积超标」这条反馈里必须带上「改算法,不要拆直线代码」**,它是本条规则的一部分,不是文案润色。

### 违规输出

- **两层**:机器层是结构化违规数组(规则类别 / 行列 / 文本),面向模型层是渲染后的文本。退出码 0 或 1 是这个工具对外的**全部**契约,生成管线只读这两样。
- **面向模型层对同类错误合并**:多个同类错误并成一行而不是逐行列出。这是五轮迭代预算能撑住的前提,不是优化。
- **违规序列全序稳定**:按源码位置排序,同一位置按规则类别名兜底成全序。理由是生成管线要 diff 两轮的结果,排序不确定就 diff 不出来。已落地的禁浮点规则已经这么做,此处沿用同一判据。
- **解析失败独占结果**:解析不过时只报「解析失败」,一条规则违规都不报。理由是解析器失败时返回的是一棵残缺的树,在残树上跑规则只会得到不可复现的结论。

### 调用的形状:子进程 + 退出码

生成管线以**子进程**调这个校验器,拿退出码与标准输出。三个候选里它是最省事也最一致的:

- 生成管线**直接 import** 工具包不可行——该包以源码形态由 Node 的类型擦除执行、其入口指向源码且只产类型声明,生成管线的编译会把它的源码并进自己的 program,导致根目录越界(与 ADR-0002 实测的模块解析问题同源);
- **新增一个 CLI 子命令**会把一个内部校验动作塞进唯一用户面(hld §9 的六个子命令是给用户与流水线的),并让生成管线每轮迭代去 spawn 一个打包产物而不是一个 `node` 脚本;
- 子进程 + 退出码与 ADR-0003 给仓库自身门禁立下的形状完全一致,依赖方向不动。

### 名单的读法与收录判据

- **一个名字都不自己存**:四张名单全部读真源包经生成器分发的同源产物,与禁浮点规则读 `Math` 成员表走同一条通道。**同源性由一条可执行断言证明**:改真源包里的名单,校验器行为随之改变。
- **内置全局白名单的收录判据:「无副作用、不读这个 VM 之外的任何状态」**。它一句话对所有内置全局一视同仁,且与禁列构成一对方向相反的判据——禁列是「一律禁」(不可复算),白名单是「一律收」(不越界)。这**替代了**先前「判据未裁决故空着」的状态:不是靠一张更大的表来回答,是靠一条判据。
- **不写「分叉容忍条款」**。先前预留的担心是这张表会与判据分叉;判据一旦确立,就没有分叉,因而没有条款。

### 一处已知缺口,记下来不补

**参赛脚本写 `Math.sqrt` 没有任何规则拦它**。`Math` 的成员级禁令那张表(`ALLOWED_MATH_MEMBERS`)有两个消费者,其中一个是仓库自身的禁浮点门禁(跑在引擎源码上),另一个在本 feature 里**不读它**——因为成员级白名单在非数值全局上没有判据可依(`Object` / `Array` / `String` 的成员不产出数值,「整数闭包」这条判据对它们不成立),做下去就是维护几百个没有判据的名字。

这不是工程问题。要不要禁会改变 gdd §6.1 的兵种设计约束(射程、造价这类量是否允许经由非整数闭包的运算得出),是**规则侧的判断**。**本 feature 的动作是把它落到 gdd §8 的开放项里,不是自己加一条规则。**

## Testing Decisions

### 什么算好测试

只断言**外部可观察行为**。本 feature 的外部行为只有两件:一段源码被接受或被带诊断拒绝;一个入口以什么退出码结束并打印什么。凡是能靠改内部结构而失效的断言,都是坏断言。

### 缝(两条)

1. **纯规则的「源码 → 违规」**。每条规则一个纯函数,各带正例与反例,「每条规则都有能被弄红的反例」沿用 D3 立下的纪律。
   - **同源断言**:改真源包里的名单,校验器行为随之改变。它证明的是「D 一个名字都没自己存」,与禁浮点规则消费同源名单的那条同形。
   - **判定链顺序的用例**:一个既命中禁列又走成员访问的构造(禁列表里的成员路径挂在白名单内的全局名下),必须判为禁列违规。这条锁死「按白名单先判就会放行」那个漏洞。
   - **解析失败独占结果**:一份语法错误的源码只产出一条解析失败,零条规则违规。
   - **全序稳定**:同一份源码两次校验得到逐项相同的序列;两份不同源码的违规按位置有序。
   - **体积规则**:上限作为参数传入,低于上限通过、高于上限违规、恰好等于上限通过。
2. **入口的退出码与面向模型层文本**。这是生成管线唯一依赖的对外契约,不测就等于把契约留在「能跑就算」的状态。断言对象是退出码与打印文本,不是入口的内部结构。
   - **同类合并的用例**:多个同类错误并成一行。没有这条用例,这个行为会被后来者改成逐行输出而无人察觉。
   - **体积提示的文案**:早期提示里必须带「改算法,不要拆直线代码」这句。

### 明确不测

- **目录遍历层不单独测**,沿用禁浮点门禁的先例:那只是纯函数之上的一层薄壳。它在这个 feature 里比禁浮点那条更薄——本 feature 的输入是一份产物文件,不是一棵目录。
- **沙箱侧的越权行为不落仓库测试**。沿用 D3 的决定:对第三方库行为的断言会被后来者误读成「沙箱这块验过了」,改由实测数字写回设计文档承担,而复验责任挂在实现真实沙箱执行器的那张票上。
- **`tsc` 那两条规则不落本 feature 的测试**。它们由生成管线的编译步骤拥有,归 E 验收。本 feature 最多验一次「它们不在我的交付里」(出口处没有白名单反转的规则)。

### 验收集:四份盲写脚本

规则标定环的四舱盲写留下了四份独立盲写的合规脚本,其中两份在当时的契约下有已知静态不符。它们是**现成的「会不会误伤合规脚本」证据**,本 feature 用它们做 implement 期间的验收。

**它们不进仓库测试**,理由与 D3 那条决定同源:一次性证据不是回归基线,而且会被后来者误读成「合规性已验过」。仓库里的测试用现造的最小样本。**「不进仓库」不等于「不验」**——四份盲写正是该验的那四份。

## Out of Scope

- **全局白名单反转的实现**。由 `tsc` 执行,归 E 的编译步骤。
- **脚本 API 的类型声明**。家已定在真源包、内容由对局内核与沙箱执行器回填;本 feature 只读符号表,不产出类型面。
- **参赛脚本的编译配置**。归 E。没有它,`tsc` 那两条无从执行。
- **`Math` 的成员级白名单对参赛脚本生效**。已落 gdd §8 的开放项,属规则侧裁定。
- **体积上限的取值**。归预算终值标定那张图;本 feature 只接受它作为参数。
- **沙箱注入符号表的内容**。归沙箱执行器;本 feature 读它,但它当前为空,而空表的语义是「还没铺」——**本 feature 的任何规则都不因它为空而误判**。
- **把四份盲写脚本落进基准目录**。它们是一次性证据,基准脚本的落库归 E。
- **命令行子命令**。本 feature 不新增(hld §9 的六个子命令不动)。
- **把校验器接进生成管线**。接线归 E;本 feature 交付被接的那个东西。
- **规则文档(面向模型的那两份)的散文**。归 E;本 feature 不写一句。

## Further Notes

### 交办出去的三笔账

| 交办项 | 归谁 | 不做会怎样 |
|---|---|---|
| 参赛脚本的编译配置(脚本 tsconfig) | **E** | `tsc` 那两条规则无从执行,白名单反转整个落空 |
| 脚本 API 的类型声明(家定在真源包) | **F + G** | 「校验器放行但运行时报未定义」在结构上仍可能发生 |
| 参赛脚本是否受整数闭包约束 | **gdd §8**(已落为开放项) | 没人记得这条设计约束曾经被发现在过 |

前两笔的根因是同一个:**C 交出的是符号表(名字数组),不是类型面**。这是第三次应用「家已定、字段未交付」纪律,前两次是变体槽位与后三类形状。

### 本 feature 要一并修正的设计文档

- hld §2.2.3:「沙箱 API 白名单由 `packages/tools` 的静态校验器在 `oxc-parser` 上的自建检查承担」→ 改为由编译器的名字解析承担,并写明**为什么**(解析器不提供作用域,自建分析器的失败模式是误伤合规脚本)。
- hld §6.2 规则表:全局白名单那一行的承载方;「编译」那一行读作「流水线里有这一步」而非「校验器内部跑这一步」;「API 误用」那一行补上它依赖真源包的类型面而非符号表。
- hld §6.2:补一条实测结论——**`oxc-parser` 不暴露作用域信息**,以及 `IdentifierReference` 与 `BindingIdentifier` 在反序列化后结构相同。这条结论只对当前锁定的解析器版本成立,与 hld §5.0 那五条沙箱实测的写法一致(带版本组合与测量日期)。
- hld §6.2:「目录薄壳不单独测」的那条先例补上本 feature 的形态(输入是一份产物文件而非一棵目录)。

### 一处需要在文档里写明的张力

hld §6.2 原本把六类规则全挂在静态校验器名下,本 feature 把其中**两类**移给了编译器。这是一次**承载权的转移**,不是一次实现细节:它意味着静态校验器不再是「参赛脚本能不能用某个名字」的唯一裁判,裁判权与编译步骤合并了。文档不改的话,后来者会去找一条不存在的白名单规则,或者——更可能——看到 `oxc-parser` 有 AST 就以为能自己写一条。

### 与前后节点的关系

- 本节点在关键路径上,是**规则集落库(M1★)的前置**:没有它,终稿契约的静态面无人判定,盲写复跑的「静态不符」只能靠人眼扫。
- 它是**生成管线**的直接依赖(FR-5 AC1 的校验迭代环节),也是**沙箱执行器**的间接依赖(注入面与白名单同源,而消费方在这里)。
