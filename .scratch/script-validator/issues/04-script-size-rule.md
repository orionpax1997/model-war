# 04: 脚本体积规则

**What to build:** 顶层脚本体积上限这条规则:量**编译后产物**的字节数,上限作为入参传入、校验器不给默认值,并且**每轮迭代都查但早期只提示不拦、冻结前才拦**。反馈文本必须带上「改算法,不要拆直线代码」——那句话是规则的一部分,不是文案润色。

**Blocked by:** 01 禁列规则端到端 + 校验器入口

**Status:** resolved

- [ ] 体积规则的上限是**入参**,校验器不给默认值;取值归规则集文件(那是 E 的交付物,现在不存在)
- [ ] 量的对象是**编译后产物**的字节数,不量原始 TS 源码(3000 行类型注解可能编译后只剩几百字节)
- [ ] 边界三态各有反例:低于上限通过、恰好等于上限通过、高于上限违规
- [ ] **时机分两级**:迭代期只提示不拦,冻结期拦。两级由一个显式的调用形态区分,不是靠猜上下文
- [ ] 提示文本里带**「改算法,不要拆直线代码」**这一句,并有用例断言它在提示路径上出现、在拦截路径上也出现
- [ ] 拦截时的诊断说清超出多少字节,便于模型判断要缩多少
- [ ] 体积规则**不是 AST 规则**,它在同一条通路上但形状不同(字节数 → 违规);它不得让其余规则被迫接受一个 AST 参数
- [ ] 规则的意图在代码头注里写明:它封的是**运行时体量**对应的控制流计数盲区(直线代码不计数、但每格工作量放大),不是源码行数

## Answer

脚本体积上限这条规则已落地并接进判定链:字节数 → 一组**没有位置**的违规,`blocking` 是它唯一分两档的那一维。8 项验收逐条有着落。合并 commit `a246c66`(合并自 `e864618`,无冲突),合并后处置 commit `f03d6a3`。

### 关键结论

1. **上限是入参,库里与入口两侧都没有默认值**。`ValidateScriptOptions.maxBytes` 必填,入口 `--max-bytes` 必填且缺参按退出码 1 处理——写一个默认值就是给一个未定值编答案(取值归 E 的规则集文件,现在不存在)。
2. **边界判据是一句比较:`byteLength > maxBytes`**。「恰好等于上限」这一态最容易写成 `>=` 而少放一档,库层与入口层各有一条用例钉它。
3. **量的对象是字节数,不是字符串长度,也不是从文本重算**。入口读原始字节后交给判定链(`byteLength`),库里不传才按 UTF-8 重算:产物不是合法 UTF-8 时解码期会替换成 U+FFFD(3 字节),两个数会差,那个差值不该由规则承担。
4. **两级由一个显式的 `phase` 区分**(`--phase` 一路传进上下文),不是靠猜「现在大概是哪一轮」。两档共用同一句判据与同一条诊断,只有 `blocking` 与语气不同:超了就一定有一条违规,少报一次会让模型在冻结期第一次听见这件事。
5. **「改算法,不要拆直线代码」是常量而不是某一档才拼的片段**,提示与拦截两条路径都由用例断言。迭代期恰恰是模型最容易随手拆循环的时候。
6. **违规没有位置(`line`/`column` 为 `null`),排序时落在末尾**。硬给一个 `1:1` 只会让「这个位置是猜的」消失在数据里;而落在开头会让「第一行是什么违规」随有没有超标而变。
7. **`maxBytes` 在共享上下文里,三条 AST 规则的纯函数签名一个没变**。它没有变成「体积规则逼别人接受的一个参数」——那三级的形状仍然是「吃上下文、吐违规」,多出来的只是上下文里一个它们不看的字段。

### 合并时处置的三点

1. **入口契约那 3 条用例:留着。** spec 的《Testing Decisions》把缝分成「纯规则」与「入口的退出码与面向模型层文本」两层,并点名「体积提示的文案」要在入口那一侧断言。更硬的理由是:迭代 0 / 冻结 1 的**退出码差**与「上限是入参」在 `--max-bytes` 上体现,这两件事在库层**没有任何可观察的等价物**(库只给 `blocking`,退出码映射是入口的事)。挪走只能挪成重复断言,覆盖不会增加也不会减少,但入口这一层就空了。
2. **`pipeline.test.ts` 里票 01 留下的过时注释:改,不是删。** 原文写「体积级还没有落地(票 04),这里不让一个未定值参与判定」,后半句现在正好相反。删掉会丢掉「为什么给一个这么大的数」这个解释;改后写成现状——体积级是真的参与判定的,只是这些用例的源码都远小于那个上限,于是它一条都不报,**「没报」不等于「没判」**。顺带把文件头注里「规则本身的判据在 `rules/forbidden-globals.test.ts` 里」补成两个规则文件。
3. **体积级在解析失败路径上不参与判定:与 spec 一致,补一条用例钉住。** 这不是实现者的疏漏而是裁决的延伸:spec《违规输出》「解析失败独占结果」说的是「**一条规则违规都不报**」,票 01 只为禁列钉过。而体积级恰恰是最可能被提前的那一级——它是字节数的事实,不必等解析结果,提到早返回之前在代码上毫无阻力。所以 `pipeline.test.ts` 里新增一条:一份既有语法错误又远超上限(上限给 1)的源码,输出恰好只有 `syntax-error`。断言只落在输出上,不碰 `validateScriptSource` 的内部早返回结构。

### 与验收清单的一处出入(已按下面的读法收口)

第 2 条写的是「量的对象是**编译后产物**的字节数,**不量原始 TS 源码**」。后半句在库层**没有机制**:判定链拿到什么文本就量什么,「这份文本是编译产物」是调用方(生成管线的编译步骤,E)给的契约,工具这一侧无从分辨。对应地,`rules/script-size.test.ts` 里那条用例名为「量的对象是编译后产物的字节数,不是字符串长度」,它真正钉住的是**字节数 vs 字符数**这一半(用一份含多字节字符的产物,按长度判会放行、按字节数判才拦得住);另一半靠测试夹具的注释声明(`CLEAN` 标注为「编译后的样子:单文件 script-mode、顶层 `function loop`」)。按「规则量字节数、谁来喂产物归 E」收口,现状维持——把它写成断言只会逼出一条靠命名而非事实成立的用例。
