### 怎么跑的

```
node packages/tools/src/validate/run-validate-script.ts <产物文件> --max-bytes <N> --phase <iteration|freeze>
```

`--max-bytes` 分两次取:一次 **1000000**(刻意宽裕,让违规只可能来自规则、不可能来自体积),
一次 **7000**(低于四份的最小值 7471,让体积级必然触发,用来取「提示 vs 拦截」的差异与实测数)。
两级各跑一遍。退出码与 stdout 是全部契约,没有 `--json` 可用,逐份违规数即**stdout 里的条数**。

### 两份「已知静态不符」的判读

先纠正一处口径:**逐条读完 10/11/12/13/14 五张票与 `draft/wording-risks.md` 之后,原始记录里带静态不符的是一份不是两份。**
`issues/14` 的验收确认逐字写的是「仅 cell-d v1 入口记法与 `MY_INDEX` 写死 **2 项**静态不符」,cell-a / cell-b / cell-c 三票的驾驶员复核结论都是
「**无静态错误可回喂**」/「违禁项 0 命中」。「两份」这个数应是把那**两项**记成了两份。逐条判读如下。

| # | 出处 | 不符内容 | 是否落在本 feature 规则范围内 | 归属 |
|---|---|---|---|---|
| ① | cell-d v1 第 405 行 | 入口落成 `function loop() {}`,与 api.md 字面 `function loop(): void` 不符 | **否** | 不是四条规则中任何一条的判据。四条规则判的是:名字是否落在禁列 / 是否带桥前缀 / 是不是模块形态 / 字节数是否超限。**入口签名的字面形状一条都不管**——没有哪一级会因为 `loop()` 少一个 `: void` 而报违规,实测也确实 0 条。它归**参赛脚本的入口契约**(hld §2.2.2 + gdd 的脚本源形态那一格),而那一格当时本身是未定项:`issues/13` 与 cell-a 的 FIXES 都实证了「4 个舱 3:1 分裂,同一句硬约束 TS 记法 3 票 / JS 记法 1 票」,终稿要二选一定死。归 07(文档裁决)与 gdd,不归本票。 |
| ② | cell-d v1 第 44 行 | `var MY_INDEX = 0` 写死,违反 api.md §5「实写时从快照认出自己,禁止写死」 | **否** | 「不许写死这个常量」是一条**语义/契约**约束,静态这一层判不了:写死与探测的区别在**运行时读到了什么**,不在源码的语法形状上。真要给它一条静态规则,判据会落到「某常量必须由某函数回读」这类白盒推断上——而按 `spec《承载的重新划分》` 的口径,编译器不做、静态分析器也不做的那类推断正是误伤的来源。它归 **api.md 的自认机制**(终稿必须补显式出口:快照标记位或独立查询函数,见 `issues/14` 的 P0-1),不归本票。 |

**结论:两项都不在范围内,因此「按规则修」这一支是空集——没有该改的产物,也没有该改的规则。**
两舱的处置记录在案:①由 `cell-d/work/script.v2.js` 改成字面 `function loop(): void`,②v2 改为探测式自认(`MY_INDEX` 初值 -1,由 `getObjectById` 回读回填)。
`.scratch/` 下是一次性证据,**原样保留,一个字未改**——包括 cell-d v1 这份「已被 v2 取代但保留为初版原文」的产物。

> **该怎么改(若日后有人要动这两项,写在这里免得重推)**:
> ① 把入口契约的源形态二选一定死(要么入口字面就写 `function loop()`,要么定死 TS 源并由 E 的编译步骤统一剥离),
>    定死之后本校验器的**正则/语法判据不需要动**——它压根不判入口形状;
> ② 补一条 API(例如 `getMyIndex()`)或快照字段,让「认出自己」有可读出口。补完之后脚本自然不必写死,
>    而**本校验器同样不需要动**——它不判「某常量是不是写死的」。

|---|---|---|---|---|
| cell-a | **7471** | 7133 | 267 | 1.00× |

| 舱 | iteration | freeze |
|---|---|---|
| cell-a | `[提示] 脚本体积 · 1 处 · 多出 471 字节`,**退出码 0** | `[拦截] … 多出 471 字节`,**退出码 1** |

两级的差异**只有三处**,与契约逐条对得上:

2. **面向模型层那半句**:`这一轮只提示、不拦截,但它会随后续功能继续涨,别留到最后才缩;` ↔ `冻结期不接受这份产物,它必须缩到上限之内;`。

两档诊断**都带「改算法,不要拆直线代码」**(逐字核对过),与 `script-size.ts` 头注「那半条规则信息两档都要带」一致。

**边界三态实测(cell-a,7471 字节)**:`--max-bytes 7471` → 0 条违规、退出码 0(**恰好等于上限通过**);`--max-bytes 7470` → 1 条、退出码 1。

**确定性**:四份 × freeze × `--max-bytes 7000` 连跑两轮,stdout 与退出码**逐字节相同**(diff 无输出)。
这条在真实产物上是第一次验,不是只在仓库的合成样本上验。

### 这次验收证明不了什么(写下来免得被当成全绿)

四份脚本在四条规则的**判据分歧区零命中**,所以「不误伤」这次只在**平凡路径**上成立:

- 没有一处 `Math`(三份的模块级与函数体里都不出现 `Math.`,cell-d 那次出现是第 9 行的注释),因此 `Math` 成员白名单放行、`Math[k]` 动态下标按不在禁列放行这些分支**一个都没被走到**;
- 没有一处**解构**(四份都没有 `const { … } =`),所以「解构简写里被绑定的名字放行」这条**最容易误伤**的判据没被走到;
- 没有一处**键位上重名**(没有 `obj.Date`、`{ Date: 1 }`),所以「同名属性不是全局」这条没被走到;
- 没有一处 `eval` / `import()` / `export`(cell-d 第 8 行注释里提到 `export/import/require/eval`,不是 AST 节点,正确地不报)。

这不是缺陷,是这四份脚本的客观形状——它们本来就是照着当时的草案契约写的合规脚本。
**但结论要写全**:本次验收证明的是「这四份合规脚本零违规、零误伤」,
**没有**证明「误伤面被穷举」。误伤面由仓库里那批**现造的最小样本**扛着:
`rules/forbidden-globals.test.ts` 的「合规写法放行」8 例(`x.Date`、`{ Date: 1, Math: 2 }`、`const { performance } = g`、
`Math.floor`、`Math[k]()`、`const { random } = Math`、`__host.eval`)、`rules/host-bridge.test.ts` 的解构简写放行、
`rules/module-system.test.ts` 的静态 `eval` 不拦。**这两批证据互补,不互相替代**——一份防回归、一份防「当时那批模型就是这么写的」。

### 不落仓库测试的理由

四份脚本**不落 `*.test.ts`,也不进 `benchmarks/`**,理由与 spec《Testing Decisions》里「对第三方库行为的断言不落仓库测试」同源:

- **它们是一次性证据,不是回归基线**。它们记录的是「2026-09-29/30 那四舱模型在**当时那份契约**下写出了什么」,
  而契约此后还会动(入口源形态二选一、api.md 补自认出口)。契约一动,它们就过期;
  而回归基线的价值恰恰在于**不过期**。把会过期的文本钉成基线,等于给后来者一个「它红了就一定是回归了」的错觉。
- **它们会被误读成「合规性已验过」**。`benchmarks/` 里的东西看起来是「照参赛契约写的样本」,
  后来者会默认它过了全部校验;而真实情况是它们过了**当时的**校验器、且**带着两处当时未裁决的契约空洞**(TS/JS 记法、index 无出口)。
  这正是 spec 把它们划进 `## Out of Scope` 的那条:「把四份盲写脚本落进基准目录 —— 基准脚本的落库归 E」。
- 仓库里的常驻用例用**现造的最小样本**:一份几行的源码就能把一条判据钉住(含反例),不必拖 13 KB 的真实脚本进来。

**「不进仓库」不等于「不验」**:这四份正是该验的那四份——它们不是「随便找的合规样本」,
是**四台不同的模型、在四舱 bwrap 隔离、只读草案契约的条件下**各自独立产出的合规脚本,
对「规则会不会误伤真实模型按契约写出来的东西」这个问题,它们是**唯一存在的证物**。
本节(逐份违规表、字节数、负控、边界探针、确定性)就是这次验收的全部证据。

### 发现(不改规则,交由你裁)

本票**未改任何 `packages/tools/src/**` 下的代码**。以下两条是验的时候撞见的,按门禁交给你决定是否开新票:

1. **解析层对 script 源形态也用 `lang: "ts"`,比入口契约宽**(契约缺口,非误伤)。
   `parse-source.ts` 里 `kind === "script"` 走的是 `parseSync("script.ts", …, { lang: "ts", sourceType: "script" })`。
   而契约(hld §2.2.2 + spec《规则跑在编译产物上》)定死校验器的唯一源形态是**编译后的 script-mode JS**。
   实测后果:cell-a/b/c 三份 `.js` 里带 TS 注解(`function loop(): void`、`Map<number,number>`、若干 `as`),
   它们**原样就能过校验**——不是被容忍,是压根没被当成 TS 看待的意外后果。
   这**不是误伤**(判据更宽 ≠ 误伤,四份的结论该是 0 仍是 0),但它是「入口契约说 JS、解析层其实按 TS 收」的一处口径差:
   一份**没编译**的产物因此也能拿到退出码 0,而生成管线那一步(`tsc`)是 E 的交付物。
   **不自行改的理由**:把 script 源形态收紧成 `lang: "js"` 是一次行为变更,而「E 的编译配置」还没落地——
   在那之前收紧,可能把 E 交出来的某种编译配置判死;该由 07(文档裁决入口源形态)或 E(交出编译配置)先定,再由一张票收紧。
2. **简报里「两份已知静态不符」与证据对不上**(口径差,已在上面逐条判读并给出更正)。
   原始记录只有 **cell-d v1 一份两项**;若简报指的是「cell-d v1 + cell-d v2」,那 v2 是**零不符**的终态
   (实测 18558 字节 / 544 行,宽裕上限下 0 条违规、退出码 0),把它算作「不符」会反过来夸大问题。
   顺带把 v2 的字节数记在这里,供预算那张图对照:**v2 = 18558 字节**,比 v1 的 13621 **多 4937 字节(+36%)**——
   一轮回喂(把不确定性写进脚本:探测 + 确认计数 + 自愈)的体量代价,值得那张图一起看。
