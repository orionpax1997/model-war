# 02: 模块系统规则

**What to build:** 脚本产物里出现任何模块语法都在编译期被拒:静态 `export` / `import`、动态 `import()`、`require`、动态 `eval`。这四种在沙箱载入期取 `SyntaxError`(hld §2.2.2 的实测结论),是编译期即可判定的事实,不该留到运行时装载失败才发现。

**Blocked by:** 01 禁列规则端到端 + 校验器入口

**Status:** resolved

- [ ] 模块系统规则是一个纯函数,形状与禁列规则同形(源码 → 带行列的违规)
- [ ] 四种形态各有**一个能被弄红的反例**:静态 `export`、静态 `import`、动态 `import()`、`require`、动态 `eval`
- [ ] 每种反例都验一遍:退出码非零、诊断里点名那个形态
- [ ] 判定链里模块系统排在禁列与桥前缀之后,顺序不变
- [ ] 违规进入聚合后**全序稳定**这条性质继续成立(新增规则不得破坏排序)
- [ ] 动态 `eval` 与静态 `eval` 的区别:若实现只拦动态形式,须在规则文档与诊断里写明静态形式为何不拦;不得留成一条读不出来的规则
- [ ] 规则的边界在代码头注里写明:解析器在 script 源形态下同样会为模块语法生成节点,所以「单文件自包含」是这条规则判的,不是源形态保证的

### 关键结论

1. **动态 `eval` 拦、静态 `eval` 不拦,判据是第一个实参的形状**:直接调用 `eval` / `globalThis.eval` 且首个实参是**字符串字面量**即静态,其余一切(变量、模板串含插值、拼接、无参、经别处中转)按动态拦。**不做常量折叠**——`"a" + "b"` 与无插值模板串算动态:折叠是另一个成本层级,而静态那一侧误伤一份本来能跑的脚本,在五轮预算里不对称地致命。这条站得住:它是一条**读得出来**的规则(看第一个实参的形状),而不是一条要读者反推的规则;它的理由同时落在三个地方——代码头注、诊断文本(`eval("一段字面量")` 那种静态形式不拦:那段代码编译期就写定了)、用例(`rules/module-system.test.ts` 里「裁决可读」那一条直接断言诊断里有「运行期才确定」「不拦」「编译期就写定」)。验收项要求的「不得留成一条读不出来的规则」因此不是靠注释兑现的,是靠诊断文本兑现的——模型在编译期就能读到为什么。
2. **额外拦 `import x = require(...)` / `export = x`:保留,不砍。** 契约(hld §6.2)没点名它们,但**判据自己点到了**:本规则判的是「这段代码是不是从自己之外取来的」,这两种形态正是这件事,而且源形态是**编译产物**——产物里若仍出现(编译目标是 CommonJS 时),它们在沙箱载入期取的是与静态 `import` 同一个 `SyntaxError`。裁决过的那条轴是「是不是模块语法」,不是「契约逐字写了哪几个词」;契约漏写一个形态是一条待修的文档缺口,不是一条可以顺手放过的口子。这条轴同时解释了下一条裁决。
3. **刻意不拦 `new Function(...)`:保留不补。** 它与 `eval` 同级,但**不是模块语法**——`new Function` 取得的是构造点的闭包,落在另一个类别上,不在这条规则的判据之内。而它的名字另有承载:真源 `packages/schema/src/builtin-globals.ts` 把 `Function` / `eval` / `AsyncFunction` 并列写在内置全局白名单的「明确不收」一栏,白名单反转由 `tsc` 执行,于是 `new Function` 在编译那一步就拿不到这个名字。加进本规则属于向契约外扩一类,而那一类里已经有实测支撑(`eval`)与名字层兜底(`new Function`),再收只会多一处需要独立论证的形态。
4. **两处判不到的地方是有记录的缺口,不是遗漏**:经变量中转与间接调用(`const f = eval; f(s)`、`(0, eval)(s)`)——判据是**被调用者**而不是标识符,判到标识符层就要查作用域,而 `oxc-parser` 0.152 不暴露任何作用域;静态 `eval` 的字符串内容——那要把字面量当源码再解析一遍。承载方写在头注里:`eval` / `require` 都不在内置全局白名单里,由编译器名字解析那一层拒,两处判据同向。
5. **边界第 7 条(「单文件自包含」是这条规则判的)有一处实测支撑**:oxc-parser 0.152 在 `sourceType: "script"` 下照样为模块语法生成节点、不报解析错误(`export const a = 1` / `import x from "std"` / `import("std")` 分别落成 `ExportNamedDeclaration` / `ImportDeclaration` / `ImportExpression`)。也就是说「载入期取 SyntaxError」这件事**不会**由解析层挡下来——本规则才是把那条契约变成编译期结论的唯一地方。头注里另记了一条实测:`import.meta` 由 oxc 直接判**解析失败**,归判定链独占的 `syntax-error`,本规则见不到它(也不需要见)。

### 与票 03 合并时的处置

1. **槽位断言过期:改,不是删。** 本票落地时桥前缀那一格仍是注释占位,所以断言钉的是 `SCRIPT_LINT_STAGES[1]`。票 03 落地后桥前缀插进第二格、本级随之挪到第三格,原断言会红。收口写法是**钉第三格(索引 2)加三条邻居的相对顺序**(`indexOf` 关系),而不是钉一个会随邻居落地而漂的裸索引:裸索引只钉住「我在某个位置」,邻居插错位时它可能仍然绿;钉住邻居才把「禁列 → 桥前缀 → 模块系统 → 体积」整条关系钉死。用例名与文件头注同步改成说清钉的是哪一格。票 04 那条「解析失败时体积级不参与判定」在同一片区域,未受影响(unit 225 条全绿)。
2. **判定链的槽位注释占位机制收工。** 本票与票 03 落地后五个槽位全齐,`pipeline.ts` 里那行「下面 N 级的槽位:票 XX 各自取消对应那行的注释」连同「只登记已落地的级」那段说明一并删掉,换成「五个槽位已齐、新加一级直接插在该在的那一格」。理由是占位服务的是「后面几张票还没写」的那段时间,留着它只会让后来者误以为还有槽位没填。四格各自带一行尾注,并在头注里点名白盒断言在哪——顺序有钉子,不靠注释盯。
