# 仓库骨架与工具链可用性确认

Status: ready-for-agent

## Problem Statement

设计文档链(fsr → srs → gdd → hld)已经收口,HLD §2.2 也已经把工具链选型写死,但**磁盘上一个字节的代码都没有**。这件事带来四个具体的痛:

1. **工具链的关键假设从未被验证**。HLD 的开放项 #5 挂着三条待确认项,其中两条在写下时就已经失效(TypeScript 7.0 早已 GA、`oxlint --type-aware` 早已 stable),而剩下的一条——类型感知 lint 在本仓库规模下的实际耗时——至今是许愿而非数字。hld §2.2.7 承诺的「`check:quick` < 5s」没有任何实测支撑。
2. **沙箱侧的五个关键行为只有二手结论**。脚本入口契约(单文件 script-mode TS 编译产物能否被 `evalCode` 载入并调用 `loop()`)、深递归的失败形态、`interruptHandler` 的截停能力、内存读数字段名、宿主桥函数删除后的不可见性——这五条决定了整个引擎的形态,却都还没有一手证据。
3. **依赖规则只是纸面承诺**。HLD §3.2 的包依赖方向、`engine` 禁一切 `node:*`、`gen` 永不进对局进程,现在没有任何机器门禁;违规要等人工 review 才发现。
4. **词汇在文档内部互串**。同一个概念有「场次 / 单场 / 对局」三种叫法,「冻结」有四个不相干的含义,「战报 / 叙事战报 / 报告」三层含义互相串用。领域语言没有单一出处,后来者会在此基础上继续制造同义词。

## Solution

搭起一个**可编译、可 lint、可测**的仓库骨架,并在搭的过程中把上面四条痛逐一钉死:工具链选型收口为 ADR、沙箱行为以实测数字写回 hld、依赖方向变成可执行断言、领域词汇收进 `CONTEXT.md` 并扫平正文。

骨架是**空壳而非半成品**:六个包各自只有一个导出符号,但每一个都真实参与编译与门禁,使得「工具链可用」这句话在第一天就有一个可重复执行的证明,而不是等第一个真实功能落地时才第一次被验证。

## User Stories

1. As a **维护者**, I want `pnpm install` 一次装齐全部工具且不执行任何未经批准的依赖构建脚本, so that 供应链面不会无声扩大。
2. As a **维护者**, I want 工具版本锁定在可用的最新稳定版而非本机恰好已装的版本, so that 别人 clone 下来得到的是同一套门禁。
3. As a **维护者**, I want 影响对局复现的依赖(编译器、沙箱运行时)精确锁版、其余交给 lockfile, so that 升级不必变成手工仪式,而复现性不受影响。
4. As a **维护者**, I want 包间类型引用经由 workspace 的 `exports` 与 project references 解析, so that 编译期就能强制依赖方向,而不是等到运行时。
5. As a **维护者**, I want 根 tsconfig 不吞掉全仓源码, so that 增量编译与类型感知 lint 不会因为一个巨型 program 而退化。
6. As a **维护者**, I want 依赖规则由 dependency-cruiser 断言并在违规时非零退出, so that 「gen 永不进对局进程」从口头约定变成机器门禁。
7. As a **维护者**, I want 依赖规则只作用于运行时代码、不作用于测试代码, so that 必然要读盘与 spawn 进程的测试不会被自己的门禁拦下。
8. As a **维护者**, I want 确定性硬门禁(禁浮点)由我们自己掌控的校验脚本承载, so that 一票否决级的约束不依赖上游标为 alpha 的扩展通道。
9. As a **维护者**, I want 那条校验脚本既服务于仓库自身的门禁、也服务于将来的参赛脚本校验, so that 「参赛脚本能用什么」只有一个出处。
10. As a **维护者**, I want 每一道门禁都有一个「能被弄红」的反例, so that 我知道它不是摆设。
11. As a **维护者**, I want 门禁以一组命名脚本暴露、由我手工触发, so that 我不必先维护一份 YAML 流水线才能得到反馈。
12. As a **维护者**, I want 快慢分层的门禁(快速反馈 / 带类型感知 / 全量), so that 编辑循环不必每次都等最慢的那道。
13. As a **维护者**, I want 门禁耗时有实测数字写进设计文档, so that 「< 5s」这类承诺要么被证实、要么被降级为观测项。
14. As a **维护者**, I want 工具链选型留下一份 ADR, so that 半年后有人问「为什么不用 ESLint」时,答案不在聊天记录里。
15. As a **维护者**, I want TS 7 不含编程 API 这类会持续生效的约束被记录, so that 将来任何「需要读 AST」的需求都会重新权衡一次而不是顺手就写。
16. As a **维护者**, I want 包间类型引用的方式偏离原设计时,偏离的原因与实测错误码被记录, so that 没有人把「不用 `paths`」当成手滑改回去。
17. As a **维护者**, I want 领域词汇有单一出处, so that 同一个概念不会在文档里长出第二种叫法。
18. As a **参赛模型作者**, I want 我读到的规则文档与引擎实际执行的机制是同一套, so that 我写出的脚本不会因为文档与实现漂移而白跑。
19. As a **参赛模型作者**, I want 我提交的脚本连同其来源与版本被完整留存, so that 别人可以复现我的对局,我也可被追责。
20. As a **参赛模型作者**, I want 我的成绩能被独立复算, so that 榜单上的排名不是一句无法验证的话。
21. As a **赛季运营者**, I want 对局产物与冻结脚本的存放边界清晰, so that 我知道哪些东西会随仓库一起长期保存、哪些可以随时删掉重生成。
22. As a **赛季运营者**, I want 冻结脚本进版本库, so that 历史对局在新的克隆上仍然可以被复算。
23. As a **赛季运营者**, I want 对局运行产物不进版本库, so that 仓库历史不会被体量持续膨胀的产物淹没。
24. As a **维护者**, I want 磁盘上的目录结构与设计文档里的拓扑图一致, so that 我能一眼看出「这里本该有东西但还没落库」。
25. As a **维护者**, I want 尚未实现的命令显式失败而不是静默返回成功, so that 自动化流程不会把「没实现」误判成「跑通了」。
26. As a **维护者**, I want 空壳里的每个导出都是真实可用的, so that 骨架不会在第一个真实功能落地时发现底层假设是假的。
27. As a **审查者**, I want 审阅时能靠 import 图与机器门禁判断架构合规, so that 架构审查有客观依据而不是靠人肉读 import。

## Implementation Decisions

### 工具链与版本

- 工具版本一律取**可用的最新稳定版**,不迁就开发机已安装的版本。具体锁定:TypeScript 7.0.2(2026-07-08 GA,`tsc` 本身即 Go 实现,`tsgo` 这个名字已取消)、oxlint 1.86.0、oxlint-tsgolint 7.0.2003、oxfmt 0.71.0、oxc-parser 0.152.0、quickjs-wasi 3.6.2、Vitest 5.0.3、fast-check 4.10.2、ajv 8.20.0、dependency-cruiser 18.4.0、esbuild 0.28.2、Stryker 10.0.0、pnpm 12.8.1。类型定义取与运行时 Node 主版本匹配的那一条,而不是 dist-tag 的 latest。
- **选择性精确锁版**:影响对局复现的依赖(编译器、沙箱运行时)以及它们的对偶(类型感知 lint 的 tsgolint)精确锁版;其余走 caret 并由 lockfile 固定,CI 以 frozen-lockfile 安装。
- **tsgolint 与 TypeScript 的版本耦合没有任何工具会替你检查**。oxlint 的 peer 只保证 tsgolint 的版本下界,不比对 TypeScript 版本。这条耦合必须在 CI 里显式断言,否则两类工具会静默错位。
- 包管理器版本写进 `packageManager` 字段钉死;依赖的构建脚本采用**白名单**而非默认放行,只批准确实需要构建的那一个。
- 采纳 oxfmt 0.x,**不设置降级到 Prettier 的退路**。理由:官方声称 JS/TS 已 100% 通过 Prettier conformance,真正未兑现的是 1.0 尚未发布,而这由精确锁版加 `--check` 门禁兜住;为尚未发生的风险长期支付格式化耗时不划算。

### 包拓扑

- 六个包(CLI app + 五个库包)加一个工具包。**工具包是新增的第 7 个成员**,HLD §3.1 的拓扑图随之更新。
- 新增工具包的动机:静态校验器有**两个消费者**(仓库自身的确定性门禁、将来的参赛脚本校验),而现有包里没有一个放得下——schema 被明文限定为无行为代码,gen 则是唯一联网包,把仓库自身的门禁挂在它下面会污染依赖方向。放进独立工具包后,依赖方向仍然是单向的。
- 工具包以源码形式由 Node 直接执行(不参与构建产物),这要求全仓库遵守「可擦除语法」约束:禁 enum、namespace、参数属性。类型定义也强制 `strict` 加未定义索引检查。

### 类型与编译

- **包间类型引用经由 pnpm workspace 的 `exports` 与 TypeScript project references 解析,不使用 `paths`**。这是对 HLD §2.2.2 的有意偏离:实测表明 TypeScript 7 下把 `paths` 直指各包源码会让源码被并入引用方项目,报 `rootDir` 越界(TS6059)与文件不在引用方文件列表内(TS6307);而 `paths` 与 `exports` 同时解析同一模块,正是 pnpm 软链环境下类型声明不可移植(TS2883)一类问题的成因。去掉 `paths` 后两条错误同时消失。**「禁用 `baseUrl`」的原结论不变**——TypeScript 7 确实已将其移除。
- 根 tsconfig 必须是 solution 形态且 `files` 置空,否则根 project 会把全仓源码吞进一个巨型 program,增量编译与类型感知 lint 同时退化。
- 各包的 outDir 保持在包内,不指向包外。
- 测试文件与实现同处源码目录,因此被 `tsc -b` 一并类型检查;测试的编译产物落在 dist 内属可接受的副作用,但测试运行器的包含范围必须显式限定在源码目录,避免二次拾取产物。

### 依赖规则

- dependency-cruiser 把 HLD §3.2 的全部规则写成可执行断言并挂在全量门禁上:schema 无依赖、replay 只依赖 schema、engine 不依赖 runner 与 gen、runner 不得依赖 engine、gen 不得依赖 engine、engine 的运行时只允许 `node:crypto` 一个内置模块。
- **规则只作用于运行时代码,测试代码豁免**。理由与 HLD §3.2 已有的那条一致:门禁约束的是运行时行为,而测试代码不进对局进程,不构成隔离风险。
- 禁止保留符号链接解析选项(pnpm 官方明确其与类型解析不兼容)。
- **对局运行产物忽略、冻结脚本入库**。理由是复算链:报告 → 单场输入物化 → 存档引用 → 重跑;若冻结脚本被忽略,新克隆的仓库永远无法复算历史对局,而且是运行时才炸的那种失败。冻结脚本体量小、且与规则集、地图同级,理应同权;对局运行产物体量随 tick 数线性增长且可由前者重生成。

### 领域词汇

- 「对局」为一场完整四人对战的唯一叫法;「场次」「单场」「比赛」「match」列为禁用叫法,并扫平四份设计文档中的既有用法。
- 「冻结脚本」定名为参赛脚本连同其编译产物、生成元数据与完整 prompt 链一次性定版后的不可变副本;并在词条里挂一条**另义警告**:「冻结」在本项目另有三个不相干的含义(快照的只读封存、占领进度的保留不动、宿主时钟的定格),那三处不得简写为「冻结」。
- 「回放 / 叙事战报 / 报告」三者分立:回放是可复算数据,叙事战报是单场散文且不得作为判定依据,报告是赛季级汇总。
- 「地图变体」与「地图版本」分立:变体是种子填充的装饰性微调,版本指规则集。
- **不收录「工具链门禁」一词**。它被提过,但按 glossary 的收录标准它属于通用工程概念而非本项目特有的领域语言,其归宿是设计文档的开放项。

## Testing Decisions

### 什么算好测试

只断言**外部可观察行为**,不断言实现细节。本 feature 的外部行为就是两件事:门禁通过或失败、以及校验器接受或拒绝一段源码。凡是能通过改内部结构而失效的断言,都是坏断言。

### 缝(只有两条)

1. **主缝:根门禁脚本的退出码**。断言对象是 CI 将来会敲的那几条命名脚本(快速、带类型感知、全量、测试),而不是任何内部函数。骨架阶段要求它们在空壳上全部退出 0。
   - **每道门禁都要有一个能被弄红的反例**。没有反例证明的检查不是检查。实施时至少对类型闸门做一次现做现验的负例(例如故意制造一处类型不匹配,确认非零退出后还原)。
2. **静态校验器的纯函数**。断言对象是「一段源码 → 一组违规」的映射,不碰文件系统。目录遍历只是它上面一层薄壳,不单独测。
   - 覆盖点:浮点字面量、小数、指数形式(即便求值结果是整数也判违规,因为它绕过整数闭包的字面审视)、大整数字面量(应放行)、整数与浮点的算术结果边界、以及 `Math` 成员白名单内外的区分。
   - 优先用属性测试:用 fast-check 断言「只有整数构成的表达式永远不产生违规」这类命题,补上手写例子覆盖不到的组合。

### 沙箱行为刻画测试:明确不做

对沙箱运行时的五条行为事实(深递归的失败形态、中断截停、内存超限形态、内存读数字段名、宿主桥函数删除后的不可见性)**不落仓库测试**。它们是对一个被第三方拥有的库的行为断言,不是对我们代码的断言;在还没有真实沙箱实现时放进仓库,会被后来者误读成「沙箱这块已经验过了」。

这五条改由**实测数字写回设计文档**承担,并把「复验」的责任显式挂到实现真实沙箱执行器的那个 ticket 上。同时,「升级沙箱运行时需重跑行为复测」这条既有条款因此在实现期之前是**空头承诺**,这一点须在文档中写明。

### 先前

- 仓库中暂无同类测试可供参照,本 feature 的测试是首批,其风格即后续的先例。
- 沿用 HLD §2.2.4 的既有禁令:禁快照测试(测试红了会被更新快照而不是查 bug)、禁覆盖率门禁(可被刷)。本 feature 阶段两者都还不适用,但禁令继续有效。
- 变异性测试(Stryker)属夜跑体检,配置留到引擎结算管线落地,不在本 feature。

## Out of Scope

- **CI/CD 流水线**。门禁以命名脚本手工触发即可;流水线形态与仓库首个真实实现强相关,现在定下来只会写一份需要重写的配置。
- **任何包的真实业务逻辑**。引擎结算管线、赛季调度、生成管线、排名与报告、回放格式的完整实现,全部不在此列。骨架里的每个导出都是真实可用的最小物,但没有行为。
- **CLI 六个子命令的实现**。骨架只登记命令名,调用未实现的命令显式失败。
- **规则侧的交接物**:规则集取值文件、地图数据、面向模型的规则文档、基准脚本。这些属于规则侧的图外交接,骨架只建目录占位。
- **参赛脚本静态校验**。它依赖由 schema 生成的白名单符号表,而该表随 schema 的落地一起产生。工具包的结构为此预留,但本 feature 只实现仓库自身的确定性门禁那部分。
- **生成物漂移检查**。门禁流水线里有这一项,但生成器尚未存在,本 feature 不放一个什么都不做的占位脚本。
- **探针代码**。用于取证的临时探针不进版本库,只把结论写进文档。

## Further Notes

### 本 feature 要一并修正的设计文档

工具链的确认过程暴露了设计文档里若干与现状冲突的表述,按「每个事实只有一个家」的原则应修矛盾的一方:

- 工具链开放项的收口:TypeScript 7.0 的 GA 时点已确认、类型感知 lint 的 experimental 表述已失效、格式化工具的 conformance 条款应改为「1.0 前接受 0.x 风险」而非整套降级方案。
- 运行时的因果链:Node 版本下限来自我们自己的代码特征(ESM、资源管理与稳定版解析 API),而非沙箱库的前置要求——后者并不声明引擎约束、也不需要任何运行标志。
- 类型感知 lint 的表述:已 stable,不再是并行试跑。
- 版本耦合的表述:由「版本号跟随 TypeScript」这种含混说法,改为两者之间的一一映射,并注明需要 CI 断言。
- 宿主桥函数前缀的静态禁令:该 lint 规则只接受精确名字列表,没有正则或通配,表达不了前缀禁令;白名单反转同样没有直接对应物。这两处的承载方式须在文档里改写。
- 依赖门禁的作用域:须写明只作用于运行时代码。
- 包拓扑图:新增工具包成员。
- 类型引用方式:由「`paths`」改为「workspace exports + project references」,并附实测错误码。

### 一处需要读者注意的张力

设计文档把「升级沙箱运行时需重跑行为复测」写成了一条门禁条款,但在本 feature 结束、沙箱实现开始之前,这条条款没有任何可执行的东西支撑它。这是已知且被接受的状态:条款在实现沙箱执行器的 ticket 上生效,不是现在。
