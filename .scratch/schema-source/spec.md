# schema 真源与生成物

Status: ready-for-agent

## Problem Statement

M1 的决策已经做完,交付物是 0。磁盘上 `rulesets/`、`maps/`、`docs/rules-v1/`、`benchmarks/`、`prompts/` 全是 `.gitkeep`,而真源包只落了两件东西:规则集版本常量与 JSON 值形状。这个状态带来六个具体痛:

1. **FR-10 AC2 的「读入端强制校验」没有任何东西可执行**。`ajv` 已经躺在根 devDependencies 里,但仓库里不存在任何一条 JSON Schema,也不存在任何调用它的代码。ruleset、地图、存档 meta、result、回放行五类数据全部处于「约定上应该有校验、实际上裸奔」的状态。
2. **生成物漂移检查在流水线里挂着,内容是空的**。hld §2.2.7 的主流水线阶段 2 列了「生成物漂移检查」并注明「待 `schema` 落地后才有内容(生成器尚不存在)」——那行字现在是**承诺的兑现期限**,不是现状描述。
3. **允许名单有两处名字,靠一句注释维持和平**。工具包的允许名单文件头写着「将来由 `@model-war/schema` 生成……今天是一张手写的静态表;`schema` 落地后这张表改为生成物、真源随之迁到 `schema` 一侧——**生成物与手写表不得并存**」。那句话现在是笔债:两处各有一份名字,「参赛脚本能用什么」这个问题有两个答案,靠自觉同步。
4. **22 个参数键没有任何机器可读的清单**。13 个定稿键散在规则标定环的交接单里,9 个预算键散在「待移交键」表里;gdd §7 的参数清单是散文表,定义含义不定义取值,而取值文件还不存在。要让 `rulesets/v1.json` 落地,得先有一份能校验、能生成文档、能被引擎 import 的键清单。
5. **「回放行的家在哪」在设计文档内部有三种说法**。hld §2.2.5 说 JSON Schema 定义在真源包内、校验对象含回放行;hld §3.1 的职责矩阵说「行格式取自 `replay` 包」;hld §7.5 说回放版本常量由 `replay` 包承担且「`replay` 为唯一真源」。同一个事实两个家,谁先落地谁说了算。
6. **沙箱侧要消费的 API 名表与静态校验器要消费的白名单,必须同源**,而今天它们连「同源」的机制都没有——hld §3.2 明写沙箱 runtime「只消费 `schema` 生成的常量/API 名表」,hld §6.2 明写白名单「由 `schema` 生成」。

## Solution

把 C 落成三件事,彼此分工明确:

- **一个真源包**:拥有五类数据形状的 TypeScript 类型与 JSON Schema、参数键清单、常量表。它**无运行时代码、无依赖**,是整张依赖图的根。
- **一个混合传输的生成器**:生成器代码在工具包,它 import 真源包;而工具包的**规则层**通过生成的源文件读同一份名单,以保住快门禁「零构建」的性质。生成器持有一张**生成物注册表**,新增生成物是加一行注册,不是重构。
- **一处 ajv 读入端校验**:在 CLI 应用里,所有外部数据的入口只有一个。校验器交付结构化的两层诊断(机器层 + 面向模型层,同类合并)。

C 结束时,M1 的读入端校验覆盖 **ruleset 与地图两类**——后三类的家已经定在真源包,但字段要到 F / H 才定,C 明确不交半成品(见 Out of Scope)。

## User Stories

1. As a **维护者**, I want 五类数据形状各有一个明确的家, so that 没有人会发现两份互相漂移的形状定义。
2. As a **维护者**, I want 回放行的类型与 JSON Schema 由真源包拥有、`replay` 包只做编解码, so that 「回放格式」不再是一个有两份定义的词。
3. As a **维护者**, I want TypeScript 类型是形状的上游、JSON Schema 手工对齐, so that 引擎侧继续享受判别联合的穷尽检查,而不是被反向生成的索引签名削弱。
4. As a **维护者**, I want 类型与 JSON Schema 的一致性由一条测试断言兜住, so that 两者漂移时红灯而不是在生产里静默放过一个错形状。
5. As a **维护者**, I want 22 个参数键有一份带类型与约束的机器可读清单, so that `rulesets/v1.json` 的落地有校验的依据,而不是照着散文抄一遍。
6. As a **维护者**, I want 派生量的派生式有明确的家, so that `spawnTicks` 这类「既在 JSON 里又由公式决定」的值不会两边算出不同答案。
7. As a **维护者**, I want 形状与取值不一致时装载期就拒, so that 错数据不会带着一个自相矛盾的兵种表走进对局。
8. As a **维护者**, I want 9 个预算键在 M1 阶段就是必填的, so that K 节点不必对真源做一次破坏性的「加必填」变更。
9. As a **维护者**, I want 预算键的占位取值在面向模型的文档里渲染成「未定」而不是 `0`, so that 「有没有标定完」在文档上一眼可见而不需要另设一个布尔字段。
10. As a **维护者**, I want 缺键与「键存在但未定」是两种不同的错误, so that 数据文件里的一处笔误不会被读成「还没标定」。
11. As a **维护者**, I want 规则版本号在三处(取值文件名 / 规则文档目录名 / 常量)之间的一致性由机器判定, so that 错配在装载期拒跑而不是等到某个对局中途。
12. As a **维护者**, I want 校验器只有一份实现, so that 「形状对不对」这个问题只有一个答案。
13. As a **维护者**, I want 校验器放在唯一用户面里, so that 引擎与调度包不各自长出一套手写的形状 if。
14. As a **维护者**, I want 校验诊断同时有机器层与面向模型层, so that 门禁排障与回喂模型用两套各自稳定的措辞。
15. As a **维护者**, I want 同类错误在面向模型层合并成一行, so that 五轮迭代预算不被重复错误吃光。
16. As a **维护者**, I want 生成物漂移在真源改动而未重跑时让门禁变红, so that 文档与名单不会悄悄过期。
17. As a **维护者**, I want 漂移检查只看生成物路径, so that 我工作树里别的未提交内容不会把报错指向错误的地方。
18. As a **维护者**, I want 新增生成物是往注册表加一行, so that E 接入文档生成时不需要改生成器骨架。
19. As a **维护者**, I want 漂移检查同时能抓住「生成物被删」与「生成物新增但没进版本库」, so that 「跑过生成器」不等于「生成物已被提交」。
20. As a **维护者**, I want 工具包的规则层仍然零构建, so that 快门禁不因多一个 `tsc -b` 而变慢,也不让新克隆在第一次跑门禁时先失败。
21. As a **维护者**, I want 允许名单不再有手写副本, so that 「参赛脚本能用什么」只有一个出处。
22. As a **维护者**, I want 真源包的对外接口是单一入口, so that 将来想收窄公共面时还来得及。
23. As a **维护者**, I want 真源包内按域分文件, so that 它长到几百行时仍然可导航。
24. As a **维护者**, I want JSON Schema 以导出的数据对象形态存在而不是独立 JSON 文件, so that 我不必为此开新的模块解析机制。
25. As a **维护者**, I want 校验器对任意输入都不抛未捕获异常, so that 一份畸形文件不会让进程带着栈回退码崩掉。
26. As a **维护者**, I want 地图的变体槽位有位置可填但形状不预设, so that 地图图(A 节点)回来时那次回填是计划内变更而不是意外返工。
27. As a **维护者**, I want 变体槽位的过渡形状显式带「待回填」标记, so that 后来者不会误以为它的形状已经定稿。
28. As a **维护者**, I want 宿主桥前缀与禁列全局名由真源包提供, so that 静态校验器与沙箱 runtime 对「什么算宿主桥」只有一个定义。
29. As a **参赛模型作者**, I want 我读到的规则文档数值表由取值真源生成, so that 文档与引擎实际执行的数值不会漂移。
30. As a **参赛模型作者**, I want 预算键未定的时候文档里写「未定」, so that 我不会把占位值当成真实限制来设计策略。
31. As a **参赛模型作者**, I want 脚本静态校验与沙箱暴露的 API 面同源, so that 不会存在「校验器放行但运行时报未定义」的情况。
32. As a **赛季运营者**, I want 地图与规则集在装载期被校验, so that 一份坏数据不会跑到一半才炸。
33. As a **赛季运营者**, I want 规则版本错配在启动时拒跑, so that 历史对局不会被新的规则集悄悄改写。
34. As a **审查者**, I want 每一类数据形状的归属能在设计文档里查到唯一出处, so that 架构审查不靠记忆。

## Implementation Decisions

### 形状的归属:五类,家唯一

- **真源包拥有全部五类形状**的 TypeScript 类型与 JSON Schema:规则集、地图、存档 meta、对局 result、回放行。
- **回放包降级为纯编解码层**:保留行格式的序列化 / 解析与回放版本常量(`CURRENT_SCHEMA_VERSION`,该常量仍由它承担,它是回放**文件格式的版本**,不是行的形状),不再重复声明行的类型。
- 依据:hld §3.1 写「行格式取自 `replay` 包」而 §2.2.5 写「JSON Schema 在真源包内、校验对象含回放行」,两者只能留一个。按「每个事实只有一个家」,留在真源包;`replay` 包的职责矩阵措辞相应收窄。
- 存档 meta 与 result 两类同上:家定在真源包,但**本 feature 不交付它们的字段**,由 H / F 的票负责回填(见 Further Notes 的计划内回填)。

### 真源的上游:TypeScript 类型,JSON Schema 手工对齐

- **TypeScript 类型是形状的上游**;JSON Schema 由它手工对齐,**不引代码生成**。
- 理由:①回放行与终局原因枚举靠**判别联合**让结算管线穷尽分支,反向生成会把它压成索引签名,直接伤到 NFR-1;②JSON Schema 能表达而 TS 表达不了的只有「禁止额外属性」与 `description`,代价很小;③代码生成要么新增运行时依赖、要么依赖 TypeScript 的编程 API——而 ADR-0002 已实测记录 **TypeScript 7 没有 JS 编程 API**,这条路在本仓库天然堵死。
- **一致性由测试断言**兜底,不是靠自觉:同一组 fixture 既过 TypeScript 类型又过 ajv;并有一条类型级断言,要求 JSON Schema 的「必填键集合」等于对应 TypeScript 类型的键联合。
- **JSON Schema 以导出的数据对象形态存在**(不是独立 `.json` 文件),理由是 ajv 接受 JS 对象,不需要文件;`.ts` 形态还让 `description`(写给模型看的说明)写起来自然,并避开 `resolveJsonModule` 与仓库现有编译配置组合的风险面。
- **JSON Schema 禁止额外属性**:五类数据一律 `additionalProperties: false`。这是「类型是真源」这一选择的主要代价补偿,必须真的关掉,否则手写的 schema 只是一份注释。

### 参数键清单与派生量

- 键清单**带类型与约束**,不是一个裸的键名数组:每个键带它的 JSON 值类型、量纲(若有)与取值范围。键清单的 JSON 值类型与 JSON Schema 由**同一次书写**产生(手写,但放在同一个模块里),避免两处各写一遍。
- **22 个键 = 13 个定稿键 + 9 个预算键**,后者在 M1 阶段取未定值(见下)。
- **派生量双存 + 装载期断言**:生产耗时一类既出现在取值文件里、又能由派生式算出的键,**两个都保留**,派生式系数作为真源包的常量导出;装载期断言二者相等,不等即拒跑。
  - 具体:生产耗时由「造价 × 系数」向上取整,系数是常量;四条兵种线的取值文件里同时写着这个数。
  - 理由:取值文件是该数据的真源,键的缺失会让兵种表的可读性依赖读者的算术;而系数只活在代码里就等于第二真源。双存两头都不放弃,且不一致在装载期就红。
  - **例外:内存软阈不入键清单**。它是「某个上限乘以一个系数」的纯展示项,落进取值文件只会多一个能填错的格子(规则标定环交接单 §2.1 已如此裁定,本 feature 照办)。
- **满产烧钱率**与生产耗时系数同族,同为真源包的常量。
- **规则版本号**由真源包导出常量,取值文件、规则文档目录名、键清单三处一致性由机器判定,错配在装载期拒跑,不静默降级。

### 预算键的必填性与未定值

- 9 个预算键在 M1 阶段**全部必填**,取值为 `0`,语义是**未定值**:机制已定、终值标定已交给后续的图。
- 规则版本文件里**缺键**与**键存在但取 `0`** 是两种不同的错误,JSON Schema 要求前者报错。
- 面向模型的规则文档的数值表把 `0` 渲染成「未定」而不是数字。这是**文档可见**,不是运行时行为——不为它引入任何判罚逻辑。
- 理由:不选「可选键」是因为那会把一次「加必填」的破坏性 schema 变更推到预算终值标定(K)节点,而 K 在关键路径上;不选「运行时见到 `0` 即拒」是因为那会让 E 阶段的终稿契约复跑被占位值卡住。

### 校验器:落在 CLI 应用

- **ajv 校验器只存在于 CLI 应用一处**。真源包交付 JSON Schema **数据**,不交付校验器——它受包依赖规则的约束,不能依赖 ajv,且被限定为「无运行时代码」。
- **引擎与调度包收已校验对象**。调度包启动时的「版本比对」是纯字符串比较(拿真源包的版本常量),零依赖。
- **隐含假设(须在 spec 里写明)**:接受「调度包不独立校验形状」,即 FR-10 AC2 的「读入端强制校验」由 CLI 这一个入口兑现。理由:hld §2.2.8 已把「schema 校验器」列在调度与 CLI 名下而不在引擎名下;CLI 是唯一用户面,所有外部数据(文件 / 参数 / 子进程输出)都从它进来,一处校验覆盖全部入口。
- 真正的风险不是「校验点少」,而是日后有人为了让调度包也能校验而手写一份形状 if ——那才是第二真源。因此**本 feature 不新增任何 CLI 子命令**,校验器的测试断言落在它导出的纯函数上。
- **诊断分两层**:机器层是 ajv 的原始诊断(路径 + 关键字 + 消息),面向模型层是渲染后的短句,含 JSON 指针。**面向模型层对同类错误合并**——多个键缺同一个字段时并成一行而不是逐行列出,这是生成管线的五轮迭代预算能撑住的前提。

### 生成器:在工具包,混合传输,注册表驱动

- **生成器代码在工具包**,不放生成管线包,原因有三条,按权重:①生成物漂移检查要进 PR 主流水线,而生成管线包按 hld §2.2.6 将来要装 HTTP 客户端与各厂商 SDK,一条「只读写仓库内文件、零联网」的仓库门禁不该让依赖面随别的节点扩张;②它要推翻 D3 刚写进 hld §3.1 的既有理由(工具包之所以独立存在,就是为了不把仓库自身的门禁挂在唯一联网包下);③两个包的产物语义不同——生成管线包按批次追加存档,文档生成物是整体重生成、判定标准是「重生成后无差异」,放一起会让漂移检查的判定逻辑和追加语义缠在一起。
  - 诚实排除两条**伪理由**:「装依赖会变慢 / 有 postinstall 风险」不成立(workspace 一次装全);「生成器会联网」不成立(它不联网,真正的理由是①的依赖面随 H 扩张)。
- **混合传输**,分界线是「能不能 afford 构建」:
  - **生成器 import 真源包**:生成器是低频入口(跑一次),前置一次 `tsc -b` 无所谓。为此工具包要**正式声明**真源包为依赖并加 project reference——这条 import 方向合法(指向依赖图的根),且改写 hld §3.2 那句「工具包不 import 任何 `@model-war/*`」为「工具包只允许 import 真源包这一个根包」。
    - 相对路径 import 真源包**已被排除**:工具包 tsconfig 的 `rootDir` 写死,引进来会 `rootDir` 越界(TS6059),ADR-0002 已实测记录。
  - **规则层读生成的源文件**:工具包以源码形态由 Node 的类型擦除执行、不产 JS、且快门禁今天**零构建**(新克隆跑第一条命令不需要先 `tsc -b`)。让规则层 import 真源包会给快门禁加上一个构建前置(实测 `tsc -b` 增量 0.32s,`check:quick` 由 1.04s 涨到约 1.36s,+31%),并让新克隆在第一次跑门禁时可能失败。改由生成器产出清单的源文件供规则层 import。
- **生成物注册表**:生成器持有一张清单,每件 = (id、产出路径、生产函数)。**本 feature 只注册一件**(内置全局白名单 → 工具包内的生成源文件)。漂移检查自动覆盖注册表里的每一件,不为「将来会有第二件」预留分支。E 接入文档生成时只需**注册**两件(规则文档的数值表、API 表),不改骨架。
- **允许名单的手写副本在本 feature 内退役**,了结它头注里记着的那笔债;真源随之迁到真源包一侧,「生成物与手写表不得并存」自此兑现。

### 漂移检查:形态与实现

- 漂移检查挂在全量门禁 `check` 的末尾,**不进 `check:quick`**(它需要 `tsc -b`,而 `check:types` 里已经有)。
- 实现是 **git 路径限定 + 状态检查两刀**,不是裸的 `git diff --exit-code`:
  1. `git diff --exit-code` 限定在生成物路径上——捕捉「改了没提交」,同时不把开发者工作树里别的未提交内容报进来(hld §2.2.5 那句「跑 `git diff --exit-code`」要按此补写,否则它描述的是一个会误报的实现);
  2. 一道按生成物路径的状态检查(未跟踪文件算失败)——**捕捉新增生成物没进版本库**。裸 `git diff` 看不见未跟踪文件,而本 feature 的第一件生成物就是新增的,它若没被提交,裸 diff 依然全绿。
- 不采用「生成到内存逐字节比对」:它不检查「生成物是否进了版本库」,而那正是这道检查的一半价值。

### 真源包的导出面

- **对外单一入口**,包内按域分文件(参数清单 / 常量表 / 规则集 / 地图 / 回放行 / 存档 meta / result / JSON Schema 各一份,统一从一个入口再导出)。
- 理由:深模块的要点是「接口小」而不是「文件少」。四个消费者都只需要从一个入口 import;包级公共面一旦做成多入口就等于对外承诺,将来想收窄就晚了。

### 沙箱侧与静态校验器的接口

- **名单类数据一律由真源包提供**:内置全局白名单(含 `Math` 成员表)、沙箱注入的 API 符号表、宿主桥前缀、禁列全局名(`Date` / `Math.random` / `performance` / `queueMicrotask`)。
- **静态校验器的规则只负责「怎么查」**(AST 遍历、违规产出、退出码),一个名字都不自己存。
- 理由:hld §6.2 明写白名单「由真源包生成,与沙箱 runtime 暴露的 API 面同源」;而宿主桥前缀禁令与「桥函数初始化后被删除」是**同一套命名约定**,在工具包存第二份就等于多了一处「什么算宿主桥」的定义。
- **不属于名单的**:脚本体积上限是**数值**,按 hld §6.2 取值在规则集文件里,不由真源包提供。
- **沙箱注入的 API 符号表在真源包内是空的**,内容随沙箱执行器(G)回填——与变体槽位同一条纪律(见 Further Notes)。

### 常量表的边界

- **进**:规则版本常量、参数键清单、生产耗时系数、满产烧钱率、内置全局白名单、沙箱注入 API 符号表。
- **不进**:WASI 三件套取值(`clock_time_get` 覆盖值 / 固定字节填充 / 时区偏移)与中断计数粒度。它们是沙箱执行器的实现常量,**取值归那一格**;真源包在回放 meta 行里只拥有对应三个字段的**名字与类型**,不拥有取值。
- 分界线:**「谁在运行时决定这个值」归实现包,「这个值叫什么、什么形状、范围如何」归真源包**。

## Testing Decisions

### 什么算好测试

只断言**外部可观察行为**。本 feature 的外部行为只有两件:一条命名脚本通过或不通过;一段数据被接受或被带诊断拒绝。凡是能靠改内部结构而失效的断言,都是坏断言。

### 缝(两条,外加一条属性测试)

1. **主缝:根门禁脚本的退出码**。断言对象是 CI 将来会敲的命名脚本(生成器、漂移检查),不是任何内部函数。骨架阶段(D3)已用同一条缝,本 feature 沿用,不新造。
   - **每道检查都要有一个能被弄红的反例**:改真源而不重跑生成,确认漂移检查非零退出后还原。
2. **副缝:校验器的纯函数**。断言对象是「一段 JSON 值 → 接受 / 带诊断拒绝」,不碰文件系统、不碰 CLI 退出码。**`map-lint` 的地图校验断言也落在这里**,不通过它的退出码测。
   - 覆盖点:合法数据接受;缺键拒;错型拒;额外属性拒;规则版本错配拒;预算键取 `0` 接受但渲染为「未定」;缺预算键与「键取 `0`」被区别对待;变体槽位取最松形状时通过、破坏四重对称的前置由 map-lint 那一侧负责。
   - **两类诊断的断言分别写**:机器层的路径与关键字、面向模型层的短句与同类合并。合并行为必须有一条用例(多个同类错误 → 一行),否则它会被后来者改成逐行输出而无人察觉。
   - **Q4 的一致性断言挂在这一条缝上**,不另开:同一组 fixture 既过 TypeScript 类型又过 ajv,外加「JSON Schema 的必填键集合 === 对应类型的键联合」的类型级断言。
3. **属性测试(一条)**:任意 JSON 值输入,校验器要么接受、要么给出结构化诊断,**永不抛未捕获异常**。这是手写 schema 最容易漏掉的一类崩,交给手写用例覆盖不到。

### 明确不测

- **沙箱侧的行为事实**(桥函数删除后的不可见性、注入面)不落仓库测试——它们是对第三方库行为的断言,不是对我们代码的断言,与 D3 的同类决定一致。
- **C 阶段不测存档 meta / result / 回放行的形状**,因为这三类本 feature 不交付。

### 先例与禁令

- 先例:D3 的 spec 已确立「根门禁脚本退出码 + 校验器纯函数」两条缝与「每道门禁都要有能被弄红的反例」的纪律,本 feature 沿用。fast-check 的属性测试风格亦有先例。
- 沿用 hld §2.2.4 的既有禁令:禁快照测试(测试红了会被更新快照而不是查 bug)、禁覆盖率门禁(可被刷)。本 feature 两者都还不适用,但禁令继续有效。

## Out of Scope

- **存档 meta、result、回放行三类形状的字段**。家已定在真源包,字段要到 H / F 才定,本 feature **不交半成品**:JSON Schema 放行额外属性就等于不校验,却会让人以为「回放行已校验」,比不写更坏。三类的回填是 F / H 票里的显式一条。
- **规则集取值文件本身**与规则文档的散文。它们归 E。本 feature 只提供键清单与生成器骨架。
- **地图的具体坐标与点位数量不变量**。归 A(地图图)。C 只定义变体槽位的过渡形状(见下)。
- **沙箱注入 API 符号表的内容**。归 G;真源包里它是空的,位置留着。
- **任何 CLI 子命令**。不新增 `validate` 之类;hld §9 的六个子命令不动。
- **工具包的依赖门禁缺口**。hld §3.2 自述该包以源码形态执行、不在依赖门的巡航范围,第三方依赖面「只靠自觉」。**这个缺口交办给 D**,不在本 feature 补——下一个碰这个包的人是 D 不是 C。理由记在这里以免日后有人以为它被漏了。
- **生成管线包作为生成器落点的方案**。已按上面三条理由排除,不是待议。
- **变异测试(Stryker)配置**。留到结算管线落地。
- **CI/CD 流水线本体**。门禁以命名脚本手工触发,与 D3 同。

## Further Notes

### 计划内回填(两条,须在各自的票里显式认领)

1. **变体槽位的元素形状**。C 交付「必填数组 + 最松的元素形状 + 显式的「待回填」标记」,map-lint 只断言四重对称性(hld §7.2 已定)。**回填触发条件是 A 节点产出地图图**;回填时**一次改完**(TypeScript 类型 + JSON Schema + map-lint 断言),漂移检查保证三处同改。这是一次**计划内的变更,不是返工**——C 的验收标准里不包含变体槽位的字段。
2. **存档 meta / result / 回放行三类形状**。同上,家已定,字段由 F / H 的票回填。

### 本 feature 要一并修正的设计文档

按「每个事实只有一个家」,以下几处与本 feature 的裁决冲突,修矛盾的一方:

- hld §2.2.5:JSON Schema 的形态(导出的数据对象而非 `.json` 文件)、漂移检查的实现(路径限定的 `git diff` + 状态检查,不是裸 `git diff --exit-code`)、校验器落点的措辞。
- hld §3.1:`replay` 包的职责收窄为「编解码 + 回放文件格式版本常量」;生成器职责的归属说明。
- hld §3.2:「工具包不 import 任何 `@model-war/*`」改为「只允许 import 真源包」;补上工具包**有意**在依赖门禁巡航范围之外(它以源码形态执行)。
- hld §2.2.7:漂移检查那行「待 `schema` 落地后才有内容」在本 feature 之后成为事实,措辞要跟上。
- hld §7.1:预算键的未定值口径与「缺键 ≠ 未定值」。
- hld §7.2:变体槽位的过渡形状标注。

### 一处需要在文档里写明的张力

FR-10 AC2 写的是「读入端强制校验」,而 C 结束时只有规则集与地图两类真正被校验。这个覆盖不完整是**刻意的**且只持续到 F / H 落地为止,但它必须写在文档里而不是留给后来者去发现——否则「读入端强制校验」会被当成已经兑现。
