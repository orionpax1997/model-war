# 06: 生产——每基地一条队列

**What to build:** `spawnUnit` 这条**玩家级**意图在真引擎上落地:下单即占住那条产线,出兵格空出来才续出那一步。四条并列的规则一并落地——**一条产线一次只有一个订单**、**产线有订单时重复下单静默丢弃**、**出兵格被任意单位占据则挂起等待**、**基地易主时那条队列取消并全额退款给原主**。

**两处最容易写错的地方写在这里**:

**一、没有「产线忙」这个错误码。** 重复下单是**静默丢弃**:不扣款、不计异常、队列不变。错误码表里本来就没有那一码,也不要新加——脚本的正确写法是先读点位上的产线订单、为空才下单,不必自己记队列,也不必靠重复下单去试探队列状态。

**二、产线订单在状态模型里只有一份数据源,在点位上。** 脚本读到的就是它,不是一张独立队列表。这条解掉了架构文档与契约面之间那处真冲突(契约面已经宣告「字段名在这段声明期间不改」),而投影回来那件事会一直等下去。

**下单的校验顺序是资金先、扣款后。** 资金不足则这一单**无效**,不占产线队列、**不扣款**,资金一个不少地留着。

## Answer

### 一、§4.1–§4.4 每处裁法与理由

**§4.1 `check()` / `run()` 的形状**(`processor/production.ts`):照 `movement.ts`/`combat.ts`——
只读视图 `ProductionView`(每栏 readonly,只收 `sites` 与 `players`)+ `checkSpawn()` + 纯函数 `runSpawn()`。
判据五条、次序即表:**基地存在 → 是基地不是资源点(`kind === "base"`)→ 属主是该座位 → 资金够 → 该基地当前无订单**。
`runSpawn()` 返回一条 `start-production`,由唯一写入口 `apply()` 同时落「占队列」与「扣款」。

**「资金不够」是结构性的**:`checkSpawn()` 判在**产生任何变更之前**,不足即返回 `false`,`runSpawn()` 返回 `null`——
压根没有变更被造出来,也就没有「先扣了款、再发现占不上队列」的中途状态。扣款与占队列收在**同一条**
`start-production` 里(理由写在该变更的注释与 `production.ts` 头注:一条规则一次落子,中间没有可观察的半截状态)。

**§4.2 易主时的取消与退款**:易主发生在步 4 的 a) 段,所以接缝写在 a) 的循环里、落在 d) 之前
(`steps/step4-object-tick.ts`)。**原主从哪来**:占领机 `captureChangeOf()` 在算出易主时,把
`previousOwner: site.owner`(易主**前**的属主)显式带在 `advance-capture` 变更单上(`driver/apply.ts` 里
该栏的注释写清了为什么不让调用方事后去状态里翻——a) 一落地,状态里的 owner 已是新主)。步 4 的接缝读
`change.previousOwner`,产出一次 `cancel-production`(清队列 + 全额退款**同一条变更**)。
退款额取自订单兵种的**全额 `cost`**(与 `remainingTicks` 无关)。**原主已淘汰(`alive === false`)也照退**:
退款只是往 `Player.resources` 这个数上加一笔,退给一个已出局的席位不违反任何不变量。
「原主已淘汰时不退款」对应的是**回归中立**那条路(点位回到 -1、没有可退的席位),归票 09。

**§4.3 推进与挂起**:d) 先落本 tick 的 `spawnUnit` 意图(下单),再按点位数值 id 升序遍历推进所有队列。
**挂起语义定死为 `remainingTicks` 停在 0**:归零那一 tick 写一次 `advance-production` 到 0;此后每 tick 再读仍是 0,
不再写 `advance-production`(0 减一会得到 -1,那条规则不存在),只每 tick 重试出兵。出兵格**就是基地格本身**;
被任意单位(含己方)占据则挂起——不跳过、不换格。`create-unit` 的属主取**基地当前的 owner**。

**下单那一 tick 计入生产耗时**:d) 先下单再推进,于是刚下的单也吃本 tick 的一次推进——
`spawnTicks = N` 的兵在下单后**第 N 个 tick 的 d)** 里归零出兵(下单 tick 记为第 1 个 tick)。
用例把它们钉死(«下单那一 tick 计入生产耗时»、«每 tick 推进»)。

**§4.4 边界**:本票只做 a)(票 05 已落)与 d)(本票),外加 a→d 之间的接缝。b) 采集 / c) 交付两段仍是
「尚未落」,归票 07——`step4-object-tick.ts` 的注释里点明了两段的位置与「别顺手实现」。

### 二、§3 那两处「最容易写错」的钉法

**一、没有「产线忙」这个错误码。** 行为上:重复下单静默丢弃(不扣款、队列不变、`events` 为空),
由 4 条用例钉。**错误码清单**这一侧:引擎包只能经 `replay` 看到类型面,看不到真源包那张运行时表,
所以用例**直接读 `packages/schema/src/script-surface.ts`**(零依赖、只在测试里读一次),抽出全部带引号的
`ERR_*` 名字(`matchAll(/"ERR_[A-Z_]+"/g)`),先断言表非空(含 `ERR_NOT_ENOUGH_RESOURCES`),再断言
**不含任何匹配 `/BUSY|QUEUE|PRODUC|BASE/` 的码**。谁哪天给 `spawnUnit` 加 `ERR_BASE_BUSY`,这一条当场变红——
不可能靠「改一个正则」糊过去而不动真源。

**二、产线订单只有一份数据源 `Site.producing`。** 本票不引入队列表、不在别处镜像一份:下单写它
(`start-production`)、推进读改它(`advance-production`)、清空它(`cancel-production`)。脚本通过快照读到的
就是 `Site.producing`(快照 = `GameState` 深拷贝,同一条形状)。

### 五、留给后续票的话

**给票 07(b) 采集 / c) 交付)**:`step4-object-tick.ts` 里两段的槽位已就位(a 与 d 之间,顺序不可换),
注释标了「尚未落」。交付进玩家池、生产花钱走玩家池,顺序理由已写在步头注。

**给票 09(淘汰 / 回归中立)**:易主的退款路径在本票是「取消队列 + 全额退款给**原主**」,退款对象由
`advance-capture` 变更单上的 `previousOwner` 显式带出(见 `driver/apply.ts`)。**回归中立**那条路(被淘汰玩家名下
点位回到 `-1`)要「取消队列且**不退款**」——它对应的是 `cancel-production` **不带 `refund`** 的那一支
(本票已把该变更的 `refund` 做成可选,正是为它留口),差别就在「有没有一个原主可退」:
易主时原主是一个真实席位(哪怕已 `alive === false`,退款只是往资源池那个数上加一笔),
回归中立时没有席位。**本票的用例只钉「退款给原主且是全额」,不覆盖回归中立分支。**

**给票 10(不变量)**:本票新增/收紧的不变量——
1. `Site.producing` 是产线订单的**唯一**数据源;非基地点位的 `producing` 恒为 `null`(资源点不是产线)。
2. 一条产线至多一条订单;下单要求属主是玩家席位、资金足、队列空。
3. `.producing !== null` 的点位,其 `owner` 必是玩家席位(非 -1)——挂起与出兵都以它为据。
4. 扣款与占队列、清队列与退款,**各是同一条变更**(不存在半截状态);`Player.resources` 只在
   `start-production`(减)与 `cancel-production.refund`(加)两处变。
5. 出兵单位属**基地当前 owner**;基地易主必先于同 tick 的队列推进(接缝在 a 段之后、d 段之前)。
6. 挂起期间 `remainingTicks` 恒为 0,不出负数。
