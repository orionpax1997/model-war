# 10: 状态维护的不变量与反例

**What to build:** 两条**关于状态维护本身**的断言落成用例。它们与「重跑十次一致」是两条不同的东西——那条测的是执行路径的可复现性，这两条测的是**状态的形状有没有被保持**。

**第一条:乱序的单位数组产生不同的 `stateHash`。** 状态哈希的规范化是「对象键升序、**数组保序**、标量走 JSON 序列化」,而数组保序的理由写在那个原语的头注里:「对象数组的升序由状态不变量保证,本函数保序不做重排」。也就是说,**它不替你重排**——所以「状态维护违反 id 升序不变量」这件事必须表现为哈希变化。若不变量被破坏而哈希照旧不变,复算那条路就看不见它,那条不变量等于不存在。

这条是**本 feature 的核心不变量测试**,它属于这一格而不是状态哈希那个包:那个包保证的是「我按你给的顺序算」,这一条保证的是「你给的顺序本来就是对的」。

**第二条:同一构造两次得到逐项相同的事件序列。** 事件流按「产出它的那一步 → 步内按对象数值 id 升序」定全序,**不允许事后按插入序**——后者会让同一局重跑得到逐项不同的事件序列,而复算与叙事战报都读这一列。叙事战报生成器只消费事件、不重新解析状态,所以事件序列的稳定性就是战报稳定性的全部。

决策依据：`.scratch/engine-core/spec.md`《`stateHash`:载荷是那一行去掉自身》《结算管线》两节。

**Blocked by:** 02（脊柱）, 09（评估——四种终局与名次）

**Status:** ready-for-agent

- [ ] **反向钉**:喂一个单位数组乱序的状态,断言状态哈希与按升序排好的那份**不同**。这条用例的存在理由写进注释(它钉的是「不变量被破坏时这件事可见」)
- [ ] 正向钉:同一份状态按 id 升序排好后,哈希与不重排的直接计算**逐字相同**（证明键升序那半确实在重排键、而数组那半确实没重排）
- [ ] 状态里的一切对象数组（单位、点位）在每 tick 结束时**按数值 id 升序维护**——不是只在发出前排一次。断言对象是**状态本身**的顺序,不是发出的那一行（后者会在写出路径上掩盖前者）
- [ ] 事件序列的全序在**机制票落地后仍成立**:同一构造跑两次,事件流逐项相同（种类、顺序、携带的数值 id 都相同）
- [ ] 事件定序规则的实现位置要**可读出来**——七步各只往收集器调具名方法,不允许某一步随手往数组里 push。那条规则写在收集器的头注里
- [ ] 两个事件同 tick 同一步产生时,按对象数值 id 升序而不是按产生顺序。用例:两处易主同 tick → 顺序由 id 定
- [ ] 每条各有一个能被弄红的反例:把写出路径改成发出前排序 → 反向钉红;把某个事件的收集改成按插入序 → 全序用例红
- [ ] 明确记下**这一票不覆盖复算一致性**（重跑十次逐 tick 全等）——那是下一票的验收,两条断言不互相替代
