# 10: 状态维护的不变量与反例

**What to build:** 两条**关于状态维护本身**的断言落成用例。它们与「重跑十次一致」是两条不同的东西——那条测的是执行路径的可复现性，这两条测的是**状态的形状有没有被保持**。

**第一条:乱序的单位数组产生不同的 `stateHash`。** 状态哈希的规范化是「对象键升序、**数组保序**、标量走 JSON 序列化」,而数组保序的理由写在那个原语的头注里:「对象数组的升序由状态不变量保证,本函数保序不做重排」。也就是说,**它不替你重排**——所以「状态维护违反 id 升序不变量」这件事必须表现为哈希变化。若不变量被破坏而哈希照旧不变,复算那条路就看不见它,那条不变量等于不存在。

这条是**本 feature 的核心不变量测试**,它属于这一格而不是状态哈希那个包:那个包保证的是「我按你给的顺序算」,这一条保证的是「你给的顺序本来就是对的」。

**第二条:同一构造两次得到逐项相同的事件序列。** 事件流按「产出它的那一步 → 步内按对象数值 id 升序」定全序,**不允许事后按插入序**——后者会让同一局重跑得到逐项不同的事件序列,而复算与叙事战报都读这一列。叙事战报生成器只消费事件、不重新解析状态,所以事件序列的稳定性就是战报稳定性的全部。

决策依据：`.scratch/engine-core/spec.md`《`stateHash`:载荷是那一行去掉自身》《结算管线》两节。

## Answer

### 落点

全部用例落在**引擎包**的 `packages/engine/src/processor/state-invariants.test.ts`(新建,8 条),与票面「这条不变量测试属于这一格而不是状态哈希那个包」一致:哈希原语(`packages/replay` 的 `stateHashOf`)测的是「我按你给的顺序算」,本文件测的是「你给的顺序本来就是对的」。

- **§3.1 反向钉**(乱序 → 哈希不同):`makeState` 造一份 units=[1,2,3] 升序态,再换序成 [3,1,2],断言两者 `stateHash` 不同。**同时经写出路径**(`buildTickLine(shuffled).stateHash`)与 `stateHashOf` 原语两处钉——因为写出路径上「发出前顺手排一下」会把违规掩盖掉,而那正是这条用例要拦的改动。注释写明存在理由:数组保序、不重排,所以「状态维护违反 id 升序」必须表现为哈希变化,否则复算那条路看不见它。
- **§3.2 正向钉**(两半各管一件事):一条断言**对象键书写顺序相反**、语义相同的两份状态哈希**逐字相同**(键那半在重排);另一条断言**升序数组**的哈希与「不重排的直接计算」(手拼载荷)逐字相同(数组那半没重排、升序是固定点)。两条与 §3.1 配对,正向面 + 反向面共同证明「键升序、数组保序」。
- **§3.3 状态数组升序**:一个 tick 里同时发生**新建(基地 11 产线归零出兵,新号 100)+ 移动(座位 2 的单位 4 右移)+ 死亡(单位 3 打死单位 5)+ 易主(点位 3、7 同 tick 易主)**,连跑 3 tick,每 tick 结束断言 `result.state.units` / `result.state.sites` 严格 id 升序。断言对象是**状态本身**,不是写出的那一行。
- **§3.4 事件全序**:同一构造连跑 3 tick,跑两遍,`second.events` 与 `first.events` 逐项 `toEqual`(种类、顺序、主体数值 id 全同)。
- **§3.5 定序规则可读**:读 `steps/*.ts`(8 个文件,去注释后),断言其中**没有** `.push(` / `.unshift(` / `.splice(`。钉的是「定序规则的实现位置只有收集器一处,任何一步绕过它直接改数组都会让规则失效」。路径用 `new URL(..., import.meta.url)` 相对定位(照 `production.test.ts` 读 `script-surface.ts` 的先例)。
- **§3.6 同一步内按 id 升序**:见下。

### §3.6 那个必须查清的要点(如实记录)

**票面建议的「两处易主同 tick → 顺序由 id 定」这个端到端构造,区分不了「按 id 定序」与「按登记序」。** 原因:步 4 的 a) 段按 `state.sites` 的次序遍历,而 `state.sites` 已由 §3.3 那条不变量保证数值 id 升序,于是两个易主的**登记序本来就等于 id 升序**。这条端到端用例照写了(`state-invariants.test.ts`「两处易主同 tick → 事件按点位数值 id 升序」),它是一条**有效的回归护栏**,但**不是**两种定序的判别器——注释里如实标注,不假装它证明了更多。

**真正能区分两者的是收集器层的直接登记用例**:`createEventCollector()` 后 `siteCaptured(7)` → `siteCaptured(3)`,断言 `events()` 交出 `3` 在前(登记序与 id 序相反,只有定序规则真的生效才会翻成 id 序)。再补了三条跨主体/跨步的:`unitDestroyed(9)` → `unitDestroyed(2)` 输出 2 在前;玩家级 `playerEliminated(3)` → `playerEliminated(0)` 输出 0 在前;跨步 `siteCaptured(1)`(步 4)→ `unitDestroyed(9)`(步 3)输出单位事件在前(步号是第一排序键,压过主体 id)。

`events.ts` 头注自己也写着兜底那条(同一步、同一主体、同一种类才轮到登记序)「在规则层**几乎**不可达」——八种事件里每种的主体在一 tick 内至多出现一次,所以正常规则路径下根本走不到登记序。这正说明端到端构造碰不到判别点,必须下到收集器层直接构造。

### 边界(留给后续票的话)

**本票不覆盖复算一致性。** 「同一局重跑十次、逐 tick 状态与哈希全等」是**下一票(票 11)的验收**——那测的是执行路径的可复现性;本票两条断言测的是**状态的形状有没有被保持**(数组按 id 升序)与**事件全序是否由规则定**。两者不互相替代:形状对了不代表每次跑都一致,每次跑一致也不代表形状维护对。
