# 03: 脚本 API 的类型面回填

**What to build:** 一份模型写错的脚本**在编译期就红**,而不是编译通过、跑到沙箱里才炸。那道防线是编译器的「找不到这个名字」,而它要有东西可依——真源包里那份脚本 API 类型声明(`packages/schema` 拥有,`tsconfig.scripts.json` 的 `types` 经它引入)。

**这是 hld §6.2「API 误用」那一行第一次真的有人。** 此前脚本编译配置的 `types` 是空数组,那一行是空头承诺;本票落定之后,「编译通过 + 白名单反转 + API 签名」三件事同时成立,**生成管线的编译步骤就此解锁,不必等沙箱执行器**。

**类型面归本 feature 而不是沙箱执行器**,理由见 `docs/adr/0006-script-api-type-surface-lands-in-engine.md`:类型面描述「脚本能读到什么状态字段」与「action 的签名」,前者的源头是本 feature 的状态模型、后者的源头是意图的 `check()`/`run()`,而沙箱执行器只搬名字、不定义任何一个。名字表按定义给不出签名,倒推出的声明必然与实现分叉。

**顺带销掉 `docs/adr/0004` 留的那笔账**:真源包那张符号表的注释写着「刻意为空,回填触发条件是沙箱执行器产出注入面」,本决定之后那句话会说错话,必须改掉,否则后来者会按注释把它当成待办而跳过。

决策依据：`.scratch/engine-core/spec.md`《脚本 API 的类型面归本 feature》一节。

**Blocked by:** 02（脊柱——空转一整场到超时,回放端到端可渲染）

**Status:** ready-for-agent

- [ ] 声明面落进真源包,覆盖快照的**全部**可读字段与**全部** action / 查询函数签名,与那张 23 条符号表逐条对齐
- [ ] 座位**不在**声明的快照形状里,只由 `getMyIndex()` 给出——契约面已经这么承诺,类型面不许留第二个入口
- [ ] 产线订单在声明里是**点位上的那一个字段**,不是一张独立队列表;这份声明与骨架那张票定下的状态模型逐字段一致（同一条形状,不是投影）
- [ ] 脚本编译配置的类型环境**只额外引入这一份声明**。一条用例钉住:一份引用 Node 专有名字的脚本**编译期就红**（引 Node 类型等于把宿主能力带进沙箱,白名单反转当场漏）
- [ ] 一条用例钉住:把某个 action 的名字拼错 → **编译期红**。这是本票的核心验收,没有它就只是搬了一份文件
- [ ] **只声明动作与查询的类型,不声明数值**——数值归规则集那条生成链。这条判据照搬符号表那条收录判据,逐字写进注释
- [ ] 那 15 条 `signature` 字符串**由声明面取代**:生成或删除,**不并列存在**。两份会分叉的真源是最坏的一种,注释里原本就写着「签名是类型面的事实」
- [ ] 符号表头注里「刻意为空,回填触发条件是沙箱执行器」那段按 `adr/0004` 的要求改掉,`adr/0004` 那笔账标注为已销
- [ ] 意图的 `check()` 的入参类型里**根本没有写入口**——这条由类型形状保证,不靠约定。类型一旦给了写入口,「它不会写引擎状态」就退化成纪律而不是事实
- [ ] 与沙箱执行器的那条同步面写进注释:类型面（形状,归本 feature）与注入面（名字铺放时机、桥函数删除时机,归沙箱执行器）**同源于一份形状,但只有一份形状**。若某个名字在声明里而注入面铺不出来,那是注入面的缺陷,不是「声明漏了」
- [ ] 一条反向用例:换成一份旧版声明 → 用例红（防止有人把这份声明做成运行时可绕过的软约束）
