# 对局内核

Status: ready-for-agent

## Problem Statement

规则与数值已落库(`rulesets/v1.json` 21 键、`docs/rules-v1/` 两份契约面、三张四重对称真图),M1 的交付物已交齐。但**从一份「四个座位 + 一张地图 + 一个种子 + 一份规则集」到一份可复算的回放,这条路一步都还没走**。`packages/engine` 里只有一份状态模型的类型声明和一份事件流恒为空数组的行字面量,`world` / `driver` / `processor` / `intents` / `snapshot` / `ruleset-loader` 全部未实现;`apps/cli` 的六条子命令里只有 `map-lint` 落地,`match` / `replay` / `verify` 三条的处理器还只是路由表里的一行。于是有五件事同时为真:

1. **「跑完一个对局」这个动作不存在**。hld §4.3 的八行结算管线(编号 0–7,其中 1–7 是那七步)与 §4.4 的移动碰撞裁决都写成了规范,`docs/gdd.md` 里每条机制都有家,但**没有一行实现它们**。而 hld §4.3 末句明写「顺序即规范:任何顺序调整都是规则变更」——现在连「是不是这个顺序」都无法验证。
2. **确定性是一票否决项,而它今天只能靠承诺**。srs 的 NFR-1 要求 CI 里有「重放一致性」测试,FR-2 AC1 要求同配置重跑 10 次每 tick 状态 hash 全一致;`packages/replay` 已经有 `stateHashOf` 与它的规范化实现(`packages/replay/src/index.ts:22-42`),但**没有任何东西产出过一行 tick**。
3. **规则集至今没有任何生产路径读它**。hld §7.1 自陈「被校验过不等于被装载时校验过:今天仍然没有任何生产路径读它」,因此 FR-10 AC2 的「错配拒跑」与「读入端强制校验」按尚未兑现记;而 `modelwar match` 要跑一场对局,第一件事就是装载规则集。
4. **三笔形状有家无字段**。`packages/schema/src/pending.ts` 挂着三份「位置与标记」:`archive-meta`(归 gen 侧)、`match-result`(归 engine 侧)、`replay-line`(归 replay 侧),字段全部未回填,按 hld §2.2.5 的纪律刻意不写放行额外属性的空 schema。而 F 要读 `archive-meta`、要产出另两份。
5. **脚本 API 的类型面无人回填,于是「API 误用」无人承担**。`tsconfig.scripts.json` 的 `types` 是空数组(其头注:「回填之前这里刻意为空」),hld §6.2「API 误用」那一行写着判据是「真源包的类型面」——那份面还没落,于是脚本写错 API 编译通过、运行时才炸。

另有一处**文档间的真冲突**必须由本 feature 裁掉,否则实现时会各写各的:`hld.md:414` 与 `hld.md:728` 说产线是 `productions: Production[]`、`ticksLeft`;`docs/rules-v1/api.md:136` 对模型承诺的是挂在基地上的 `producing: { type, remainingTicks } | null`,并已宣告「字段名在这段声明期间不改」;而 `api.md:149` 自己承认那是承诺不是投影。三份文档三个说法,照 hld > gdd > srs > fsr 的采信顺序也解不开——它们争的是同一件东西的家。

## Solution

把 F 交付到**一条外部缝**:一个进程内函数,吃一份已物化的对局输入,产出一份可复算的回放。引擎内部的一切——状态模型、唯一写入口、结算管线、六个 intent、快照边界、规则集装载——都藏在这条缝后面。

- **对外只有一条缝**:`runMatch`。`apps/cli` 的 `match` 与 `replay` 两条子命令接完;`verify` 归沙箱执行器那一格(它要重新执行真脚本,而真脚本要真 VM)。
- **执行器是缝上唯一的变量**,缝的形状照 hld §4.5 已有的两次宿主桥调用;`StubRunner` 让「跑完一个完整对局」这道闸门在沙箱落地之前就开,`QuickJsRunner` 落地后换掉它,结算管线一行不改。
- **三笔形状有家无字段的账,这一格销两笔半**:`match-result` 与 `replay-line` 归本 feature 定死;`archive-meta` 因为 `hld.md:714-715` 已经逐项列全字段,提前定死形状、销掉 pending 条目。
- **顺带把四笔没人认领的跨节点账接住**:规则集装载期校验接线、脚本 API 类型面、状态模型与契约面的产线形状冲突、以及 A 交办出去的三张真图首触实测复核。

本 feature 不实现沙箱、不实现生成管线、不实现赛季。它交付的是**一条能在没有沙箱的情况下把一个对局跑完并留下可复算证据的通路**。

## User Stories

1. As a **对局内核维护者**, I want 一条 `runMatch` 的外部缝就能跑完一个对局, so that 结算管线的顺序、每一步的裁决与整场的一致性都在同一处被验证,而不是散在几个包的单元测试里。
2. As a **对局内核维护者**, I want 结算管线的七步顺序与每步的判据能在小夹具上单独验, so that 「交换/穿行/链式移动」这类只在两格单位上出现的情形不必靠整场对局的涌现来观察。
3. As a **对局内核维护者**, I want `processTick` 只作为处理器自己的内部构造器、不进包的导出面, so that 赛季调度与 CLI 不会开始依赖它——那会让引擎的接口面积翻倍、深度减半。
4. As a **规则侧维护者**, I want 「四方全部被淘汰」这种可达状态有明确的结果与名次, so that 判别联合的穷尽性是真的,而不是只在常见局面下看起来穷尽。
5. As a **规则侧维护者**, I want 席位不在快照里、经济死亡没有状态字段, so that 状态里只放不可推导的事实,派生事实只留事件一次。
6. As a **规则侧维护者**, I want 产线订单在状态模型与契约面里是同一份形状、同一套字段名, so that 契约面那句「字段名在这段声明期间不改」的承诺有一个真实的投影,而不是一份等回填的承诺。
7. As a **规则侧维护者**, I want 事件流按「产出它的那一步、步内按数值 id 升序」定全序, so that 同一局重跑得到逐项相同的事件序列。
8. As a **赛季调度维护者**, I want 每一行 tick 的 `stateHash` 覆盖那一行会写出的全部内容(含事件), so that 事件流的一次漏记在 `verify` 面前是可见的,而不是等到叙事战报少了一段才发现。
9. As a **赛季调度维护者**, I want 回放 meta 行显式记执行器身份(`stub` 还是 `quickjs`), so that 桩跑的读数与真沙箱跑的读数在数据上可分——否则有人会拿桩的读数当座位轮换的结论。
10. As a **赛季调度维护者**, I want 规则内结果(超时、四方全淘汰、席位异常出局、经济死亡)一律给零退出码, so that 赛季不会把它们当崩溃重跑剔除,让合法对局从报告里凭空消失。
11. As a **赛季调度维护者**, I want 装载期拒跑与引擎自身故障是两个不同的非零码, so that 「配置错了要人改」与「代码错了要人查」在 CI 日志里分得开。
12. As a **生成管线维护者**, I want 冻结脚本存档的形状由真源包定死并有读入端校验, so that 一份缺档或哈希不符的存档在执行前被拒,而不是跑出一场用到错误产物的对局。
13. As a **生成管线维护者**, I want 脚本 API 的类型面落在真源包里, so that 「白名单反转」这条由编译器承担的判据有类型可依,拼错的 API 名在编译期就红。
14. As a **生成管线维护者**, I want 生成管线的编译步骤不必等沙箱执行器就能起步, so that 它与引擎的实现期完全并行。
15. As a **沙箱执行器维护者**, I want 拿到一条已在 `StubRunner` 上跑通的缝, so that 我落地真 VM 时要证明的是沙箱行为本身,而不是两个执行器之间的等价性。
16. As a **沙箱执行器维护者**, I want `check()` 的入参类型里根本没有写入口, so that 「它在 VM 内跑得动」是类型形状保证的事实,不是一条纪律。
17. As a **沙箱执行器维护者**, I want 新增宿主桥要过 `packages/schema` 宿主桥前缀那道核对, so that 注入面与静态禁令永远两端一致。
18. As a **模型作者**, I want 我的脚本读到的状态对象改了也污染不了引擎, so that 我在 `loop()` 里做的任何试探都不会在下一 tick 变成别人的问题。
19. As a **模型作者**, I want 经济死亡的时点从事件里读到, so that 战报与报告给出的时刻与规则判定严格同一。
20. As a **模型作者**, I want 契约面承诺的 `producing` 字段真的在快照里读到, so that 我不必在脚本里另记一份产线队列。
21. As a **维护者**, I want 乱序的 `units` 数组产生不同的 `stateHash`, so that 状态维护违反 id 升序不变量时这件事是可见的,而不是被哈希悄悄吸收。
22. As a **维护者**, I want `input.json` 不含赛季配置, so that 同一份对局能被赛季复算,也能被单独重跑。
23. As a **维护者**, I want 首触的复核读数落在它被复验的那一条旁边, so that 「读数」与「偏差」不在两个地方各有一份。
24. As a **审查者**, I want 引擎的六个 intent 不是六条浅缝, so that 引擎的接口面积小到调用方要学的东西少于它拿到的能力。
25. As a **审查者**, I want 沙箱相关的事一条都不在本 feature 的交付里, so that 「引擎已验过」不会被误读成「沙箱已验过」。

## Implementation Decisions

### 交付面:两条子命令,一条外部缝

**外部接口唯一:`runMatch`**,吃一份已物化的对局输入,产出一份回放。`apps/cli` 登记的六条子命令里,本 feature 接完 `match` 与 `replay` 两条;`verify` 归沙箱执行器那一格。

`verify` 归 G 的理由:它要**重新执行真脚本**才能比对(FR-2 AC2 与 NFR-1 的对象是正式对局),而真脚本要真 VM。把它留在 F 只会得到一条只对桩回放成立的通路,而那恰恰是「已验过」的假象。

**验收闸门三件**,缺一不可:

1. 一条 `modelwar match <input.json>` 在进程内用 `StubRunner` 跑完一个对局,产出逐 tick JSONL 与末行 `result`。
2. `modelwar replay` 能把那份回放渲染成 ASCII 画面(不依赖引擎状态)。
3. **FR-2 AC1 的确定性验收**:同配置重跑 10 次,每 tick 的 `stateHash` 全部一致(`srs.md:42`)。

**顶层 bin 之外不许有第二个入口。** 测试走 `runMatch` 这个接口,但不得绕过 CLI 另开一条「库调用」的路——否则 FR-6 AC2 的拒跑与 FR-2 AC1 的重跑会比对在两套代码上。

### 进程退出码:二分,不是分类学

| 码 | 含义 | 判据 |
|---|---|---|
| `0` | 产出了一份合法的 `result` 行 | 胜、负、超时、四方全淘汰、席位异常出局、经济死亡**全都是 0** |
| `2` | 装载期拒跑 | 输入缺项、规则集版本三处不一致、地图校验失败、存档缺档、哈希不符 |
| `1` | 引擎自身故障 | 未捕获异常、确定性断言失败 |

两条纪律:**规则内结果一律 0**——gdd 的异常与出局机制意味着一份完全正常的对局可以带着三个异常出局的席位,那是对局内容不是进程状态,给它非零码会让赛季按 hld §8.4 的崩溃条款重跑并剔除,让合法对局从报告里消失;**子码要定死不留给实现**,`1` 是所有非零退出里唯一**不该有**的值,任何误用立刻暴露。

### 输入物化:形状定死在真源包,不加 pending

`input.json` 的形状**这一格就定死在 `packages/schema`**(类型 + JSON Schema + 读入端校验),`PENDING_SHAPES` **不加**第四条。理由是 pending 那三条的共同特征是「字段随那一票的实现才确定」,而 `hld.md:721` 已把它的五项逐项列全(4 × 存档路径 + 地图 + 种子 + 规则集版本 + 各文件 hash)。留成 pending 意味着 F 要么写一份 `pending.ts:6-12` 明令禁止的空 schema,要么跳过读入端校验,两条都是那条纪律点名要拒的。

**它不含 `season.yaml`。** 赛季配置是赛季调度的输入,单个对局只认自己这份 `input.json`——这条不写清,后来者会把赛季参数塞进去,那份文件就会长成第二个 `season.yaml`,而 FR-7 AC3 要求的是「每个对局可凭它复算」。

### 冻结脚本存档:形状提前定死,pending 条目销掉

`hld.md:714-715` 已经把 `meta.json` 的字段**逐项列全**。同一份 hld 的 §7.4 说「字段已列全」,`pending.ts:19-20` 说「字段随 gen 管线写出的那一版确定」——**这是一个事实两个家,按采信顺序 `pending.ts` 是错的一方**。本 feature 据 hld 定死形状与读入端校验,`PENDING_SHAPES` 里 `archive-meta` 这条**销掉**,改写成「形状已定,字段值随生成管线落库」。生成管线落地时只填值不改形状;真要改就是一次有意的变更,像改一个错误码名那样。

**FR-6 AC2 里那个「runner」明确为本 feature 的进程**:它是第一个执行脚本的进程,缺档必须在执行前拦住(FR-6 AC2 明写「报错退出,不跳过」);赛季调度复用同一条校验路径,不复写。这句话要写回 hld §7.4,否则「runner」两个包都算。

### 状态模型:产线订单的单一数据源在 `Site`

**`Site` 上加 `producing: { type: UnitType; remainingTicks: number } | null`;删掉 `Production` 类型与 `productions[]`;tick 行跟着不带 `productions` 栏。** `Site.remaining` 确认是资源点储量,`producing` 是产线订单,两个字段都在 `Site` 上。

决定性理由是 hld §4.5 已经裁了「快照 = GameState 的**深拷贝**」——让状态模型长成契约承诺的形状,是唯一不引入投影层的路。另一条路(状态保持 `productions[]`、快照投影到 `site.producing`)会给快照加一个投影层,那是**新的漂移面**,而且 `api.md:149` 把「投影回来」当成一件未来的事在等,它会一直等下去。选本条则三处(契约面 / 状态模型 / 回放行)用**同一个形状**,`api.md:149` 那句「还没有对应的投影」直接消掉。

要改的文档:`hld.md:414` 的状态模型字面量、`hld.md:728` 的 tick 行栏位。

### 执行器:缝就是两次桥调用,StubRunner 是第一个适配器

`engine:runner` 的缝照 hld §4.5 原样交付:`__setSnapshot(snapshot)` 进、`__drainIntents()` 出。详见 [ADR-0005](../../docs/adr/0005-runner-seam-is-the-two-bridge-calls.md)。

`StubRunner` 有一条硬约束:**必须同样做「拷一份快照、拿到 intent 数组」两件事,不能抄近路直接读引擎状态**。它一旦读真状态,测试就在验一条生产不走的路,而 FR-3 AC1 会变得无法证伪。

**测试侧的参赛策略写成普通 TS 函数**,不经字符串、不经 VM——那正是 StubRunner 存在的理由(让结算管线在没有沙箱的情况下可测)。

### 模块的深度:六个 intent 不构成缝

外部缝唯一,就是 `runMatch`。`processor` 与六个 intent 全是它的实现内部。**六个 intent 各自有且只有一个实现,因而它们不是缝**——把六个 intent 做成六个带公开接口的模块(各自导出 `check()` 与 `run()`、各自有上下文类型)是六条浅缝:接口面积大、实现小,调用方要学的东西多于它拿到的能力。真正变的东西只有执行器一处,所以缝只有一道。

**`processTick(state, intents, ruleset) → { state', events }` 是私有内部缝**:只给处理器自己的测试做构造器,**不进包的导出面**。它是内部缝而不是第二道对外缝,依据是「一个模块一个接口」。

**`check()` 的约束由类型保证,不靠约定**:它的入参类型是「只读视图 + 规则集 + intent」三样,**类型里根本没有写入口**,于是「它不会写引擎状态」是形状事实。`run()` 拿写入口。两者同文件、同一条注册表条目;`check` 随 runtime bundle 打包给沙箱执行器,那是一次**打包决策,不是一条缝**。

### 结算管线:八行里的七步,顺序即规范

照 hld §4.3 实现,编号 0–7;`0 dispatch` 建四方只读快照并按 `playerIndex 0..3` 串行执行各执行器的 `loop()`、收集 intents(预算与异常裁决在这一层),1–7 是那七步。`hld.md:497` 末句「顺序即规范:任何顺序调整都是规则变更」是本 feature 的验收对象,不是描述。

**七步各产出哪些事件**(`hld.md:734` 的八种事件):

| 步 | 事件 |
|---|---|
| 0 dispatch | `exception`、`budget-soft-warning`(由执行器上报,不来自结算) |
| 1 validate | 无(丢弃的 intent 走事件流的调试可观测栏,不带独立事件类型) |
| 2 movement | `first-contact` |
| 3 combat | `unit-destroyed`(聚合) |
| 4 objectTick | `site-captured`、`economy-dead` |
| 5 evaluate | `player-eliminated`、`victory` |
| 6 emit | 无(它就是写这一行) |
| 7 loop guard | 无 |

事件之间按「产出它的那一步 → 步内按对象数值 id 升序」定全序。**不允许事后按插入序**——那会让同一局重跑得到逐项不同的事件序列,而 `verify` 与叙事战报都读这一列。

### 快照边界:一份深拷贝 + 一次深 freeze

**每 tick 一次 `structuredClone` 深拷贝 + 一次深 freeze(同一次递归遍历),四个座位共用这一份只读快照。**

四条取舍:不用 JSON 往返(它顺手规范化键顺序,而 `stateHash` 另有一套规范化排序,两套规范化合成一套极难查;`structuredClone` 是全局不是 `node:` 导入,避开了 hld 的依赖巡航约束);不用四份拷贝(每 tick 四倍开销,而快照是每 tick 的主要开销,先用四倍成本去给 NFR-3 那个「X」定基线是在给一个可以避免的开销定基线);不只冻顶层(`Object.freeze` 是浅的,冻住顶层后嵌套的单位数组、点位数组仍可写,而四个座位**串行**执行,座位 0 若经任何路径改了嵌套字段,座位 1 读到的就是脏的);不完全不冻(hld 点名要 freeze 不是装饰,而 `snapshot` 是宿主回调能碰到的对象)。

深 freeze 之后,任何写入在 strict 模式下当场抛 `TypeError`,脏数据**走不出 tick**——这与 hld §4.5 那句「隔离靠拷贝边界,而非只读封存语义」不矛盾:那句话说的是**隔离**(引擎真状态不受影响)靠拷贝,深 freeze 是另一件事(防宿主回调误写),后者正是 hld 点名要的那层。

三条配套:**引擎真状态(那一份)永远不 freeze**,它要被 `apply()` 写;**深 freeze 与 `stateHash` 的规范化序列化是两次遍历,不许合并**——合并会让「这一 tick 冻没冻」依赖「这一 tick 算没算 hash」;`structuredClone` 有一条用例钉住「不共享引用」。

### 终局:加第四个原因,`all-eliminated`

同 tick 全部伤害算完、统一扣血、归零者死亡,所以**两名玩家可以在同一个 tick 同归于尽**;若这两人各自都是最后一名单位且无基地,淘汰步会把**四方全部**淘汰,此时 gdd 的捷径条款(要求「仅剩玩家」)与主胜利条件都不成立。**没有胜者,而 `rankings` 与 `reason` 必须给出答案**,否则那个「判别联合的穷尽性」是假的。

`reason: "victory" | "shortcut" | "timeout" | "all-eliminated"`。`rankings` 在这一档按 gdd §3.1 的第 2–4 条算(无存活层 → 按淘汰时间倒序 → 同 tick 淘汰者并列同名次),首名就是最后出局的那一方,**字段集不变,只多一个枚举值**。

两条配套:`reason` 的判别联合要有**穷尽性断言**(编译期一条 `satisfies never` 兜住);**已淘汰玩家的 `territoryScores` 恒为 0** 这一点要在接口面上说清(基地与资源点已回归中立不贡献、存活单位造价为 0),否则赛季报告会出现「领土分 0 却排第 1」的读不懂。

不选「复用 `timeout`」:那会让「600 tick 打满」和「第 37 tick 全灭」在数据上无法区分,而报告正是靠 `reason` 分类。不选「改机制保证有幸存者」:那要给 combat 步加一条「预判本 tick 会不会灭干净」的反向依赖,是个新的漂移面,而且它要改的是 gdd 的战斗裁决——本 feature 改不了。

### 事件流:两个「不设字段」的裁法

**经济死亡不设状态字段。** gdd 给的形式定义是「玩家无任何农民单位且 `resources` < 农民造价」,而 `Player` 类型有 `alive` 与 `exceptionTicks` 却没有它。分界线是**可推导性**:`alive` 的判定链复杂(无单位且无基地 → 判定顺序 → 点位回归中立),重推要重跑整条 evaluate 步,所以它配得上字段;经济死亡是两个谓词的与,任何人拿 tick 行的 `players[].resources` 与 `units` 一眼能算。加上 `CONTEXT.md` 记着它**不可逆**(资源只减不增:无农民就没有采集产出,抢点不产生被动收入),**事件一次即全部信息**。

代价要写明:**回放里经济死亡的时点只能从 `economy-dead` 事件读**,不能从某个字段反查。事件也**每局只发一次**,不发成每 tick 重发——战报生成器只消费事件,几百条同义事件要靠它自己去判首次。

**首触的判据欠 gdd 的账,但它不进 `rulesets`。** 精确定义(任意敌对单位 Chebyshev ≤ 2,全局第一次一条)现在**只存在于一次性桩数据** `.scratch/rules-calibration/sim/data-rerun-200/tables.md:51`;`gdd.md:123` 只有定性的半句「首触判据吃的是接近度」。本 feature 按该口径实现并在代码注释里注明读数出处,欠账记在 gdd 那一侧。

**首触阈值是观测量,不是规则参数,所以 `rulesets/v1.json` 保持 21 键是对的。** hld 那条「一切数值不出现结构中,统一来自规则集装载」指的是**参与裁决的数值**;首触阈值不判胜负、不判合法、不影响移动,只被用来给事件流标一个时刻,与 hld 开放项 #3(座位轮换偏置)同类。判据是「凡观测量不进参数表」——这与 C 节点那个「21 不是 22」的裁决同源,不是它的反例。

### `stateHash`:载荷是那一行去掉自身

规范化**已有家**在 `packages/replay/src/index.ts:22-42`:对象键升序、**数组保序**、标量走 `JSON.stringify`;它保序不重排的理由写在头注里——「对象数组的升序由状态不变量保证(units/sites 按数值 id 升序维护),本函数保序不做重排」。

**载荷 = 整个 tick 行去掉 `stateHash` 自身**(`tick` + `players` + `units` + `sites` + `events`)。这让 `stateHash` 成为**行内容的自摘要**:`verify` 只需重算并与该行比对,不需要维护一份「哪些字段进 hash」的清单,而**那份清单本身就是一个会漂移的第二真源**——tick 行的字段是要加栏的。加栏自动进 hash,这正是要的效果;一个**不**自动进 hash 的新字段才是漂移面。含 `tick` 是白捡的:它顺带把行序钉住。

**一条反向钉**:喂一个 `units` 乱序的数组进去,`stateHashOf` 应当给出**不同**的 hash。保序是设计,所以「状态维护违反 id 升序不变量」必须表现为 hash 变化;否则不变量被破坏时 hash 照旧不变,`verify` 看不见。**这条是本 feature 的核心不变量测试,不是 replay 包的。**

### meta 行:加一栏执行器身份

`hld.md:726-727` 的 meta 行有十栏,其中 `quickjsWasiVersion` / `sandboxRuntimeHash` / `wasiClock` / `wasiRandomFill` **四栏全是沙箱产物**,本 feature 没有 QuickJS、没有 WASI、没有定格时钟、没有确定性随机填值。

**四栏填 `null`(不是空串、不是 `0`——「未发生」与「恰好是空串」要能区分,与 `Site.remaining` 用可选而非哨兵值同族),并加一栏 `runner: "stub" | "quickjs"`。**

不加这一栏就把可读性押在「四个字段同时为空」这个约定上,而 hld 那行字段清单将来加一栏沙箱字段就会静默失效——这正是 gdd §8 记录里反复出事的形态(口径不随读数一起带)。这一栏有真实消费者:报告要分开「桩跑的」与「真沙箱跑的」,**座位轮换实效那一格(开放项 #3)的读数必须来自真沙箱**;一份桩回放与一份真回放在结构上不可区分,就会有人拿桩的读数当结论,而那是一次性交接单已经犯过的错。

「桩回放不是合法回放」被排除:回放是「可复算原始数据」,一份不能被读、不能被渲染的东西不叫回放。

### 脚本 API 的类型面归本 feature

详见 [ADR-0006](../../docs/adr/0006-script-api-type-surface-lands-in-engine.md)。要点:类型面描述「脚本能读到什么状态字段」与「action 的签名」,前者的源头是本 feature 的状态模型、后者的源头是 `intents` 的 `check()`/`run()`,而沙箱执行器只搬名字、不定义任何一个。`packages/schema/src/script-surface.ts` 那 22 行 `signature` 字符串在本次回填中**由类型面取代**(生成或删除,不并列存在——它自己写着「签名是**类型面**的事实」)。

连带两条:「API 误用」那条承载条款第一次有人;[ADR-0004](../../docs/adr/0004-contract-api-surface-lands-in-rules-landing.md) 留的那笔账(符号表注释里的「刻意为空,回填触发条件是沙箱执行器产出注入面」在 ADR-0004 之后会说错话)随本次回填销掉。

**生成管线的编译步骤在本 feature 落地时解锁,不必等沙箱执行器**——`tsconfig.scripts.json` 的类型面一填,「编译通过 + 白名单反转 + API 签名」三件事同时成立。

### 规则集装载期校验接线

`hld.md:151` 自陈「接进子命令装载路径的只有地图那一半……规则集那一侧的调用点随 runner 落地」,以及「被校验过不等于被装载时校验过」。`validateRuleset` 纯函数与读真文件的单元用例都已落地,差的是**接线**——`modelwar match` 装载时调它,版本号三处(文件名 / 目录名 / 常量)对不上就拒跑(FR-10 AC2 的错配拒跑)。

`packages/schema` 侧的分家纪律不变:schema 交付**数据**,判罚逻辑在 `apps/cli` 那一侧的唯一 ajv 实例里。引擎不自己写一份规则集校验。

### A 交办出去的账:首触复核与三条桩结论

**三张真图的首触实测复核落在本 feature**,读数与结论**就地补在 `gdd.md:123` 首触那段末尾**,不开新的 §8 记录。理由是单事实单家:那一段末句自己写着「这条偏差的家在 gdd」,那么复核它的读数与结论的家就该紧挨着被复验的那一条。`gdd.md:123` 已收口的记录那类载体是**规则侧决定**(现象 → 证据 → 裁决 → 影响面 → 回流触发),而这次复核不产生新裁决——确认就不该占一条记录的位置,推翻才该。

**复核必须带上基线偏差,并说明它与墙无关**:标定环在**无墙**夹具上实测的首触中位就是 34,比 `1/15 = 40` 这个设计锚点**早 6 tick**。不把它算进去,真引擎跑出来的 34/35/37 会被误读成「墙把首触推了」。量值与理由的家只在那一条,本 spec 不复制。

**gdd §8 #7 / #9 / #10 三条桩结论的复验不在本 feature 的交付里**,但**夹具归本 feature 建**:桩不是引擎,那三条现在是关于一个已丢弃实现的观察。真引擎上的属性测试或基准门禁形式落在后续那一格(门禁/流水线),本 feature 负责让它们有可跑的宿主。

## Testing Decisions

### 什么算好测试

只断言**外部可观察行为**。本 feature 的外部行为只有三件:一条 `runMatch` 产出(或不产出)一份回放;一个子命令以什么退出码结束;那份回放被重跑十次是否逐 tick 一致。凡是能靠改内部结构而失效的断言,都是坏断言。

**优先级:接口即测试面。** 调用方与测试穿过同一道缝——外部那条是 `runMatch`;要测内部结构,说明那个模块的形状选错了。

### 缝(两条,一外一内)

**1. 外部缝:`runMatch(input) → replay.jsonl`**。这是闸门、也是 `verify` 与赛季将来要穿的那道缝。

- **端到端一场**:用 `StubRunner` 与四份写在测试里的 TS 策略跑完一整局,断言产出合法 JSONL、末行有 `result`、每 tick 有 `stateHash`。
- **确定性(FR-2 AC1)**:同配置重跑 10 次,每 tick `stateHash` 全等。这条不通,其余全部不算数。
- **四种终局各有断言**:主胜利、捷径条款、超时、四方全淘汰。**最后一条是本 feature 独有的**——它是判别联合穷尽性的证据。
- **退出码语义**:缺档 / 版本三处不一致 / 地图校验失败 → `2`;规则内结果(超时、全淘汰、异常出局、经济死亡)→ `0`。**「异常出局的席位仍然给 0」这条必须有用例**,它是被误改概率最高的一条。
- **只读隔离(FR-3 AC1)**:一个策略在 `loop()` 里试着改快照,断言引擎状态在下一 tick 不受影响。

**2. 私有内部缝:`processTick(state, intents, ruleset) → { state', events }`**。只给处理器自己的测试做构造器,**不进包的导出面**。七步里最脆的判据在这里用小夹具验:

- **移动碰撞裁决**:同格竞争按 `(tick + playerIndex) mod 4` 轮转优先;交换/穿行(A→B 同时 B→A)与链式移动(A→B 同时 B→C)按「本轮开始时的占位」判定;己方单位之间同样裁决。这几条在整场里几乎无法构造。
- **占领**:转轨重计无侵蚀、同阵营进度保留不动、无人站立不衰减、单格单驱动者。
- **骑兵二次移动**:重复整轮结算一次,第二轮以第一轮结算后的占位为基准,轮转优先中的 `tick` 值不变。
- **战斗同时性**:先算全部伤害、攻击者本 tick 死亡不影响其攻击生效。
- **产线**:每基地一条队列、一次一个;重复下单静默丢弃(**不扣款、不计异常**);出兵格被任意单位占据则挂起;基地易主时按 gdd 处理队列。**注意没有「产线忙」这个错误码**——重复下单是静默丢弃,不是错误。
- **交付目标**:单位同时相邻多个己方基地时,交付给**数值 id 最小**的那个(gdd §5 是规则侧的真源)。
- **intent 分组**:每单位只留最后一个,前面的静默丢弃、不计异常、不占异常配额;`spawnUnit` 是玩家级 intent,不参与单位级分组。
- **事件定序**:同一构造两次得到逐项相同的事件序列;**乱序输入的 `units` 数组产生不同的 `stateHash`**(那条反向钉放这里,因为它是关于状态不变量的)。

**明确不测**:目录遍历层、包导出面的形状、快照拷贝的内部步骤(只测「不共享引用」这个可观察结果)。

### 明确不测的东西

- **沙箱行为一条都不测**。沿用 D3 的先例:对第三方库行为的断言会被后来者误读成「沙箱这块验过了」。真 VM 的行为由 G 那一格的实测承担(开放项 #8 的五条复验是它的第一条验收)。
- **不测「编译器的白名单反转」**。它由 `tsconfig.scripts.json` 与生成管线的编译步骤拥有。本 feature 最多验一次「类型面在真源包里且被编译配置引到」。
- **不测 gdd 的机制正确性本身**。本 feature 实现的是 gdd 的裁决,不是验证 gdd 的裁决对不对——发现某条约束在数值下不成立,是回报 gdd 的事(gdd §6.1 那七条约束里明写「若某条在数值下不成立,R2 风险即被触发」)。

### 验收集:三张真图 + 四份盲写脚本

**三张真图的首触读数**是 A 交办出来的账,本 feature 跑它、读数与结论落 `gdd.md:123`(见 Implementation Decisions)。**四份盲写脚本不作为验收集**——它们的读数出自两个不同的契约世代(标定环的草案与终稿重跑),`gdd.md` 抬头那条口径明写「与终稿契约下重跑的三舱不可互比」;而本 feature 不换契约,拿它们当验收集只会引入一个不可比的基线。要验的是「用真引擎跑出首触读数」这一件事,不是「与桩的读数一致」。

## Further Notes

### 关键路径上的位置

F 是 G 的硬前置,G 是 K 的硬前置,K 是 I 的硬前置。这条串行段是全图最长的一段,所以本 feature 的体量与它的位置不对称——**它大且它挡路**。两条能减压的事实:`StubRunner` 让「跑完一个对局」的闸门在沙箱之前就开,而**生成管线与本 feature 零依赖边**(它只要规则集装载、校验器、类型面),所以 F 的实施期里 H 可以整格并行,不必等 G。

### 与前后节点的关系

- **上游**:C(真源包与生成物)✅、A(三张真图)✅、E(规则集与契约面、脚本编译配置)✅、D(静态校验器)✅——四条前置全部已解除。

### 一处刻意留下的开放项

### 提交与门禁

本仓的机器门禁会在 implement 期间直接拦住这个 feature 的产物:`check:no-float` 巡航 `packages/engine/src`,而状态演化必须是全整数运算(NFR-1 / FR-2 AC3),引擎源码里任何浮点字面量当场红;`check:declared-deps` 拦未声明依赖(注意 `structuredClone` 是全局不是 `node:` 导入,不受依赖巡航约束,而 `node:crypto` 是唯一允许的 `node:*`);`check:drift` 拦真源与生成物不一致(本 feature 回填三份形状,那三份都是真源,漂移检查要随之生效);`check:bench` 判基准产物逐字节可复现(它读 `benchmarks/*/script.js`,本 feature 改了状态模型形状,若那些产物走的是受影响的路径,`check:bench` 会先红)。
