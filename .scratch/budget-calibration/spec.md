# 预算参数终值标定

Status: ready-for-agent

图上的节点 K(`docs/diagrams/v0-milestone-dag.md` §4 收尾层,波次 7)。工作单元 = 一个 `.scratch/<feature>/`,走 `grill-with-docs`(已完成,二十八问)→ `to-spec`(本文件)→ `to-tickets` → `implement`。判据之家是 `docs/hld.md` §5.3 与 §12 开放项 #2;本单元负责把判据文本补进 §5.3 并关掉那个开放项。节点 K 不是迷雾,不走 `wayfinder`。词表用 `CONTEXT.md` 的既有词条(未定值／终值／标定／余量／中断粒度／分配上限／预算探针／标定复算／基准脚本／对局／回放)。

## Problem Statement

面向模型的契约里,八个预算参数键**全部**渲染为「未定」;引擎组装层见到未定值就跳过,交出去的是一份**空预算**——四条轨一条都没启用,`observations.jsonl` 从项目开始至今**一个字节都没生成过**。这带来七个具体后果,其中五个是本次 grilling 才查清的:

1. **没有判罚**。脚本可以无限烧控制流事件、无限打 API、无限占内存、无限挂——没有一条轨会截停它。赛季要跑真实模型对抗,这是硬缺口。
2. **内存两个键的读数当前会自己涨**。执行器每 tick 泄漏一份快照(参数 handle 从未 dispose),空脚本 **+360 B / +5 对象每 tick**、真实快照 600 tick 涨 18 MB,单局墙钟 27812 ms。内存判罚线标的就是「tick 末存活堆」,不修就标的是一份会漂的读数。
3. **事件计数轨的有效分辨率是 5000,而契约写的是 `events/tick`**。判定只在宿主中断点上发生(`eventCount += 5000` 后比 `>=`),所以小于一格的取值彼此等价——契约的措辞会让人以为可以取 7500 这种数,而它的实际行为是 10000。
4. **「1168 场实测异常 0 次」是零证据,而且永远不可能成为证据**。那批桩「控制流/内存/预算/QuickJS 限制完全不模拟」,没有机制去产生异常。`exceptionTickLimit` 的下限至今悬空。
5. **两个对抗夹具在,但不是标定探针**。纯计算死循环与 API 轰炸两臂的夹具确实已入库,但它们是**机制验证**夹具(阈值是随手给的测试常量 400),不产标定读数;而图上的措辞说它们「仓库里不存在」,读者会以为要从零造。
6. **`memoryTickCeiling` 的夹逼注脚两头都空**。上界写 `memoryLimit − 最大单次分配`,而「最大单次分配」没有可代入的实测定值(实测封顶依分配形态从 96% 到 `limit − 请求量` 都有);下界要的「正常脚本 tick 末存活峰值」,其「装 runtime bundle 之后」的基线**从未被记录过**(空 VM 基线 75,128 B 有实测并已冻成常量)。
7. **契约里 `loop()` 抛异常会被记成一次异常这件事根本没有实现**。文档写 `exceptionTicks++`,实现里异常被原样重抛、冒成整场 `engine-crash`。「故意写崩」这一路因此产不出证据。

## Solution

用**真引擎上的读数**把八个键标出来,分批落成终值,并把判据文本与连带对账一次收口。顺序不是可选的:先修快照泄漏(否则内存读数不成立),再造三类预算探针与两个量测探针,按已定的推导规则取值,然后逐轨落 `final`、跑失配断言、写回文档。

交付物有五种:①泄漏修复 + 稳态回归测试 ②`budget-probes` 探针与其读数 ③`rulesets/v1.json` 的八键终值 ④一条静态结构门禁 + 一条动态失配断言 ⑤`hld`/`gdd`/`srs`/`dag` 的连带对账。

## User Stories

1. 作为赛季运营者,我想要八个预算键有终值,这样赛季在真实模型对抗下能有确定的判罚。
2. 作为赛季运营者,我想要「纯计算死循环」被截停,这样单个脚本不能靠空转把整场拖死。
3. 作为赛季运营者,我想要「API 轰炸」被截停,这样单个脚本不能靠每 tick 数万次查询把对局拖慢。
4. 作为赛季运营者,我想要阈值「贴边但安全」,这样正常脚本永远不被误杀,而滥用脚本在毫秒级出局。
5. 作为赛季运营者,我想要硬超时只作废整场、不判负,这样机器负载不会污染胜负。
6. 作为赛季运营者,我想要一场被硬超时作废的对局被重跑一次、再失败则进问题清单,这样偶发不会被静默丢弃。
7. 作为脚本作者(参赛模型),我想要契约里的事件计数上限写清「有效分辨率是一整格」,这样我按 7500 写脑内模型时不会得到 10000 的实际行为。
8. 作为脚本作者,我想要内存有两个不同的约束(分配上限 = 硬顶、判罚线 = tick 末存活堆),这样我知道「瞬时借满后自行释放」是被接受的。
9. 作为脚本作者,我想要异常容忍有几次的机会,这样一次偶发不会让我当场出局。
10. 作为脚本作者,我想要脚本体积上限明确,这样我知道规则文档里的「编译产物」口径限制的是哪一份字节。
11. 作为第三方复算者,我想要标定读数带**真的**沙箱运行时哈希,这样 `verify` 不会因为哈希对不上而拒绝复算。
12. 作为第三方复算者,我想要读数文件里写清测法与口径,这样我能自己重跑一遍并得到同一批数。
13. 作为第三方复算者,我想要终值失效事件被明文记录,这样我知道哪次改动之后旧报告不可互比。
14. 作为引擎维护者,我想要一条「存活堆不随 tick 增长」的回归断言,这样快照泄漏不会再次被引入。
15. 作为引擎维护者,我想要一条断言钉住「事件计数上限必须是中断粒度的整数倍」,这样后来者不会取到一个行为不可预期的值。
16. 作为引擎维护者,我想要一条断言把中断粒度常量与它散落在文档里的副本锁在一起,这样改常量的人不会漏改说明书。
17. 作为引擎维护者,我想要「写崩脚本 → 异常计数」这条缺口另开一张票而不是被标定顺手改掉,这样判罚语义的变更走它自己的评审。
18. 作为后续节点 L 的实现者,我想要 K 交出的是**读数**而不是性能目标值,这样 NFR-3 的 `X` 由性能节点按自己的口径定。
19. 作为后续节点 I 的实现者,我想要八个键是定值,这样赛季调度与排名能在确定的判罚下产生报告。
20. 作为 K 的实现者,我想要每个键的取值规则是「读数 × 系数」而不是一个拍出来的数,这样重采读数后我能直接重算。
21. 作为 K 的实现者,我想要读数与探针都入版本库,这样明年复核终值时不必从零重建仪表。
22. 作为 K 的实现者,我想要挖出来的引擎缺口有票、有指针,而不是变成实现过程中的顺带改动。
23. 作为本轮标定的读者,我想要一份「哪些读数只能当量级参考、哪些是交付证据」的明文,这样不会把一次性 prototype 的旧读数误当成标定依据。
24. 作为本轮标定的读者,我想要图上那句「对抗探针仓库里不存在」被改掉,这样不会有人为了不存在的缺口再写一遍已有夹具。
25. 作为本轮标定的读者,我想要「1168 场异常 0 次」这条命题被标注作废,这样它不会再被当成待补的证据挂在图上。

## Implementation Decisions

### 1. 八个键的取值规则(这一节是交付的核心)

每条规则都以「读数 × 系数」表达,**最终数字由重采读数代入得出**;下表第三列给出用旧读数(204 KB 级存活堆、179 次 API 峰值、1.82 ms 单 tick 峰值)代入的示范值,仅供实现者对账,不是终值的替代品。

| 键 | 取值规则 | 代入示范 | 依据 |
|---|---|---|---|
| `eventTickLimit` | 必须是中断粒度的整数倍;取「诚实全局峰值所在的下一格」 | **10,000** | 诚实局读数 p95 已满一格,故 5,000 会误杀;分辨率由第 2 条决定 |
| `apiCallTickLimit` | 诚实全局峰值 × 2(分辨率 1) | **400** | 计数精确,噪声小;留一倍给赛季脚本进化 |
| `memoryLimit` | 2 的幂,≥ 8 × `memoryTickCeiling`,≥ 16 × 诚实存活峰值 | **4 MiB** | 粗保护,不是判罚线;上限过大等于废掉这个键 |
| `memoryTickCeiling` | 2.5 × 诚实峰值、取整到 64 KiB;并要求 0.8 × 该值 ≥ 1.5 × 诚实峰值 | **512 KiB** | 下界由软阈推出(见第 3 条);上界见第 3 条 |
| `wallClockSoftLimit` | max(50 ms, 20 × 诚实 p95) | **50 ms** | 观测机制有约 8 ms 的硬下界(见第 4 条);它是观测项,逼太紧只会把宿主负载写进披露数据 |
| `wallClockHardTimeout` | 2 的幂,≥ 200 × 诚实单 tick 峰值,≥ 100 × 软限 | **1000 ms** | 最后防线,只兜计数轨的盲区;它作废整场,有成本账(见第 4 条) |
| `exceptionTickLimit` | 容错 1–2 次 + 同 tick 最大叠加数 | **3** | 诚实脚本应恒为 0;**拒绝取 1**——它会把「瞬时借满即还」这个已接受的残余变成出局条件 |
| `scriptSizeLimit` | 2 的幂,≥ 4 × 基准产物最大值 | **32768 B** | 它是唯一封「直线代码不计量」盲区的键;硬下界 7579 B(见第 7 条) |

**余量分轨,不是统一系数**:计数两轨贴边(诚实与对抗差 ≳1000× / ≳10⁴×,贴边无风险),物理量轨(内存、墙钟)留宽(受机器负载与地图规模影响)。

**统计单元**:先取「每场每席的峰值」,再在这组峰值上取全局最坏;墙钟软限用 p95,硬超时用全局峰值。**任何键都不得以 p50 级读数作依据**——事件计数的 p50 恒为 0,是粒度假象。

### 2. 中断粒度是这类上限的有效分辨率

`eventTickLimit` 的真实截停点是 `ceil(limit / 中断粒度) × 中断粒度`,**取 1..5000 全部等价**。三条纪律:

- 该键的终值**必须是中断粒度的整数倍**,并有一条静态断言钉住。
- 契约面那个 `events/tick` 的单位要补一句分辨率说明——否则它教出来的是一个错的心智模型。
- **中断粒度不可配置**:它是宿主对 wasm 侧回调周期的镜像,改 TS 常量只会让读数系统性偏小、不会让回调变密,而**没有任何门禁会发现**,旧回放还会因此不可复算。因此要加一条断言,把它与散落在 `hld` 里的三处副本锁在一起;并且它属于「使终值失效」的变更之一(见第 9 条)。

### 3. 内存两个键 + 软阈推导项

- 软阈 = `0.8 × memoryTickCeiling`,是**推导项、不入键清单**(系数是真源包里的常量,引擎另留一个显式覆写点,但那不是第二个要标定的数)。由「软阈要高于诚实峰值」推出 `ceiling > 1.25 × 诚实峰值`,规则里再加一档裕度到 2.5 ×。
- **夹逼上界要改写**。原式 `memoryLimit − 最大单次分配` 不可执行:实测封顶依分配形态从 mallocSize 的 96% 到 `limit − 请求量` 都有,而「最大单次分配」没有可代入的定值(仓库里那句「一次性分配 1MB 封在 limit−1MB」是推论,没有探针支撑)。新上界取 `memoryTickCeiling ≤ 0.5 × memoryLimit`——与分配形态无关、在无探针时也站得住,并且给读数留出可测区间。
- **`分配上限` 与「该轨不启用」是两件事**,必须写进判据文本与 `CONTEXT.md` 已有词条:分配上限未定 = VM 不设任何上限;判罚线未定 = 该轨不启用。两者都在未定值状态下的「无保护」形态不同。
- **`runGC()` 的扫描税要计价**。内存判罚线单独启用会让每 tick 多一次强制回收(实测固定扫描税 0.5–3.3 ms/tick),而这笔税落在**同一个 tick** 的墙钟里,所以它要进 `wallClockSoftLimit` 与硬超时的取值考量,不能只算脚本自己的耗时。

### 4. 墙钟两键与它们不属于的第三个量

- 墙钟轨**不参与判罚、不进回放、不进状态哈希**;软限只产观测、硬超时只作废整场(与 `engine-crash` 同轨,重跑一次后进问题清单并排除出排名)。
- 读钟的粒度是**每约 10 万控制流事件一次**(约 8 ms 量级);短脚本抽样不到就一条观测都不产。这是软限取值的**机制下界**,不是余量问题。
- **硬超时是单 tick 上限,不是整局**;它与 NFR-3 的「对局平均墙钟 `X`」不是同一个量。**`X` 归节点 L**:K 只交基准脚本的单局墙钟分布读数,L 在性能节点里定目标值并写回 srs。K 的 `readings.md` 按既有形态只放数与测法、不放建议阈值。
- 硬超时的成本账要记明:触发即整场作废并重跑,一个每 tick 都擦线的对局会变成分钟级;取值「宁小勿大」与「盲目放大」都错,它的定位是**成本兜底**,不是判据。

### 5. 异常键与「三轨异常探针」

- `exceptionTickLimit` 计的是**次数、不清零**,累加点只有三处(事件轨／内存判罚线／API 轨),**同 tick 最多 2 次**(事件轨早退,内存与 API 可叠)。取值据此定。
- **原「故意写崩」探针不成立**:`loop()` 抛异常在实现里被重抛成整场 `engine-crash`,不产生异常计数。所以命题① 改为**由三轨异常探针给出**——三类探针各自反复触发对应的轨,产出异常计数的读数,`exceptionTickLimit` 的下限由此得出。
- 文档里「`loop()` 抛异常 → 异常计数」那句要么删、要么修,并且**实现补齐另开一张引擎票**,不进本单元的验收(它会改变「异常」这个域概念的定义,必须走自己的评审)。
- 验收命题②(对抗探针各抓住一个)的完整形态是**双向**:同一组终值下,三类探针必被截停,**且**三份基准脚本必不被截停;并且「被抓住」**必须指定是哪条轨抓的**、截停时的读数是多少。理由是硬超时会把整场作废却看起来像「抓住了」,不指定轨名时命题②会被假满足。

### 6. 探针、读数的落点与两条既有缝

**零新增缝**——复用两条既有缝:

- **缝 A:引擎侧「读数测试 + `MW_READINGS_DIR` 落盘」约定**。三处用途全走它:ticket 0 的稳态回归测试、八键的标定读数采集、动态失配断言。探针经真执行器会话的每一步骤逐条镜像「每 tick 次序」而不改任何判定,因而可以直接当作座位执行器塞进四人对局。**`prototype/readings-probe.mjs` 已解过这道题**,新探针从它长出来,不另起一份;它记录的两个坑要继承:①计数器回调只在构造时装上,所以探针必须显式给事件上限一个极大值才能拿到事件读数;②wasm 侧的计数器跨调用不清零、有相位残留,读数 5000 可能只是残影,读数文件必须按「格数」记而不是按事件数记。
- **缝 B:门禁缝**。新增一条静态门禁 `check:budget`(薄壳 + 纯函数 + 退出码,零构建,只依赖真源包与文件系统),与既有 `check:*` 同族;它承载的断言见第 7 条。动态失配断言留在默认 `test` 项目里(它是引擎侧读数测试)。

**不能落在哪**(两条都违反既有纪律,实现时不要试):探针不能放工具包的运行时源码里 import 引擎(hld §3.2 只许 import 真源包,声明了也会 TS2307);也不能放进沙箱行为探针那一族(那条缝**刻意不 import 引擎**,只到运行时层,量不到引擎的逐 tick 读数)。

**读数落点**:`.scratch/budget-calibration/readings.md`(数 + 测法,不放建议阈值)与同级 `.json`。`.scratch/**` 不忽略、产出可入库复核,这是既有纪律。**读数必须带真的沙箱运行时哈希**——伪造哈希会被 `verify` 直接拒绝复算,那批读数就不是证据。已存在的一次性 prototype 目录**整份提交**并在顶部加失效声明(它的读数取自打过补丁的构建与伪造哈希,只能当量级参考),因为快照泄漏一旦修好,那批「18 MB / 600 tick、墙钟 10×」的数字**再也复现不出来**,而它们是泄漏票唯一的量化证据。

**命名**:重跑命令挂一个显式脚本名(对齐既有 `probes:*` 一族的命名),它内部是「设 `MW_READINGS_DIR` + 跑探针测试」——因为唯一能跑真引擎的路径是引擎自己的测试缝;门禁名 `check:budget`。

### 7. 静态门禁 `check:budget` 要断的东西

1. `eventTickLimit` 是中断粒度的整数倍。
2. 已定稿的键满足各自的**硬下界/夹逼**:`scriptSizeLimit ≥ 基准产物最大值(当前 7579 B)`、`memoryTickCeiling ≤ 0.5 × memoryLimit`、`memoryLimit ≥ 8 × memoryTickCeiling`、软阈(由系数推出的那个数)严格高于诚实峰值(如实测值以常量形式记录在探针侧常量文件里)。
3. 中断粒度常量与它在文档里的三处副本逐字一致。
4. 门禁必须遵守既有的**防假绿**惯例:读到零个文件/零个键按**失败**处理,不报「干净」。

### 8. 落库形态

- 八键**就地**把 `rulesets/v1.json` 里的标定状态从未定值改为已定稿,**不新开版本**——未定值是「终值归后续图」的占位,换成终值不构成「取值变更」,契约散文一个字不动(面向模型的数值表是生成物,状态一改就渲染成数字)。这条调和写进了 `docs/adr/0009-budget-final-values-are-revocable.md`。
- **允许按轨分批落**:组装层逐键读标定状态,每个键是独立开关,分批不产生中间态语义问题,也让「计数轨落定后立刻跑双向失配断言」成为可能。
- **终值可失效、不可就地改**:三类失效事件(契约散文修订／快照结构变更／runtime 版本或中断粒度变更),失效时开新收尾节点**重标**。ADR 0009 是这条的家。

### 9. 连带对账(收口票的内容)

- `docs/hld.md` §5.3 补「标定判据」小节(本 spec 第 1–5 条即其内容),并**关掉 §12 开放项 #2**;夹逼注脚按第 3 条改写;「`loop()` 抛异常 → 异常计数」那句按第 5 条修。
- **写进 hld 的判据文本只写规则与键名,不写任何取值**。`docs/hld.md` 在散文门禁的扫描范围内,它禁止「键名与一个数字直接绑定」的赋值形态(连接件只放行空白与 `=` `:` `为` `是` `(`,以及反向写法)。判据本身是安全的——「必须是中断粒度的整数倍」「上界取分配上限的一半」「≥ 4 × 基准产物最大值」都是关系式,不含键名绑数字;但**一旦把代入示范里的那些数抄进 §5.3,门禁当场红**。取值的唯一家是 `rulesets/v1.json` 与由它生成的面向模型的数值表,§5.3 只写规则并指过去。这条不是措辞洁癖:判据文本是**规则**,而规则的重采不改变文字——只有取值会变。
- `apps/cli` 里那条「八键逐字等于各自占位值」的断言与它的键数不变量,在键落定后必然要改写(未定键数会从 8 变 0),要写成「定稿键逐字取终值」的既有范式;`ruleset-keys.ts` 的标定状态是唯一判据,不得改成「值是不是 0」。
- 生成物必须重生成,否则 drift 门禁红。
- `selfproof` 的脚本体积上限在占位期取的是「三份入库产物的最大值」地板;终值落定后它会改用声明的值,所以**`scriptSizeLimit` 必须 ≥ 7579 B**,否则该门禁的静态校验段会红,而它不在默认链上——只会在有人手跑时才发现。
- 图上那句「对抗探针仓库里不存在」要改(机制夹具已在,缺的是标定形态),并**标注「1168 场异常 0 次」这条命题作废**(改为由三轨异常探针给出证据)。
- `srs` 的 `X` 不动(K 不取值),但要在读数文件里留指针给 L。

## Testing Decisions

**好测试的判据**:只测外部可观察行为。对读数类断言,外部行为 = 「以某组预算设置跑某份脚本,返回的观测与故障位」;对门禁类断言,外部行为 = 「命名脚本的退出码与标准输出」。**不测内部数据结构、不测私有函数、不断言中间计数。**

四个测试面:

1. **引擎侧读数测试(缝 A)** —— 先例是 `packages/engine/src/runner/quickjs.test.ts` 与 `packages/engine/src/fixtures/fixtures.test.ts`。ticket 0 的回归测试沿用该文件里既有的「两 tick 同值」形态(现有先例断的是计数逐 tick 重置,这里断存活堆不随 tick 增长——**该文件目前没有存活堆稳态用例,这正是缺口**),并用既有 helper(存活堆读取与基线)钉住「判据读的是存活堆字段而非内存用量字段、不是对象数」。可选落盘沿用 `MW_READINGS_DIR` 约定,不设时不产文件副作用。
2. **门禁三段式(缝 B)** —— 先例是 `packages/tools/src/gates.test.ts` 的 `spawnSync` 形态:干净 → 违规红 → 改回绿,三段都断言退出码与报告文本。本门禁的反例用「改一份临时预算取值」而不是改源码,与产物类门禁「改一个字节再按字节还原」的形态同族。
3. **规则集断言** —— 先例是 `apps/cli` 的规则集文件测试(定稿键逐字取终值 + 键数不变量)。
4. **文档一致性** —— 生成物 drift 门禁覆盖数值表;中断粒度那三处副本由 `check:budget` 覆盖(它读文档源文本,不依赖生成);散文门禁覆盖「hld 里没有把终值抄成赋值形态」——它是「判据文本只写规则」这条纪律的执行者,收口票必须跑它。

**动态失配断言**放默认 `test` 项目:三类探针必被截停(且断言给出轨名与截停时的读数)、三份基准脚本必不被截停。它同时是「终值仍自洽」的常驻守卫——引擎或契约变了而终值没重标,它会红。

## Out of Scope

- **NFR-3 的对局平均墙钟 `X`**:K 交读数,取值与写回归节点 L。
- **1168 场(含 1336 场重跑批)桩的重跑**:那批桩不模拟运行时,补跑也给不出异常证据;命题①改由三轨异常探针给出。
- **重编沙箱 wasm 以改中断粒度**:它要连带重做版本耦合门禁、行为探针与文档三处,不在本单元。
- **消除「直线代码不计量」盲区**:粒度机制决定它只能被脚本体积上限**封住**、不能被消灭。
- **引擎侧「`loop()` 抛异常 → 异常计数」的实现补齐**:另开引擎票,本单元只修文档措辞并留指针。
- **墙钟硬超时的重跑与剔除**:属节点 I 的赛季调度。
- **把标定变成每赛季自动重标的流水线**:归 L 的门禁与流水线。
- **模型选择与参赛模型数**:归节点 I。
- **`memoryLimit` / `memoryTickCeiling` 之外的其它未定键**:本单元只碰八个预算键,其余键不在视野。

## Further Notes

- 本 spec 的全部决定来自一次完整的 grilling(二十八问,五轮)。四条与直觉相反:①**余量必须分轨**——计数轨贴边、物理量轨留宽,统一系数是错的;②**`eventTickLimit` 取 5000 会误杀正常脚本**,因为它的有效分辨率是一整格而诚实局 p95 已满一格;③**「故意写崩」探针在当前引擎里产不出证据**,命题①必须改形态;④**`memoryTickCeiling` 的夹逼上界必须改写**,原式没有可代入的实测值。
- 四处 grilling 覆盖不到、由本 spec 补上的发现:①`分配上限` 与「该轨不启用」是两种不同的无保护,契约与词条都要说清;②软阈是推导项,由「软阈要高于诚实峰值」反推出判罚线的下界;③`runGC()` 的扫描税与脚本耗时落在同一个 tick,必须一起计价;④hld 在散文门禁的扫描范围内,所以判据文本**只能写规则不能写取值**。
- 已写入的域文档:`CONTEXT.md` 新增七条词条(标定／终值／余量／中断粒度／分配上限／预算探针／标定复算);`docs/adr/0009-budget-final-values-are-revocable.md`(终值可失效不可就地改,并调和「就地写终值」与既有「取值变更即开新契约目录」那条 ADR)。
- **已知风险三条**:①标定样本薄——基准脚本只有两个模型档、其中一份还是降级产物,读数的代表性要在报告里如实记;②wasm 侧计数器有相位残留,诚实局的「满一格」可能是残影,所以事件轨的取值只能按格数论证、不能按事件数论证;③内存两个键的终值依赖泄漏修复先行,顺序不能调。
- 一次性 prototype 的四份产出(README／readings／泄漏隔离脚本／仪表化探针)是要继承的资产而不是废弃品:泄漏隔离脚本是泄漏票唯一的量化证据,仪表化探针是正式探针的起点。它们**整份提交**,但读数部分带失效声明。
