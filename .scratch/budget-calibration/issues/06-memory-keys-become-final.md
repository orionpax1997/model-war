# 06: 内存两键落 final

**What to build:** `memoryLimit` 与 `memoryTickCeiling` 写入规则集、标定状态转为定稿;软阈(推导项)与诚实峰值的关系被钉住;失配断言扩到内存轨。

**下界由软阈反推:** 软阈是「判罚线的 0.8 ×」这个推导项。若它低于诚实存活堆峰值,正常脚本就会开始产内存压力观测——噪声。于是「软阈要高于诚实峰值」直接给出 `判罚线 > 1.25 × 诚实峰值`;规则在此之上再加一档裕度。**软阈不是键**,不新增第九个要标定的数。

**上界要换形态:** 原式「分配上限 − 最大单次分配」不可执行——实测封顶依分配形态从约 96% 到「上限 − 请求量」都有,而「最大单次分配」没有可代入的定值。新上界取「判罚线 ≤ 分配上限的一半」:与分配形态无关,在没有探针的前提下也站得住,并给读数留出可测区间。

**两个「未定」不是一件事,判据文本要说清:** 分配上限未定 = VM **不设任何上限**;判罚线未定 = 该轨**不启用**。两种「无保护」的形态不同,混掉会让读者以为未定值是安全的。

**扫描税与脚本耗时落在同一个 tick:** 判罚线启用后每 tick 多一次强制回收(固定扫描税 0.5–3.3 ms/tick 量级),它属于同一个 tick 的墙钟,不能只算脚本自己的耗时。

判据见 spec 的 Implementation Decisions 第 1、3、7、8 条。
